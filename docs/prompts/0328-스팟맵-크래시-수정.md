# 0328 회고: SpotMap getLayer 크래시

작성일: 2026-07-25 · 소요시간: 약 2시간 · 관련 커밋: 6e859d0

---

## 1. 한 줄 요약

스팟이 2곳 이상인 스토리에서 상세 → 수정으로 이동할 때 터지던 네이버 지도 크래시를, 폴리라인 생성이 아니라 **클린업 순서** 문제로 규명해 고쳤다.

## 2. 왜 / 목적 / 이유

**왜(동기·문제)**
스팟 2곳 이상 스토리에서 상세 화면(지도) → 수정 화면(지도)으로 이동하면 `maps-gl.js`에서 `Cannot read properties of undefined (reading 'getLayer')`로 앱이 죽었다. 스팟 1곳이거나 SpotFinder에서는 재현되지 않았다.

**목적(목표 상태)**
지도가 있는 화면 사이를 오갈 때, 그리고 테마를 전환할 때 크래시가 나지 않는 것. 사용자 입장에서는 "내가 쓴 글을 수정하러 들어가면 화면이 죽는다"가 사라지는 것이 전부다.

**이유(채택 근거)**
처음 가설은 "타일 준비 전에 폴리라인을 그려서"였고, 그대로 갔으면 못 고쳤다. 스택트레이스를 끝까지 따라가 보니 진입점이 생성이 아니라 **해제**였다 — `SpotMap.tsx`의 `l.setMap(null)`이 이미 `destroy()`된 지도의 GL 레이어 제거 경로(`setMapGL` → `removeLayer` → `getLayer`)를 타고 있었다.

크래시 경로가 둘이었다.
- 언마운트 시 클린업 선언 순서 때문에 지도 destroy가 오버레이 해제보다 먼저 실행
- 테마 전환 시 별도 커밋에서 이미 죽은 맵을 해제

SpotFinder가 멀쩡했던 이유도 여기서 설명된다 — 거기는 GL 폴리라인이 0개이고 마커가 HTML 오버레이라 이 경로 자체가 없다.

## 4. 작성·수정한 코드

> ⚠️ 커밋 전 CC "읽고 보고만" 모드로 실제 파일 대조 필요. 아래는 재구성이다.

```tsx
// app/(protected)/story/[id]/SpotMap.tsx
// 지도 effect를 마커·폴리라인 effect 뒤로 재배치 —
// React는 클린업을 선언 역순으로 실행하므로, 지도가 뒤에 오면 해제가 먼저 끝난다.
const destroyedMapsRef = useRef(new WeakSet<naver.maps.Map>());

// 오버레이 해제 시 생존 가드
if (!destroyedMapsRef.current.has(map)) {
  l.setMap(null);
}

// 지도 destroy 시 WeakSet에 등록
destroyedMapsRef.current.add(map);
map.destroy();
```

`exhaustive-deps`는 effect 본문에서 안정 참조를 캡처하는 방식으로 해소했다.

## 5. 결과 / 교훈

dev 스모크 4항목 통과. 상세 → 수정 왕복, 테마 전환, 스팟 다수 스토리, SpotFinder 모두 정상.

**교훈 하나만 남긴다.** 이 버그는 가설을 세운 순서대로 갔으면 못 고쳤다. LCP 경고 · viewTransition · 시드 데이터 · 타일 준비 대기 — 네 가설이 순차로 기각됐고, 결정타는 전부 **스택트레이스**였다. "그럴듯한 원인"보다 "코드가 실제로 지나간 경로"가 먼저다.

그리고 **재현되지 않는 케이스가 원인을 말해준다.** SpotFinder가 멀쩡한 이유를 설명할 수 있게 된 순간 원인이 확정됐다. 다음에도 "왜 저기서는 안 터지지?"를 진단 도구로 쓴다.
