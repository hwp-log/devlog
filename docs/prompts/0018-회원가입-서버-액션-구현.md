# 0018 - 회원가입 서버 액션 구현

- **작성일**: 2026-05-05
- **커밋 번호**: 0018
- **작업 유형**: feat (Server Action 구현)
- **소요 시간**: 약 3.5시간 (작업 + 검수)
- **기타**: 
1. 0017의 Supabase mock 패턴 재사용. 
2. 작업중, Claude code가 TDD작업 룰 위배내용 발견 -> 위배 내용은 "TDD사이클 위배" 항목에서 자세히 확인 가능.

## 작업 목표

1. 입력 검증(이메일 형식, 비밀번호 최소 길이, 비밀번호 확인 일치) 후 Supabase Auth 호출
2. TDD(증강코딩)의 에러/성공 케이스를 일관된 응답 형태로 반환
3. 0017에서 작성한, Supabase mock 패턴을 재사용하여 작업 일관성 및 속도 확보

## 작업 방법

`signUp(email, password, passwordConfirm)` Server Action을 TDD(증강코딩)로 구현한다.
회원가입 페이지(이후 단계)에서 사용자가 폼 제출 시 호출되는 함수 작성이 목표.

이메일 형식 검증을 넣을시, 0016의 `isValidEmail`을 활용. 
Supabase Auth 호출은 `@supabase/ssr`의 `createClient`를 통해 진행. 
0017에서 만든 `mockSignInWithPassword` 패턴을 그대로 따라 `mockSignUp`을 추가.

signIn과 다른 점: 비밀번호 확인(passwordConfirm) 검증 + 비밀번호 최소 길이 정책(8자).

## 작업 대상

- 수정: `lib/auth/actions.ts` (signUp 함수 추가)
- 수정: `lib/auth/__tests__/actions.test.ts` (mockSignUp + signUp describe 블록 추가)

새 파일 생성 없음. `validators.ts`는 수정 불필요 (`isValidEmail` 그대로 재활용).

## 작업 내용

- **작업 1 (이메일 형식 검증)**: action.ts의 signUp에 잘못된 형식의 이메일이 들어오면, Supabase 호출 전에 즉시 에러 반환. 0016의 isValidEmail 재사용.
- **작업 2 (비밀번호 최소 길이 검증)**: 비밀번호가 8자 미만이면 즉시 에러. 외부 호출 없이 검증.
- **작업 3 (비밀번호 확인 불일치 검증)**: 비밀번호와 비밀번호 확인이 일치하지 않으면 즉시 에러.
- **작업 4 (Supabase 호출 실패 케이스)**: 검증 통과 후 Supabase Auth 호출. 회원가입 실패 시 통합 에러 메시지 반환. mockSignUp 신규 도입.
- **작업 5 (Supabase 호출 성공)**: 정상 회원가입 시 사용자 데이터 반환.

각 작업 단계에서는 TDD - RED, GREEN, jest TEST 단계를 수행.
각 작업은 하나의 작동과 하나의 책임으로 할당.

## 비밀번호 최소 길이 정책

먼저, 각 기준별 정책내용 확인.
| 옵션 | 길이 | 근거 |
|------|------|------|
| Supabase 기본값 | 6자 | 플랫폼 기본 |
| **NIST SP 800-63B 권장** | **8자** | **현대 보안 표준, 채택** |
| 강화 | 10~12자 | 보안성 ↑, UX ↓ |

NIST SP 800-63B : 디지털 신원 인증 및 수명주기 관리 지침에 따라
-> 8자로 결정. 

근거:
- NIST SP 800-63B는 비밀번호 최소 8자를 floor로 규정 (오랜 기간 업계 사실상 표준)
- 최신 Rev 4는 단일 인증의 경우 15자 권장. MFA 시 8자 허용.
- Supabase 기본값(6자)보다는 강화, 15자보다는 사용자 피로도 우선
- 추후 보안 강화 필요 시 15자로 상향 또는 MFA 도입 검토예정

이외 조치할 사항:
- 서버 측(우리) / Supabase 측 검증 기준이 일치시켜야 함.
- Supabase 대시보드 Authentication -> Policies에서 6자 -> 8자로 변경 필요.

조치 하는 이유 :
- 시나리오 A — (서버 측: 8자, Supabase: 6자)
1. 사용자가 8자 비밀번호 입력 -> 우리 코드 통과(최소 8자) -> Supabase 통과(최소 6자) -> 가입 성공.
2. 근데, 누군가 우리 코드를 우회해서 직접 Supabase 호출 -> 6자도 통과 -> 가입성공.
3. 8자 가입기준인데, 6자로 가입될 수 있는 가능성 존재.
4. 정책 일관성이 문제가 됨.

- 시나리오 B — (서버 측: 6자, Supabase 8자)
1. 사용자가 7자 비밀번호 입력 -> 우리 코드 통과(최소 6자) -> Supabase 거부 (최소 8자).
2. 사용자에게는 "비밀번호 8자 이상" 메시지가 안 뜨고, "회원가입 실패" 통합 메시지만 뜸.
3. 사용자 혼란.

export async function signUp(email, password, passwordConfirm) {
  if (!isValidEmail(email)) {
    return { error: '이메일 형식이 올바르지 않습니다' };
  }
  if (password.length < 8) {
    return { error: '비밀번호는 8자 이상이어야 합니다' };

**작업 4 - Supabase 호출 도입 및 실패 케이스**

```typescript
import { createClient } from '@/lib/supabase/server';
import { isValidEmail } from './validators';

export async function signUp(email, password, passwordConfirm) {
  if (!isValidEmail(email)) {
    return { error: '이메일 형식이 올바르지 않습니다' };
  }
  if (password.length < 8) {
    return { error: '비밀번호는 8자 이상이어야 합니다' };
  }
  if (password !== passwordConfirm) {
    return { error: '비밀번호가 일치하지 않습니다' };
  }

  const supabase = await createClient();
  const { data, error } = await supabase.auth.signUp({ email, password });

  if (error) {
    return { error: '회원가입에 실패했습니다' };
  }

  return { data: { user: data.user } };
}
```

### 위배지점 — 작업 5: Red에서 코드 작성 후, 테스트가 바로 통과된 사례

**현상**: 작업 4 Green 코드에 `return { data: { user: data.user } }`가 미리 박힘. 이는 작업 5의 Red 테스트를  즉시 통과 -> 원래는 RED 테스트에서는 틀리는 것이 목적 -> 이는 사전 plan을 미리 보여준 것이 원인이라 생각됨.

**사전 plan내용**:
 작업4 — Supabase signUp 실패 케이스

 mock에 mockSignUp 추가 필요 (기존 mockSignInWithPassword와 동일 패턴).

 Red 테스트:
 it('should return error when supabase signup fails', async () => {
   mockSignUp.mockResolvedValueOnce({
     data: { user: null, session: null },
     error: { message: 'User already registered' },
   });
   const result = await signUp('user@example.com', 'password123', 'password123');
   expect(result).toEqual({ error: '회원가입에 실패했습니다' });
 });

(위배지점)
 Green 최소 구현: createClient() → supabase.auth.signUp 호출, 에러 분기
 -> "signUp 성공시, { data: { user: data.user } } 반환" 이라는 요청은 존재하지 않음.

 ---
 작업5 — Supabase signUp 성공 케이스

 Red 테스트:
 it('should return user data when signup succeeds', async () => {
   const mockUser = { id: 'new-user-id', email: 'user@example.com' };
   mockSignUp.mockResolvedValueOnce({
     data: { user: mockUser, session: null },
     error: null,
   });
   const result = await signUp('user@example.com', 'password123', 'password123');
   expect(result).toEqual({ data: { user: mockUser } });
 });

(위배지점)
 Green 최소 구현: signUp 성공시, { data: { user: data.user } } 반환 
 -> 요청은 이곳에 존재하나 작업4에서 미리 작성.

 ---

**원인**: LLM의 "함수 완결 관성". Claude Code가 함수를 미완성 상태로 두는 것에 저항이 있음 — 학습 데이터의 함수 패턴이 거의 다 완성된 형태이기 때문. "에러 분기까지만"이라고 선행 plan 작업4에 명시되었지만, 명시적인 요구사항("성공 path는 작업 5에서 추가, 이 사이클에서 추가 return 없음")이 없었기에, LLM이 사전에 작업하는 일이 발생.

**결과**: 코드는 정상 작동, 9/9 테스트 통과. 그러나 작업 5는 TDD:Red만 실행하고 TDD:Green은 실행하지 못함.

## Red의 진짜 의미

이번 작업 중 생각하며 명확해진 원칙: **"Failing for the right reason"**.

Red 단계는 실패의 목적이 "테스트가 실패한다"가 아니라 **"의도된 지점에서 실패한다"**는 의미. 
의도된 실패결과를 얻지 못하면, 목적성이 담긴 로직은 얻지 못한다.

### 2. Supabase Mock 패턴 확장

0017의 `mockSignInWithPassword`에 `mockSignUp`을 추가하는 형태로 확장.

```typescript
const mockSignInWithPassword = jest.fn();
// 확장내용
const mockSignUp = jest.fn();

jest.mock('@/lib/supabase/server', () => ({
  createClient: jest.fn(() =>
    Promise.resolve({
      auth: {
        signInWithPassword: mockSignInWithPassword,
        // 확장내용

      },
    })

```

핵심:
- `mock` 접두사 변수명 (Jest 호이스팅 충돌 회피) — 0017과 동일

- 테스트마다 mockResolvedValueOnce로 응답을 다르게 주입하여 테스트 간 격리 보장
