# 0107 회고: 스토리에서 촬영지에 작품 제목 연결하는 기능

- 작성일: 2026.6.18
- 소요: 약 3사간 (설계 결정 + 1~5단계 구현 + 버그 2건 수정 + 동작 검증)
- 관련 커밋: 8306d61

---

## 1. 한 줄 요약

0106에서 만든 작품 데이터 위에, 사용자가 스토리 동선의 촬영지(Spot)에 어느 작품인지 검색·선택해 연결하는 입력 UI와 저장·복원 흐름을 연결했다. 자동완성 combobox부터 DB 저장, 재로드 시 제목 표시까지 한 바퀴를 완성하고, 그 과정에서 드러난 버그 2건(저장 캐시, 제목 재조회 누락)을 수정했다.

---

## 2. 왜 / 목적 / 이유

### 가. 작품의 식별 기준을 제목이 아니라 ID로 삼은 이유 (핵심)

- **왜**: "작품 = 제목"이라고 흔히 생각하지만, 제목은 표기 흔들림(`오징어게임` vs `오징어 게임`)·중복·사후 수정이 잦아 식별 기준(key)으로 부적합하다.
- **목적**: 작품을 안정적으로 가리키고, 0106에서 설계한 운영자 사후 병합(중복 작품을 하나로 합치기)이 작동하게 한다.
- **이유**:
  - 식별 기준을 안정적인 movieId로 두면, 제목이 바뀌거나 중복이 병합돼도 연결이 깨지지 않는다. 제목을 곳곳(Spot마다)에 베껴 저장하면, 작품 하나를 수정·병합할 때 연결된 모든 Spot을 다 따라가 고쳐야 한다.
  - 그래서 Spot엔 movieId만 저장하고(정본은 Movie 테이블 한 곳), 제목은 화면에 보여줄 때 movieId로 조인해 가져온다. 정본을 한 곳에만 두는 정규화.
  - **제목은 "부(副) 메타정보"다.** 시스템이 작품을 식별·검색·연결·묶기 하는 기준은 전부 movieId(주 메타정보)이고, 제목은 그걸 사람에게 보여주기 위한 표시용 부속이다. 이 우선순위가 아래 버그(제목 표시 후순위)의 근본 원인이 됐다.

### 나. 자동완성에 APPROVED만 노출, PENDING 제외한 이유

- **왜**: 0106 5단계 함수가 `status='APPROVED'`만 반환한다. 0107에서 "사용자 추가 작품(PENDING)도 자동완성에 띄울지" 재검토 대상이었다.
- **목적**: 검증되지 않은 작품이 다른 사용자에게 "정답처럼" 노출되는 것을 막는다.
- **이유**: PENDING을 자동완성에 띄우면, 검증 안 된 작품(오타·잘못된 표기일 수 있음)이 후보로 떠서 다음 사용자가 "남이 골랐으니 맞겠지"로 따라 고른다 → 잘못된 정보가 번진다. 자동완성에 떴다는 사실 자체가 일종의 보증처럼 작동하기 때문이다.
- **트레이드오프(인지)**: APPROVED만 띄우면 사용자 추가 작품끼리는 자동완성으로 안 묶여 중복이 생길 수 있다. 그 중복은 운영자 사후 병합으로 처리한다. 즉 "입력 단계 중복 방지"를 포기하고 "잘못된 정보 확산 방지(신뢰성)"를 택했다. 데이터가 적은 초기엔 틀린 정보 하나가 더 치명적이라 신뢰성을 우선.
- **결론**: 0106 함수를 그대로 유지(재검토 결과 = 변경 없음).

### 다. movieTitle을 LocalSpot에 두되 DB엔 저장 안 한 이유 (sourceNickname과의 차이)

- **왜**: 화면에서 작품 제목을 보여주려면 movieTitle이 어딘가 있어야 하는데, DB Spot엔 movie_id만 있다.
- **목적**: 편집 중에는 제목을 바로 표시하되(화면 상태), DB엔 정본만 두어 정규화를 유지한다.
- **이유**: movieTitle은 화면 표시용 임시 캐시일 뿐, 정본은 Movie 테이블에 있다. DB에 movie_title 컬럼을 만들어 베껴 저장하면 정규화가 깨진다(병합·수정 시 곳곳을 다 고쳐야 함). 그래서 LocalSpot(화면 상태)에만 movieTitle을 두고, DB 저장은 movieId만 한다.
- **0103 sourceNickname과의 차이(중요)**: 두 패턴은 표면상 "표시용 값을 같이 들고 다닌다"로 비슷하지만 본질이 다르다.
  - sourceNickname = **의도적 스냅샷**. 플랜을 담은 그 시점의 작성자 닉네임을 박제해 DB에 저장한다. 원본이 바뀌어도 "담을 때의 출처"는 고정돼야 하므로 일부러 베껴 저장.
  - movieTitle = **임시 캐시**. 정본(Movie)이 바뀌면 따라 바뀌어야 하므로 DB에 저장하지 않고, 매번 조인해 최신 제목을 가져온다.
  - 즉 "값을 같이 저장하느냐(스냅샷)" vs "값을 매번 조회하느냐(캐시)"가 갈린다. 변하면 안 되는 값은 스냅샷, 항상 최신이어야 하는 값은 조회.

### 라. "새 작품 추가"를 3.5단계로 분리한 이유

- **왜**: 자동완성에 원하는 작품이 없을 때 사용자가 새 작품을 만드는 기능은 movies 테이블 INSERT(쓰기)다.
- **목적**: 이번 3단계는 "읽기+선택"만으로 좁혀 안전하게, 쓰기는 따로 검수한다.
- **이유**: 새 작품 추가는 INSERT + RLS INSERT 정책(0106에서 보류) + Server Action이 더 필요하다. 읽기(자동완성)와 쓰기(새 작품)는 위험도가 달라 분리했다. 0106의 읽기/쓰기 분리 감각의 연장.

### 5단계 — 저장 액션에 movieId 반영

```

[검수 모드 — 핵심 2개]

   movieTitle은 안 들어가는지(DB 컬럼 없음).
2. movieId 없는 Spot이 null로 안전하게 저장되는지.

```

### 버그 수정 — 재로드 시 제목 표시 (읽고 보고만 먼저)


## 4. 코드 작성 & 수정

### 1단계 — Server Action 래퍼 (클라가 자동완성 부를 통로)

```ts

import { searchMovies } from '@/lib/movie/queries';
import type { MovieSuggestion } from '@/lib/movie/queries';

export async function searchMoviesAction(query: string): Promise<MovieSuggestion[]> {
  return searchMovies(query);   // server-only 함수를 클라에 노출하는 통로
}
```

### 3단계 — SpotPopup 자동완성 combobox (핵심 발췌)

```tsx
// components/SpotPopup.tsx
const [selectedMovieTitle, setSelectedMovieTitle] = useState(spot.movieTitle ?? '');
const debounceRef = useRef<ReturnType<typeof setTimeout> | null>(null);

function handleMovieInput(value: string) {
  setMovieInput(value);
  if (debounceRef.current) clearTimeout(debounceRef.current);
  if (!value.trim()) { setMovieSuggestions([]); setShowDropdown(false); return; }
  debounceRef.current = setTimeout(async () => {        // 디바운스 300ms
    const results = await searchMoviesAction(value);
    setMovieSuggestions(results);
    setShowDropdown(results.length > 0);
  }, 300);

  // ...
}
```

## 5. 결과 / 배운점

### 결과

- 작품 연결 한 바퀴 완성: 자동완성 검색·선택 → 화면 상태 → DB 저장(movie_id) → 재로드 시 제목 표시.
- 실제 동작 검증: "쉬"/"오징어게임" 자동완성 매칭 확인, DB에 movie_id 저장 확인(Supabase), 상세 보기에서 제목 표시 확인.
- 버그 2건 수정: (1) 첫 저장 시 Prisma validation 에러(빌드 캐시 stale) → 재시도 후 정상, (2) 재로드 시 제목 미표시 → 조회에 movie 조인 + 매핑 추가.

### 배운점

- **식별 기준을 제목이 아니라 ID로 잡는다.** "작품 = 제목"이라는 통념을 의심하고, 표기가 흔들리고 병합·수정이 잦은 제목 대신 안정적인 movieId를 주 식별자로 삼았다. 그래야 0106의 운영자 병합이 가능하고, 연결이 깨지지 않는다.
- **제목은 부 메타정보였다.** 시스템의 식별·검색·연결·묶기는 전부 movieId 기준이고, 제목은 사람에게 보여주기 위한 표시용 부속이다. 그래서 제목 표시가 우선순위에서 밀려 재조회 구현이 나중이 됐다 — "작품=제목"이라는 통념 때문에 누락처럼 보였지만, 설계상 제목은 조연이었다. 버그의 근본 원인은 이 우선순위였다.
- **스냅샷과 캐시는 다르다.** movieTitle을 "0103 sourceNickname과 같은 패턴"이라 생각했지만 본질이 다르다. sourceNickname은 변하면 안 되는 값이라 의도적으로 베껴 저장(스냅샷), movieTitle은 항상 최신이어야 해 저장하지 않고 매번 조회(캐시). "변하면 안 됨 → 스냅샷, 최신이어야 함 → 조회"의 기준.
- **누락 버그는 전수 조사로 반쪽 수정을 피한다.** 재로드 제목 버그를 "읽고 보고만"으로 먼저 조사하니, 화면이 편집·상세 두 경로였다. 편집만 고쳤으면 상세 보기에선 여전히 안 보였을 것. 고치기 전에 "필요한 위치 전부"를 찾는 게 반쪽 수정을 막았다.
