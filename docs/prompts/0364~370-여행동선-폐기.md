# 0364~370 회고: 여행동선 폐기와 지도 상호작용

작성일 2026-07-26 / 소요 약 3시간 / 커밋 0364~0370

## 핵심 판단

- **기능을 지우는 결정이었다.** 동선은 플랜이 할 일이고 스토리는 다녀온 뒤의 기록이라,
  같은 것을 두 번 적게 하는 구조였다. 게다가 플랜대로 여행했을 리도 없다.
- **부수 이득으로 크래시 계열 하나가 구조적으로 사라졌다.**
- **지웠다가 절반을 되살렸다.** 순서 편집은 버렸지만 "무엇을 찍었나"는 순서와 다른
  정보였다.
- **`fitBounds`가 신뢰 불가라는 사실이 두 컴포넌트에서 독립적으로 재발했다.**

## 한 줄 요약

스토리의 여행동선(경로선·순서 편집)을 폐기하고 "점 찍고 리뷰"로 축소한 뒤, 지도
상호작용을 SpotFinder 수준으로 끌어올렸다.

## 왜 / 목적 / 이유

**왜** — 스토리를 쓸 때마다 스팟 순서를 신경 써야 했다. 마커에 번호가 붙고 선이 이어지니
"순서가 맞나"를 계속 의식하게 됐고, 그게 작성 피로감의 실체였다.

**목적** — 서비스 본연(촬영지·들린 장소를 기록하는 것)에 충실하게. 인상 깊은 곳만
점을 찍고 리뷰를 쓰면 끝나는 흐름.

**이유** — 동선은 이미 플랜에서 짠다. 스토리는 다녀온 뒤의 리뷰라 동선을 또 적을 필요가
없고, 애초에 플랜 동선대로 여행했을 리도 없다. 계획과 기록의 역할 분담이 명확해진다.

## 결과 / 배운 점

### 지우는 결정의 이득

폴리라인 렌더를 걷어내니 **0328의 GL 크래시 계열 원인 하나가 구조적으로 사라졌다.**
`removeLayer` → `getLayer` 경로를 타서 죽던 것이었고, SpotFinder는 폴리라인이 0개라
무사했었다.

기능을 지우면 그 기능이 만들던 버그도 함께 사라진다. 유지보수 면적이 줄었다.

데이터는 건드리지 않았다. `order` 필드와 재인덱싱, 제출 payload는 그대로 두고 렌더만
걷었다. 되살릴 여지를 남기는 비용이 0이었다.

### 지운 뒤 절반을 되살리기

순서 편집을 걷으면서 "여행순서 바꾸기" 카드가 사라졌고, 그 안에 있던 **찍은 장소 목록**도
함께 없어졌다.

실제로 써보니 지도의 점만 보고 어디에 뭘 찍었는지 기억해야 했다. 순서와 "무엇을 찍었나"는
다른 정보였는데 한 카드에 있었다는 이유로 같이 지워진 것이다.

목록만 되살렸다. 복구는 재구성하지 않고 제거 직전 커밋의 파일을 참조했고, `SpotList`의
readOnly 경로가 이미 "번호 없는 목록 + 선택"이라 **수정 0줄로 재사용**했다.

처음엔 메뉴 카드에 상시 표시했는데 140px에서 잘려 답답했다. 별도 모드로 옮겨 카드 전체
높이를 쓰게 했다.

### 같은 함정에 두 번

지도가 여러 좌표를 아우르지 못하고 확대된 채로 뜨는 문제를 고치려 했다. 코드를 보니
`fitBounds` 호출이 이미 있었고 가드까지 갖춰져 있었다.

규칙만 교체하려다 멈추고, **기존 코드가 왜 안 먹는지부터** 확인하게 했다. 목 계측으로
effect가 실행되고 올바른 인자로 `fitBounds`를 부르는 것까지 확인됐다. 즉 코드는 정상이고
**SDK 쪽 문제**였다.

그리고 레포에 이미 답이 있었다. `SpotFinderMapNaver`에 "GL `fitBounds`는 퇴화 스팬을
무시하고 준비 전엔 빈 bounds로 계산" 실측 주석이 있었고, 그래서 그쪽은 이미 `fitBounds`를
폐기하고 프로젝션 직접 산출로 갔다. **SpotMap만 `fitBounds`가 잔존해 있었던 것.**

`map.getProjection()`으로 픽셀 스팬을 구해 줌을 산출하는 방식으로 바꿨다.

이 패턴이 이 트랙에서 세 번 반복됐다.

| 처방 | SpotFinder | SpotMap |
|---|---|---|
| `fitBounds` 기각 → 프로젝션 산출 | 이미 적용 | 0367에서 뒤늦게 |
| `morph`가 안전한 전환 수단 | 이미 사용 | 0369에서 뒤늦게 |
| `customStyleId` 기각 → 페이드 오버레이 | 이미 적용 | 0370에서 뒤늦게 |

같은 SDK를 쓰는 두 컴포넌트인데 한쪽의 실측이 다른 쪽에 건너가지 않았다. 지도 관련
실측 결론을 한 곳에 모으는 게 후속 과제.

### 토글이 만든 착각

마커를 클릭하면 "왜 검색·찍기 메뉴가 나오지?"라는 증상이 있었다. 원인은
`handleMarkerClick`이 **토글**이었다는 것 — 같은 마커를 다시 누르면 `activeSpot`이
`null`이 되고, 그러면 사이드 카드가 메뉴로 떨어진다.

팝업이 "닫힌" 게 아니라 메뉴가 "드러난" 것이었다. 토글을 걷어 마커 클릭은 항상 보기
팝업으로 고정하고, 닫기는 팝업의 ×가 전담하게 했다.

### 색이 의미를 잃었다

순서를 폐기했는데 마커 색이 `첫=초록 / 끝=빨강 / 중간=파랑` 시맨틱이었다. 순서가 없으니
그 색이 무엇을 뜻하는지 모호해졌다.

파랑 단색으로 통일하고 목록의 색 도트도 `MapPin` 아이콘으로 바꿨다. 목록↔마커 대응은
**선택 시 펄스 연동**이 이미 담당하고 있어서 색 구분이 필요 없었다.

기능을 지우면 그 기능을 전제하던 표현도 함께 정리해야 한다.

## 대표 코드

```ts
// components/SpotMap.tsx  (발췌 — fitAllSpots의 프로젝션 산출 구간만)
    const size = map.getSize();
    if (!size || size.width === 0 || size.height === 0) return false;
    let minLat = spotList[0].lat, maxLat = minLat, minLng = spotList[0].lng, maxLng = minLng;
    for (const s of spotList) {
      minLat = Math.min(minLat, s.lat); maxLat = Math.max(maxLat, s.lat);
      minLng = Math.min(minLng, s.lng); maxLng = Math.max(maxLng, s.lng);
    }
    // Mercator 상수 하드코딩 대신 SDK 프로젝션 위임 — GL 도/픽셀 비가 표준 256 예측과 어긋났던
    // 실측 이력(SpotFinder 주석) 준용
    const proj = map.getProjection();
    const pSW = proj.fromCoordToOffset(new naver.maps.LatLng(minLat, minLng));
    const pNE = proj.fromCoordToOffset(new naver.maps.LatLng(maxLat, maxLng));
    const dx = Math.abs(pNE.x - pSW.x);
    const dy = Math.abs(pNE.y - pSW.y);
    const FIT_PADDING = 60; // 구 fitBounds 패딩 60 유지
    const availW = size.width - FIT_PADDING * 2;
    const availH = size.height - FIT_PADDING * 2;
    const dz = Math.log2(Math.min(availW / dx, availH / dy));
    const targetZoom = Math.min(Math.max(map.getZoom() + dz, map.getMinZoom()), ZOOM_FOCUS);
    const center = proj.fromOffsetToCoord(
      new naver.maps.Point((pSW.x + pNE.x) / 2, (pSW.y + pNE.y) / 2),
    );
    apply(center, targetZoom);
    return true;
```
