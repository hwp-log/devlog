## 1. 한 줄 요약

`story-photos` 버킷 96개 파일 중 DB가 참조하지 않는 81개(45.32MB, 전체 용량의 91%)를
삭제해 버킷과 DB 참조를 1:1로 맞췄다. 되돌릴 수 없는 작업이라
**조사 → 삭제 직전 재대조 → 백업 → assert → 삭제 → 재대조** 6단계로 나눠 진행.

## 2. 왜 / 목적 / 이유

### 왜 지웠나
스토리 7건을 DB에서 삭제했지만 그 스토리들이 쓰던 사진은 Storage에 그대로 남았다.
`story-photos`는 **public 버킷**이라 참조가 끊겨도 경로만 알면 계속 접근된다.
출처 불명 사진이 섞여 있어 "DB에서 안 보인다"는 것이 "없다"를 뜻하지 않았다.

### 목적
버킷의 실제 내용물을 DB 참조와 일치시킨다 — 참조되는 것만 남고, 남은 것은 전부 참조된다.

### 왜 조사와 삭제를 두 단계로 나눴나
**"참조 없음"은 삭제해도 된다는 뜻이 아니기 때문이다.** DB 대조로는
① 작성 중이라 아직 제출되지 않은 업로드 ② 외부에 공유된 URL
③ 코드 밖(문서·메모)에서의 참조를 구분할 수 없다.
①은 실제로 후보에 있었다 — 조사 당일 07:02~07:03에 올라온 4건.
그래서 조사는 재료만 내게 하고 판정은 내가 했다.

### 왜 "조사 때 만든 81개 목록"을 쓰지 않았나
설계의 핵심이다. 조사와 삭제 사이에 시간이 흐르고, 그 사이 새 업로드나
참조 변경이 있으면 목록이 거짓말이 된다. 삭제 대상은 **삭제 직전에
같은 프로세스 안에서 처음부터 다시 계산**했고, 조사 시점 수치는
비교 기준값으로만 썼다.

그 위에 게이트를 걸었다 — 삭제 대상이 조사 때보다 **늘었으면 중단**한다.
늘었다는 건 내가 보지 못한 파일이 생겼다는 뜻이고, 그건 임의 판정할 대상이 아니다.
반대로 **줄었으면 그대로 진행**한다 (참조가 늘어난 방향 = 안전).

### 왜 안전망 필드를 고집했나
지시한 참조원은 5개였다 — `Story.content` / `StorySpot.photoUrl` /
`Spot.photoUrl` / `Spot.coverUrl` / `User.avatarUrl`.
여기에 `Story.photoUrl` · `MyPlan.coverUrl`을 더해 스캔하게 했다.
**빠뜨린 참조원 하나가 살아있는 파일을 "고아"로 만들기 때문이다.**

결과적으로 두 대조의 차이는 0건이었지만 안전망이 헛돈 건 아니었다 —
`MyPlan.coverUrl`이 버킷 파일 2개(이태원 클라쓰·수리남 플랜 커버)를
실제로 참조하고 있었고, 그 2개가 마침 `StorySpot.photoUrl`로도 참조돼
결과가 같아졌을 뿐이다. 스팟 쪽 참조가 먼저 끊겼다면 그 2개는 지워졌다.

### 왜 백업을 넣었나
Supabase Storage에는 휴지통이 없다. 45MB 로컬 복사는 값싼 보험이고,
없으면 복구 경로가 0이다. 백업이 1건이라도 실패하면 삭제하지 않고
중단하도록 걸었다.

[목표]

쓰다 만 글이 없다는 걸 확인하고 넘겼다.

## 4. 코드

레포에 남긴 코드는 없다. 아래는 스크래치패드 임시 스크립트의 핵심부다.

### 4-1. 버킷 나열 — supabase-js 대신 REST

```typescript
// createClient()는 Node 20에서 realtime 초기화 중 죽는다
//   Error: Node.js 20 detected without native WebSocket support
// 읽기(list)만 필요하므로 Storage REST를 직접 호출
async function listRaw(bucket: string, prefix: string, limit: number, offset: number) {
  const res = await fetch(`${url}/storage/v1/object/list/${bucket}`, {
    method: 'POST',
    headers: { apikey: key, Authorization: `Bearer ${key}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ prefix, limit, offset, sortBy: { column: 'name', order: 'asc' } }),
  });
  if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);
  return res.json();
}
```

`list`는 **한 뎁스만** 반환하고 기본 limit이 100이다. 경로가
`<userId>/<uuid>.<ext>`와 `<userId>/spot/<spotId>/<ts>.<ext>` 두 갈래라
재귀 + 페이지네이션이 둘 다 필요했다. 디렉터리는 `id === null`로 판별한다.

```typescript
for (const e of data) {
  const full = prefix ? `${prefix}/${e.name}` : e.name;
  if (e.id === null) out.push(...await listAll(bucket, full)); // 디렉터리
  else out.push({ path: full, size: e.metadata?.size ?? 0 });
}
```

### 4-2. 대조 키 — raw URL이 아니라 Storage 경로

```typescript
const PREFIX = `/storage/v1/object/public/${BUCKET}/`;
function toPath(u: string): string | null {
  try {
    const p = new URL(u).pathname;
    return p.startsWith(PREFIX) ? decodeURIComponent(p.slice(PREFIX.length)) : null;
  } catch { return null; }
}
```

문자열 비교였다면 쿼리스트링·URL 인코딩 차이로 살아있는 파일이
"참조 없음"이 됐을 것이다. 기존 `lib/story/photo-cleanup.ts`의
`extractStoragePath`와 같은 접근이다. 접두사가 안 맞으면 `null` —
`Spot.coverUrl` 35건(TourAPI `tong.visitkorea.or.kr`)이 여기서 자연히 걸러진다.

### 4-3. 참조 수집 — 지시 5필드 + 안전망 3필드

```typescript
const stories = await prisma.story.findMany({ select: { content: true, photoUrl: true } });
for (const s of stories) {
  for (const g of s.content.matchAll(/<img[^>]+src=["']([^"']+)["']/g)) add(g[1], 'Story.content');
  add(s.photoUrl, 'Story.photoUrl[안전망]');
}
// StorySpot.photoUrl / Spot.photoUrl / Spot.coverUrl / User.avatarUrl ...
for (const p of await prisma.myPlan.findMany({ select: { coverUrl: true } }))
  add(p.coverUrl, 'MyPlan.coverUrl[안전망]');
```

### 4-4. 게이트 — 조사 시점보다 삭제 대상이 늘면 중단

```typescript
const SNAPSHOT = { total: 96, referenced: 15, unreferenced: 81 };

if (targets.length > SNAPSHOT.unreferenced) {
  console.log('⛔ 중단 — 삭제 대상이 조사 시점보다 늘었다. 조사 이후 올라온 파일은 임의 판정하지 않는다.');
  process.exit(2);
}
if (targets.length < SNAPSHOT.unreferenced)
  console.log('ℹ️ 삭제 대상이 조사 시점보다 줄었다 (참조가 늘어난 방향 = 안전). 줄어든 대로 진행.');
```

### 4-5. 백업 실패 시 중단 + 삭제 직전 assert

```typescript
if (failB.length) {
  console.log('⛔ 중단 — 백업 실패. 복구 경로 없는 삭제는 하지 않는다.');
  process.exit(3);
}

const overlap = targets.filter(f => refSet.has(f.path));
if (overlap.length) {
  console.log(`⛔ 중단 — 삭제 목록에 참조 파일 ${overlap.length}건 혼입`);
  process.exit(4);
}
```

`targets`는 정의상 `refSet`의 여집합이라 이 assert는 논리적으로 항상 통과한다.
그럼에도 넣은 이유는, 되돌릴 수 없는 작업에서는 **"항상 참일 것"과
"확인했다"가 다르기** 때문이다. 리팩터링 한 번에 전제가 무너질 수 있다.

### 4-6. 삭제 — 버킷명 상수 고정

```typescript

```

"avatars를 건드리지 말 것"을 주의력이 아니라 **구조**로 지켰다 —
버킷명이 상수라 avatars로는 요청이 나갈 수 없다. 나열조차 하지 않았다.

## 5. 결과 / 배운점

### 결과

**삭제 직전 재대조** — 조사 시점과 차이 0

```
전체 96개 / 49.84MB
  ├ 참조됨   : 15개 / 4.52MB
  └ 참조 없음: 81개 / 45.32MB
조사 시점 대비 — 전체 +0 / 참조됨 +0 / 참조없음 +0
```

**백업** — 81/81 성공, 45MB. 이후 `~/Desktop/dotrip-storage-backup-20260816`으로
복사하고 **82개 파일 SHA-1 전량 일치** 확인 (파일 수·용량뿐 아니라 내용까지).

**삭제** — 1배치, 요청 81 / 성공 81 / 실패 0

**삭제 후 재대조**

| 검증 | 결과 |
|---|---|
| ① 참조되는 15개 잔존 | 15/15 ✅ 유실 0 |
| ② DB는 참조하나 파일 없음 | 0건 ✅ |
| ③ 전후 파일 수·용량 | 96개 49.84MB → 15개 4.52MB (−81개 / −45.32MB) |
| ④ 남은 파일 중 참조 없음 | 0건 ✅ |

버킷과 DB 참조가 **1:1**이 됐다. DB·코드·`avatars` 무변경.

**부수 관측**: 삭제한 81개 중 **44개**가 0575에서 걷어낸 `public/seed/*.png`
12장과 바이트 크기가 정확히 일치했다 (narcosaints 12개, crimecity 6개, …).
해시 대조는 하지 않아 증명은 아니지만, 같은 시드 사진이 작업 중 반복
재업로드된 흔적으로 읽힌다. **0575와 0576이 같은 줄기라는 물증**이기도 하다.

### 배운점

- **되돌릴 수 없는 작업은 "정확한 계산"이 아니라 "틀렸을 때의 대비"로 설계한다.**
  대조 로직이 맞다는 확신과 별개로 백업·게이트·assert를 넣었다.
  전부 통과했으니 결과만 보면 낭비지만, 그 셋이 없었으면 이 작업은
  "아마 맞을 것"에 45MB를 건 도박이었다.

- **조사 결과에는 유효기간이 있다.** 목록을 만든 순간부터 그것은 과거다.
  조사와 실행 사이가 벌어질수록 목록은 사실이 아니라 가설이 된다.
  이번엔 차이가 0이었지만, 그건 재대조를 했기에 **아는** 사실이지
  안 했으면 몰랐을 사실이다.

- **지시한 목록이 전부라고 가정하지 않는다.** 참조원을 5개로 지시했는데
  실제로는 8개를 봐야 했다. 차이는 0이었지만 `MyPlan.coverUrl`은 실제로
  버킷을 참조하고 있었다 — 우연히 다른 필드와 겹쳤을 뿐이다.
  삭제형 작업에서 참조원 누락은 **조용히 데이터를 잃는** 유형의 실수다.

- **금지사항은 주의력이 아니라 구조로 지킨다.** "avatars 건드리지 말 것"을
  버킷명 상수로 고정해 물리적으로 불가능하게 만들었다.
  "조심하겠다"는 지킬 수도 못 지킬 수도 있지만, 상수는 항상 지킨다.

- **도구가 환경을 가린다.** `supabase-js`의 `createClient`가 Node 20에서
  realtime 초기화로 죽었다 — Storage만 쓸 건데 WebSocket 때문에.
  REST 직접 호출로 우회했다. 래퍼가 필요한 것보다 많이 들고 올 때는
  아래 계층으로 내려가는 게 빠르다.
