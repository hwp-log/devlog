**배운점**: 테스트 통과/실패 여부보다도, 의도에 맞는 결과가 나와야 한다.

> 단순 테스트가 아닌, 코드를 일부러 망가뜨렸을 때 진짜 기능작동이 실패하는지 보는 방식.

### 2. act() 경고 처리 대응

작업 진행 중 useActionState의 비동기 처리로 인한 act() 경고가 5번 누적. 매번 테스트시 경고가 발생하면, 작업 흐름이 깨지고, 미루면 다음 작업에서 더 누적되기에 작업 4(redirect 추가) 진입 전에 별도 대응하기로 결정.

**배운점**: 사실 테스트할 SignupForm 함수코드는 이상 없이 정상 작동. 문제는 테스트가 비동기 작업이 끝나기 전에 검사한 것. 작동코드가 아니라 테스트 코드의 검증 행동이 빠져서 발생한 문제. SignupForm.tsx는 변경 없이 테스트 파일만 수정해서 47/47 통과 + 경고 0건 달성.

추가내용 : action.test.ts에서 각 테스트 항목별 await signupAction(null, formData); 코드 추가

### 3. signupAction redirect + 가짜 검증 테스트 교체

회원가입이 성공하면 /login 으로 리다이렉트가 되는지 확인해야 했는데, 테스트 내용에서는 기존 “성공 시 data 가 반환된다”는 내용으로 진행했었다. 왜냐하면 아래의 형태였기에 착각했기 때문이다.

```ts
if (success) {
  redirect('/login');
}
return { data: user };  // 성공 시 반환
```

문제는 실제로 `return { data: user }`를 받았다고 하더라도 진짜로 redirect가 실행되었는지는 알 수 없다.
따라서 테스트 내용을 redirect를 작동시키는지로 바꿨다.

## 코드 변화 (실제 결과물)

### 1. SignupForm (Client Component)

```typescript
// app/(auth)/signup/SignupForm.tsx
'use client';
import { useActionState, useState } from 'react';

type Strength = '약함' | '보통' | '강함';

function getPasswordStrength(password: string): Strength | null {
  if (password.length === 0) return null;
  if (password.length < 8) return '약함';
  let score = 0;
  if (/[A-Z]/.test(password)) score++;
  if (/[0-9]/.test(password)) score++;
  if (/[^A-Za-z0-9]/.test(password)) score++;
  if (score >= 2) return '강함';
  if (score >= 1) return '보통';
  return '약함';
}

export function SignupForm({ action }: SignupFormProps) {
  const [state, formAction] = useActionState(action, null);
  const [strength, setStrength] = useState<Strength | null>(null);

  return (
    <form action={formAction}>
      {/* 이메일 input */}
      {/* 비밀번호 input + onChange로 강도 계산 */}
      <p>8자 이상 입력해주세요</p>
      {strength && <StrengthIndicator strength={strength} />}
      {/* 비밀번호 확인 input */}
      {state && 'error' in state && (
        <p role="alert">{state.error}</p>
      )}
      <button type="submit">회원가입</button>
    </form>
  );
}
```

### 2. signupAction (Server Action)

```typescript
// app/(auth)/signup/actions.ts
'use server';
import { redirect } from 'next/navigation';
import { signUp } from '@/lib/auth/actions';

export async function signupAction(_prevState: unknown, formData: FormData) {
  const result = await signUp(
    formData.get('email') as string,
    formData.get('password') as string,
    formData.get('passwordConfirm') as string,
  );

  if (result && 'data' in result) {
    redirect('/login');
  }

  return result;
}
```

## 결정

### 1. 회원가입 페이지 = Client Component
- **결정**: 회원가입 페이지 = Client Component (SignupForm)
- **근거**:
  - 비밀번호 강도 실시간 계산 필요 → useState 필수 → Client Component 필수
  - 로그인 페이지(Server Component, 0019)와 차이: 회원가입은 실시간 UI 피드백 본질
- **참조**: AGENTS.md "Required Patterns > Next.js 16" (Server Component 우선 원칙 + 인터랙션 필수 시 Client)

### 2. 비밀번호 확인 필드 유지
- **결정**: 회원가입 폼에 비밀번호 확인 필드 유지
- **근거**:
  - 운영 비용 (이메일 재설정 비용 직접 부담)
  - Show Password 토글의 육안 검증 한계
  - 한국 사용자 관습 (네이버, 카카오 등)
  - 포폴 맥락 (가입 전환율이 핵심 KPI 아님)
- **인지된 반대 의견**: UX Movement, Echobind 등 업계 주류는 제거 권장 (전환율 56.3% 증가)
- **결론 프레임**: 업계 무시 아닌 맥락 재해석

### 3. Show Password 토글 미도입
- **결정**: 비밀번호 입력 필드에 Show Password 토글 추가하지 않음
- **근거**:
  - 토글 사용 시 사용자 비밀번호 검증을 시각 의존
  - 복잡한 비밀번호일수록 한 글자 오타 육안 발견 어려움
  - 결국 비밀번호 재설정 요청 증가 → 이메일 발송 비용 증가
  - 1인 개발자가 감당하기 어려운 운영 비용
- **대체**: 비밀번호 확인 필드로 오타 방지
- **다른 의견**: UX Movement, NN/g (Nielsen Norman Group) 등은 토글 권장
- **결론 프레임**: 업계 권고 무시 아닌 운영 비용 맥락 재해석
- **재검토 시점**: 사용자 트래픽/비용 데이터 누적 후

### 4. 비밀번호 강도 표시 추가 (회원가입만)
- **결정**: 회원가입 폼에 비밀번호 강도 인디케이터 추가
- **근거**:
  - 사용자가 비밀번호 강도를 시각적으로 인지하면 자연스럽게 강한 비밀번호 선택 유도 (강제 복잡도 규칙보다 효과적)
  - 강제 규칙(대소문자/숫자/특수문자 의무) 없이 길이 + 강도 표시로 유도하는 방향
- **참조**: NN/g 강도 표시 권장
- **적용 범위**: 회원가입 페이지만 (로그인 페이지 제외)
- **구현**: `getPasswordStrength()` 함수 (길이 + 대문자/숫자/특수문자 점수)
