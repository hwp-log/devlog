# 0087 회고: My Plan 카드를 비용 구성 중심으로 재디자인

작성일: 2026-06-10
소요: 약 1시간
관련 커밋: eb22518 (feat: 0087 My Plan 카드 디자인 — 예산 누적 막대·총액·범례·hover lift)

## 1. 한 줄 요약
My Plan 카드를 제목·날짜 같은 메타정보 나열에서 벗어나, 비용 구성을 한눈에 보여주는 누적 막대(+총액·범례)를 주인공으로 재디자인했다. 카드를 "티켓", 상세를 "깊이 보는 곳"으로 역할을 나눴다.

## 2. 왜 / 목적 / 이유

**왜 (동기/문제)**
기존 My Plan 카드는 제목, 날짜, 화폐 종류만 표시했다. 그런데 이건 기본 메타정보일 뿐, 정작 중요한 계획과 비용 내용이 한눈에 들어오지 않았다. 카드를 봐도 "이 계획이 어떤 계획인지"가 와닿지 않았다.

**목적 (도달할 상태 / 사용자 가치)**
카드만 봐도 각 계획의 핵심 — 비용이 어디에 얼마나 몰리는지 — 이 한눈에 파악되게 한다. 카드와 상세가 각자의 목적에 맞는 정보를 담게 역할을 나눈다.

**이유 (채택 근거 / 의사결정)**
핵심은 "목적과 내용의 일치"였다. 상세 페이지는 깊이 들여다보는 곳이라 "한눈 요약"이 오히려 목적과 어긋난다 — 한눈에 들어오는 정보는 상세가 아니라 카드에 있어야 맞다. 카드를 티켓·예매권처럼 "한눈에 필요한 정보만 집약하는 곳"으로 보자 디자인이 풀렸다. 그래서 카드의 주인공을 항공+5카테고리 누적 막대(비용 구성)와 총액으로 잡았다. 카드와 상세가 같은 비용 합계 계산을 쓰므로, 계산 함수는 공통 유틸로 추출해 양쪽이 한 곳을 공유하게 했다.

## 4. 코드 작성 & 수정

### 비용 합계 계산을 공통 유틸로 추출 (추출하면서 개선)

```ts
// lib/plan/calc-cost-summary.ts (신규)
// 기존 PlanDetail.tsx의 로컬 함수를 공통 유틸로 추출하면서 더 견고하게 다듬었다.
export function calcCostSummary(costs: { category: string; amount: number }[]) {
  const totals = { TRANSPORT: 0, ACCOMMODATION: 0, FOOD: 0, ENTRANCE: 0, ETC: 0 };
  for (const cost of costs) {
    if (cost.category in totals) {                       // 정의된 카테고리 외 값은 무시 (안전 가드)
      (totals as Record<string, number>)[cost.category] += cost.amount;
    }
  }
  return totals;
}
```

- 파라미터 타입을 `PlanCost[]`가 아니라 `{ category: string; amount: number }[]`로 느슨하게 잡았다 — 특정 모델(PlanCost)에 묶이지 않아 재사용성이 높다.
- `if (cost.category in totals)` 가드를 더했다 — 정의된 5개 카테고리 외의 값이 들어와도 무시해 안전하다. (PlanDetail 로컬 함수 때는 없던 안전장치.)

### 카드에 비용 표시용 쿼리 include

```tsx
// app/(protected)/my-plan/page.tsx
const plans = await prisma.myPlan.findMany({
  where: { ownerId: user!.id },
  orderBy: { createdAt: 'desc' },
  include: {
    costs: true,
    flight: true,
    _count: { select: { spots: true } },   // 카드에 스팟 수 표시용
  },
});
```

### 누적 막대 + 총액 + 범례 (실제 구현)

```tsx
// 각 카드 안 — summary = calcCostSummary(plan.costs), total = calcPlanTotal(...) 계산 후
{isEmpty ? (
  <p className="text-xs text-slate-400 py-3">예산 미입력</p>
) : (
  <>
    {/* 누적 막대: 각 구간 폭 = 금액 / 총액 비율 */}
    <div className="flex h-2 rounded-full overflow-hidden bg-slate-100 mb-3">
      {flightAmt > 0 && (
        <div style={{ width: `${(flightAmt / total) * 100}%`, backgroundColor: FLIGHT_COLOR }} />
      )}
      {CATEGORIES.map((cat) =>
        summary[cat] > 0 ? (
          <div
            key={cat}
            style={{ width: `${(summary[cat] / total) * 100}%`, backgroundColor: CATEGORY_COLOR[cat] }}
          />
        ) : null
      )}
    </div>

    {/* 총액 */}
    <p className="text-right text-xl font-bold text-[#1A1A1A] mb-3">
      {formatAmount(total, plan.currency as 'KRW' | 'USD' | 'JPY')}
    </p>

    {/* 범례: 비용 > 0 항목만 (색 점 + 라벨) */}
    <div className="flex flex-wrap gap-x-3 gap-y-1">
      {flightAmt > 0 && (
        <span className="flex items-center gap-1 text-xs text-slate-500">
          <span className="w-2 h-2 rounded-full shrink-0" style={{ backgroundColor: FLIGHT_COLOR }} />
          항공
        </span>
      )}
      {CATEGORIES.map((cat) =>
        summary[cat] > 0 ? (
          <span key={cat} className="flex items-center gap-1 text-xs text-slate-500">
            <span className="w-2 h-2 rounded-full shrink-0" style={{ backgroundColor: CATEGORY_COLOR[cat] }} />
            {CATEGORY_LABEL[cat]}
          </span>
        ) : null
      )}
    </div>
  </>
)}
```

- 막대 각 구간의 폭을 `금액 / 총액 * 100%`로 줘서, 비용이 큰 카테고리가 넓게 차지한다 — "어디에 돈이 몰리는지"가 폭으로 바로 드러난다.
- `flex h-2 rounded-full overflow-hidden`으로 얇고 둥근 단일 막대 안에 색 구간을 가로로 쌓았다.
- 막대와 범례 모두 `> 0` 조건으로 빈 카테고리를 제외했다 — 노이즈 제거를 양쪽에 일관되게 적용.

## 5. 결과 / 배운점
- 결과: 카드만 봐도 비용 구성(숙박 중심인지, 교통 중심인지)이 한눈에 드러나고, 총액이 시선 중심에 온다. 메타정보 나열 카드에서 "한눈에 파악되는 티켓"으로 바뀌었다.
- 배운점 1 (정보 위계): 정보를 어디에 두느냐는 그 화면의 목적이 정한다. 상세는 높은 밀도(전부 자세히), 카드는 낮은 밀도(핵심만 빠르게). 카드를 "티켓"으로 보면 담을 것이 분명해진다 — 한눈에 필요한 것만. 디자인을 "예쁘게"가 아니라 "각 화면의 목적에 맞는 정보 밀도"로 사고한 작업이었다.
- 배운점 2 (추출은 개선의 기회): 카드와 상세가 같은 비용 합계 계산을 쓰므로 calcCostSummary를 한 곳(lib/plan)에 두고 양쪽에서 import했다. 단순히 옮긴 게 아니라, 옮기면서 파라미터 타입을 느슨하게(재사용성) 하고 category 가드를 더했다(안전). 같은 로직이 여러 곳에 흩어지면 한쪽만 고쳐 불일치 버그가 난다(fmtTime 중복으로 겪은 문제와 같은 원칙) — 정의는 한 곳, 사용은 여러 곳. 그리고 추출은 중복 제거이자 코드를 다듬을 기회다.
- 배운점 3 (노이즈 제거): 막대와 범례 모두 비용이 0보다 큰 항목만 노출했다. 비어 있는 카테고리까지 보이면 한눈에 들어와야 할 정보가 흐려진다 — "한눈"이라는 목적을 지키려면 덜 중요한 것을 빼는 결정도 필요하다.
