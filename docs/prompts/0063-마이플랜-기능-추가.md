# 0063 마이플랜(My Plan) 기능 추가 회고

## 한 줄 요약

다른 사람의 여행계획을 복사하거나 자신의 여행 계획(My Plan) 작성하는 기능을, 테이블 설계부터 작성·상세·삭제까지 완성했다.

## 왜 · 목적 · 이유

핵심 판단은 **PlanSpot(장소)과 PlanCost(비용)를 어떻게 연결하느냐**였다. 처음엔 `createdAt`(생성 시각)으로 둘을 매칭했는데, 같은 Day에 항목이 여러 개면 시각이 비슷해 매칭이 틀어질 위험이 있었다. 그래서 `PlanCost`에 `planSpotId`(nullable FK)를 추가해 "이 비용은 이 장소 것"이라고 직접 연결하는 방식으로 바꿨다.

## 작성한 프롬프트

작업을 단계로 끊어 각 단계마다 plan 요청 → 검수 → 승인 → 구현 순으로 진행:

1. 테이블 + RLS (스키마 → 마이그레이션 SQL → RLS → 적용)
2. 네비 + 빈 페이지 (UserDropdown 링크 + 목록 페이지)
3a. 새 계획 작성 (제목·기간·통화 폼 + Server Action)
3b. 상세 + Day별 항목 추가 (타임라인 + 항목 추가)
3b 보완. PlanCost에 planSpotId FK 추가 (createdAt 매칭 → 직접 연결)
추가. 계획 삭제 + 저장 후 상세 화면 이동

각 프롬프트는 `[배경]/[목표]/[하지 말 것]/[검수 모드]` 형식으로, "하지 말 것"에 다음 단계 범위와 "커밋은 직접 한다"를 명시했다.

## 코드 작성 · 수정

**테이블 (MyPlan / PlanSpot / PlanCost)**
- MyPlan: ownerId(User FK, cascade), sourceStoryId(String? — FK 아님, 출처 표시만), title, currency(enum), startDate/endDate
- PlanSpot: planId(FK cascade), day, order, name, lat/lng
- PlanCost: planId(FK cascade), planSpotId(String? FK, **SetNull**), day, category(enum), label, amount(Int 최소단위)
- enum Currency / CostCategory 추가

**RLS (12개 정책)**
- MyPlan은 비공개 — select도 owner 검증 (Spot은 공개 USING(true)였지만 My Plan은 owner_id = auth.uid())
- PlanSpot/PlanCost는 planId 통해 EXISTS로 소유자 검증

**마이그레이션 (Prisma 7 — 두 번)**
- shadow DB가 Supabase storage 스키마 부재로 실패 → `migrate diff --from-config-datasource`로 SQL 생성 → `db execute` 적용 → `migrate resolve --applied`로 이력 등록 → `generate` 수동
- Prisma 7에서 플래그가 `--from-schema-datasource` → `--from-config-datasource`로 변경된 점 확인

**화면 / Server Action**
- 작성: createMyPlanAction — 인증 확인, ownerId는 세션 user.id로 고정(클라이언트 값 안 씀), 저장 후 상세로 redirect
- 상세: findFirst({ id, ownerId })로 소유 검증, Day 탭(기간으로 Day 수 계산), 항목 추가는 PlanSpot + PlanCost를 한 트랜잭션에서 저장하며 planSpotId로 연결
- 삭제: deleteMyPlanAction — deleteMany({ id, ownerId })로 본인 것만, cascade로 하위 항목 자동 삭제

## 결과 · 배운점

- My Plan 기능이 **만들기 → Day별 항목 채우기 → 삭제**까지 한 바퀴 작동. 같은 Day에 항목 2개를 넣어도 각 장소에 비용이 정확히 매칭됨을 확인.
- **createdAt 매칭의 함정**: 화면에 항목 하나일 땐 멀쩡해 보여도, 데이터가 여러 개면 "시각으로 추측"하는 연결은 틀어진다. 직접 FK로 잇는 게 맞다.
- **Prisma 7 마이그레이션**: shadow DB 우회 + `migrate resolve`로 이력 맞추기를 안 하면 다음 마이그레이션 때 충돌난다. 수동 적용해도 이력은 꼭 등록.
- **소유 검증은 코드 + RLS 이중**: 조회·삭제 모두 ownerId 조건을 코드에서도 걸고, RLS에서도 막는다.
- 다음: 작성/상세를 한 화면 편집기로 통합할지(편집기형 vs 만들기→채우기 분리)는 멘토와 상의. 카카오 지도 검색 연동, 카테고리 집계 막대, Story 복사/불러오기는 이후 사이클.
