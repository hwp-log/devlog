## 1. 한 줄 요약

담기가 MyPlan 1행 + PlanSpot 5필드만 복사하던 것을 날짜·인원·비용·항공·Spot 연결까지 넓혔다가,
항공과 날짜를 차례로 다시 덜어내 **"남이 짠 구조와 참고값만 담기고 예약·일정은 담는 사람이 정한다"**로 수렴시켰다.

## 2. 왜 / 목적 / 이유

### 국면 ① — 넓힌 이유: 담은 플랜이 Day 1만 보였다

담기 기능을 직접 써보다 발견했다. 3일치 공개 플랜을 담았는데 Day 1만 떴다.

조사해 보니 `day` 값 자체는 정상 복사되고 있었고, 원인은 **`startDate`/`endDate`를 안 가져오는 것**이었다 —
상세·편집 두 화면이 날짜에서 dayCount를 역산하고, 없으면 1로 떨어진다.

그리고 이건 표시 문제로 끝나지 않았다. 편집 화면을 열어 저장하면 `updatePlanWithItemsAction`이
`deleteMany` 후 폼 상태로 재생성하므로 **화면에 못 뜬 day 2·3이 DB에서 실제로 사라진다.**
표시 결함이 데이터 손실로 확정되는 경로였다.

같이 훑다 보니 안 가져오는 게 더 있었다.

- **비용(`PlanCost`)** — 0103의 명시적 배제였다("비용은 PII, 복사는 우회로"). 그런데 그 근거는
  0097 "공개 상세는 정밀 금액을 미전송·구간 가공"이었고, **0557·0558이 그 계열을 이미 폐기했다**
  (0557 = 비공개면 글 자체를 가림 / 0558 = 공개한 것은 실값으로).
  공개 상세에서 실값으로 보이는 금액을 담기에서만 막을 이유가 사라져 있었다.
- **항공(`PlanFlight`)** — 0103 회고 어디에도 언급이 없다. 0068에 이미 있던 테이블이므로
  **배제 의도가 기록된 적 없는 누락분**으로 판단했다.
- **`PlanSpot.spotId`** — 안 옮기면 사본의 장소 사진·주소·작품이 통째로 빈다(0494 조인 소스).

### 국면 ② — 항공을 뺀 이유: 복사할 수 있다와 복사해도 된다는 다르다

재검토가 걸린 계기는 **시점의 어긋남**이었다. 원본은 이미 다녀온 여행이고
담은 사람은 앞으로 갈 여행을 짠다. 그런데 복사된 항공권은 **이미 지나간 편의 예약**이다.
지나간 항공편이 최신 플랜에 그대로 실려 있는 것 자체가 이상해 보였고,
거기서 기준이 바뀌었다.

국면 ①은 **"스키마에서 빠진 게 뭔가"**를 기준으로 훑었고, 그 기준에서 `PlanFlight`는 당연히 채워야 할 칸이었다.
기준을 **"받는 쪽에서 쓸모가 있는가"**로 바꾸면 답이 뒤집힌다.

- 항공권은 **특정 편명·특정 시각의 예약**이다. 비용·일정은 "이렇게 다녀왔다"는 참고값으로 성립하지만
  편명은 참고가 되지 않는다 — 담은 사람이 그대로 쓸 수 없다.
- 가격이 매일 바뀐다. 원본 시점 금액이 남아 있으면 오해를 부르고, 이건 주의 문구 한 줄로 덮을 수 있는 오차 폭이 아니다.
- 담은 사람은 자기 날짜로 다시 검색하는 게 맞고, **그 경로(작성 폼의 "항공편 검색")는 이미 있다.**

비용이 남은 이유가 정확히 여기서 갈린다. 비용은 참고값으로 성립하고, 항공은 성립하지 않는다.

### 국면 ③ — 날짜를 뺀 이유: 담은 시점에는 확정된 일자가 없다

담은 사람이 자기 일정에 반영하기 전까지 날짜는 정해지지 않은 값이다.
그때까지 필요한 건 "며칠짜리로 어떻게 도느냐"뿐이고, 그래서 Day에만 담는다.
원본 날짜를 실어 오는 건 그 빈칸을 **남의 확정값으로 메우는 것**이었다.

여기에 다른 이유가 겹쳤다. 지난 여행 플랜을 담으면 과거 날짜가 그대로 들어와,
0581에서 막은 것이 담기로 우회된다.

그런데 날짜 복사만 빼면 국면 ①이 고쳤던 Day 1 문제가 되살아난다.
원인을 다시 보니 dayCount가 날짜 하나에만 의존하고 있었다
(`plan-finder/[id]/page.tsx` · `my-plan/[id]/edit/page.tsx` 둘 다 없으면 1로 폴백).

**국면 ①에서 날짜를 복사한 건 원인을 고친 게 아니었다.**
Day 1만 보이는 증상이 사라지니 해결된 것처럼 보였을 뿐이고,
날짜를 걷어내야 할 다른 이유가 생기고 나서야 원인이 드러났다.
진짜 해법은 3단 폴백이었다 — 날짜가 없어도 PlanSpot의 최대 day로 Day 구조가 산다.

- **담기가 가져오는 건 Day 구조다.** 며칠짜리로 어떻게 도느냐는 따라 담을 값이지만,
  실제 날짜는 담은 사람이 자기 일정에 맞춰 정하는 값이다.
- **과거 날짜 유입 경로였다.** 지난 여행 플랜을 담으면 과거 날짜가 그대로 들어와,
  0581에서 막은 것이 담기로 우회된다.

날짜 복사만 빼면 국면 ①이 고쳤던 Day 1 문제가 되살아난다. 그래서 원인을 봤더니,
진짜 원인은 **dayCount 산출이 날짜 하나에만 의존한 것**이었다
(`plan-finder/[id]/page.tsx` · `my-plan/[id]/edit/page.tsx` 둘 다 없으면 1로 폴백).

즉 **국면 ①의 진짜 해법은 날짜 복사가 아니었다.** 날짜 복사는 증상(Day 1만 보임)을 덮은 것이고,
덮개를 걷어내야 할 다른 이유(과거 날짜 유입)가 생기고 나서야 원인이 드러났다.

## 3. 작성한 프롬프트

세 사이클 모두 **조사 → 계획 → 실행** 3단계였고, 조사 단계에서 **답해야 할 것을 미리 못 박은 게 공통 형태**다.

국면 ① (조사 요청, 검수 모드):

```
copyPublicPlanAction이 실제로 무엇을 복사하고 무엇을 빠뜨리는지 조사해 보고.
복사되는 필드·테이블 전량 / 복사되지 않는 것 전량 / Day 1만 복사되는 원인 /
PlanCost·PlanFlight를 복사하지 않는 게 의도된 것인지 판단할 근거가 코드나 주석에 있는지.
❌ 코드 수정 ❌ DB 수정 ❌ 개선 방안 제시
```

이어진 계획 요청에서 금지(❌ coverUrl ❌ isPublic 변경 ❌ Day 증감 로직 ❌ 버튼 위치)를 명시하고
**"PlanCost·PlanFlight 스키마의 어떤 필드를 복사할지 목록으로 먼저 제시할 것"**을 요구했다.

국면 ②:

```
[목표] copyPublicPlanAction에서 PlanFlight 복사 제거
   - 뺀 이유를 주석으로 남길 것 (편명·시각 예약이라 재사용 불가 + 가격 변동)
   - PlanCost·PlanSpot.spotId·날짜·인원 복사는 그대로 유지
[하지 말 것] ❌ PlanCost 복사 제거 ❌ 빨강(danger) 계열 ❌ 항공편 검색 UI 변경
[검수 모드] theme.ts에 warning 토큰이 있으면 그것을 쓰고, 없으면 어떤 값을 쓸지 먼저 보고할 것.
```

"있으면 쓰고 없으면 먼저 보고"는 **AI가 색을 임의로 정하지 못하게 막는 장치**였다.
실제로 없었고, 값 두 개를 근거와 함께 보고한 뒤 진행했다.

국면 ③:

```
[검수 모드] 착수 전 확인:
- dayCount를 쓰는 곳이 그 두 파일 말고 더 있는지
- Day 탭 라벨을 만드는 코드가 어디에 있는지
```

둘 다 "고칠 곳이 정말 두 곳뿐인가"를 묻는 질문이었고, **둘 다 아니었다**(아래 4번).

## 4. 코드 작성 & 수정

### 최종 복사 범위 (`plan-finder/[id]/actions.ts`)

세 사이클을 거친 결과. 넓힌 것 중 항공·날짜만 빠졌다.

| 대상 | 복사 | 근거 |
|---|---|---|
| 제목·설명·지역·작품·통화 | O | 기존 |
| `headcount` | O | 국면 ① |
| `PlanCost` (planSpotId 재매핑) | O | 국면 ① — 전제 소멸(0103 → 0557·0558) |
| `PlanSpot.spotId` | O | 국면 ① — 사진·주소·작품 조인 소스(0494) |
| `startDate` · `endDate` | **X** | 국면 ③ — Day 구조만, 날짜는 담는 사람이 |
| `PlanFlight` | **X** | 국면 ② — 편명·시각 예약 |
| `coverUrl` | X | 원본 이미지 소유권 |
| `isPublic` | X (false 고정) | 담은 것이 자동으로 다시 공개되지 않는다 |

### 비용 재매핑 — 2패스 `spotIdMap`

`PlanCost.planSpotId`를 원본 id 그대로 실으면 **남의 플랜 항목을 가리키는 비용 행**이 생긴다.

```ts
      const spotIdMap = new Map<string, string>();
      for (const spot of original.spots) {
        const created = await tx.planSpot.create({
          data: {
            planId: plan.id, day: spot.day, order: spot.order, name: spot.name,
            lat: spot.lat, lng: spot.lng, spotId: spot.spotId,
          },
        });
        spotIdMap.set(spot.id, created.id);
      }
      for (const cost of original.costs) {
        await tx.planCost.create({
          data: {
            planId: plan.id,
            // 매핑에 없으면 null로 강등 = 기타 지출(라벨은 남는다). 모든 원본 항목을
            // 복사하므로 실제로는 도달하지 않지만, 끊긴 연결이 남의 id를 가리키느니 낫다.
            planSpotId: cost.planSpotId ? spotIdMap.get(cost.planSpotId) ?? null : null,
            day: cost.day, category: cost.category, label: cost.label, amount: cost.amount,

        });

```

### 조사 — 지정한 두 파일이 전부가 아니었다

`dayCount`를 쓰는 곳은 5곳이었다.

| 위치 | 폴백 | 이번 처리 |
|---|---|---|
| `plan-finder/[id]/page.tsx` | 1 | 변경 |
| `my-plan/[id]/edit/page.tsx` | 1 | 변경 |
| `lib/plan/queries.ts`(목록 카드) | **null** | 미변경 |
| `lib/plan/summary-line.ts`(스토리 요약) | 생략 | 미변경 |
| `MyPlanNewForm.tsx` `calcDays` | `[]` | 미변경 |

Day 탭 라벨은 4곳이었고 **폴백 문안이 이미 다 있었다** — 지금까지 도달 불가였을 뿐이다
(날짜가 없으면 dayCount가 1이거나 days가 비어 탭 자체가 안 떴다).
실제 작업은 `PublicCostSection`의 `DAY N` → `Day N` 대소문자 1건이었다.

### 일수 3단 폴백 (`lib/plan/day-count.ts` 신설)

```ts
export function resolvePlanDayCount(
  startDate: Date | null,
  endDate: Date | null,
  spots: { day: number }[],
): number {
  if (startDate && endDate) {
    const diff = endDate.getTime() - startDate.getTime();
    return Math.max(1, Math.ceil(diff / 86_400_000) + 1);
  }
  if (spots.length > 0) return Math.max(1, ...spots.map((s) => s.day));
  return 1;
}
```

두 페이지가 이미 같은 식을 복제하고 있었고 여기에 폴백 단이 하나 더 붙으면 어긋날 여지가 커져 함수로 뽑았다.
두 페이지 모두 `plan.spots`를 이미 조회하므로 **쿼리 변경은 없다.**

`queries.ts`·`summary-line.ts`는 합치지 않았다 — **식은 같지만 폴백이 다르다.**
저쪽은 날짜가 없으면 "일수 표시 없음"이고 이쪽은 day로 대체한다.
식만 공유하면 폴백이 조용히 갈리므로, 합칠 거면 폴백까지 같이 봐야 한다는 걸 주석에 남겼다.

커밋 순서는 **폴백 → 날짜 제거**로 잡았다 — 뒤집으면 그 사이 담은 플랜이 Day 1만 보인다.

### 복사한 금액에는 시점 고지를 붙였다

담기가 비용을 실어 오게 됐으므로 "이 금액은 원본 작성 시점 값"이라는 사실이 화면에 필요해졌다.
조건은 `sourcePlanId` 유무 하나다 — `isOwner`를 안 건 이유는 담은 플랜을 나중에 공개로 돌리면
남에게도 같은 사실이 성립하기 때문. 읽기 상세와 편집 폼 두 화면에 같은 문구·조판으로 넣었다.

처음엔 `text-hint`(옅은 회색)였는데, hint는 theme.ts에서 "아직 값이 없음" 층으로 정의된 색이라
**읽고 확인하라는 문장에는 안 맞았다.** 그래서 경고 축(`warning`)을 신설해 주황 + 정보 아이콘으로 올렸다.

```tsx
        <p className="mt-2 flex items-start gap-1.5 text-[13px] text-warning break-keep">
          <Info aria-hidden size={14} className="mt-[3px] shrink-0" />
          <span>원본 작성 시점의 금액입니다. 현시점에서는 다를 수 있으니, 확인 바랍니다.</span>
        </p>
```

> 이 축(색 값·문구·조판)은 이후 여러 번 갈아엎혔다 — 이 시점의 `warning`은 라이트 `#b45309`·다크 `#f59e0b`였고
> 지금은 값도 형태도 다르다(면 배너). **정본은 배너 외형·문구 묶음(0589·0590·0596~0598)**을 볼 것.
> 이 편에서 중요한 건 색이 아니라 **"복사한 금액에는 출처 시점을 고지한다"**는 결정 하나다.

## 5. 결과 / 배운점

### 결과

- 세 사이클 모두 `npx tsc --noEmit` 통과. `npm test` 실패 목록이 기존과 정확히 동일
  (auth 5스위트 + SpotPopup = 6스위트/8테스트) — 회귀 없음. 이 액션에 테스트는 여전히 0건이다.
- 최종 동작: 담으면 **날짜 없이 Day 구조·인원·비용·장소 연결이 실린다.** 항공은 담는 사람이 다시 검색한다.
- **실화면 확인 완료** — ① 날짜 없이 Day 탭이 뜬다 ② 편집 화면에서도 같다
  ③ 비용이 복사되고 주의 문구가 뜬다 ④ 항공은 실리지 않는다.
  단 ③④는 이 트랙 시점이 아니라 **0594 작업 중 확인됐다**
  (담은 사본의 PlanCost 8행 합 464,000 / PlanFlight 레코드 없음).

### 배운점

- **결정에는 전제가 있고, 전제는 다른 사이클에서 조용히 무너진다.**
  0103의 비용 배제는 그 시점에 옳았고 근거도 명확했다. 0558이 전제를 폐기했지만 그때 담기 액션은
  다른 이유(isDraft 제거)로만 손댔다 — 같은 파일을 고치면서도 그 안의 오래된 판단이 아직 유효한지는 안 봤다.
  "이 결정의 근거가 아직 살아 있는가"는 근거를 뒤집는 커밋 쪽에서 챙겨야 한다.
  **되돌릴 때 코드보다 이유를 남겨야 하는 것도 같은 문제의 뒷면이다** — 0103이 항공을 언급조차
  안 해서 국면 ①이 그걸 누락으로 판단했다. 지운 자리에 이유가 없으면 다음 사람이 같은 조사를 해서
  같은 결론에 또 도달한다.
- **복사할 수 있다와 복사해도 된다는 다르다.**
  "빠진 게 뭔가"를 기준으로 스키마를 훑으면 `PlanFlight`는 당연히 채워야 할 칸이다.
  **담은 사람이 그 값을 쓸 수 있느냐**를 기준으로 보면 편명·시각은 처음부터 복사 대상이 아니다.
  온전한 복제의 기준은 "원본과 같아지는 것"이 아니라 "받는 쪽에서 쓸모가 있는 것"이다.
- **증상을 없앤 변경은 원인을 고친 것처럼 보인다.**
  날짜를 복사하자 Day 1 문제가 사라졌고 그걸로 해결됐다고 판단했다. 진짜 원인은 dayCount가
  날짜 하나에만 의존한 것이었고, 날짜 복사는 그 위에 덮은 것이었다.
  덮개를 걷어내야 할 다른 이유가 생기고 나서야 원인이 드러났다.
- **표시 결함과 데이터 손실은 한 칸 차이다.**
  day가 화면에 안 뜨는 것까지는 되돌릴 수 있는 상태였지만, 그 화면에서 저장을 한 번 누르면 확정된다.
  delete-후-재생성 저장 구조에서는 "폼에 안 실린 것 = 지워질 것"이라,
  폼이 데이터를 다 못 싣는 상황 자체가 손실 예약이다.

## 결정 (Decisions)

- **담기는 비용(`PlanCost`)을 복사한다** — 0103의 배제 근거(0097 정밀 미전송)가 0557·0558로 소멸.
  공개 상세에서 실값으로 보이는 것을 담기에서만 막을 이유 없음.
- **담기는 `PlanSpot.spotId`를 승계한다** — 안 옮기면 사본의 사진·주소·작품이 빈다(0494 조인 소스).
  `PlanCost.planSpotId`는 2패스 `spotIdMap`으로 재매핑한다.
- **담기는 `PlanFlight`를 복사하지 않는다** — 편명·시각 예약이라 재사용 불가 + 가격 변동.
  **재제안하지 않는다.**
- **담기는 날짜를 복사하지 않는다** — Day 구조만 가져오고 날짜는 담은 사람이 지정한다.
  과거 날짜 유입 차단(0581)의 우회로를 만들지 않는다.
- **dayCount는 3단 폴백** — 날짜 역산 → PlanSpot 최대 day → 1. 상세·편집 두 화면 공유(`lib/plan/day-count.ts`).
- **목록·요약의 일수 폴백은 통합하지 않는다** — 식은 같아도 폴백 의미가 다르다. 합칠 땐 폴백까지 함께.
- **복사한 금액에는 시점 고지를 붙인다** — 조건은 `sourcePlanId` 유무 하나. 소유자 여부로 가르지 않는다.
  > **이 조건은 이후 뒤집혔다.** 0593이 `!isPublic`을 더했고, 0594가 그 기준을 버리며 `isOwner`로 갈음했다
  > ("확인 바랍니다"는 담은 사람에게 하는 말이지 남에게 할 말이 아니다).
  > 현행 조건은 `isOwner && sourcePlanId && !costEdited` — **정본은 배너 판정 묶음(0593·0594·0595)**.
  > 이 편에서 살아 있는 결정은 "복사한 금액에는 출처 시점을 고지한다"는 것 하나다.
- **`coverUrl`은 복사하지 않는다 / `isPublic`은 false 고정** — 원본 이미지 소유권 / 담은 것이 자동 재공개되지 않는다.
- **뒤집힌 결정의 정본은 코드 주석** — 0103 회고는 시점 기록으로 그대로 둔다.

## 겹치는 축 (다른 회고 참조)

- **항공** — 담기는 항공을 복사하지 않으므로(0580) **0587의 인원 곱셈(`flightTotal`)이 담은 플랜에 적용될 일이 없다.**
  "날짜가 바뀌면 항공권도 무효"(0586)도 같은 근거의 다른 적용이다.
- **날짜** — 과거 날짜 유입 차단은 **날짜 처리 묶음(0581·0583·0584·0586)**과 같은 줄기다.
  특히 이 트랙이 만든 "날짜 없이 항목이 실린 폼"이 0583의 발단이 된다.
- **비용 주의 문구** — 색·문구·형태의 정본은 **배너 외형·문구 묶음(0589·0590·0596~0598)**.
  배너를 언제 띄울지의 판정은 **배너 판정 묶음(0593·0594·0595)**.

## 남은 것 (별건)

- **기존에 담긴 플랜은 소급 복구되지 않는다.** 이 트랙의 변경은 앞으로의 담기에만 적용된다.
  이미 날짜 없이 담긴 사본의 day 2·3은 3단 폴백으로 이제 보이지만, 트랙 이전에 담긴 사본의 비용·`spotId`는 없다.
  백필 여부는 미정.
- **목록 카드와 상세의 일수 폴백이 다르다.** 날짜 없는 플랜에서 상세는 "3일", 카드는 무표시.
  의도된 차이인지 미판정(`lib/plan/day-count.ts` 주석에 명시).
- **스토리→플랜 복사 경로(`sourceStoryId` 계열, 0097)**가 같은 유형의 누락을 갖는지 미조사.
