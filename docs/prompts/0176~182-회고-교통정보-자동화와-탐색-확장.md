## 1. 한 줄 요약

시안의 "강릉역에서 15분" 메타줄 자리를 채우는 트랙. 좌측 열 하단에 네이버 지도
딥링크 길찾기 버튼을 넣어 상세 경로 안내를 통째로 위임하고, Spot에 교통 기준점
필드를 추가한 뒤 **수동 입력을 하루 만에 폐기하고 저장 시 서버 자동 계산으로
일원화**. 검색은 작품명에서 작품명 OR 스팟명으로 확장하되 주소 검색은 의도적으로
비지원. 문구·포커스 전이로 마감.

## 2. 왜 / 목적 / 이유

### 길 안내는 네이버에 위임 (0176)
- **왜**: 촬영지를 찾은 사용자의 다음 행동은 "가보기"인데 진입점이 없었다.
- **목적**: 우리 화면은 콘텐츠 탐색까지, 실제 이동 안내는 전문 앱으로.
- **이유**: 길찾기의 실체는 출발지 설정·실시간 교통·환승·내비게이션인데, 이걸
  임베드하면 네이버 지도 본판보다 못한 축소판을 만드는 셈이다. 네이버가 이 용도의
  공식 통로(지도 앱 URL Scheme)를 운영하고 있어 그대로 사용. 사용자가 "이탈"로
  느끼지 않는 조건은 **버튼이 행동을 예고하는 것**이라, 라벨에 스팟명을 넣고
  (`"서울스퀘어" 길찾기`) 주 버튼(primary)으로 배치했다.
- **위치는 좌측 열 하단**. 우측 패널 하단도 검토했으나 기각 — 교통 정보(메타줄)가
  좌측 리스트에 있으니 "그럼 차로는?"이라는 후속 질문도 같은 열에서 받아야 동선이
  끊기지 않는다. 대상은 `selectedSpot`(0172 초기 자동 선택 덕에 항상 존재).

### 교통 기준점 필드 (0177) → 자동 계산 (0178) → 폼 제거 (0179)
- **왜**: 시안의 메타줄 자리가 데이터 부재로 비어 있었다.
- **처음 판단(v1 수동)**: 스키마에 옵셔널 2필드를 추가하고 등록 폼에서 손으로 채운다.
  시딩할 때 어차피 장소를 아니까 현실적이라고 봤다.
- **뒤집힌 이유**: 폼에 입력 필드 2개가 붙은 화면을 실물로 보니 판단이 바뀌었다.
  **스토리를 쓰는 사람은 여행 갔다 온 사람이지 그 동네 교통을 조사한 사람이 아니다.**
  빈 필드는 작성자 피로도만 늘리고 대부분 빈 채로 남는다. v2로 미뤄둔 자동 계산을
  당겼다.
- **목적**: 작성자가 교통 정보의 존재를 신경 쓰지 않게 한다. 좌표만 찍으면 채워진다.
- **이유**: 계산 시점은 **저장 시 1회, 서버에서**. 조회마다 호출하면 API 낭비이고
  클라에 키가 노출된다. 0177에서 만든 필드가 그대로 저장처로 재사용되므로 스키마는
  헛일이 아니라 자동화의 그릇이 됐다. 자동화가 실증된 뒤 0179에서 폼 필드를
  제거해 입력 경로를 없앴다 — **기능이 늘어나는데 화면은 단순해지는** 방향.

### 표시 규칙 = 기준점 종류가 수단을 결정
- **왜**: "강릉역에서 15분"이 도보인지 차인지 모호했다.
- **이유**: 역 이용자는 대부분 대중교통 여행자라 도보가 자연스럽고, 공항은 소음·안전
  규제상 도시에서 멀 수밖에 없어 차가 기본이다. 그래서 **역 = 도보 / 공항 = 차로**를
  기준점 이름에서 파생한다(mode 필드 저장 없음 — 파생 가능한 사실은 저장하지 않는다).
  사용자가 수단을 고르지 않아도 되고 입력 필드도 하나 줄었다. 파생이 깨지는 조건
  (버스터미널·선착장 등장)과 그때의 정답(transitMode enum 전환)은 주석에 명시.

### 검색은 넓히되 주소는 비지원 (0180)
- **왜**: "서울스퀘어"를 쳐도 빈 결과였다. 검색이 작품명만 매칭했기 때문.
- **주소 검색을 넣지 않은 이유**: 검색 범위는 서비스 정체성이 정한다. Dotrip에 온
  사용자는 촬영지를 찾으러 온 것이지 주소를 찾으러 온 게 아니다. 오히려 주소 검색이
  되면 "강남구 역삼동"에 촬영지가 없을 때 빈 결과가 서비스 결함처럼 보인다. 범용
  지도 흉내는 못 이기는 게임이다.
- **대신 폭을 넓혔다**: 사용자가 가장 자연스럽게 칠 검색어인 장소명이 빠져 있었다.
  작품명 OR 스팟명 하나의 술어로 정의하고 칩·리스트가 파생 소비.
- **지도는 검색을 소비하지 않는다**: 두 근거. ① 역할 분리 — 검색은 찾기 도구,
  칩·리스트 클릭은 필터·이동 도구. ② 실무 — `visibleSpots`에 검색을 태우면
  키스트로크마다 마커·클러스터가 전체 파괴·재생성되는데, 이 지도는 재그리기 충돌
  이력(0167 동결 버그)이 있는 예민 구간이다. 리스크 대비 이득이 없다.

### 문구·포커스 (0181·0182)
- **왜**: 헤더는 "영화·드라마 촬영지 검색"인데 placeholder는 "드라마·영화" 역순이었다.
  검색창 포커스는 색이 뚝 바뀌었다.
- **이유**: placeholder는 헤더가 이미 큰 정의를 줬으니 "뭘 쳐도 되는지"를 알리는
  역할로 분담 → `작품명·촬영지를 입력하세요`. 버튼 라벨은 "경로 찾기"를 검토했다가
  **"길찾기"로 회귀** — 국내 지도 표준 어휘이고, 도착하는 화면(네이버 지도)의 메뉴와
  단어가 같아야 "제대로 왔다"는 확신을 준다. 포커스는 focus 링 제거가 아니라
  hover/focus **위계** 문제였다(hover가 focus만큼 강해 두 색이 번갈아 번쩍임).
  링 자체는 접근성 필수 요소라 유지하고, transition에 box-shadow를 포함해 서서히
  떠오르게 했다.

### 길찾기 딥링크 (0176)
```
[배경]

"강릉역에서 도보 15분")가 표시될 예정인데, 그 정보를 본 사용자의
후속 질문(차로는? 대중교통은?)을 받을 진입점이 없음. 좌측 열
하단 고정 버튼으로 네이버 지도 길찾기 딥링크를 추가한다. 공식
스펙: 네이버 지도 앱 URL Scheme(nmap://, NCP 문서 "지도 앱 연동
URL Scheme"), 모든 URL에 appname 파라미터 필수, Android는
intent:// 래핑 시 미설치 폴백 자동, iOS는 스킴 시도 후 미설치 시
App Store 유도 관례.

[목표]
1. 스펙 실측 확증: NCP 공식 문서에서 길찾기(/route) 액션 파라미터

   지도 웹 길찾기 URL 형식도 확증
2. 좌측 열 하단 고정(sticky) 영역에 주 버튼(primary) 추가 —
   라벨 "[선택 스팟명] 길찾기", 대상 = selectedSpot (0172 초기
   자동 선택으로 항상 존재. spots 빈 배열이면 버튼 미표시)
3. 클릭 시: 모바일 = nmap 스킴(Android intent 래핑 / iOS 폴백),
   데탑 = 네이버 지도 웹 길찾기 새 탭. 도착지 = 스팟 좌표+스팟명,

4. URL 조립을 lib 유틸로 분리 (스팟 → URL), 컴포넌트는 호출만
5. 검증: 데탑 새 탭 URL 좌표·명칭 정확, 선택 변경 시 버튼 라벨
   추종, 리스트 스크롤 시 버튼 고정, 플랫폼 분기 실측

[하지 말 것]
❌ 경로·소요시간 자체 계산 (다음 사이클에서 별도)
❌ 우측 패널 접촉  ❌ 지도·마커·정렬 로직 접촉
❌ 버튼 스타일 발명 — 기존 primary 버튼 문법 재사용

[검수 모드]
URL 조립(★★★)·selectedSpot 연동·플랫폼 분기 근거만.
```

### 교통 자동 계산 (0178)
```
[목표]
1. 스펙 실측 확증 (web_search, 이 결과에 따라 설계 확정):
   ① 좌표 주변 지하철역·기차역·공항을 찾을 NCP/네이버 API
   (장소 검색·지오코딩 계열) — 카테고리 검색 가능 여부
   ② Directions API의 도보 경로 지원 여부 (역=도보 규칙).
   미지원이면 직선거리 기반 추정(도보 4~5km/h) 대안 제시,
   표기는 "도보 약 N분"으로 정직하게
   ③ 호출 비용·무료 한도 보고
2. 서버 액션(스토리 생성·수정)에서 스팟 저장 루프 내 자동 계산 —
   기준점 검색 → 소요시간 → 필드 저장. 폼에 값이 이미 있으면
   덮어쓰지 않음 (수동 입력 우선)
3. 실패 허용: API 실패·기준점 없음이면 null 저장하고 스토리
   저장은 정상 진행 — 절대 저장을 막지 않음. 실패는 서버 로그만
4. API 키는 서버 전용 환경변수 (NEXT_PUBLIC_ 금지)
5. 검증: 기존 스팟 좌표로 검색 결과 실측 보고 — 기준점 이름·
   소요분이 상식과 부합하는지 표로. API 무응답 시 저장 정상 진행

[하지 말 것]
❌ 조회 시점 계산 (저장 시 1회만)  ❌ 클라이언트에서 API 호출
❌ 0177 폼 필드 제거 (자동값 수정 통로로 유지)
❌ 리스트 표시 로직 변경

[검수 모드]
API 선정 근거(★★★)·저장 루프 통합 지점(★★★★ — 실패 허용
분기)·키 취급만. plan 단계에서 목표 1 확증 결과를 먼저 보고.
```

### 검색 확장 (0180)

  검토했는데, 원인은 검사 스크립트가 input value를 못 읽은 것이었다. "결과가 이상할
  때 코드부터 의심"이 항상 맞지는 않는다 — 측정 방법도 용의자다.
- **plan 단계에서 외부 사실을 먼저 확증시키면 설계가 바뀐다.** 0178 프롬에 "목표 1
  확증 결과를 plan에서 먼저 보고"를 넣었더니, 구현 전에 두 사실이 드러났다:
  네이버엔 필요한 검색 API가 없고, Directions는 도보를 지원하지 않는다. 이 둘이
  "카카오 채택 + 직선거리 추정"이라는 설계를 정했다. 구현 후에 알았으면 다시
  만들었을 것이다.
- **검색이 답이 아닌 문제가 있다.** 공항 찾기를 키워드 검색으로 계획했는데 실측에서
  상위 15개가 부동산 중개사·렌터카·주차장으로 채워지고 공항 본체는 0건이었다.
  국내 민간 공항은 15곳이고 수십 년 단위로만 변한다 — **정적 데이터가 정답인
  문제였다.** API 콜도 0이 되고 오탐도 0이 됐다. plan을 그대로 밀었으면 "제주신공항
  부동산에서 차로 5분"이 저장될 뻔했다.
- **하루 전 판단을 뒤집는 근거는 실물이다.** 수동 입력 v1은 "시딩할 때 어차피
  아니까"라는 전제였는데, 폼에 빈 필드 2개가 붙은 화면을 보자마자 전제가 틀렸음이
  보였다. 작성자는 여행자지 조사자가 아니다. 스키마는 그대로 자동화의 저장처가 됐고
  폼만 걷어냈다 — **되돌린 게 아니라 한 단계 올라간 것.**
- **분기의 의미는 바뀔 수 있다.** "수동 입력 우선" 분기를 폼 제거 후 지우려 했는데,
  실측하니 수정 흐름에서 StoryWriteForm이 DB 기저장 값을 payload로 되돌려 보내고
  있었다. 분기를 지우면 수정 저장마다 전 스팟이 재계산된다. 코드는 그대로 두고
  **의미만 "기저장 값 재사용(재계산 회피)"으로 다시 적었다.**
- **범위를 좁히는 것도 기능이다.** 주소 검색을 넣지 않기로 한 결정이 검색 확장의
  절반이었다. 무엇을 지원하지 않을지가 정해져야 무엇을 지원할지가 선명해진다.
- **표준 어휘를 이기려 하지 않는다.** "경로 찾기"가 더 정확해 보였지만 국내 지도
  생태계의 단어는 "길찾기"이고, 도착하는 화면의 메뉴도 "길찾기"다. 버튼 단어와 도착
  화면 단어가 같을 때 사용자는 "제대로 왔다"고 느낀다.

## 결정 (Decisions)

- **상세 경로 안내는 네이버 지도에 위임**: 우리 화면은 접근성 감각(메타줄)까지,
  수단별 상세 경로는 딥링크로 이관. 임베드 비채택.
- **길찾기 버튼 = 좌측 열 하단, 대상은 selectedSpot**, 라벨에 스팟명 포함.
  우측 패널 배치는 기각(교통 정보가 좌측에 있어 동선이 끊김).
- **버튼 라벨 = "길찾기"** ("경로 찾기" 검토 후 회귀 — 국내 지도 표준 어휘 +
  도착 화면 메뉴와 어휘 일치).
- **교통 표시 규칙 = 기준점 이름에서 파생**: "공항"으로 끝나면 차로, 그 외 도보.
  mode 필드 미저장. 전환 조건(터미널·선착장 등 등장) 주석 명시.
- **소요시간은 직선거리 추정 + "약 N분" 표기**: 도보 67m/분×1.3, 차로 667m/분×1.4,
  최소 1분. NCP Directions는 자동차 전용(도보 미지원 공식)이라 정확 계산 불가.
- **POI 검색 = 카카오 로컬 REST (서버 전용 키)**: 네이버 생태계에 좌표+반경+카테고리
  검색 API 부재가 실측 확인됨. 지도·길찾기(네이버)와 층이 다름 — 화면에 그리는 것은
  전부 네이버, 서버 데이터 조회만 카카오.
- **공항은 검색이 아니라 정적 목록 15곳 + 하버사인**: 키워드 검색 오탐 실측
  (필터 통과 0건), 저빈도 변경 데이터라 정적이 정확·안정·API 0콜.
- **자동 계산은 저장 시 1회, 트랜잭션 진입 전 전처리**: 조회 시 계산·클라 호출 금지.
  실패는 null 흡수 — 스토리 저장을 절대 막지 않음.
- **"기저장 값 재사용" 분기 유지**: 수정 흐름이 DB 값을 payload로 되돌려 보내므로
  분기 제거 시 매 수정마다 전 스팟 재계산.
- **교통 입력 폼 제거, 자동 일원화**: 읽기 표시는 유지(자동 결과 확인용).
- **검색 = 작품명 OR 스팟명, 주소·지역 비지원**: 술어 하나를 칩·리스트가 파생 소비.
  지도는 검색 비소비(키스트로크마다 클러스터 재생성 리스크 + 역할 분리).
- **검색 중 선택 상태 유지**: 선택은 사용자 행위의 결과, 검색은 탐색 보조.
