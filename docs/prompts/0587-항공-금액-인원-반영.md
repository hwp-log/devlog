# 0587 회고: 항공 금액 인원 반영

**작성일**: 2026-08-17
**관련 커밋**: `339647f`(flightTotal 신설·계산 계층) · `7c7fb04`(폼·상세·목록) · `16d32f3`(카드·마이페이지·스토리)

## 1. 한 줄 요약

`PlanFlight.totalAmount`가 1인 요금인데 총액에 그대로 더해지던 것을, 곱셈을 `flightTotal()` 한 곳으로 모으고 호출부 7곳에 인원을 전달해 표시·합계 전부에 반영했다.

## 2. 왜 / 목적 / 이유

- 인원을 2명으로 바꿔도 항공 금액이 그대로였다. 숙소·식비는 사용자가 직접 입력하니 인원을 감안해 적지만, **항공만 시스템이 넣는 값**이라 1인 요금이 그대로 남았다.
- 이름이 오해를 부른 면이 있다. `totalAmount`의 "total"은 **왕복 총액**(가는편+오는편)이지 전원 총액이 아니다.

## 3. 작성한 프롬프트

```
- PlanFlight.totalAmount가 1인 요금인지 총액인지 먼저 확인해 보고
  (검색 API가 무엇을 반환하는지, 저장 시 가공이 있는지)
[하지 말 것]
❌ 저장된 totalAmount 값 자체를 변형해서 DB에 넣기
   — 원본은 그대로 두고 표시·합계에서만 곱할 것
[검수 모드] 착수 전 확인:
- totalAmount의 의미(1인 요금 / 총액)
- 이미 인원을 반영하는 코드가 있는지
- 공개 상세·편집·카드 중 어디까지 고쳐야 하는지
```

"DB 값을 변형하지 말 것"이 방향을 결정했다. 저장 시 곱해 넣으면 인원을 바꿀 때마다 항공 행을 다시 써야 하고, 1인 요금이라는 원본 사실이 사라진다.

## 4. 코드 작성 & 수정

### 조사 ① — 1인 요금이 맞았다 (3단 확인)

| 단계 | 코드 | 결론 |
|---|---|---|
| API 호출 | `lib/flights/client.ts:66` — `adults: '1'` | 1인 기준 조회 |
| 파싱 | `lib/flights/parser.ts:27` — `totalAmount: Math.round(it.price.raw)` | 응답 그대로 |
| 저장 | `my-plan/new/actions.ts:169` `flightFields()` — `totalAmount: offer.totalAmount` | 무가공 |

세 줄 다 현행 코드에 그대로 있다. **값의 의미를 확정한 건 필드 이름이 아니라 이 경로**다.

### 조사 ② — 인원을 반영하는 코드는 한 곳도 없었다

`headcount`는 전부 `N인` **표시용**이었다. 곱셈은 어디에도 없었다.

### 조사 ③ — 범위는 호출부 7곳(파일로는 8개)

항공 금액은 `calcPlanTotal` / `summarizePlanCost` 두 함수를 반드시 지난다. 그 소비처가 전부 대상이었고, **`mypage/page.tsx`만 `headcount`를 select조차 안 하고 있어** 쿼리도 함께 고쳤다(`16d32f3`에서 `+ headcount: true` 한 줄이 추가된 건 이 파일뿐이다).

> **초안은 "호출부 7곳"으로만 적었으나 실제 호출 파일은 8개다.** `calc-plan-total.ts:19-20`
> 주석이 `story(new·edit)/page`를 한 항목으로 묶어 7로 센 것이다. 전체 목록:
> `MyPlanNewForm` / `plan-finder/[id]/page` / `lib/plan/queries.ts` / `my-plan/page` /
> `mypage/page` / `story/[id]/page` / `story/new/page` / `story/[id]/edit/page`.

### 수정 — 곱셈은 한 곳

```ts
/**
 * 항공 총액 = 1인 요금 × 인원. **곱셈은 이 함수 한 곳**이고 나머지는 전부 여기를 거친다.
 * headcount는 스키마 기본값이 1이고 저장 시 1~20으로 클램프되지만(validate-input),
 * 방어적으로 하한 1 — 0이 들어오면 항공비가 통째로 사라져 조용한 과소 집계가 된다.
 */
export function flightTotal(
  flight: { totalAmount: number } | null | undefined,
  headcount: number,
): number {
  return (flight?.totalAmount ?? 0) * Math.max(1, headcount);
}
```

> **초안은 타입 없는 축약형으로 적었으나 실제는 위 형태다** — 타입 시그니처가 붙어 있고,
> `Math.max(1, …)`의 근거도 두 겹이다. 초안이 옮긴 "0이면 조용한 과소 집계"는 뒷절반이고,
> 앞절반은 **저장 시 이미 1~20으로 클램프된다**(`validate-input`)는 사실이다.
> 즉 이 하한은 정상 경로에서는 걸릴 일이 없는 **이중 방어**다.

`summarizePlanCost`에서 특히 조심한 지점은 **항공 금액이 나오는 곳이 셋**(`total` · `itemGroups`의 항공 그룹 · `ratios`의 FLIGHT)이라는 것이다. 한 곳만 곱하면 비중 합이 100%에서 어긋난다. 셋 다 같은 파생값(`flightAmount`)을 쓰게 했다.

공개 상세는 `PublicCostSection`이 `flight.totalAmount`를 직접 그리므로(그룹 요약·탑승료·상세내역 3행), `plan-finder/[id]/page.tsx`가 `publicFlight`를 만드는 시점에 곱해서 넘긴다 — **그 지점부터 이 값의 의미가 "전원 총액"으로 바뀐다**는 걸 주석에 박았다. `PublicFlightTable`은 금액을 안 그려서(편별 가격 열 없음, 0492) 영향이 없다.

### `headcount` 기본값 1로 둔 이유

필수 인자로 바꾸면 컴파일 오류로 호출부를 강제로 찾을 수 있어 더 안전하다. 그런데 기존 테스트 8개 호출이 전부 깨지고, AGENTS.md가 테스트 수정을 금한다. **기본값 1 + 실제 호출부 7곳 전수 명시**로 갔고, 대신 "새 호출부를 만들면 반드시 넘길 것 — 빠뜨리면 1인으로 조용히 계산된다"를 함수 주석에 남겼다.

### 검산

```
2인 · 항공O        총액  650000 | 항공  500000
4인 · 항공O        총액 1150000 | 항공 1000000
2인 · 항공X        총액  150000 | 항공       0
0인(방어) · 항공O   총액  400000 | 항공  250000
기본값 생략         총액  400000 | 항공  250000

항공 비중이 1인(62%)에서 2인(76%)으로 이동 — 합계와 같은 기준
```

## 5. 결과 / 배운점

- `npx tsc --noEmit` 통과. `npx next build` 컴파일 성공. `npm test` 실패 목록 기존과 동일(auth 5스위트 + SpotPopup = 6스위트/8테스트) — 회귀 없음.
- DB는 무변경이다. `PlanFlight.totalAmount`는 계속 1인 요금이고, 저장 경로도 손대지 않았다.
- 폼은 `editor.headcount` 파생이라 **인원 입력 즉시** "항공" 행과 총액이 다시 계산된다.
- **실화면으로만 판정 가능한 것** (코드 대조로는 확정 불가 — 미확인):
  1. 폼에서 인원 1→2로 바꿀 때 "항공" 행과 총액이 **즉시** 두 배가 되는지
  2. 공개 상세의 항공권 **그룹 요약 · 탑승료 · 상세내역 세 값이 서로 같은지**
  3. 카테고리 비중 합이 100%인지 (인원 변경 후에도)
  4. 목록 카드·마이페이지 평균이 함께 오르는지
  5. 검색 결과 카드(1인 25만원)와 선택 후 합계(2인 50만원)의 낙차가 실제로 혼란을 주는지
     — 아래 별건 "× N인 표기" 판단의 근거가 된다
- 배운점 초안 1: **이름이 검증을 대신하지 못한다.** `totalAmount`는 "총액"으로 읽히지만 실제로는 왕복 1인 요금이었고, 그 의미는 코드 세 군데(API 파라미터 → 파서 → 저장)를 따라가야 확정됐다. 값의 의미를 정하는 건 필드 이름이 아니라 **그 값이 만들어진 경로**다.
- 배운점 초안 2: **같은 값이 여러 자리에 나오면 곱셈은 반드시 한 곳이어야 한다.** 항공 금액은 총액·항목 목록·비중 세 자리에 나오는데, 하나만 고쳤다면 비중 합이 100%를 벗어나는 형태로 어긋났을 것이다 — 그건 눈에 잘 안 띄는 종류의 오류다. 파생값을 먼저 만들고 세 자리가 그걸 쓰게 하는 게 순서다.

## 겹치는 축 (다른 회고 참조)

- **이 곱셈이 담은 플랜에는 적용될 일이 없다.** 담기가 `PlanFlight`를 복사하지 않기
  때문이다(0580) — 담은 사본에는 항공 행 자체가 없으므로 `flightTotal`이 늘 0을 낸다.
  **담기 복사 범위 묶음(0579·0580·0582)이 이미 반대편에서 같은 연결을 걸어 두었다**
  (그 편 "겹치는 축": *"0587의 인원 곱셈(`flightTotal`)이 담은 플랜에 적용될 일이 없다"*).
  이 편에서 그 참조를 마주 건다 — **한 사실이 두 회고에서 각자의 방향으로 읽힌다.**
- **"날짜가 바뀌면 항공권도 무효"(0586)**도 같은 근거의 다른 적용이다 —
  항공만 시스템이 넣는 값이라 사람이 고쳐 주지 않는다는 것이 양쪽의 공통 전제다.
  **플랜 날짜 처리 묶음(0581·0583·0584·0586)** 참조.
- **`summarizePlanCost`의 세 지점(total·itemGroups·ratios)**은 이 편이 만든 게 아니라
  **비용 섹션 통일 트랙(0567~0570)**이 정리해 둔 구조다. 항공 그룹이 맨 위에 오는 순서는
  0499·0504에서 확정됐고, 이 편은 그 세 자리가 **같은 파생값을 쓰게** 했을 뿐이다.
- **`PublicFlightTable`은 영향 없음** — 편별 가격 열이 없어 금액을 그리지 않는다(0492).

## 결정 (Decisions)

- **`PlanFlight.totalAmount`는 1인 요금** — DB 값은 그대로 두고 표시·합계에서만 곱한다.
- **곱셈은 `flightTotal()` 한 곳** — 총액·항목·비중이 전부 이 파생값을 쓴다.
- **`headcount` 기본값 1** — 테스트 호환 때문. 대신 실제 호출부는 전수 명시
  (주석 기준 7항목 / 파일로는 8개). 새 호출부를 만들면 반드시 넘긴다.
- **공개 상세는 `publicFlight` 생성 시점에 곱한다** — 그 지점부터 "전원 총액"으로 의미 전환(주석 명시).

## 남은 것 (별건)

- **검색 결과 카드의 금액은 1인 요금 그대로다**(`FlightSearchSection.tsx:158`,
  `₩{offer.totalAmount.toLocaleString()}` — 현행 확인). 검색 UI 변경이 금지 범위라 손대지 않았다. **"검색 결과엔 25만원, 고르면 합계엔 50만원"** 이 되어 사용자가 놀랄 수 있다 — "× N인" 표기 여부는 미판정.
- **인원 반영을 검증하는 테스트가 없다.** 기존 8개는 전부 기본값 1 경로라 통과하지만 ×N 동작은 커버되지 않는다.
- `PlanCost`의 1인당/전체 구분은 여전히 별건(백로그).
- 0579~0586에서 넘어온 것: 담긴 플랜 소급 복구 / 목록 카드와 상세의 일수 폴백 불일치 / 축소 확인 문구에 비용 미포함 / 항공권 초기화에 확인 없음 / 스토리→플랜 복사 경로 점검 / `todayStr()` 통합 / 드래그 핸들 히트 영역.
