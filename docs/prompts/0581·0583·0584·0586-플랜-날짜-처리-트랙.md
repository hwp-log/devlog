## 1. 한 줄 요약

플랜에 과거 날짜가 들어가는 것을 막았더니 **날짜가 불완전한 중간 상태**가 드러났고,
그것을 막자 **일수가 줄 때 항목이 사라지는 경우**가 남았고, 그것을 닫자
**날짜가 바뀌면 항공권도 무효**라는 같은 종류의 사실이 하나 더 나왔다 —
네 사이클을 거쳐 "날짜는 바꿔도 되지만, 날짜에 매달린 것이 조용히 사라지지는 않는다"로 수렴했다.

---

## 2. 왜 / 목적 / 이유

### 0581 — **시작점**: 막아뒀던 검증이 사라져 있었다

계기는 담기였다. 담은 플랜에 날짜가 없어서 지정하려고 달력을 열었는데,
**과거 날짜가 그대로 선택됐다.** 원래는 지난 날짜가 희미하게 표시돼 못 고르게 돼 있던 것인데
어느 순간 풀려 있었다. 새 기능이 아니라 **있었어야 할 것이 없어진 상태**를 발견한 것이다.

여행 계획인데 지난 날짜가 들어가면 데이터가 이상해진다. 그래서 열었는데,
착수 전 조사에서 드러난 실태가 예상보다 아래였다.

- **서버 검증이 아예 없었다.** 저장 게이트는 `if (!title)` 한 줄이 전부였고 date input에 `min`도 없었다.
- **"도착일 ≥ 출발일"도 실제로는 없었다.** 있다고 여겨졌지만 실제로 있던 건 `calcDays`가
  역순 날짜에서 빈 배열을 반환하는 **부수 효과**였다. 화면에서 일정이 사라지니 막힌 것처럼 보였을 뿐,
  저장은 그대로 됐다 — 일정 항목 0건으로. "이미 있으면 그대로 두기"가 아니라 새로 넣어야 하는 항목이었다.

여기서 이 트랙 전체가 걸린 코드가 처음 등장한다. **`calcDays`의 빈 배열**이다.
0581은 그걸 "검증이 아니었다"고 확인만 하고 지나갔고, 두 사이클 뒤 그게 부작용으로 돌아온다.

제약이 하나 있었다: **출발일이 과거인 플랜이 1건 존재한다**
(이태원 클라쓰 촬영지 방문계획 / 2026-06-04 / 공개). 플랜파인더 시연 데이터라
이게 저장 불가가 되면 안 됐다. 하한을 "오늘"이 아니라 `min(오늘, 기존 저장값)`으로 잡은 이유가 이것이다.

### 0583 — **부작용**: 앞 묶음이 전제를 바꾸자 잠든 결함이 깨어났다

이 사이클은 **고치려고 연 게 아니다.** 앞 묶음의 0582로
**"날짜 없이 항목이 실린 폼"이 처음 생겼다** — 담기가 날짜를 복사하지 않고
Day 구조만 가져오게 되면서다. 그전까지 날짜 없는 플랜은 폼에 항목을 실을 수 없었으므로
**이 경로는 존재하지 않았다.**

그 경로를 처음 지나간 게 담기였다. 날짜 없이 담긴 플랜에 날짜를 넣으려니
0581에서 막 손본 그 달력을 다시 쓰게 됐고, 출발일만 입력한 순간 항목이 사라지는 게 보였다.

`calcDays`가 도착일이 없다고 빈 배열을 반환하고, days가 통째로 비면서
3일치 항목이 화면에서 사라진다.
**그대로 저장하면 `deleteMany` 후 0건 재생성이라 실제로 삭제된다.**

0581이 "검증이 아니었다"고 확인하고 넘어간 그 빈 배열이, 두 사이클 뒤에 삭제 경로가 됐다.
코드는 그동안 한 줄도 바뀌지 않았다 — **바뀐 건 그 코드가 기대던 전제**다.

다음 단계(Day 증감·삭제 경고)까지 열지 않고 **중간 상태만 먼저 막기로** 했다.
경고 문구의 문제가 아니라 데이터 손실 경로이기 때문이다.

### 0584 — **파생**: 0583이 남긴 잔여 위험 하나

앞의 둘과 달리 이건 화면에서 발견한 게 아니다. **0583 완료 보고가 유일한 잔여 위험으로
지목해 둔 것**을 이어받아 닫았다. 부작용은 쓰다가 드러나고 파생은 기록을 타고 이어진다.

0583은 **날짜가 불완전한 중간 상태**(한쪽만 입력·역순)만 막았다.
날짜가 둘 다 유효하면서 기간이 좁아지는 경우 — 3일 → 2일 — 는 여전히 3일차 항목을
**경고 없이** 버렸다.

여기서 "경고 없이"가 문제의 핵심이다. **축소 자체는 정당한 조작이다**(여행이 짧아질 수 있다).
0583처럼 "하지 않는다"로 풀 수 없고, 잃는 게 있다는 사실을 사용자가 모른 채
저장에 도달하는 것만 막으면 된다.

### 0586 — **파생**: 날짜에 매달린 게 항목만이 아니었다

이것도 화면이 아니라 범주를 훑다 나왔다. 0583·0584가 "날짜가 바뀌면 항목이 무효가 된다"를
두 번 다뤘고, **그 기준으로 폼을 다시 보니 같은 조건에 걸리는 게 하나 더 있었다.**

앞 세 사이클이 본 것은 전부 **일정 항목**이었다. 그런데 날짜가 바뀔 때 무효가 되는 게 하나 더 있었다.

- `FlightOffer`는 **특정 편명·특정 시각의 예약**이다(`departsAt`·`arrivesAt`·`flightNo`).
  날짜가 바뀌면 그 표는 그 순간 무의미해진다.
- **부분 무효화가 없다.** 공항·금액만 남기고 시각만 지우는 식의 절충이 성립하지 않으므로
  객체 전체를 비우는 게 맞다.

이건 앞 묶음 0580의 판단("항공권은 편명·시각 예약이라 담은 사람이 그대로 쓸 수 없다")과
**같은 근거가 같은 데이터에 다시 적용된 것**이다. 그때는 다른 사람에게 넘어갈 때였고,
이번엔 같은 사람이 날짜를 바꿀 때다. 그래서 **담기는 항공을 복사하지 않으므로(0580)
이 초기화는 담은 플랜이 아니라 직접 만든 플랜에서 의미가 있다** — 담은 플랜에는 비울 항공권이 애초에 없다.

## 3. 작성한 프롬프트

네 사이클 모두 `[검수 모드] 착수 전 확인` 형태였고, **그 질문이 그대로 설계를 결정한 게 공통점**이다.
"고쳐라"가 아니라 "무엇이 사실인지 먼저 답하라"였고, 매번 답이 구현을 바꿨다.

0581 — 조사 → 계획 → 실행 3단계:

```
[검수 모드] 착수 전 확인할 것:
- 현재 날짜 검증이 어디에 있는지(클라·서버)
- 출발일이 과거인 기존 플랜이 몇 건인지
- 수정 화면에서 그 플랜들이 막히지 않을 방법
```

두 번째 항목이 원격 DB 조회를 요구했고, **답이 1건(하필 공개 시연 데이터)이라 하한 규칙 자체가 갈렸다.**
세 번째는 "막지 마라"가 아니라 "막히지 않을 **방법**"이라 설계를 답으로 요구한 질문이었다.

금지 항목도 근거와 함께 지정됐다: `saveDisabled`에 날짜 조건 추가 금지(0527에서 "제목만"으로 확정) /
`FlightSearchSection`의 `todayStr()` 수정 금지 / 기존 플랜 데이터 수정 금지 /
**담기 경로의 날짜 처리는 별건**(그건 앞 묶음 0582가 맡았다).

0583:

```
[검수 모드] 착수 전 확인:
- calcDays가 빈 배열을 반환하는 조건 전량
- days를 덮어쓰는 곳이 그 한 군데인지
```

두 질문이 그대로 수정의 근거가 됐다. 첫 질문의 답("빈 배열은 무효 날짜일 때만 나온다")이
`null` 전환의 정당성이고, 둘째 답("덮어쓰기는 한 군데")이 한 줄 수정으로 끝난 이유다.

0584:

```
[하지 말 것]
❌ 확인 창을 새 모달 컴포넌트로 만들기 — 기존 확인 UI 패턴이 있으면 그것을 쓸 것

[검수 모드] 착수 전 확인:
- 기존 확인 창 패턴이 어디에 있는지(글쓰기 양식 교체 경고 등)
- 취소 시 날짜 입력을 되돌리는 방법
```

"있으면 그것을 쓸 것"이 이번의 하네스였다. 확인 창은 새로 만들고 싶어지는 종류의 UI다.

0586:

```
- 어떤 필드가 항공권을 구성하는지 먼저 보고 (편명·시각·공항·금액 등)
- 항공권이 이미 비어 있으면 아무 일도 하지 않을 것
- 항공 비용이 총액에 잡혀 있으면 그것도 함께 처리할지 보고
[검수 모드] 착수 전 확인:
- 항공권 상태가 어디에 있는지(editor 안인지 별도인지)
- 날짜 변경 핸들러에서 접근 가능한지
```

"총액도 함께 처리할지 보고"가 유용한 질문이었다 — 답이 "할 게 없다"였고,
그걸 **확인해서** 알게 됐다(아래 4번).

## 4. 코드 작성 & 수정

### 0581 — 규칙 단일 소스 (`lib/plan/date-limits.ts` 신설)

네 함수. 클라와 서버가 **같은 함수**를 쓴다 — 한쪽만 막으면 사용자가 이유를 모른다.

> 초안은 "세 함수"로 적었으나 실제 export는 **네 개**다 — `savedDateStr`가 빠져 있었다.
> 같은 커밋(`0eb9fc9`) 산물이고, DB의 `DateTime`을 date input 형식(`YYYY-MM-DD`)으로 바꾸는 변환이다.
> 이게 없으면 클라의 하한 기준(폼 초깃값 문자열)과 서버의 하한 기준(DB `Date`)이 **형식부터 갈린다.**
> 단일 소스라는 이 절의 주장이 실제로 성립하게 만드는 네 번째 조각이다.

```ts
export function todayStrKst(): string {
  return new Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Seoul' }).format(new Date());
}

export function savedDateStr(d: Date | null): string | null {
  return d ? d.toISOString().split('T')[0] : null;
}

export function minStartDate(saved: string | null): string {
  const today = todayStrKst();
  return saved && saved < today ? saved : today;
}

export function validatePlanDates(input: { startDate: string; endDate: string; saved: string | null }): string | null {
  const { startDate, endDate, saved } = input;
  if (!startDate) return null;
  const min = minStartDate(saved);
  if (startDate < min) {
    return min === todayStrKst()
      ? '출발일은 오늘 이후로 선택해주세요'
      : `출발일을 기존 날짜(${min})보다 이전으로 바꿀 수 없습니다`;
  }
  if (endDate && endDate < startDate) return '도착일은 출발일 이후여야 합니다';
  return null;
}
```

세 가지를 판단해 주석에 남겼다.

- **KST 고정.** 배포 환경(Vercel)은 UTC라 로컬 시각을 쓰면 한국 00:00~09:00 사이에 "어제"를 오늘로 판정한다.
  그 창에서는 **오늘 출발하는 계획을 저장할 수 없다.**
- **하한만 본다.** 상한(먼 미래)은 막지 않는다 — 몇 년 뒤 여행을 계획할 수 있다.
- **날짜 미설정은 허용.** `startDate`는 nullable이고 "아직 안 정한 계획"이 성립한다.

파일을 `validate-input.ts`(0405, "다른 필드 상한이 생기면 여기로 모은다")에 합치지 않고 갈랐다.
축이 다르다 — 저쪽은 값의 범위(순수 상수·클램프)고 이쪽은 오늘 기준 시점 판정(KST·저장값 의존)이다.
양쪽에 상호 참조 주석을 달았다.

### 0581 — 서버 검증과 클라 `min`

서버(`my-plan/new/actions.ts`)는 `create`가 `saved: null`, `update`가 이미 조회하던 `existing`을 그대로 쓴다.

```ts
  const dateError = validatePlanDates({
    startDate: payload.startDate,
    endDate: payload.endDate,
    saved: savedDateStr(existing.startDate),
  });
  if (dateError) return { error: dateError };
```

반환은 기존 `{ error }` 형태 그대로 → 폼의 `saveError`가 이미 표시한다. 새 UI가 없다.

클라(`MyPlanNewForm.tsx`):

```tsx
  const savedStartRef = useRef(initialState?.startDate || null);
  const startMin = minStartDate(savedStartRef.current);
  // 출발일: min={startMin} / 도착일: min={editor.startDate || startMin}
```

**ref로 고정한 게 핵심이다.** `editor.startDate`를 기준으로 쓰면 폼에서 날짜를 고르는 순간
하한이 따라 움직여, 과거 플랜에서 한 번 미래로 바꾸면 **원래 날짜로 되돌릴 수 없게 된다.**
하한 기준은 "최초 저장값"이어야 하고, 그 값은 서버가 `existing.startDate`로 잡는 것과 같아야 한다.

### 0583 — 반환 타입으로 두 뜻을 가른다

조사 결과, 빈 배열이 나오는 조건은 둘이었다.

```ts
  if (!startDate || !endDate) return [];   // ① 둘 중 하나라도 빔
  if (diff < 0) return [];                 // ② 역순
  const dayCount = Math.max(1, ...);       // 이후로는 최소 1 — 빈 배열 불가
```

`dayCount`가 `Math.max(1, …)`이라 **정상 경로에서는 빈 배열이 나올 수 없다.**
즉 `[]`는 오로지 "날짜가 무효"라는 뜻이었는데, 타입상으로는 "0일짜리 계획"과 구분되지 않았다.
호출부가 가를 수 없으니 그냥 덮어썼다.

`days`에 값이 들어가는 지점은 4곳이지만 **덮어쓰기는 `handleDateChange` 한 곳뿐**이었다 —
나머지는 `prev.days.map()`(항목 갱신), 초깃값, 서버 `initialState`다.
항목 추가·삭제·드래그는 전부 `updateDayItems`를 거쳐 날짜와 무관하다.

```ts
function isValidRange(startDate: string, endDate: string): boolean {
  if (!startDate || !endDate) return false;
  return new Date(endDate).getTime() >= new Date(startDate).getTime();
}

function calcDays(startDate: string, endDate: string, prev: DayPlan[]): DayPlan[] | null {
  if (!isValidRange(startDate, endDate)) return null;
  const diff = new Date(endDate).getTime() - new Date(startDate).getTime();
  const dayCount = Math.max(1, Math.ceil(diff / (1000 * 60 * 60 * 24)) + 1);
  return Array.from({ length: dayCount }, (_, i) => {
    const day = i + 1;
    return prev.find((d) => d.day === day) ?? { day, items: [] };
  });
}
```

이 변경이 **새 거짓 표시를 만든다.** 지표 밴드의 기간 라벨이 역순 날짜를
`days.length > 0`으로 판정하고 있었다(구 주석에 그 의존이 명시돼 있었다).
days를 보존하면 역순 상태에서 "2박 3일"이 뜬다. 그래서 `isValidRange`를 술어로 뽑아 공유시켰다.

```ts
  const durationLabel =
    isValidRange(editor.startDate, editor.endDate) && editor.days.length > 0
      ? formatDurationLabel(editor.days.length)
      : '—';
```

**재계산 여부와 표시 여부가 같은 판정을 써야** "항목은 유지되는데 기간은 3일"처럼 어긋나지 않는다.

### `handleDateChange` — 세 사이클이 한 함수에 층으로 쌓였다

네 편을 한 편으로 묶는 근거는 문서 편집상의 편의가 아니다. **코드에 그 형태가 남아 있다.**
0583·0584·0586이 전부 같은 함수에 들어갔고, 실행 순서가 곧 사이클 순서다.

```ts
  // 0584: 계산을 setEditor 갱신 함수 **밖**에서 한다 — 갱신 함수는 순수해야 하고 StrictMode에서
  //   두 번 호출되므로, 안에서 confirm을 부르면 확인 창이 두 번 뜬다. 결정이 끝난 뒤 한 번만 갱신.
  function handleDateChange(field: 'startDate' | 'endDate', value: string) {
    const nextStart = field === 'startDate' ? value : editor.startDate;
    const nextEnd = field === 'endDate' ? value : editor.endDate;
    // 0583: null(= 아직 기간이 아님)이면 days를 건드리지 않는다 — 날짜를 한쪽만 고른
    //   중간 상태에서 기존 항목이 사라지지 않게. 날짜 값 자체는 그대로 반영해 입력을 막지 않고,
    //   두 날짜가 유효해지는 순간 재계산이 돌아 정상 흐름으로 복귀한다.
    const newDays = calcDays(nextStart, nextEnd, editor.days);

    // 0584: 축소(재계산 결과가 기존보다 적음)일 때만 확인 — 확장·동일·판정불가(null)는 그대로 진행.
    if (newDays && newDays.length < editor.days.length) {
      const dropped = editor.days.filter((d) => d.day > newDays.length);
      const count = dropped.reduce((n, d) => n + d.items.filter(isSavableItem).length, 0);
      if (count > 0) {
        const label = dropped.map((d) => `${d.day}일차`).join('·');
        // 취소 = 상태 미갱신. 제어 입력이라 React가 date input을 이전 값으로 되돌린다.
        // 확인 UI는 네이티브 confirm — 레포의 파괴적 동작 확인 표준(삭제 5곳 동일).
        if (!confirm(`${label} 항목 ${count}개가 삭제됩니다. 계속할까요?`)) return;
      }
    }

    // 0586: 날짜가 실제로 바뀌면 선택해 둔 항공권을 비운다. 같은 날짜 재선택이거나
    //   이미 비어 있으면 아무것도 하지 않는다 — 불필요한 remount를 만들지 않기 위함.
    //   축소 확인(위 0584)을 **통과한 뒤**에만 실행된다 — 취소하면 항공권도 그대로 남는다.
    const clearFlight = value !== editor[field] && editor.flight !== null;

    setEditor((prev) => ({
      ...prev,
      [field]: value,
      ...(newDays ? { days: newDays } : {}),
      ...(clearFlight ? { flight: null } : {}),
    }));
  }
```

순서가 의미를 갖는 지점이 둘이다.

- **0586이 0584 뒤에 있다.** 축소 확인을 취소하면 `return`으로 빠지므로 항공권도 그대로 남는다.
  순서가 반대였다면 "취소했는데 항공권만 사라진" 상태가 됐다.
- **계산이 `setEditor` 밖에 있다.** 0584가 구조를 바꾼 이유다 — 구 구조는 `setEditor(prev => …)`
  안에서 계산했는데, 갱신 함수는 순수해야 하고 StrictMode에서 두 번 호출된다.
  그 안에서 `confirm`을 부르면 **확인 창이 두 번 뜬다.**

### 0584 — 조사가 코드를 두 번 줄였다

**확인 창은 이미 표준이 있었다.** 레포에 커스텀 모달·다이얼로그 컴포넌트가 하나도 없다
(`role="dialog"`·`<dialog>`·`Modal` 전무). 파괴적 동작의 확인은 전부 네이티브 `confirm`이고 5곳에서 쓰인다.

| 위치 | 문구 |
|---|---|
| `my-plan/[id]/PlanOwnerActions.tsx:72` | `계획을 삭제하시겠습니까?` |
| `my-plan/_components/MyPlanCardMenu.tsx:58` | `계획을 삭제하시겠습니까?` |
| `story/[id]/DeleteButton.tsx:11` | `정말 삭제하시겠습니까?` |
| `my-story/_components/MyStoryCard.tsx:42` | `정말 삭제하시겠습니까?` |
| `til/[id]/TilDetail.tsx:68` | `정말 삭제할까요?` |

**되돌리기는 코드가 필요 없었다.** date input이 `value={editor.startDate}`인 **제어 컴포넌트**라,
취소 시 상태를 갱신하지 않고 `return`하면 React가 입력값을 이전 값으로 되돌린다 —
`<input value="고정" onChange={()=>{}}/>`가 타이핑을 무시하는 것과 같은 경로다.
되돌리기 로직도, remount용 `key`도 필요 없었다.

**개수는 `isSavableItem` 기준.** 이름이 빈 행은 어차피 저장되지 않으므로 "삭제됩니다"에 세면 거짓 경고다.
지표 밴드의 "장소 N곳"과 같은 조건이라 화면에 보이는 수와도 맞고, 덕분에
**"사라질 게 0건이면 확인 없이 진행"이 별도 분기 없이 이 조건 하나로 충족된다.**

### 0586 — 총액은 손댈 게 없었고, 섹션은 빌 뻔했다

```ts
  const flightAmount = editor.flight?.totalAmount ?? 0;
  const total = calcPlanTotal(…, editor.flight);
```

> **0587이 이 줄을 덧씌웠다.** 현행은 `flightTotal(editor.flight, editor.headcount)`로,
> 인원 곱셈이 들어갔다. `editor.flight` **파생**이라는 성질은 같으므로 이 절의 결론
> (`null`이 되면 자동으로 0)은 그대로다. 위 코드는 0586 시점 형태다.

둘 다 `editor.flight` 파생이라 `null`이 되면 자동으로 0이 된다. 그리고 항공 금액은
`PlanCost` 행으로 **존재하지 않는다** — 스키마 `CostCategory` enum에 `FLIGHT`가 없고
금액은 `PlanFlight.totalAmount` 한 곳에만 산다. 단일 소스라 지울 곳도 하나였다.

그런데 **그냥 `null`로 만들면 섹션이 빈다.** `FlightSearchSection`의 렌더 분기는 둘뿐이다.

```tsx
      {flight && !showForm && ( … 선택된 티켓 … )}
      {showForm && ( … 검색 폼 … )}
```

`showForm`은 `useState(!flight)`로 **마운트 시점에 한 번만** 정해진다.
티켓이 선택된 상태(`showForm === false`)에서 부모가 `flight`를 비우면
**두 분기 모두 거짓 → 섹션이 통째로 사라진다.**
정상 경로인 "변경" 버튼은 `onChange(null)`과 `setShowForm(true)`를 **함께** 부르기 때문에
이 문제가 없었다 — 부모가 초기화하는 순간 그 짝이 깨진다.

```tsx
      <FlightSearchSection key={editor.flight ? 'picked' : 'empty'} … />
```

`FlightSearchSection` 파일은 **손대지 않았다**(항공편 검색 UI 변경 금지).
`key`는 부모의 렌더 지시라 그쪽 조판·로직은 무변이고, remount되면 `useState(!flight)`가
다시 평가돼 검색 폼으로 돌아간다. 정상 경로에도 영향이 없다 —
티켓 선택 시 `onChange(offer)` + `setShowForm(false)`가 같이 돌지만,
remount 후 `useState(!flight)`도 `false`를 주므로 결과가 같다.
검색 결과 목록과 입력해 둔 공항 코드가 함께 초기화되는데,
**날짜가 바뀌면 그 검색 결과도 무효**라 의도에 부합한다.

### 검산 — 네 사이클을 하나의 날짜 변경 동작표로

네 편의 검산 표를 합쳤다. 한 번의 날짜 입력이 세 가지를 동시에 결정한다.

| 상황 | days | 확인 창 | 항공권 |
|---|---|---|---|
| 신규 · 과거 날짜 저장 | — | — | 서버 차단 "출발일은 오늘 이후로…" |
| 기존 과거 플랜(2026-06-04) 그대로 저장 | — | — | **통과** ← 지켜야 했던 것 |
| 기존 과거 플랜을 더 과거로 | — | — | 차단 "기존 날짜(2026-06-04)보다 이전으로…" |
| 출발일만 입력 | **보존** | 없음 | 비움(값이 바뀌었으므로) |

| 역순(도착 < 출발) | **보존**, 기간 라벨 `—` | 없음 | 비움 |
| 정상 3일 → 5일(확장) | 재계산 5일, 4·5일차 빈 칸 | 없음 | 비움 |
| 3일 → 2일 (3일차 4개) | 확인 후 재계산 | `3일차 항목 4개가 삭제됩니다. 계속할까요?` | 확인 통과 시 비움 |
| 5일 → 2일 | 확인 후 재계산 | `3일차·4일차·5일차 항목 4개가…` | 확인 통과 시 비움 |
| 3일 → 2일, 3일차가 빈 행뿐 | 재계산 | 없음(`isSavableItem` 0건) | 비움 |
| 축소 확인을 **취소** | 미갱신(React가 입력 되돌림) | 취소됨 | **유지** |
| 같은 날짜 재선택 | 재계산(동일) | 없음 | **유지**(값 불변) |
| 항공권 없는 상태에서 날짜 변경 | 위 규칙대로 | 위 규칙대로 | 무동작 |

## 5. 결과 / 배운점

### 결과

- 네 사이클 모두 `npx tsc --noEmit` 통과. `npm test` 실패 목록이 기존과 정확히 동일
  (auth 5스위트 + SpotPopup = 6스위트/8테스트) — 회귀 없음. 0586은 `npx next build` 컴파일도 확인했다.
- 서버 액션은 0586에서 무접촉이다. 저장 시 `payload.flight`가 `null`이면 기존
  `updatePlanWithItemsAction`이 이미 `planFlight.deleteMany`를 수행한다.
- 부수 해소(0583): `savableDayCosts`가 `c.day <= editor.days.length`로 거르므로,
  days가 비면 **일자별 비용도 전량 저장 대상에서 탈락**하고 있었다. 같은 원인이라 함께 풀렸다.
- **실화면 확인 완료** 
  ① 달력이 하한 이하를 못 고른다 
  ② 기존 저장값이 과거인 플랜도 날짜를 안 건드리면 저장된다 
  ③ 날짜 없이 담긴 플랜에서 출발일만 입력해도 탭·항목이 유지된다
  ④ 축소 시 확인 창이 뜬다 
  ⑤ **취소하면 날짜 입력이 이전 값으로 돌아온다**
  — 0584 조사가 "코드로 확신할 수 없는 유일한 지점"이라 표시한 항목이 여기서 닫혔다
  ⑥ 날짜 변경 시 검색 폼으로 복귀하고 총액에서 항공 금액이 빠진다 
  ⑦ 같은 날짜 재선택 시 티켓 유지

### 배운점

- **부수 효과를 검증으로 착각하면 없는 안전망을 믿게 된다.**
  "도착일 ≥ 출발일"은 있다고 여겨졌지만 실제로 있던 건 `calcDays`의 빈 배열 반환이었다 —
  화면에서 일정이 사라지니 막힌 것처럼 보였을 뿐 저장은 됐다.
  그리고 **그 빈 배열이 두 사이클 뒤 0583의 부작용으로 돌아온다.**
  검증처럼 보이는 부수 효과는 안 막을 뿐 아니라, 전제가 바뀌면 반대로 해를 끼친다.
- **잠들어 있던 결함은 다른 변경이 깨운다.**
  0583의 코드는 오래 그대로였지만 문제가 없었다 — 날짜 없는 플랜에 항목이 실릴 수 없었기 때문이다.
  앞 묶음의 0582가 그 전제를 바꾸자 같은 코드가 삭제 경로가 됐다.
  **전제를 바꾸는 변경에서는 "이 전제에 기대던 코드가 어디인가"를 같이 봐야 한다.**
  이 트랙에서 부작용이 하나뿐이었던 건 운이 아니라, 0582 완료 보고가 그 위험을 먼저 적어 뒀기 때문이다.
- **"막는다"의 기준선은 오늘이 아니라 기존 값일 때가 있다.**
  하한을 오늘로 잡는 건 자연스럽지만, 그러면 이미 저장된 과거 데이터가
  **날짜와 무관한 수정까지 막힌다.** 새 규칙을 넣을 때는 "이 규칙을 지금 위반 중인 데이터가 몇 건인가"를
  먼저 세야 한다 — 이번엔 그게 프롬프트의 확인 항목으로 지정돼 있었고, 실제로 1건이 있었고,
  하필 공개 시연 데이터였다.
- **막을 것과 알릴 것은 다르다.**
  0583의 중간 상태는 정당한 조작이 아니므로 "하지 않는다"로 풀었다(보존).
  0584의 축소는 정당한 조작이라 막을 수 없고 알리는 게 답이었다(확인).
  0586의 항공권 초기화는 알리지도 않았다 — **거기가 지금 남은 비대칭이다**(아래 별건).
  같은 트랙 안에서 세 가지 답이 나왔고, 갈림길은 "사용자가 그걸 하려던 것인가"였다.
- **추가한 코드가 0줄인 요구사항이 있다.**
  "취소 시 날짜를 되돌린다"는 되돌리기 상태를 하나 더 두는 그림이 먼저 떠오르지만,
  제어 컴포넌트는 상태를 갱신하지 않는 것 자체가 거부이고 React가 입력을 복원한다.
  확인 창도 같은 결이다 — 레포에 이미 5곳에서 쓰는 표준이 있었고 커스텀 모달은 하나도 없었다.
  **일관성은 컴포넌트를 잘 만들어서가 아니라 안 만들어서 지켜졌다.**
- **빈 값 하나에 두 뜻을 담으면 호출부가 판단할 수 없다.**
  `[]`는 "0일"과 "판정 불가"를 겸하고 있었고, 정상 경로에서 0일이 나올 수 없다는 사실은 함수 안에만 있었다.
  반환 타입을 `T[] | null`로 가르는 것만으로 호출부가 옳은 결정을 할 수 있게 된다 —
  로직을 더 넣은 게 아니라 **이미 있던 구분을 타입으로 드러냈을 뿐이다.**
- **상태를 밖에서 바꾸면 안쪽의 파생 상태와 짝이 깨진다.**
  `showForm`은 `flight`에서 파생됐지만 마운트 시점에 한 번만 복사됐다 —
  사본이라 원본이 바뀌어도 따라오지 않는다. 자식이 prop을 초기값으로만 쓰는 구조에서는
  부모가 그 prop을 바꾸는 순간 자식이 아무 데도 속하지 않는 상태가 될 수 있다.
  `key`는 그 사본을 다시 뜨게 하는 수단이다.

## 결정 (Decisions)

**날짜 규칙**
- **날짜 하한 = `min(오늘, 기존 저장값)`** — "이미 지난 여행 기록은 보존하되 새로 과거를 만들지는 못한다".
  클라·서버 같은 함수(`lib/plan/date-limits.ts`).
- **시점 판정은 KST 고정** — 배포가 UTC라 로컬 시각은 한국 새벽에 하루가 어긋난다.
- **상한은 두지 않는다** — 먼 미래 계획은 정상.
- **날짜 하한은 `validate-input.ts`가 아니라 별도 파일** — 값의 범위와 시점 판정은 축이 다르다.
- **`saveDisabled`는 제목만 유지** — 0527 확정을 이번 트랙으로 뒤집지 않는다.
  날짜 오류는 서버 `{ error }` → `saveError` 경로로 보인다.

**날짜가 바뀔 때 무엇을 하는가**
- **`calcDays`의 `null` = 재계산 불가** — 호출부는 기존 days를 보존한다. 빈 배열은 더 이상 반환하지 않는다.
- **날짜 값 자체는 항상 반영한다** — 입력을 막지 않고, 유효해지는 순간 복귀.
- **`isValidRange`는 재계산과 표시가 공유한다** — 판정이 갈리면 화면이 어긋난다.
- **축소는 막지 않고 알린다** — 확인 창은 네이티브 `confirm`(레포 파괴적 동작 표준 5곳).
  커스텀 모달은 만들지 않는다. **확장·동일·판정불가는 확인 없음.**
- **개수 기준은 `isSavableItem`** — 저장되지 않을 빈 행을 "삭제"로 세지 않는다. 0건이면 확인 없이 진행.
- **취소 = 상태 미갱신** — 제어 입력이라 React가 날짜를 되돌린다. 별도 되돌리기 상태 없음.
- **날짜가 바뀌면 항공권은 통째로 비운다** — 편명·시각 예약이라 부분 무효화가 없다.
  0580(담기 항공 미복사)과 같은 근거. **값이 실제로 바뀔 때만**(같은 날짜 재선택·이미 빈 상태는 무동작).
- **항공권 복구는 `key` remount로** — 자식 파일을 고치지 않고 부모가 해결한다.
- **항공 금액은 따로 처리하지 않는다** — `editor.flight` 파생이고 `PlanCost` 행이 없다.
- **판정 순서는 축소 확인 → 항공권 초기화** — 취소가 항공권까지 되돌려야 한다.

## 겹치는 축 (다른 회고 참조)

- **항공** — 0586의 근거는 **0580(담기 항공 미복사)과 같다**: 편명·시각 예약이라 재사용이 안 된다.
  적용 지점만 다르다 — 0580은 다른 사람에게 넘어갈 때, 0586은 같은 사람이 날짜를 바꿀 때.
  **담기가 항공을 복사하지 않으므로 이 초기화는 담은 플랜이 아니라 직접 만든 플랜에서 의미가 있다**
  (담은 플랜에는 비울 항공권이 없다). 정본은 **담기 복사 범위 트랙(0579·0580·0582)**.
- **0583의 발단** — 앞 묶음의 0582가 만든 **"날짜 없이 항목이 실린 폼"**이다.
  담기가 Day 구조만 가져오게 되면서 처음 생긴 상태이고, 그 트랙 회고의 「겹치는 축」이
  반대편에서 같은 연결을 걸어 두었다.
- **과거 날짜 차단(0581)의 우회로** — 담기로 과거 날짜가 유입되던 경로는 **0582가 닫았다**(날짜 미복사).
  즉 이 트랙의 시작점이 앞 묶음의 결정 하나를 만들었고, 그 결정이 다시 이 트랙의 0583을 불러냈다.
- **항공 금액 인원 반영** — `flightAmount`는 이후 **0587**이 `flightTotal(flight, headcount)`로 대체했다.
  파생이라는 성질은 같아 0586의 판단에 영향 없음.

## 남은 것 (별건)

- **항공권 초기화에는 확인 창이 없다.** 선택해 둔 항공권이 예고 없이 사라진다.
  0584의 일정 항목은 축소 시 확인을 받는데 항공권은 안 받는 **비대칭**이 이 트랙 안에서 생겼다 —
  확인 UI 통일에서 함께 볼 것(0586 지시상 그 사이클 범위 밖이었다).
- **축소되는 날의 일자별 비용은 확인 문구에 없다.** `savableDayCosts`가 `c.day <= days.length`로 거르므로
  3일차를 자르면 3일차 비용도 사라지는데, 문구는 "항목 N개"만 말한다.
  문구를 지정받아 그대로 썼다 — 비용까지 알릴지는 미판정.
- **클라 `min`은 타이핑 입력을 완전히 막지 못한다** — 브라우저가 invalid 표시만 하고 값은 들어간다.
  서버가 실제 방어선이고, 그 경우 사용자는 저장을 눌러야 안다. 인라인 에러 표시는 미구현.
- **`FlightSearchSection`의 `todayStr()`와 `todayStrKst()`가 중복이다.** 0581 지시상 손대지 않았다.
  그쪽은 클라 로컬 기준이라 해외에서 쓰면 판정이 갈린다 — 통합 대상.
- 앞 묶음에서 넘어온 것: 기존에 담긴 플랜 소급 복구 / 목록 카드와 상세의 일수 폴백 불일치 /
  스토리→플랜 복사 경로(`sourceStoryId`, 0097) 점검.
- 0585에서 넘어온 것: 드래그 핸들 히트 영역 14px.
