## 1. 한 줄 요약

부실하던 마이페이지에 비밀번호 변경 기능을 더하고, Story 예산 요약에 연결된 여행플랜으로 가는 링크를 붙였다. 비번 변경은 "현재 비번 확인" 방식을 표준 조사로 확정하고 Supabase 공식 메서드로 구현했으며, 예산 링크는 "비공개 플랜이 노출되지 않게" isPublic 체크를 넣었다. 두 작업 모두 추측으로 넘어가지 않고 검증(web_search, 코드 확인)으로 결정을 잡았다.

## 2. 왜 / 목적 / 이유

### 가. 재로그인 대신 updateUser({ current_password })를 쓴 이유 (핵심)

- **왜**: 비밀번호 변경 시 "현재 비밀번호가 맞는지" 검증이 필요한데, 두 방법이 있었다. (1) 그 비번으로 재로그인을 시도해 성공 여부로 확인, (2) `updateUser`에 current_password를 같이 넘겨 한 번에 검증+변경.
- **목적**: 현재 로그인 세션을 건드리지 않고 검증과 변경을 처리한다.
- **이유**:
  - 재로그인(`signInWithPassword` 재호출) 방식은 — Supabase가 쿠키 기반 인증이라, 서버에서 다시 로그인을 호출하면 **새 세션/쿠키를 발급해 현재 로그인 상태를 흔들 수 있다.** "현재 비번 확인"이라는 부수 작업이 의도치 않게 세션을 건드리는 부작용.
  - `updateUser({ current_password, password })`는 한 번의 호출로 "현재 비번 검증 + 새 비번 변경"을 같이 한다. 재로그인을 거치지 않으니 세션을 건드릴 일이 없다.
  - 이 방법은 **검색으로 찾아냈다.** CC가 처음엔 재인증 방식을 제안했지만, "Supabase에서 현재 비번 검증을 어떻게 하는 게 표준인지" 한 번 더 web_search → updateUser에 current_password를 넘기는 공식 방법(supabase-js 2.102.0+)을 발견. 설치 버전(2.106.1)이 충족하는지, 타입 정의에 current_password가 있는지까지 확인하고 적용했다.
  - "내가 아는 것 같은데?"(CC 제안대로 재인증)에서 멈추지 않고, 라이브러리가 전용 방법을 제공하는지 검증해 더 나은 길을 찾은 케이스.

### 나. 마이페이지엔 "현재 비번 확인", 메일 인증은 별도로 분리한 이유

- **왜**: 처음엔 "마이페이지 비번 변경에 메일 본인인증을 넣자"고 했으나, 결국 현재 비번 확인만 쓰고 메일 인증은 안 넣었다.
- **목적**: 기능을 그 상황에 맞는 본인 확인 수단으로 설계한다.
- **이유**: "비밀번호 변경"과 "비밀번호 재설정"은 다른 상황의 다른 기능이다(web_search로 OWASP 표준 확인).
  - **변경 (마이페이지)** — 로그인한 상태에서 바꾼다. 이미 로그인했으니 본인이 거의 확실하고, "현재 비번" 입력으로 한 번 더 확인하면 충분하다. 여기에 메일 인증까지 더하면 — 이미 로그인 + 현재 비번을 아는 사람한테 메일까지 요구하는 셈이라 과하다(사용자만 번거롭고 보안은 딱히 안 강해짐).
  - **재설정 (로그인 화면, "비번 찾기")** — 비번을 까먹어 로그인을 못 하는 상태. 현재 비번을 모르니 확인이 불가능 → 메일이 유일한 본인 확인 수단.
  - 즉 한 기능에 둘 다 넣는 게 아니라, 다른 자리에 각각 둔다. 마이페이지엔 현재 비번 확인, 메일 재설정은 "비번 찾기"로 분리(킵 — 다음 작업).

### 다. 예산 링크에 isPublic 체크를 넣은 이유 (직관을 검증으로 뒤집음)

- **왜**: Story 예산 요약에 "이 여행플랜 보기" 버튼을 만들 때, 처음엔 "비공개 플랜이면 어차피 Story에 연결 안 되지 않냐 → isPublic 체크 불필요"라고 추측했다.
- **목적**: 비공개 플랜의 비용 정보가 노출되거나 404가 나지 않게 한다.
- **이유**: CC에 "Story에 플랜 연결 시 isPublic을 강제하는지" 확인시키니 — **비공개 플랜이 Story에 붙을 수 있는 경로가 두 개**였다.
  - **경로 1**: 연결할 때 검증이 없다. planId 설정 코드가 "소유자 본인인지"만 확인하고 isPublic은 안 본다 → 비공개 플랜도 처음부터 연결 가능.
  - **경로 2**: 연결 후 비공개로 토글 가능. `togglePlanPublicAction`이 연결된 Story가 있는지 안 본다 → 공개로 연결한 뒤 나중에 비공개로 바꿀 수 있다.
  - 그러니 "Story에 붙은 플랜 = 항상 공개"는 거짓. 따라서 isPublic 체크가 필수였다.
  - 안 넣었을 때의 문제: (1) **404** — PlanFinder 상세는 `isPublic: true`만 조회하므로 비공개 플랜에 버튼이 떠 있으면 누를 때 404. (2) **사생활** — 비공개 플랜의 비용·일정으로 가는 통로가 열림.
  - 그래서 버튼에 `planIsPublic && planId` 조건 → 공개일 때만 표시. 연결 로직이 어떻든(검증 없든, 나중에 토글되든) 버튼 쪽에서 항상 막힌다.
  - **직관을 검증으로 뒤집은 사례**: "비공개면 연결 안 됨"으로 그냥 넘어갔으면 isPublic 체크를 안 넣었을 것이고, 비공개 플랜에서 404 + 사생활 노출이 났을 것. "비공개면 연결 안 되지 않냐"는 질문이 검증의 출발점이 됐다.
  - 0108의 "비공개를 My Plan에만 가둔다"와 연결: Story엔 비공개가 없지만 My Plan엔 있으므로, Story→Plan 링크는 그 Plan의 isPublic을 존중해야 한다.

## 3. 작성한 프롬프트 (핵심 발췌)

### 표준 조사 — "세계적으로 비번을 어떻게 바꾸나"

비번 변경은 보안(★★★★★)이라, 구현 전 표준을 web_search로 확인.

```
- 비번 변경(로그인 상태) → 현재 비번 입력으로 확인 (앱 내에서, 메일 안 거침)
- 비번 재설정(로그인 못 함) → 메일 토큰으로 확인
- 한 기능에 둘 다 요구하지 않음. 다른 자리에 각각.
- (NIST: 주기적 만료·복잡도 강제는 안티패턴, 길이가 중요)
```

## 4. 코드 작성 & 수정

### 비번 변경 — Server Action

```ts
// app/(protected)/mypage/actions.ts
export async function updatePasswordAction(
  currentPassword: string, newPassword: string,
): Promise<{ error: string } | null> {
  if (!currentPassword || !newPassword) return { error: '모든 항목을 입력해주세요' };
  if (newPassword.length < 8) return { error: '비밀번호는 8자 이상이어야 합니다' };  // signUp과 동일 정책

  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return { error: '로그인이 필요합니다' };

  const { error } = await supabase.auth.updateUser({
    current_password: currentPassword,   // 현재 비번 검증 + 변경 한 번에
    password: newPassword,
  });
  if (error) {
    if (error.status === 422 || error.message.toLowerCase().includes('credential'))
      return { error: '현재 비밀번호가 올바르지 않습니다' };
    return { error: '비밀번호 변경에 실패했습니다' };
  }
  return null;
}
```

> 비밀번호는 로그·반환값에 절대 안 실음. 닉네임 저장과 같은 패턴(Server Action, createClient, getUser).

### 비번 변경 — 폼

```tsx
// app/(protected)/mypage/PasswordForm.tsx (신규)
// 입력 3개(type="password"): 현재 / 새 / 새 비번 확인
// 클라 검증 순서: 빈 값 → 8자 미만 → 새 비번 != 확인 → Server Action 호출
// 성공 시 3필드 초기화
```

> [검수 시 인지] 현재 비번 틀렸을 때 에러 형식(status 422 / "credential")이 추측이라, 실제 틀린 비번으로 테스트해 분기가 맞는지 확인 필요 — 문서와 실제가 어긋난 사례가 있어 코드만 믿지 않고 실제 동작으로 검증.

## 5. 결과 / 배운점

### 결과

- 마이페이지 비번 변경 완성: 현재/새/확인 입력 → updateUser로 검증+변경. 정상·틀린 비번·8자 미만·불일치 동작 확인.
- 예산 링크 완성: 공개 플랜일 때만 "이 여행플랜 보기" 표시, 누르면 PlanFinder 상세로. 비공개로 토글하면 버튼 사라지는 것까지 직접 확인(isPublic 체크 실증).
- 두 작업 모두 추측으로 안 넘어가고 검증으로 결정 — 비번은 web_search+버전 확인, 예산은 코드 확인.

### 배운점

- **라이브러리는 표준 방법을 먼저 찾는다.** "현재 비번 확인"을 재로그인으로 직접 구현하려다, 검색으로 updateUser+current_password 공식 방법을 발견했다. 직접 구현은 세션 부작용 위험이 있었고, 공식 방법이 그걸 피했다. 바퀴를 재발명하기 전에 라이브러리가 제공하는지 검증한다.
- **현재-비번-확인은 세션 탈취 방어이지 비번 유출 방어가 아니다.** 비번을 이미 아는 공격자는 비번 변경 단계로 못 막는다(이미 탈취됨). 현재-비번-확인이 막는 건 "비번은 모르고 세션만 훔친" 공격자다. 비번 유출 자체는 MFA·변경 알림 메일·세션 무효화 같은 다른 계층에서 막는다. 방어가 계층별로 다르다.
- **변경과 재설정은 본인 확인 수단이 다르다.** 로그인 상태면 현재 비번, 로그인 못 하면 메일. 상황에 안 맞는 수단을 끼우면(로그인한 사람한테 메일 인증) 과해진다. 기능을 상황에 맞게 설계한다.
- **직관은 검증으로 확인한다 — 코드가 심판이다.** "비공개면 연결 안 됨"이라는 직관을, 코드 확인으로 뒤집었다(연결 시 검증 없음 + 토글 가능 = 비공개도 붙을 수 있음). 이후 "Story에 비공개 필드가 있나"도 기억이 갈렸지만 schema를 직접 확인해 정리했다. 추측이 갈릴 때 코드가 진실이다.
