## 1. 한 줄 요약

목록 그리드가 마지막 줄에서 비는 문제를 열 수 규칙으로 풀고, 페이지 전환 깜빡임을 네 번 잘못 고친 뒤 원인이 렌더가 아니라 이미지 로드였음을 실측으로 확인했다.

---

## 2. 왜 / 목적 / 이유

### 왜 (동기·문제)

더미 30개를 넣고 목록을 보니 세 가지가 걸렸다.

- **마지막 줄이 비었다.** 페이지 크기가 14인데 열 수가 폭에 따라 3·4·5·6·7로 변해서 어느 값을 골라도 딱 떨어지지 않았다
- **글쓰기 화면으로 이동할 때 목록 스켈레톤이 떴다.** `loading.tsx`가 하위 라우트까지 상속된다는 걸 몰랐다
- **페이지를 넘길 때 화면이 깜빡였다.** 이게 이 구간에서 가장 오래 붙든 문제다

### 목적 (도달하려는 상태)

- 어떤 화면 폭에서도 마지막 줄이 꽉 찬다
- 목록용 로딩이 목록 화면에서만 뜬다
- 페이지를 넘길 때 빈 구간도 번쩍임도 없다
- 시·군 이름으로 지역을 적어도 커버가 붙는다

### 이유 (채택 근거)

**페이지 크기가 아니라 열 수를 고친 이유(0425)** — 처음엔 페이지 크기를 조정하려 했는데, `auto-fill`이 5열·7열까지 만들어내면 **어떤 페이지 크기도 안 떨어진다.** 5와 7은 12든 15든 나누지 못한다. 그래서 열 수를 페이지 크기의 약수로 제한하는 쪽이 근본이다. 열이 1·2·3·4·6만 나오게 하고 페이지를 12로 두면 전 구간에서 마지막 줄이 찬다.

**`auto-fill`을 버린 대가** — 0415에서 `auto-fill`로 간 이유가 카드 최소 폭 320px 보장이었다. 브레이크포인트로 돌아가면 그 보장이 깨질 수 있어, **각 열 수에서 카드가 320px을 유지하는 뷰포트 폭을 계산해서** 브레이크포인트로 삼았다.

**빈 `loading.tsx`로 덮지 않은 이유(0426)** — 하위 라우트에 빈 `loading.tsx`를 두면 목록 스켈레톤은 안 뜨지만, **`null` 폴백도 Suspense 경계라 빈 화면이 한 번 뜬다.** 스켈레톤 플래시가 블랭크 플래시로 바뀔 뿐이다. 라우트 그룹으로 경계 자체를 좁히면 하위 라우트는 Next의 기본 동작(이전 화면 유지 후 전환)으로 돌아간다.

**전환 연출을 결국 없앤 이유(0430)** — 스토리는 서버 왕복이 있어 스켈레톤이 정당하게 뜨는데, 플랜파인더는 **데이터가 이미 클라이언트에 있어 대기가 0**이다. 없는 대기를 채우려는 연출이 오히려 번쩍임을 만들었다.

**유명 도시만 넣지 않은 이유(0432)** — 처음엔 관광지 위주로 40개를 추렸다. 그런데 실제 촬영지 분포를 보니 **파주·안성·양주·과천·화성·구리·영월**처럼 관광지가 아닌 곳에 몰려 있었다. 스튜디오와 세트장이 땅값 싼 수도권 외곽에 있고 조용한 로케이션도 한적한 데서 찍기 때문이다. **감으로 고른 목록은 반드시 샌다**는 게 데이터로 드러나 전수(226개)로 갔다.

## 3. 작성한 프롬프트

> 아래 프롬프트는 작업 당시 대화 기록에서 재구성한 것이라 실제로 던진 원문과 표현이 다를 수 있다. 지시 내용과 범위·금지사항은 동일하다.

### 0431 — 인접 페이지 프리로드 (전문)

```
[배경]
페이지 전환 깜빡임의 최종 원인 확정(네트워크 탭 실측):
넘기는 순간 그 페이지 이미지 12장이 그제서야 요청되고(200, 장당 216~294ms),
받는 동안 카드가 폴백으로 떴다가 채워지는 것이 깜빡임의 실체.
프로덕션 빌드에서도 동일 확인.
전환 기법으로는 감출 수 없고, 미리 받아두는 것이 유일한 해법이다.

[먼저 확인 — 읽고 보고만]
1. PlanListClient에서 pageItems·전체 정렬 결과(sorted)의 구조
2. PlanCard가 이미지를 next/image로 그릴 때 실제 요청되는 URL 형태
   (원본이 아니라 /_next/image?url=...&w=...&q=... 최적화 URL임에 유의)
3. PlanCard의 sizes 값 — 프리로드 URL의 w 파라미터를 맞추는 근거

[목표]
현재 페이지를 보는 동안 인접 페이지(다음·이전)의 커버를 프리로드한다.

- currentPage·sorted가 바뀔 때 인접 페이지의 coverUrl 목록을 뽑아
  백그라운드에서 미리 로드
- 핵심: next/image가 요청할 최적화 URL과 정확히 같은 형태여야
  브라우저 캐시가 맞는다.
  getImageProps로 카드와 같은 props(sizes 포함)를 넣어 srcSet을 얻고
  그 URL들을 new Image()로 로드하는 방식을 검토할 것.
  더 나은 방법이 있으면 근거와 함께 제안
- 이미 프리로드한 URL은 Set(ref)으로 기억해 중복 요청 방지
- coverUrl null은 건너뜀
- 프리로드 실패는 조용히 무시 (화면에 영향 없어야 함)
- 필터·정렬이 바뀌면 인접 페이지 구성도 바뀌므로 그때도 다시 계산

[하지 말 것]
❌ 전환 방식 변경 (현재 즉시 교체 상태 유지)
❌ 전체 페이지 한꺼번에 프리로드 (인접 페이지만)
❌ 정렬·필터·슬라이스 로직 변경
❌ 커밋 번호 임의 지정 — 0431만 사용

[검수 모드]
1페이지에서 2~3초 머문 뒤 2페이지로 넘겼을 때 즉시 뜨는지.
네트워크 탭에서 프리로드가 인접 페이지 분량만 나가는지,
전환 순간에는 같은 URL이 (disk cache) 또는 요청 0인지.

plan 요청.
```

**`원본이 아니라 최적화 URL`이라는 함정을 프롬프트에 박아둔 게 이 커밋의 성패였다.** `next/image`는 원본 URL이 아니라 `/_next/image?url=…&w=640` 같은 주소를 요청하므로, 원본을 미리 받아두면 카드가 요청하는 것과 달라 캐시가 안 맞는다.

## 4. 작성·수정한 코드

### 0425 — 열 수를 페이지 크기의 약수로

`auto-fill`을 버리고 명시 브레이크포인트로 돌아갔다.

```diff
- grid-cols-[repeat(auto-fill,minmax(320px,1fr))]
+ grid-cols-[minmax(min(320px,100%),1fr)]
+ min-[704px]:grid-cols-2 min-[1040px]:grid-cols-3
+ min-[1372px]:grid-cols-4 min-[2040px]:grid-cols-6
```

브레이크포인트 값은 **계산해서 얻었다.** 콘텐츠 폭 = 뷰포트 − 좌우 패딩 48 − gap 14이고, 각 열 수에서 카드가 320px을 유지하는 최소 뷰포트가 702·1036·1370·2038이다. 그걸 절상해 704·1040·1372·2040으로 잡았다.

**5열이 없는 것이 이 커밋의 목적이다.** 12의 약수만 남긴다.

1열 트랙에도 처리가 들어갔다.

```
minmax(min(320px,100%),1fr)
```

`minmax(320px,1fr)`이면 뷰포트 320px(콘텐츠 272px)에서 열이 320px을 강제해 가로 넘침이 난다. `min()`으로 감싸면 좁은 화면에서는 컨테이너 폭까지 줄고 넓은 화면에서는 320 하한이 유지된다.

스토리는 한 티어만 뺐다.

```diff
- grid-cols-2 md:grid-cols-3 lg:grid-cols-4 xl:grid-cols-5 2xl:grid-cols-6
+ grid-cols-2 md:grid-cols-3 lg:grid-cols-4 2xl:grid-cols-6
```

`PLAN_PAGE_SIZE`는 14 → 12가 됐고 주석에 근거를 붙였다.

```ts
// 0425: 12 = 그리드 열 수 1·2·3·4·6의 공배수
//       → 꽉 찬 페이지에서 마지막 줄이 항상 채워짐.
```

스켈레톤 두 개도 같은 클래스로 맞췄는데, **상수로 못 뽑고 리터럴을 복사했다.** Tailwind JIT이 완전 리터럴만 스캔하기 때문이다. 대신 양쪽에 상호 참조 주석을 달아 "한쪽만 바꾸면 로딩 전환 시 레이아웃 시프트"를 명시했다.

### 0426 — 라우트 그룹으로 경계 좁히기

파일 넷을 `(list)` 그룹 안으로 옮겼다. 전부 순수 rename이고 `import` 상대 경로만 한 단계씩 올라갔다.

```
plan-finder/loading.tsx  →  plan-finder/(list)/loading.tsx
plan-finder/page.tsx     →  plan-finder/(list)/page.tsx
story/loading.tsx        →  story/(list)/loading.tsx
story/page.tsx           →  story/(list)/page.tsx
```

`_components/`는 그룹 밖에 남겼다. 상세 화면도 쓰는 것이라 목록 전용 그룹 안으로 넣을 이유가 없다. 그래서 `./_components/…`가 `../_components/…`가 됐다.

**라우트 그룹은 URL에 영향을 주지 않는다.** `/plan-finder`는 그대로고 Suspense 경계만 좁아진다.

### 0427 — 크로스페이드 (되돌려짐)

스토리의 전환 연출을 이식했다. 아웃 280ms → 스왑 → 인 280ms.

```ts
const [fading, setFading] = useState(false);
const swapTimer = useRef<ReturnType<typeof setTimeout> | null>(null);

const goTo = (next: number) => {
  if (next < 1 || next > totalPages || next === currentPage || fading) return;
  setCardEntry(false);
  setFading(true);
  swapTimer.current = setTimeout(() => {
    setPage(next);      // opacity 0 상태에서 슬라이스 교체 + 최상단 스크롤
    setFading(false);   // 같은 커밋에서 0→100 페이드인 시작
  }, 280);
};
```

```diff
- <div key={`${sort}-${filter}-${currentPage}`} className="grid …">
+ <div key={`${sort}-${filter}`}
+      className={`grid … transition-opacity duration-[280ms]
+                  ${fading ? 'opacity-0' : 'opacity-100'}`}>
```

**`key`에서 `currentPage`를 뺐다.** 리마운트되면 transition이 안 걸리기 때문이다. 스크롤 이펙트도 `useEffect`에서 `useIsoLayoutEffect`로 승격했다 — 스왑 커밋 후·페인트 전에 실행돼야 새 페이지가 이전 스크롤 위치로 그려지는 프레임이 없다.

주석에 짝을 명시했다.

```
// duration-[280ms]는 goTo의 스왑 타이머 280ms와 짝 — 한쪽만 바꾸면 스왑이 노출된다.
```

**연출을 정교하게 맞춰놨지만 깜빡임은 남았다.** 카드가 사라진 뒤 새 카드가 뜨기까지 280ms 동안 화면이 비었기 때문이다.

### 0429 — 스켈레톤 층 (커밋 전 폐기)

그 빈 구간을 스켈레톤으로 채우려 했다. 스토리처럼 스켈레톤을 flow에 깔고 카드를 `absolute`로 덮은 뒤, `fading`을 두 레이어에 반대로 걸어 카드가 사라지는 동안 스켈레톤이 그 자리를 채우는 구조다.

**구현했지만 더 나빠졌다.** 스토리는 그 사이에 서버 대기가 있어 스켈레톤이 머무는데, 플랜파인더는 대기가 0이라 스켈레톤이 `opacity-1`에 도달한 순간 바로 스왑되고 사라진다. **한 프레임만 보이니 "로딩이 떴다"가 아니라 "뭔가 번쩍했다"로 읽혔다.**

커밋하지 않고 0430에서 되돌렸으므로 이 시도는 코드에 남지 않았다.

### 0428 — 등장 모션 제거

0427이 조건부로 남겨둔 `appear-up` 계열을 통째로 걷어냈다. 지워진 것이 줄줄이 이어졌다.

| 지워진 것 | 도입 시점 |
|---|---|
| `hasInteracted` state | 0411 |
| `baseDelay` 계산 | 0411 이전 |
| `cardEntry` state | 0427 |
| 카드 래퍼 `<div>` | 시안 적용 초기 |
| 그리드 `key` | 0427에서 축소된 형태 |

```diff
- {pageItems.map((plan, i) => (
-   <div key={plan.id} className={cardEntry ? 'appear-up' : undefined} style={…}>
-     <PlanCard {...plan} />
-   </div>
+ {pageItems.map((plan) => (
+   <PlanCard key={plan.id} {...plan} />
  ))}
```

**`hasInteracted`는 0411에서 `ref`를 `state`로 바꿔가며 만든 것인데 여기서 사라졌다.** 그때 그 작업이 낭비였던 건 아니다 — 그때는 필요했고 지금 필요가 없어진 것이다.

래퍼가 사라지면서 `PlanCard`가 그리드의 직계 자식이 됐고, `map`의 인덱스도 필요 없어졌다(순차 지연 `i * 0.12`가 없어졌으므로).

### 0430 — 전환 자체를 되돌림

`fading`·`swapTimer`·`resetTransition`·`Pagination`의 `disabled`까지 전부 제거하고 `goTo`를 동기로 되돌렸다.

```ts
const goTo = (next: number) => {
  if (next < 1 || next > totalPages || next === currentPage) return;
  setPage(next);
};
```

```ts
// 페이지 전환 애니메이션 없음(0430, 0427·0429 되돌림): 데이터가 이미 클라이언트에 있어
// 즉시 교체하면 빈 구간도 번쩍임도 없다. 서버 대기가 0이라 스켈레톤이 한 프레임만 스쳐 번쩍이던 문제 제거.
```

**남긴 것이 무엇인지가 중요하다.** `useIsoLayoutEffect`와 최상단 스크롤은 유지했고, `loading.tsx` 진입 로딩도 그대로 뒀다 — 그건 실제 서버 대기이므로 성격이 다르다.

이 상태에서 깜빡임은 사라졌지만 **변화가 뚝 끊기는 느낌**이 남았다.

### 0431 — 진짜 원인

네트워크 탭을 열었다. 페이지를 넘기는 순간 **이미지 요청이 12개씩 새로 나갔다.** 처음 가는 페이지는 200 응답에 장당 216~294ms, 갔던 페이지로 돌아가면 304였다. 프로덕션 빌드에서도 같았다.

**깜빡임은 그리는 문제가 아니라 배달 문제였다.** 카드가 폴백으로 떴다가 이미지가 도착하는 대로 채워지는 그 구간이 실체였고, 전환 기법으로는 감출 수 없다.

해법은 미리 받아두는 것인데, 함정이 하나 있었다.

```ts
// 커버 이미지 sizes — 인접 페이지 프리로더(PlanListClient)가 같은 srcSet을 얻으려면
// getImageProps에 이 값을 그대로 넣어야 한다.
// 단일 소스: 아래 <Image>와 프리로더가 공유(한쪽만 바꾸면 캐시 어긋남).
export const PLAN_CARD_SIZES = '(max-width: 767px) 100vw, 400px';
```

`next/image`는 원본이 아니라 `/_next/image?url=…&w=…` 최적화 URL을 요청한다. **원본을 프리로드하면 카드가 요청하는 주소와 달라 아무 효과가 없다.** 그래서 URL을 손으로 조립하지 않고 카드와 **같은 props**를 `getImageProps`에 넣어 같은 `srcSet`을 얻었다.

```ts
const preloadedRef = useRef<Set<string>>(new Set());

useEffect(() => {
  for (const coverUrl of adjacentCovers) {
    if (preloadedRef.current.has(coverUrl)) continue;   // 중복 요청 방지
    preloadedRef.current.add(coverUrl);
    try {
      const { props } = getImageProps({ src: coverUrl, alt: '', fill: true, sizes: PLAN_CARD_SIZES });
      const img = new Image();
      img.onerror = () => {};        // 실패는 조용히 무시
      if (props.sizes)  img.sizes  = props.sizes;
      if (props.srcSet) img.srcset = props.srcSet;
      img.src = props.src;           // srcSet 미지원 폴백
    } catch { /* getImageProps 실패도 무시 */ }
  }
}, [adjacentKey]);
```

`srcset`과 `sizes`를 그대로 넘겨 **브라우저가 카드 렌더 때와 동일한 후보를 고르게 위임했다.** 우리가 `w` 값을 계산하면 DPR이나 뷰포트 차이로 어긋난다.

`deps`에는 배열이 아니라 문자열을 넣었다.

```ts
// 매 렌더 새 배열이라 effect 재실행 방지용 문자열 키(내용이 바뀔 때만 실행).
const adjacentKey = adjacentCovers.join('|');
```

프리로드 범위는 인접 한 페이지씩이고 경계에서는 조건부다. 전체를 미리 받으면 안 볼 이미지까지 받는 낭비가 된다.

### 0432 — 기초자치단체 전수

`MUNICIPALITIES`를 소스로 두고 `CITY_TO_PROVINCE` Map을 파생시켰다.

```ts
대구: ['중구', '동구', '서구', '남구', '북구', '수성구', '달서구', '달성군', '군위군'],
      // 군위군: 2023.7 경북→대구 편입
강원: ['춘천시', '원주시', '강릉시', …, '고성군', '양양군'],
      // 고성군: 강원·경남 공유 → 강원에 배정(임의 선택, 어느 쪽이든 회색 방지는 달성)
세종: [],   // 기초자치단체 없는 단층제
```

**주석에 판정 이력을 남겼다** — 군위군의 대구 편입(2023), 인천 남구→미추홀구 개칭(2018), 고성군의 임의 배정. 나중에 "왜 경북에 군위군이 없지"를 다시 파지 않아도 된다.

접미는 무차별로 만들지 않았다.

```ts
for (const [key, cities] of Object.entries(MUNICIPALITIES)) {
  for (const full of cities) {
    if (AMBIGUOUS_DISTRICTS.has(full)) continue;
    CITY_TO_PROVINCE.set(full, key);
    const base = full.replace(/[시군구]$/, '');          // 접미 1자만 제거
    if (base !== full && !BASE_SKIP.has(base)) CITY_TO_PROVINCE.set(base, key);
  }
}
```

**정식명을 소스로 두고 뒤 한 글자를 떼서 `base`를 파생한다.** `경주` + 접미 3종을 곱하는 방식이면 `경주군` 같은 존재하지 않는 조합이 맵에 들어간다.

이름이 겹치는 것은 두 방식으로 막았다.

```ts
// 전국에서 여러 광역시가 공유하는 자치구 이름 — 단일 토큰으로 시·도 구분 불가(반드시 오배정).
const AMBIGUOUS_DISTRICTS = new Set(['중구', '동구', '서구', '남구', '북구', '강서구']);
const BASE_SKIP = new Set(['광주']);  // 경기 '광주시'의 base. '광주'는 광주광역시로 확정.
```

`AMBIGUOUS_DISTRICTS`는 정식명·base 둘 다 등록하지 않고, `BASE_SKIP`은 **정식명은 살리고 base만 차단한다.** `광주시`는 경기로 가되 `광주`는 광주광역시로 남는다.

판정은 2단이 됐다.

```ts
// 판정 순서: ① 시·도 사전(약칭·정식명·별칭) → ② 시·군·구 매핑(0432) → ③ null.
return FREE_TEXT_ALIAS.get(firstToken) ?? CITY_TO_PROVINCE.get(firstToken) ?? null;
```

**시·도 사전이 항상 우선이다.** `광주`처럼 양쪽에 있을 수 있는 토큰이 광역시로 확정되고, `BASE_SKIP`과 함께 이중 방어가 된다.

테스트에서 `경주`가 **실패 케이스에서 성공 케이스로 옮겨갔다.**

```ts
it.each([
  ['경주', '경북'], ['강릉시', '강원'], ['영월군', '강원'], ['강남구', '서울'],
])('시·군·구 이름은 소속 시·도로 수렴(0432): %s → %s', …)
```

실패 케이스는 `['없는도시시'], ['중구']`로 교체됐다. `중구`가 남아 있는 게 중요하다 — 공유 자치구 제외가 의도대로 동작하는지를 직접 검증한다.

## 5. 결과 / 배운 것

### 결과

- 전 구간에서 마지막 줄이 꽉 찬다 — 열 1·2·3·4·6 + 페이지 12
- 글쓰기·상세 진입 시 목록 스켈레톤이 안 뜬다(하위 라우트 첫 스트림에서 셔머 0회 실측)
- 페이지 전환에서 빈 구간·번쩍임이 사라졌다
- 시·군 이름으로 지역을 적어도 커버가 붙는다 — 더미 재생성에서 **커버 null 6개 → 0개**

### 배운 것

**증상을 세 번 고쳐서 안 되면 진단이 틀린 것이다.** 깜빡임을 네 번 고쳤다.

| 시도 | 결과 |
|---|---|
| 0427 순차 페이드 | 가운데가 비어 깜빡임 |
| 0429 스켈레톤으로 채움 | 대기가 0이라 한 프레임만 스쳐 번쩍임 |
| 0430 즉시 교체 | 공백은 없지만 변화가 뚝 끊김 |
| (0431 이전) 페이드인만 | 여전히 깜빡임 |

네 번 다 **렌더 층**을 만졌고 네 번 다 증상이 남았다. 그때 코드를 더 고치는 대신 네트워크 탭을 열었어야 했다. 실측하니 이미지 12장이 그제서야 요청되고 있었고, **원인이 렌더가 아니라 로드**라는 게 한 번에 드러났다. 지금은 규칙으로 만들어 뒀다 — **같은 증상을 세 번 고쳐서 안 되면 코드를 멈추고 측정한다.**

**같은 구조라도 조건이 다르면 결과가 다르다.** 0427·0429는 스토리의 전환 연출을 정확히 이식한 것이었다. 그런데 스토리가 부드러운 이유는 구조가 아니라 **서버 대기가 가운데를 채워주기 때문**이었고, 플랜파인더는 그 칸이 0ms다. 구조를 아무리 정확히 베껴도 이 차이는 안 메워진다. **"스토리와 같게"라는 요구를 구조 복사로 읽은 것이 두 번의 실패를 만들었다.**

**최적화 계층이 있으면 프리로드도 그 계층을 통과해야 한다.** `next/image`가 요청하는 건 원본이 아니라 최적화 URL이다. 원본을 미리 받아두면 캐시가 안 맞아 효과가 0이다. `getImageProps`에 카드와 같은 props를 넣어 같은 `srcSet`을 얻고 브라우저에 후보 선택을 위임하는 게 유일하게 맞는 방식이었다.

**감으로 만든 목록은 반드시 샌다.** 유명 관광도시 40개를 추렸는데 실제 촬영지가 있는 안성·과천·영월·구리·양주가 하나도 없었다. 스튜디오가 수도권 외곽에 있다는 도메인 사실이 직관을 뒤집었다. **전수를 넣는 비용이 목록을 관리하는 비용보다 낮다면 전수가 맞다** — 행정구역은 정적 데이터라 자주 안 바뀌고, 바뀌어도 실패 양상이 지금과 같다(null 폴백).

**되돌리는 것도 결과다.** 0430은 0427·0429를 전부 지운 커밋이다. 코드가 순수하게 줄기만 했지만, 그 과정에서 "이 화면에는 전환이 필요 없다"는 판단이 남았고 그 근거를 주석에 적었다. 다음에 누가 같은 연출을 넣으려 할 때 그 주석이 막아준다.

### 남긴 것

- 스켈레톤 그리드 클래스가 **본체와 리터럴로 중복**돼 있다. Tailwind JIT이 완전 리터럴만 스캔해 상수로 못 뽑았고, 상호 참조 주석으로만 방어한다
- 프리로드는 인접 한 페이지씩이라 **들어오자마자 1초 안에 넘기면** 아직 안 끝난 상태일 수 있다. 그건 어떤 방법으로도 못 없애는 잔여다
- 도시 매핑이 주는 건 **"회색 카드가 안 뜬다"까지다.** 풀은 시·도 단위라 여수 플랜이 받는 건 전남 풀 10장이지 여수 사진이 아니다. 도시별 풀 세분화는 무명 도시에 자기 사진이 없어 성립하지 않는다
