## 1. 한 줄 요약
새 계획 작성을 '제목 폼 → 상세' 두 단계에서, 빈 편집기 한 화면에서 입력 즉시 반영되고 마지막에 한 번 저장하는 구조로 바꿨다.

## 2. 왜 / 목적 / 이유 — 두 단계를 한 화면으로 통합
- **왜(동기/문제):** 작성이 두 화면으로 나뉘면, 비용을 다는 뒤 화면에서 앞 화면의 맥락(특히 목적·영감)이 안 보인다. 사용자가 "이 여행을 왜 가는지"를 놓친 채 숫자만 채우게 되어 맥락이 끊긴다.
- **목적(도달 상태/사용자 가치):** 목적·기간·일정·비용이 한 화면에 한눈에 들어오고, 입력하는 즉시 전체에 반영되는 경험.
- **이유(의사결정):** 두 단계를 하나의 편집기로 합치고, 화면 전체를 단일 state(`EditorState`)에서 그려 입력 즉시 반영 + 저장은 마지막에 한 번. 맥락 단절을 없애는 게 핵심.

## 3. 작성한 프롬프트
(실제 보낸 프롬프트로 교체·보강 — 4단계 골자)
```
[배경] 새 계획이 '제목 폼 → 상세' 두 단계라 작성 중 맥락이 끊김.
[목표] 빈 편집기 한 화면에서 입력 즉시 반영 + 한 번 저장.
[하지 말 것] ❌ 자동 저장 ❌ 저장 전 서버 왕복
[검수 모드] EditorState 단일 출처 / 날짜 변경 시 항목 보존
plan 요청.
```

## 5. 결과 / 배운점
- **결과:** 한 화면에서 작성·실시간 반영·한 번 저장 완성. 카테고리별 비용 집계 실시간 표시.
- **배운점:**
  - 항목 식별은 인덱스·생성시각이 아니라 **id** — 같은 날 항목이 여럿일 때 삭제·수정이 안 엉킨다.
  - 파생 값(카테고리 합계)은 state로 두지 않고 **계산** — 단일 출처라 동기화 버그가 없다.
  - 저장은 **트랜잭션**으로 묶고 ownerId는 **세션**에서 — 원자성 + 보안.
  - 면접 포인트: "왜 한 화면이냐"의 답은 기술이 아니라 **맥락 유지라는 UX 원칙**.
