# 0148-0150 회고: 관리자 작품명 관리기능 추가

2026.07.02 / 약 4시간 30분 / 관련 커밋: `feat: 0148 관리자 권한 기반 도입`, `fix: 0148 story layout 관리자 링크 누락 수정`, `feat: 0149 관리자 작품 관리 사이클 완성`, `fix: 0150 지도 검색 이동 위치 어긋남 수정`

## 1. 한 줄 요약

사용자 작품 제출(PENDING) → 관리자 검토(승인/거절/병합/되돌리기)의 전체 사이클을 구축하고, 그 과정에서 마이그레이션 미적용 미스터리와 지도 이동 버그(3겹)를 확증 기반으로 해결했다.

## 2. 왜 / 목적 / 이유

**왜 (동기/문제):** 촬영 작품명을 사용자마다 다르게 입력하면("오징어 게임" vs "오겜") 카테고리가 흩어져 검색이 망가진다. 자유 입력은 허용하되 흩어진 표기를 하나로 모을 사람 — 관리자 — 가 필요했다.

**목적 (목표 상태):** 사용자는 목록에 없는 작품명을 자유롭게 제출할 수 있고, 관리자는 제출된 작품을 기존 작품과 비교해 승인·병합·거절할 수 있는 상태. 표기 변형이 시간이 갈수록 자동 정리되는 구조.

**이유 (채택 근거, 결정별):**

- **role 컬럼 방식 (vs JWT custom claims):** 관리자가 1명뿐이고 Prisma로 User 테이블을 이미 관리 중. JWT 훅 설정의 복잡도가 규모 대비 과함. 확장 시 custom claims 전환 스토리는 면접용으로 보존.
- **관리자 승격 UI를 만들지 않음 (DB 직접 UPDATE만):** 앱 안에 승격 경로가 없으면 권한 상승 공격 표면 자체가 제거됨. 권한 이양 기능도 같은 이유 + 발생 빈도(관리자 1명)로 YAGNI 판단.
- **layout 가드 + 액션별 requireAdmin 이중 구조:** Next.js에서 layout의 접근 차단은 페이지 렌더만 막고 Server Action 호출은 못 막는다. 액션은 layout을 거치지 않는 별도 엔드포인트이므로, 모든 관리자 액션 첫 줄에서 role을 재검증.
- **거절 시 Movie만 삭제, Spot은 보존 (movieId만 null):** 작품명은 관리자 관할인 분류 정보지만, 촬영지 기록(좌표·리뷰·사진)은 사용자의 자산. 관리자 권한은 분류까지만 미친다. 회원 탈퇴를 익명화로 처리한 것과 같은 사상.
- **병합은 PENDING→APPROVED 단방향:** 방향이 고정되면 관리자가 헷갈릴 일이 없고 구현이 단순. 단, 실사용에서 오승인이 비가역이라는 경계 비용이 드러나 unapproveMovie(승인 되돌리기)를 당일 추가 — 기존 도구들이 상태(status) 기준으로 동작하도록 설계돼 있어, 상태만 되돌리면 병합 버튼이 자동 재활성됨.
- **지도 이동을 map.jump()로 (vs prop 동기화):** react-kakao-maps-sdk는 center와 level을 별개 layout effect로 분리 호출한다(소스 확증). 중심+레벨 동시 변경은 카카오 공식 원자 API인 jump()가 정답.

// lib/admin/guard.ts — 권한 검증 중앙화
export async function requireAdmin() {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) throw new AdminGuardError('UNAUTHENTICATED');
  const profile = await prisma.user.findUnique({
    where: { id: user.id }, select: { role: true },
  });
  if (profile?.role !== 'ADMIN') throw new AdminGuardError('FORBIDDEN');
  return user;
}

## 5. 결과 / 배운점

**결과:** 제출→검토 사이클 작동 (오승인 복구 포함 5종 도구). 지도 검색 이동 정상화. 커밋 4건 푸시.

**배운점:**

1. **검증 쿼리가 부정확하면 그 위의 모든 추론이 무너진다.** role 컬럼 존재를 SQL로 "확인"했지만 `table_schema='public'` 조건이 빠져 auth.users의 내장 role을 본 것이었다. 이 잘못된 전제("DB엔 있다") 위에서 풀러 오염 가설·프로젝트 재시작·포트 변경까지 40분을 헛걸음했다. 앱의 에러는 처음부터 정직했다. '확인했다'와 '정확하게 확인했다'는 다르다.
2. **아는 절차도 빼먹는다 — 지식이 아니라 체크리스트의 문제.** 마이그레이션 4단계 우회는 0121에서 직접 실행해본 절차인데, 이번엔 db execute가 통째로 누락됐다(history로 확증). plan의 "적용 순서" 섹션은 읽는 문서가 아니라 한 줄씩 지워나가는 체크리스트로 다뤄야 한다.
3. **수정 대상은 파일명이 아니라 사용처 전수 조사로 잡는다.** 관리자 링크가 /story에서만 안 보인 원인은 NavLinks를 쓰는 layout이 두 개였기 때문. grep 전수 조사가 5분 만에 확정했다.
4. **버그는 겹으로 온다 — 한 겹 벗기면 다음 겹이 드러난다.** 지도 버그는 ① ref/prop 이중 조종 ② panTo-setLevel 경합 ③ SDK의 분리 호출, 세 겹이었다. 각 단계에서 "고쳤는데 안 됨"이 아니라 확증(코드 인용→SDK 소스→공식 문서)으로 다음 겹을 특정했기에 미궁에 빠지지 않았다.
5. **상태 중심 설계는 배당금을 준다.** 도구들을 status 기준으로 동작하게 만들어두자, 오승인 복구가 "상태 되돌리기" 하나로 완성됐다(병합 버튼 자동 재활성). 흐름 중심으로 짰다면 복구 경로를 따로 이어붙여야 했을 것이다.
