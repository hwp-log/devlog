## 1. 한 줄 요약

플랜파인더 목록을 텍스트 행에서 커버 사진 카드로 바꾸고, 그 카드에 넣을 사진을 어디서 가져올지를 정하는 체계를 만들었다.

---

## 2. 왜 / 목적 / 이유

### 왜 (동기·문제)

플랜파인더 목록이 아바타와 카테고리 비율(%)이 늘어선 4열 행 리스트였다. 스토리·스팟파인더는 이미 시각 우선으로 정리돼 있는데 이 화면만 표 같았고, 색이 전부 하드코딩(`slate-*`, `sky-500`, 리터럴 hex)이라 다크 모드가 아예 없었다.

시안을 적용하려 하니 선행 문제가 드러났다. **카드가 커버 사진을 전제로 하는데 플랜에는 사진이 없었다.** `MyPlan`에 이미지 필드 자체가 없고, `PlanSpot`은 `Spot`을 참조하지 않아 촬영지 사진을 끌어올 경로도 없었다.

### 목적 (도달하려는 상태)

- 목록 카드가 사진 위에 정보를 얹는 형태가 되고, 라이트·다크 양쪽에서 읽힌다
- 플랜을 만들면 사람이 아무것도 하지 않아도 커버가 붙는다
- 그 사진이 무작위가 아니라 그 플랜과 관련이 있다

### 이유 (채택 근거)

**색 이관을 먼저 뗀 이유** — 카드 구조를 바꾸면서 색까지 같이 만지면 다크에서 깨졌을 때 원인이 구조인지 색인지 안 갈린다. 레이아웃 무변경으로 색만 옮기는 커밋을 앞에 뒀다.

**커버를 업로드가 아니라 자동 부여로 정한 이유** — 업로드 UI를 붙이면 반나절이 나가고, 사용자가 사진을 안 올리면 카드가 비는 건 그대로다. 이미 갖고 있는 자산(촬영지 커버 45장, 관광공사 API)으로 자동으로 채우면 사용자 행동에 의존하지 않는다.

**인원수를 계산에 안 쓰기로 한 이유** — 카드에 "1인당 얼마"를 띄우려다 조사에서 막혔다. 항공편 API를 `adults: '1'`로 하드코딩해 붙여둬서 `PlanFlight.totalAmount`가 이미 1인 기준이고, 여기에 인수를 또 나누면 항공비만 중복으로 나뉜다. 나머지 비용이 인원 총액인지 1인분인지는 자유 입력이라 데이터에 답이 없다. **정확히 하려면 비용 항목마다 "1인당/전체" 구분이 필요하고 그건 입력 폼까지 걸리는 별건**이라, 인수는 나누는 데 쓰지 않고 메타 줄에 표시만 하기로 했다.

**금액을 band 중앙값으로 표기한 이유** — `summarizePlanCost`가 정밀 총액을 클라이언트로 안 보내고 구간(band)만 내보내는 구조였다. 시안대로 `약 38만원`을 쓰려면 그 설계를 바꿔야 하는데, 중앙값(`(lower+upper)/2`)이면 "약"이라는 말에 걸맞은 근사치이면서 서버가 정밀 총액을 안 내보내는 구조를 그대로 둘 수 있다. 필터·정렬이 이미 `band.lower` 기준이라 코드 변경도 최소였다.

### 0404 — 지역 이미지 풀 (`prisma/seed-region-covers.ts`, 신규)

파일 헤더에 설계 전제를 남겼다.

```ts
// 0404: 지역 대표 이미지 풀 생성. KorService2 searchKeyword2(지역명 검색)로 firstimage 수집.
// 런타임 TourAPI 호출 회피용 사전 시드 — 결과는 region-covers.json에 통째로 write(재실행 안전).
// 가로/세로 판별 없음: searchKeyword2 응답에 치수 필드가 없고, 카드 커버는 중앙 크롭이라 세로도 수용.
// firstimage 원격 URL만 저장(Storage 미복사 — 기존 선례 유지). 스크립트 전용, 런타임 호출 아님.
const REGIONS = ['서울', '제주도'] as const;
const PER_REGION_MAX = 10; // 지역당 최대 채택(8~10 목표)
const NUM_OF_ROWS = 30;    // 후보 여유(로드 실패·중복 컷 감안)
```

핵심은 **로드 검증 게이트**다. API가 URL을 준다고 그 URL이 실제로 뜨는 건 아니다.

```ts
// 로드 검증 — 200 + content-type image/* 만 통과 ("저장됨 ≠ 표시됨" 방지)
async function isLoadableImage(url: string): Promise<boolean> {
  try {
    const res = await fetch(url, { redirect: 'follow', signal: AbortSignal.timeout(8000) });
    const ct = res.headers.get('content-type') || '';
    await res.arrayBuffer();
    return res.status === 200 && ct.startsWith('image/');
  } catch { return false; }
}
```

수집 흐름은 `API 호출 → firstimage 있는 것만 → http→https → 중복 제거 → 게이트 통과분만 누적`이다.

```ts
for (const region of REGIONS) {
  const items = (await searchKeyword(region)).filter((i) => i.firstimage && i.firstimage.trim());
  const seen = new Set<string>();
  const urls = items
    .map((i) => i.firstimage!.replace(/^http:\/\//, 'https://'))
    .filter((u) => (seen.has(u) ? false : (seen.add(u), true)));

  const accepted: string[] = [];
  for (const u of urls) {
    if (accepted.length >= PER_REGION_MAX) break;
    if (await isLoadableImage(u)) accepted.push(u);
    await delay(250);  // rate limit
  }
  regions[region] = accepted;
}
```

**가로/세로 판별을 넣지 않은 판단**이 주석에 남아 있다. JPEG 치수 파싱은 PNG처럼 고정 위치가 아니라 SOF 마커를 찾아 세그먼트를 순회해야 해서 파서가 잘못 짜이면 멀쩡한 사진이 조용히 걸러진다. 카드 커버는 중앙 크롭이라 세로 풍경도 위아래만 잘리고 중앙이 남아 대체로 봐줄 만하다. **30장을 눈으로 훑는 게 파서를 짜는 것보다 싸다**고 봤다.

결과 JSON은 `_source` 메타와 `regions`를 2층으로 분리했다. 지역 키와 메타 키가 같은 층에 있으면 읽는 쪽에서 밑줄 키를 걸러내야 해서 실수 여지가 생긴다.

### 0405 — 커버 부여 (`lib/plan/region-cover.ts`, 신규)

```ts
// 0405: 지역 문자열 → region-covers.json(0404) 풀에서 커버 URL 1개 무작위 선택.
// 런타임 TourAPI 호출 없음(사전 시드 JSON만 읽음). 매칭 실패 시 null(호출부에서 커버 미부여).
import coversData from '../../prisma/region-covers.json';
const pools: Record<string, string[]> = coversData.regions;

// 지역명 첫 토큰 → 풀 키 별칭. 지역 추가 시 여기만 손본다.
const REGION_ALIAS: Record<string, string> = {
  서울: '서울', 서울특별시: '서울',
  제주도: '제주도', 제주: '제주도', 제주특별자치도: '제주도', 제주시: '제주도',
};

export function normalizeRegionKey(region: string | null | undefined): string | null {
  if (!region) return null;
  const firstToken = region.trim().split(/\s+/)[0];
  const key = REGION_ALIAS[firstToken];
  if (key && pools[key]?.length) return key;
  return null;
}
```

`region`이 자유 입력이라 `제주도 서귀포시`, `서울 용산구 이태원`처럼 시·도 뒤에 뭐가 붙는다. **첫 토큰만 잘라 별칭 맵으로 정규화**하면 뒤에 뭐가 오든 풀 키에 수렴한다. 처음에는 정확 일치로 짰다가 `서울특별시`·`제주` 같은 표기가 전부 실패하는 걸 보고 별칭을 넣었다.

`normalizeRegionKey`가 빈 풀까지 걸러내므로 `pickRegionCover`는 인덱싱 전에 빈 배열을 다시 검사하지 않는다.

```ts
export async function pickPlanCover(movie, region, excludePlanId?): Promise<string | null> {
  const { movieCovers, all } = await collectCandidates(movie, region);
  if (all.length === 0) return null;

  // 후보 URL만 집계(전체 행 미수집). 집계에 없는 URL은 0회로 취급.
  const grouped = await prisma.myPlan.groupBy({
    by: ['coverUrl'],
    where: { coverUrl: { in: all }, ...(excludePlanId ? { id: { not: excludePlanId } } : {}) },
    _count: { coverUrl: true },
  });

  const countOf = new Map<string, number>();
  for (const g of grouped) if (g.coverUrl) countOf.set(g.coverUrl, g._count.coverUrl);

  const minCount = Math.min(...all.map((u) => countOf.get(u) ?? 0));
  const minUrls  = all.filter((u) => (countOf.get(u) ?? 0) === minCount);

  // 최소 집합에 작품 후보가 있으면 작품 후보 중 무작위, 없으면 남은 것 중 무작위
  const movieSet = new Set(movieCovers);
  const movieMin = minUrls.filter((u) => movieSet.has(u));
  const pickFrom = movieMin.length > 0 ? movieMin : minUrls;
  return pickFrom[Math.floor(Math.random() * pickFrom.length)];
}
```

## 5. 결과 / 배운 것

### 결과

- 목록이 커버 사진 카드로 바뀌고 라이트·다크 양쪽에서 읽힌다
- 플랜을 만들면 커버가 자동으로 붙는다. 기존 5개는 백필로 채웠고 **5/5 전부 매칭 성공**
- `PlanCard`는 122줄이 지워지고 83줄이 들어왔다 — 표시 정보를 줄였더니 코드도 줄었다
- 커버 선택은 **후보 URL만 대상으로 하는 groupBy 1회**라 플랜이 몇만 개가 돼도 돌아오는 행이 20개 이하다

### 배운 것

**화면 하나를 만들려다 데이터 모델의 구멍을 발견했다.** 카드에 "1인당 얼마"를 띄우려던 것뿐인데, 조사에서 항공편이 `adults: '1'`로 하드코딩돼 있고 비용 항목에 인원 개념이 없다는 게 드러났다. 그때 만들 때는 화면에 안 드러나던 문제라 알 수가 없었고, 표시하겠다고 하는 순간에야 보였다. **3일 안에 정확히 고칠 수 없다고 판단해 표시 범위를 줄이는 쪽을 택했다** — 인수는 정보로만 보여주고 나눗셈은 하지 않는다.

**"저장됨 ≠ 표시됨"을 게이트로 만들었다.** API가 이미지 URL을 준다고 그게 실제로 뜨는 건 아니다. `status 200 + content-type image/*`를 확인하는 함수 하나가 나중에 죽은 링크가 카드에 박히는 걸 막는다. 이건 촬영지 커버 백필에서 이미 겪은 문제라 그 선례를 그대로 가져왔다.

**정확한 파서보다 눈으로 훑는 게 쌀 때가 있다.** 가로/세로 판별을 넣으려다 JPEG 치수 파싱의 위험(잘못 짜면 멀쩡한 사진이 조용히 걸러짐)을 보고 접었다. 30장짜리 데이터에서는 사람이 보는 게 빠르고, 이상하면 그때 넣으면 된다.

**eslint가 잡은 건 스타일 위반이 아니라 실제 결함이었다.** `react-hooks/refs`가 렌더 중 `ref.current` 읽기를 잡았는데, 파보니 `ref`는 리렌더를 유발하지 않아 `baseDelay`가 애초에 갱신될 수 없는 구조였다. **화면 결과에 영향을 주는 값이면 `state`**라는 원칙으로 되돌리니 규칙도 통과하고 의도도 명확해졌다. 규칙을 우회(`eslint-disable`)했으면 결함이 그대로 남았다.

**범위를 좁히는 지시가 스스로를 막을 수 있다.** 0402에서 `my-plan 수정 금지`를 걸어놓고 상세 화면 이관을 목표에 넣었는데, 그 상세의 흰 카드가 `my-plan`과 공용이라 고칠 길이 없었다. 금지 목록을 쓸 때 **그 파일이 어디까지 공유되는지**를 먼저 봐야 한다.

### 남긴 것

- 커버가 **부여 시점에 `MyPlan.coverUrl`로 복사·저장**된다. 나중에 `Spot.coverUrl`이나 지역 풀을 고쳐도 이미 만들어진 플랜은 안 바뀐다(재부여 필요) — 이 성질이 뒤에 여러 번 발목을 잡는다
- 지역 풀이 서울·제주도 2종뿐이라 그 외 지역은 커버가 안 붙는다
- 관광공사 `searchKeyword2`는 그 지역의 아무 POI나 주기 때문에 **사진이 그 플랜과 무관하다**. 이 문제가 다음 구간의 주제가 된다
