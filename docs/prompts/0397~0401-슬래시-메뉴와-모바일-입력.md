## 1. 한 줄 요약

모바일에서 키보드가 화면을 먹는 상황을 전제로 슬래시 메뉴와 입력 동작을 다듬었고, 그 과정에서 "키보드에 무언가를 앵커한다"는 접근 자체를 웹앱에 부적합하다고 판단해 접었다.

## 2. 왜 / 목적 / 이유

**왜(문제)** — 네 가지가 모바일 키보드와 얽혀 있었다.

1. 검색으로 스팟을 추가하면 이름 입력칸에 커서가 붙어 키보드가 올라오고, 그 바람에 지도가 가려졌다. 위치를 확인하며 리뷰를 써야 하는 화면인데 방해가 됐다.
2. 본문에서 `/`로 슬래시 메뉴를 연 뒤 스크롤하면 메뉴가 원래 자리에 남아 본문과 따로 움직였다. 모바일은 메뉴 높이가 부족해 반드시 스크롤해야 하므로 실사용에서 항상 걸렸다.
3. 입력칸을 탭하면 화면이 확대되고 포커스가 풀려도 돌아오지 않았다.
4. 슬래시 메뉴가 키보드 유무에 따라 크기가 달라져 모양이 일정하지 않았다.

**목적** — 키보드가 올라와도 화면이 흔들리지 않고, 메뉴가 캐럿을 따라가되 항상 같은 모양인 상태.

**이유** — 슬래시 메뉴의 높이 부족을 두고 노션이 어떻게 푸는지 조사했더니, 노션은 모바일에서 슬래시를 주 진입로로 쓰지 않고 키보드 위 가로 툴바를 쓴다. 즉 **높이 부족을 푼 게 아니라 그 문제가 생기는 구조(키보드 위에 뜨는 세로 팝업)를 피한 것**이었다. 같은 방향으로 키보드 부착 툴바를 검토했으나, 모바일 웹은 브라우저 크롬이 함께 관여하고 iOS 26에는 키보드 해제 후 `visualViewport.offsetTop`이 복귀하지 않는 버그가 있어 불안정하다고 판단해 접었다. 대신 0398의 `size()` 클램프로 이미 만들어진 "작고 내부 스크롤되는 메뉴" 형태를 모바일에서 상시 유지하는 쪽을 택했다.

## 4. 코드 작성 & 수정

### 0397 — 자동 포커스 (`SpotPopup.tsx`, `SpotMap.tsx`)

찍기와 검색이 다르게 동작하는 코드 근거가 없었다. `autoFocus`는 공유 `SpotPopup` 한 벌이고 두 경로가 같다. 실제 차이는 **iOS의 user-gesture 휴리스틱**이었다 — 검색은 DOM 버튼 탭이라 키보드가 뜨고, 찍기는 지도 클릭 + `await`를 거쳐 억제된다.

```tsx
// 모바일은 키보드가 지도를 가리므로 자동 포커스 제거, 데스크톱은 유지
<SpotPopup autoFocusName={!isMobile} ... />
```

`autoFocus`를 끄는 것은 제스처 타이밍과 무관하게 성립하는 처방이다.

### 0398 — 캐럿 추적 (`SlashCommand.tsx`)

일회성 `computePosition`에서 `autoUpdate` 기반으로 전환했다. 참조가 캐럿(가상 요소)이므로 `contextElement`에 에디터 dom을 물려 스크롤 조상까지 감지하게 했다.

배치는 세 번 바꿨다.

| 시도 | 결과 |
|---|---|
| `bottom-start` + `flip()` | 스크롤 중 위아래로 튐 — `flip`이 아래 공간에 따라 뒤집음 |
| `top-start`, `flip` 제거 | 튐은 없으나 본문과 헤더를 가림 |
| **`bottom-start`, `flip` 제거** | 채택 |

앵커가 화면 밖일 때는 처음에 `visibility:hidden`으로 숨기게 했으나 "툭 사라진다"는 판정으로 같은 커밋 안에서 걷어냈다(중간 산물이라 커밋에는 흔적이 없다). 대신 z-index를 헤더(sticky z-10)보다 낮춰, 스크롤로 캐럿이 올라가면 메뉴가 헤더 뒤로 밀려 들어가게 했다.

여기서 요구 하나가 **자체 모순**이었다. "z를 헤더(10)보다 아래, 탭바(40)보다 위로" — 10 < 40이므로 단일 z로 양립할 수 없다. 헤더 뒤 tuck을 우선해 z-9를 유지하고, 탭바 가림은 z가 아니라 `size()`의 `padding.bottom`으로 **공간을 예약해 물리적으로 회피**했다.

```ts
// 탭바 rect를 실측해 그 top까지 예약 — safe-area 자동 반영,
// 데스크톱은 탭바가 lg:hidden이라 height 0 → 예약 8px로 무변
const bottomReserve = tb && tb.height > 0 ? window.innerHeight - tb.top + 8 : 8;
```

`size()`로 가용 높이를 CSS 변수에 주입해 넘치면 내부 스크롤하게 하고(`overscroll-none`, 0389 선례), `selectedIndex` 변경마다 `scrollIntoView({block:'nearest'})`로 키보드 이동 시 선택 항목이 보이게 했다.

태그 입력 옆 '추가' 버튼도 함께 제거했다 — 데스크톱·모바일 모두 Enter로 들어가므로 불필요하고, Enter 경로와 `isComposing` 가드는 그대로 뒀다.

### 0399 — 자동확대 (`SpotPopup.tsx`)

입력 표면을 전수 조사해 16px 미만인 두 곳만 고쳤다.

| 위치 | 현재 폰트 | 판정 |
|---|---|---|
| 제목 / 태그 / 플랜 select | 21~23px / 16·14 / 16·14 | 통과 |
| 본문 `.ProseMirror` / 장소 검색 / 스팟 이름 | 16px | 통과 |
| **스팟 리뷰 textarea** | 14px | 수정 |
| **작품명 검색 input** | 14px | 수정 |

콜아웃 문단 14px은 고치지 않았다. 포커스를 받는 호스트가 `.ProseMirror`(16px)이므로 확대 대상이 아니다.

`viewport` 메타의 `maximum-scale`·`user-scalable=no`로 막는 우회는 WCAG 2.1 위반이라 채택하지 않았다.

### 0400 — 크기 고정 (`SlashCommand.tsx`)

키보드가 올라온 상태에서는 `size()` 클램프가 작동해 잘 쓰이는데, 키보드를 내리면 공간이 생겨 메뉴가 커지면서 모양이 달라졌다.

```ts
// 상한이지 하한이 아니다 — 좁으면 그에 맞춰 줄어든다
const target = isMobile ? Math.min(MOBILE_MAX_H, availableHeight) : availableHeight;
```

`MOBILE_MAX_H = 208` 근거: 항목 1행 약 52px(`py-2` 16 + 2줄 텍스트 약 36) + 라벨 약 24 + 상단 6 → 라벨 + 3.5행이면 212px이고, 항목 2~3개 + 스크롤 어포던스가 드러나는 선에서 208로 내려 잡았다. 산식은 근사이고 상수는 실측 조정값이다.

스티키 라벨 위로 항목이 비치던 문제도 함께 고쳤다. 원인은 스크롤 셸의 `padding-top`이었다 — `sticky top:0`은 **패딩 박스 상단**에 붙으므로 그 위 6px 밴드가 노출된다.

```diff
- 셸: p-1.5          라벨: pt-1.5
+ 셸: px-1.5 pb-1.5  라벨: pt-3      (총 12px 유지)
```

### 0401 — 떨림 (`SlashCommand.tsx`)

`autoUpdate` 기본은 스크롤·리사이즈 리스너 기반이라 캐럿 같은 가상 참조를 한 프레임 늦게 따라가고, 그것이 떨림이 된다.

```ts
autoUpdate(virtualEl, el, reposition, { animationFrame: true });
// 위치는 top/left → transform: translate3d (레이어 승격)
// 좌표는 물리 픽셀 그리드에 스냅
const rx = Math.round(x * dpr) / dpr;
```

닫힘 시 `destroy`가 `cleanup()`으로 rAF 루프를 정지시킨다(`onExit`·Escape 연결). `size()` 계산은 `offsetWidth/Height` 기준이라 `transform`과 무관해 정확성이 유지된다.

## 5. 결과 / 배운점

### 결과

- 검색으로 추가해도 키보드가 올라오지 않아 지도가 보인다.
- 슬래시 메뉴가 스크롤에 따라 캐럿을 따라가고, 헤더 뒤로 밀려 들어간다.
- 모바일에서 키보드를 올렸다 내려도 메뉴 크기가 일정하다.
- 입력칸 탭 시 화면이 확대되지 않는다.
- 데스크톱 떨림은 해소, 모바일 관성 스크롤 구간에는 미세 잔여가 남는다.

### 배운점

- **같은 코드가 경로에 따라 다르게 동작하면 원인은 코드 밖에 있을 수 있다.** 찍기와 검색의 키보드 차이는 분기가 아니라 iOS의 user-gesture 휴리스틱이었다. 코드에서 근거를 못 찾았을 때 "없는 분기를 찾는" 대신 플랫폼 동작을 의심해야 했다.
- **참고 대상이 문제를 "푼" 게 아니라 "피한" 것일 수 있다.** 노션은 슬래시 팝업의 높이 문제를 해결한 게 아니라 모바일에서 그 구조를 안 쓴다. 벤치마킹할 때 해법만 보면 그 해법이 성립하는 전제를 놓친다.
- **웹앱에서 키보드에 앵커하는 접근은 피하는 편이 낫다.** iOS는 키보드 시 layout viewport를 그대로 두고 밀어올리기만 하며 사용자가 스크롤하면 그 보정이 풀린다. iOS 26에는 해제 후 `offsetTop`이 복귀하지 않는 버그도 있다. 네이티브는 OS가 툴바 자리를 보장하지만 웹은 그게 없다.
- **요구가 자체 모순일 수 있다.** "헤더(10)보다 아래, 탭바(40)보다 위"는 단일 z로 만족 불가능했다. 이때 답은 우선순위를 정하고 **다른 축으로 푸는 것**이었다 — z가 아니라 레이아웃 공간 예약.
- **상한과 하한을 구분해야 한다.** 고정 크기를 하한으로 두면 공간이 없을 때 화면 밖으로 나간다. 상한으로만 두면 좁을 땐 줄고 넓을 땐 안 커져 "항상 같은 모양"이 성립한다.
- **`position: sticky`는 패딩 박스 상단에 붙는다.** 스크롤 컨테이너에 `padding-top`이 있으면 그 밴드로 콘텐츠가 비친다. 여백은 sticky 요소 자신이 갖게 해야 한다.
- **`flip()`은 스크롤 중 튐의 원인이 된다.** 한 방향 고정이 필요하면 `flip`을 빼고 `size()`로 클램프 + 내부 스크롤이 정석이다.
- **완전히 해결되지 않는 것을 그렇다고 적어야 한다.** iOS 관성 스크롤의 잔여 떨림은 `animationFrame: true`로도 남는다. 정공법(같은 스크롤 컨테이너 안 `absolute`)은 좌표계·tuck·예약을 다시 잡아야 해 범위가 크다는 것까지 함께 남겼다.

### 남은 것 / 후속

- 슬래시 메뉴 모바일 관성 스크롤 미세 떨림 — 남으면 `fixed` 대신 에디터 스크롤 컨테이너 안 `absolute`(구조 변경, 큼).
- 캐럿이 탭바 바로 위인 극단 상황에서 메뉴 하단 일부가 탭바 뒤로 들어간다(사라짐 방지를 우선한 결과).
- 모바일 블록 입력의 주 진입로를 툴바로 옮기는 방향은 보류. 키보드 앵커 없이 성립하는 형태(에디터 상단 sticky 툴바 등)라면 재검토 가능.
