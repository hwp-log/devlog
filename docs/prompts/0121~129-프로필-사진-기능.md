## 1. 한 줄 요약

프로필 사진을 클라이언트가 Storage에 직접 업로드하고 Server Action엔 URL만 넘기는 구조(옵션 B)로 만들되, "본인 폴더만 허용"이라는 한 가지 규칙을 앱 계층(Server Action 가드)과 DB 계층(Storage RLS) 두 곳에서 막아 이중으로 방어했다. 삭제·교체 때는 DB(avatarUrl)를 먼저 정리하고 Storage 파일을 나중에 지워 화면에 깨진 이미지가 뜨는 중간 상태를 없앴고, 스키마 추가(0121)에서 Supabase shadow DB 벽에 부딪혀 마이그레이션 우회 패턴을 세웠다. 사진 표시는 모양이 같은 화면(원형 24px) 3곳만 공용 컴포넌트로 묶고, 모양·크기가 다른 화면(말풍선·헤더)은 fallback 로직만 공유했다.

## 2. 왜 / 목적 / 이유

### 삭제 순서 — DB(포인터)를 먼저 끊고 Storage(실물)를 나중에 지운다 (0124)

- 왜: removeAvatar에서 "Storage 파일 먼저 → DB 나중"으로 가면, DB의 `avatarUrl`이 이미 사라진 파일을 계속 가리키는 순간이 생긴다. 화면은 `avatarUrl`을 진실의 출처로 삼아 `<img src={avatarUrl}>`로 Storage를 불러오는데, 대상이 없으니 404가 떨어지고 깨진 이미지 아이콘이 뜬다. "포인터는 살아있는데 가리키는 대상이 없는" 모순 구간이다.
- 목적: 삭제 도중 어느 시점에 화면을 봐도 "아바타 있음" 또는 "아바타 없음" 둘 중 하나로만 보이는, 깨진 중간 상태가 없는 일관성.
- 이유:
  1. 화면은 DB(`avatarUrl`)를 보고 Storage 이미지를 불러온다. 그래서 **포인터(DB)를 먼저 끊으면**, Storage 파일이 잠깐 고아로 남아도 아무도 그걸 안 가리키니 화면은 즉시 "아바타 없음"(이니셜 fallback)으로 깔끔하게 빠진다.
  2. 반대 순서는 "가리키는데 없는" 404 구간을 만든다. 앱이 죽는 게 아니라, 화면이 계속 불러오려다 깨진 이미지가 뜨는 게 사용자 눈에 보이는 증상이다.
  3. 이건 removeAvatar만의 얘기가 아니라 **삭제 순서의 일반 원칙**이다 — "참조하는 쪽(DB 포인터)을 참조당하는 쪽(Storage 실물)보다 먼저 정리한다." DB 외래키 삭제, 캐시 무효화도 같은 논리다. 가리키는 걸 먼저 끊는다.
  4. **이 순서는 CC 제안을 그대로 받은 게 아니라, 역질문으로 바로잡은 결정이다.** CC의 첫 plan은 removeAvatar를 updateAvatar와 반대로 "Storage 먼저 → DB null"로 짰는데, "DB를 null로 먼저 갱신하면 즉시 이니셜 폴백이라 Storage 삭제가 실패해도 깨진 이미지가 안 뜬다"고 짚어 순서를 뒤집었다. ③의 0124 프롬프트가 그 순간이다.

### 이중 방어 — 같은 "본인 폴더" 규칙을 앱과 DB 두 계층에서 막는다 (0122 · 0124)

- 왜: 프로필 사진을 옵션 B(클라가 Storage에 직접 업로드 → Server Action엔 URL만 전달)로 만들면, 클라가 넘기는 URL을 그대로 믿을 수 없다. 남이 `{피해자id}/...` 경로의 URL을 위조해 넘기면 다른 사람 자리에 사진을 끼워 넣을 수 있다.
- 목적: 클라가 어떤 URL을 넘기든, "본인 폴더가 아닌 것"은 앱에서도 DB에서도 통과하지 못하는 상태.
- 이유:
  1. **앱 계층 가드 (Server Action).** `updateAvatarAction`이 DB 저장 전에 `extractAvatarPath(newUrl, user.id)`로 두 겹을 검사한다 — (a) URL이 우리 `avatars` 버킷 public prefix로 시작하나, (b) prefix를 떼고 남은 경로가 `{본인 user.id}/`로 시작하나. 둘 중 하나라도 어긋나면 즉시 `잘못된 아바타 URL입니다`로 차단한다. 단, 이건 **경로 위조 차단**이지 "이 URL에 진짜 이미지가 있나"까지 검증하는 건 아니다(존재하지 않는 파일이면 화면에서 깨진 이미지로 드러날 뿐, 권한 문제는 아니다).
  2. **DB·Storage 계층 RLS (Storage 정책 4개).** 앱을 우회해 Storage API를 직접 때려도, `storage.objects`의 RLS가 한 번 더 막는다. 쓰기 3종(INSERT/UPDATE/DELETE) 정책에 공통으로 `auth.uid()::text = (storage.foldername(name))[1]`이 들어간다 — 경로를 폴더 배열로 쪼개 최상위 폴더가 로그인 사용자 UUID와 일치할 때만 허용. 즉 같은 "본인 폴더" 규칙을 DB 계층에서 다시 강제한다.
  3. **읽기는 일부러 연다.** SELECT 정책만 `TO public`이라 누구나 폴더 조건 없이 읽는다. 프로필 사진은 공개 자원이라 읽기를 잠그면 오히려 안 보인다. "읽기는 공개, 쓰기만 소유자로 잠금"이라는 비대칭이 의도다.
  4. **UPDATE만 USING + WITH CHECK 양쪽이다.** USING은 "수정 대상 행을 고를 때" 본인 것만 보이게 하고, WITH CHECK는 "수정 결과가 어디로 가는지"를 검사한다. WITH CHECK가 없으면 본인 파일을 골라(USING 통과) 남의 폴더 경로로 옮기는 폴더이동 공격이 가능하다. 그래서 UPDATE만 양쪽에 같은 식을 넣었다.

### Supabase shadow DB 우회 마이그레이션 (0121)

- 왜: 0121에서 User 스키마에 `avatarUrl`을 추가하려고 `prisma migrate dev`를 돌렸는데 `ERROR: schema "storage" does not exist`로 멈췄다. `migrate dev`는 drift 검증을 위해 빈 shadow DB를 임시로 만들어 모든 마이그레이션을 재실행하는데, 이 레포의 옛 마이그레이션 `20260523074954_storage_rls`가 Supabase 전용 `storage` 스키마를 참조한다. 깡통 shadow DB엔 그 스키마가 없어 거기서 막힌다.
- 목적: shadow DB를 거치지 않고도 마이그레이션을 안전하게 적용하고, 히스토리에도 정상 기록되는 상태.
- 이유: 문제의 뿌리는 "Supabase의 비표준 스키마(`storage`)에 RLS를 걸어둔 게, 이후 모든 일반 마이그레이션을 막는다"는 구조적 마찰이다. 그래서 shadow DB를 만드는 `migrate dev` 자체를 피하고, 마이그레이션 파일을 수동 작성해 `db execute`로 직접 적용한 뒤 `migrate resolve`로 히스토리에 "적용됨"만 기록하는 우회를 세웠다(4단계는 ④에). 이 패턴은 프사 기능에 한정된 게 아니라 이후 모든 마이그레이션에 적용되는 표준이 됐다. (다만 현재 레포 문서/AGENTS.md에는 이 절차가 적혀 있지 않다 — 흔적은 `package.json`의 `db:execute` 스크립트, `prisma.config.ts`의 DIRECT_URL datasource, 마이그레이션 폴더 명명 패턴뿐이다. 이 회고가 그 미문서화를 메우는 첫 기록이다.)

### 공용화는 두 층위로 나눈다 — 모양은 컴포넌트, 규칙은 함수 (0126 · 0128 · 0129)

- 왜: 같은 프로필 사진을 여러 화면에 표시하다 보면 중복이 쌓인다. 그렇다고 모든 화면을 한 컴포넌트로 묶으려 하면, 화면마다 크기·모서리가 달라 props(size, borderRadius...)가 폭발한다.
- 목적: 중복은 줄이되, 한 컴포넌트가 화면별 분기로 설정 덩어리가 되지는 않는 상태.
- 이유: "같은 것"이 무엇인지를 두 층위로 갈랐다. **모양·크기가 같은 화면**(원형 24px — Story 카드·Story 상세·PlanFinder 상세)은 `AuthorAvatar` 컴포넌트 하나로 공용화했다(`app/story/_components/` → `components/`로 이동, 0129). 반면 **모양·크기가 다른 화면**은 컴포넌트를 공유하지 않고 인라인으로 두되, "이니셜+색상 생성" 규칙은 같으니 `getAvatarInfo` 함수 하나로 공유했다 — 0126 PlanFinder 카드 말풍선(64px·좌하단만 각진 모양)과 0128 헤더 UserDropdown(32px, 카드의 24px와 크기 다름)이 그 사례다. 즉 같은 건 모양이 아니라 fallback 규칙이라고 본 것이다. 0114 회고의 "추상화 시점" 축보다 한 단계 정밀하다 — 무엇을 공용화하고 무엇을 안 할지를 모양·크기/로직으로 가른 판단이다.

### 곁가지 — 교체 때도 옛 파일을 정리한다 (0124)

- 왜: 새 사진으로 교체하면 옛 Storage 파일이 아무도 안 가리키는 고아로 남는다.
- 이유: `updateAvatarAction`이 DB를 새 URL로 바꾼 뒤, 옛 `avatarUrl`의 Storage 파일을 `remove`한다. 삭제(removeAvatar)든 교체(updateAvatar)든 Storage에 쓰레기를 남기지 않는다는, 위 삭제 순서와 같은 결의 정리 원칙이다.

-- SELECT: 모든 사람이 아바타 조회 가능 (퍼블릭 프사) — 읽기만 공개

FOR INSERT TO authenticated

### Server Action — 가드 + 삭제/교체 순서 (0124)

```ts
// app/(protected)/mypage/actions.ts (line 52~117)

// 앱 계층 가드: (a) 버킷 public prefix 일치 (b) 본인 폴더 일치 — 둘 다 통과해야 path 반환
function extractAvatarPath(url: string, userId: string): string | null {
  const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL!;
  const prefix = `${supabaseUrl}/storage/v1/object/public/avatars/`;
  if (!url.startsWith(prefix)) return null;          // (a) 버킷·도메인 prefix
  const path = url.slice(prefix.length);
  if (!path.startsWith(`${userId}/`)) return null;   // (b) 본인 폴더
  return path;
}

export async function updateAvatarAction(newUrl: string): Promise<{ error: string } | null> {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return { error: '로그인이 필요합니다' };

  // DB 저장 전 가드 — 본인 폴더 경로가 아니면 즉시 차단
  if (!extractAvatarPath(newUrl, user.id)) {
    return { error: '잘못된 아바타 URL입니다' };
  }

  const current = await prisma.user.findUnique({
    where: { id: user.id },
    select: { avatarUrl: true },
  });
  await prisma.user.update({
    where: { id: user.id },
    data: { avatarUrl: newUrl },
  });

  // 곁가지 — 교체 시 옛 Storage 파일 정리 (고아 방지)
  if (current?.avatarUrl) {
    const oldPath = extractAvatarPath(current.avatarUrl, user.id);
    if (oldPath) {
      await supabase.storage.from('avatars').remove([oldPath]);
    }
  }
  revalidatePath('/mypage');
  return null;
}

export async function removeAvatarAction(): Promise<{ error: string } | null> {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return { error: '로그인이 필요합니다' };

  const current = await prisma.user.findUnique({
    where: { id: user.id },
    select: { avatarUrl: true },
  });
  if (!current?.avatarUrl) return null;

  // 1) DB(포인터) 먼저 비우기 → 화면이 즉시 "아바타 없음"으로 빠짐
  await prisma.user.update({
    where: { id: user.id },
    data: { avatarUrl: null },
  });

  // 2) Storage(실물) 나중 삭제 → 잠깐 고아로 남아도 아무도 안 가리킴
  const oldPath = extractAvatarPath(current.avatarUrl, user.id);
  if (oldPath) {
    await supabase.storage.from('avatars').remove([oldPath]);
  }
  revalidatePath('/mypage');
  return null;
}
```

## 5. 결과 / 배운점

### 결과
- 프로필 사진을 업로드·교체·삭제하고, 사이트 전체(마이페이지·헤더·Story 카드/상세·PlanFinder 카드/상세·SpotFinder 출처 패널)에 표시한다. 옵션 B 구조에 앱 가드 + Storage RLS 이중 방어를 적용했고, 삭제·교체 시 깨진 이미지나 고아 파일이 남지 않는다. 0121 마이그레이션은 shadow DB 우회로 적용했고, 그 패턴이 이후 표준이 됐다. (커밋 9개 배포 완료.)

### 배운점
- **삭제·정리는 "참조하는 쪽을 먼저 끊는다."** 화면이 DB(`avatarUrl`)를 보고 Storage를 부르니, 포인터(DB)를 먼저 비우면 실물(Storage)이 잠깐 남아도 화면은 일관되다. 반대로 실물을 먼저 지우면 "가리키는데 없는" 404 구간이 생긴다. 외래키 삭제, 캐시 무효화도 같은 원칙이다. 이 순서는 CC가 짠 첫 plan을 그대로 따르지 않고 역질문으로 바로잡은 결정이었다 — 도구가 짜준 안에도 "왜 이 순서인가"를 되물어야 한다.
- **타입이 통과해도 데이터가 흐르는지는 별개다.** 0127에서 authorAvatarUrl을 옵셔널 타입으로 둬 tsc는 통과했지만, 실제 값이 쿼리·호출처를 안 거쳐 항상 이니셜만 뜰 뻔했다. 옵셔널 타입은 "없어도 되는 값"처럼 보여 런타임 누락을 숨긴다. 표시 기능을 추가할 때마다 `queries.ts` select → 호출처 전달까지 데이터 경로를 grep으로 끝까지 따라가야 한다.
- **신뢰 경계마다 같은 규칙을 다시 막는다.** 클라가 넘긴 URL은 앱에서(가드), Storage API 직접 호출은 DB에서(RLS) — "본인 폴더만"이라는 한 규칙을 두 계층에서 각각 강제했다. 한 곳이 뚫려도 다른 곳이 막는 이중 방어다. 그리고 읽기는 일부러 열고 쓰기만 잠근 비대칭이 "공개 자원의 소유권 보호"라는 의도를 드러낸다.
- **플랫폼의 비표준이 도구의 표준 절차를 깬다.** Supabase가 `storage` 스키마에 RLS를 두는 구조가, Prisma의 `migrate dev`(shadow DB 재실행)를 막았다. 도구가 안 돌 때 "왜 안 도나"를 플랫폼 구조까지 거슬러 올라가야 우회가 보인다. 그렇게 세운 패턴은 일회성이 아니라 표준이 되니, 레포에 문서로 남겨야 한다(이 회고가 그 시작).
- **공용화의 단위는 "보이는 모양"이 아니라 "같은 규칙"일 수 있다.** 모양·크기가 같은 화면(원형 24px 3곳)은 컴포넌트로, 모양·크기가 다른 화면(말풍선 64px·헤더 32px)은 로직(함수)으로 공유했다. 모든 걸 한 컴포넌트로 묶으려 하면 props가 폭발한다 — 무엇을 공용화하고 무엇을 안 할지를 가르는 게 추상화의 핵심이다.
