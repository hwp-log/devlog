## 1. 한 줄 요약

버블 선택 목록에서 "눌러도 아무 일이 없다", "선택이 풀린다"를 각각 추적했더니 셋 다 **판정은 정상인데 표현만 틀린 것**이었다.

---

## 2. 왜 / 목적 / 이유

### 왜 (동기·문제)

세 가지 증상이 겹쳐 있었다.

1. **눌러도 아무 일이 없다** — 인라인 코드가 걸린 텍스트에서 굵게·취소선이 안 걸렸다. 버튼은 멀쩡해 보이는데 반응이 없으니 고장난 것으로 읽혔다.
2. **비활성이 안 보인다** — 비활성 처리를 넣었는데 실기기에서 활성과 구분이 안 됐다.
3. **선택이 풀린다** — 목록을 열면 파란 선택 표시가 사라지고, 뒤로를 눌러도 안 돌아왔다.

### 목적 (목표 상태·사용자 가치)

**"할 수 있는 것과 없는 것이 눌러보기 전에 보이는 상태."** 사용자가 "고장났나"를 느끼는 건 눌렀는데 아무 일도 없을 때이지, 처음부터 회색이면 납득한다.

그리고 선택은 이 기능의 전제다. 목록 항목 대부분이 선택한 텍스트에 거는 것이라, 선택이 풀리면 기능 자체가 성립하지 않는다.

### 이유 (채택 근거·결정 기준)

**비활성 판정을 `editor.can()` 하나로 모은 것**이 첫 결정이다. 규칙을 직접 짜지 않고 Tiptap의 판정을 받아쓰면, 마크가 늘어도 자동으로 맞는다. 네 진입점(툴바·버블·ToolbarMore·BubbleMore)이 각자 판단하던 것을 한 맵으로 통일했다.

**조합 불가를 다루는 업계 방식은 셋**이다 — ① 비활성(워드·한글 표준) ② 조용한 교체(ProseMirror `excludes`, 당시 상태) ③ 설명. ①을 골랐다.

**행 비활성에 native `disabled`를 쓰지 않은 것**은 WAI-ARIA 메뉴 패턴 때문이다. native `disabled`는 포커스를 빼앗아 화살표 순회를 끊는다. `aria-disabled` + 실행 가드로 갔다.

### 0466 — 앵커를 선택 rect로

```tsx
// app/(protected)/story/new/BubbleMore.tsx
// 앵커는 ⋯ 버튼이 아니라 선택 rect 가상 엘리먼트. 트리거 앵커는 invisible 버블의
// 잔존 레이아웃 위(top-end여도 선택 위 ~68px = 버블 높이+오프셋 2회의 죽은 공간)에
// 목록을 띄워 그만큼 위 본문을 더 가리던 원인.
const { from, to } = editor.state.selection;
const virtualEl = {
  getBoundingClientRect: () => posToDOMRect(editor.view, from, to),
  contextElement: editor.view.dom,
};
return autoUpdate(virtualEl, pop, () => {
  computePosition(virtualEl, pop, {
    strategy: 'fixed',
    placement: 'top-end',
    middleware: [offset(8), flip(), shift({ padding: 8 })],
  }).then(({ x, y }) => {
    Object.assign(pop.style, { left: `${x}px`, top: `${y}px` });
  });
});
```

## 5. 결과 / 배운 점

### 결과

- code 마크 구간에서 다른 마크 항목이 회색으로 표시돼 "고장난 것처럼 보이던" 증상이 사라졌다
- 비활성이 실기기 다크 배경에서도 식별됐다
- 목록이 버블이 있던 자리에 얹혀 죽은 공간 약 60px을 회수했다
- 목록을 열어도 선택 표시가 유지됐고, `invisible` 배선을 통째로 철거했다

### 배운 점

**1. 셋 다 "판정은 맞는데 표현이 틀렸다"였다.**

- 마크 충돌: `can()` 배선은 정상인데 회색 처리가 없어 무반응으로 보였다
- 비활성 시각: `opacity-40`은 적용됐는데 이미 회색인 아이콘이라 대비 차가 안 났다
- 선택 풀림: PM `state.selection`은 무너지지 않았고 iOS가 **시각적으로만** 지웠다

세 번 다 배선을 다시 뜯을 뻔했다. 헤드리스로 값을 실측해 "안 오는 게 아니라 안 보이는 것"을 먼저 가른 것이 시간을 아꼈다.

**2. 상태 축을 나누지 않으면 색이 서로를 먹는다.**

`선택/hover = 배경 채움`, `비활성 = 콘텐츠 강등(배경 금지)`으로 축을 갈랐다. 축이 겹치면 비활성 행에 hover 배경이 얹혀 두 상태가 구분되지 않는다. 화살표 이동이 비활성 행을 건너뛰게 한 것도 같은 이유다.

**3. iOS는 탭에서 `mouseenter`만 발화하고 `mouseleave`가 없다.**

"안 풀리는 hover"의 정체가 CSS `:hover` 고착이 아니라 JS `selectedIndex` 잔존이었다. 비활성 행을 선택 대상에서 빼자 그 경로 자체가 사라졌다.

**4. 가설이 틀렸다는 것도 실증해야 한다.**

"`invisible`이 선택을 깬다"는 내 가설은 틀렸다. `prosemirror-view` 소스에서 blur 중 `selectionchange`를 게이팅하는 것을 확인하고, 헤드리스로 외부 focus 후에도 선택이 유지되는 것을 재봤다. 그러고 나서야 진짜 원인(auto-focus)에 닿았다.

**5. 웹에서 못 하는 것을 인정하는 데도 근거가 필요하다.**

iOS 자체 선택 메뉴는 `-webkit-touch-callout`이 iOS 15부터 동작하지 않고, 유일하게 통하는 `user-select: none`은 에디터에 쓸 수 없다. 차단이 불가능하다는 것을 확인한 뒤에야 `blur` 시도를 정당하게 접을 수 있었다.

## 결정 (Decisions)

- 적용 불가 표현은 **비활성**(워드·한글 방식) — "조용한 교체"는 무반응으로 읽혀 기각
- 판정 소스는 `editor.can()` 하나 — 규칙을 직접 짜지 않는다
- 행은 `aria-disabled` + 실행 가드, 버튼은 native `disabled` — 메뉴 순회 보존
- 상태 축 2개: 선택/hover = 배경 / 비활성 = 콘텐츠 강등
- iOS 자체 선택 메뉴 겹침 **수용** — 차단 불가 확정, `blur`는 선택을 깨 기각
- 작게 × 제목은 UI 비활성 + CSS 가드 두 겹 — 가드가 기존 저장 글 표시도 정상화
