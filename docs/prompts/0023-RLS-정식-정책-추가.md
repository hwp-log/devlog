USING vs WITH CHECK 차이 학습이 핵심.

> **RLS (Row Level Security)**
> Postgres의 행 단위 접근 제어 기능. Supabase에서 "본인 글은 본인만 본다" 정책을 DB 차원에서 강제할 때 사용.
> 0022 임시 정책에서 0023 정식 정책으로 단계적 강화.

> **anon key vs RLS 관계**
> anon key = Supabase 클라이언트 공개 API 키 (브라우저에 노출됨).
> RLS = DB 차원 행 접근 룰 (anon key 노출돼도 Supabase의 정책이 데이터 접근차단).
> 즉 anon key는 "공개 노출 OK" 설계. 진짜 보안은 RLS 정책이 담당.

> **USING vs WITH CHECK**
> USING = "기존 행 검사" (SELECT / UPDATE / DELETE 시점).
> WITH CHECK = "새 데이터 검사" (INSERT / UPDATE 시점).
> UPDATE는 둘 다 적용 = 수정 전 + 수정 후 검증.

## 이번 작업의 3가지 핵심 요소

### 1. anon key 공개 + RLS = 클라이언트 안전성 모델

Supabase는 anon key를 클라이언트(브라우저)에 노출하는 설계. Next.js의 NEXT_PUBLIC_ 접두사 환경변수는 빌드 타임에 자바스크립트 코드에 그대로 작성 됨.
즉 누구나 F12 개발자 도구로 anon key를 확인 가능. 그러나 이게 보안구멍은 아님.

**배운점**: 주니어 단골 오해 = "환경변수 = 비밀". 실제로는 NEXT_PUBLIC_ 접두사 환경변수 = 공개 자원. Supabase 보안 모델은 "API 키는 공개되어 있으니 보안은 DB 내부에서 챙긴다" 철학. 즉 anon key 노출 자체는 위험 X, RLS 정책이 행 단위로 막아주는 게 진짜 보안. 0022 시점 임시 정책으로 anon 차단까지만 작성, 0023 정식 정책으로 본인 행만 접근 가능하게 격리 완성. 면접에서 "환경변수 보안 어떻게 하나요?" 질문 받으면 "Supabase 환경에서 anon key는 공개 전제 + RLS가 진짜 보안" 답변 가능.

### 2. USING vs WITH CHECK 차이

PostgreSQL RLS 정책의 두 가지는 적용 시점이 다름. USING은 "기존 행을 보여줄/변경할 권한이 있나" 검사, WITH CHECK은 "새 데이터를 추가/수정한 결과가 정책 조건을 만족하나" 검사.

**배운점**: 4개 정책의 패턴이 작업 본질에 따라 다름.

| 정책 | USING | WITH CHECK | 이유 |
|------|-------|-----------|------|
| SELECT | O | X | 기존 행 검사만 (조회) |
| INSERT | X | O | 새 데이터 검사만 (기존 행 없음) |
| UPDATE | O | O | 수정 전(USING) + 수정 후(CHECK) 둘 다 검증 |
| DELETE | O | X | 삭제 전 검사만 (삭제 후 행 없음) |

UPDATE에 USING + WITH CHECK 둘 다 적용한 이유 = 사용자가 자기 행을 수정하면서 user_id를 타인 것으로 변경하는 시나리오 차단. USING은 "이 행 수정 시도 가능?" + WITH CHECK은 "수정된 결과가 여전히 본인 user_id?" 둘 다 검증해야 user_id 탈취 차단. 면접에서 "USING과 WITH CHECK 차이?" 질문 시 시점 + 작업 본질 둘 다 풀이 가능.

### 3. 단계적 도입 흐름 (임시 → 정식)

0022에서 임시 정책(`FOR ALL TO authenticated USING (true) WITH CHECK (true)`) 작성. anon 차단까지는 박혀있지만 인증 사용자끼리는 모든 행 접근 가능 상태. 0023에서 임시 정책 DROP 후 정식 정책 4개로 교체.

**배운점**: 0022 시점에 정식 정책 박으면 Supabase 학습 본질이 흐려짐(작업 진행 + 정책 학습 동시 진행). 임시 정책으로 anon 차단까지만 적용한 뒤 0022 회고에서 "0023에서 정식 정책 적용" 약속, 0023에서 RLS 학습 및 적용에 집중. git history에 단계별 흔적 박혀있어서 면접에서 "왜 단계적으로?" 질문 시 의도성 답변 가능. "0022 임시 정책 = 작업 진행 가능 상태 + anon 차단까지, 0023 정식 정책 = 본인 행 격리 + 학습 모드 깊이" 흐름 명확.

## 코드 작성 내용 (실제 결과물)

### 1. 임시 정책 제거 (DROP)

```sql
-- 0022에서 작성한 임시 정책 제거
DROP POLICY "auth_users_full_access_temp" ON til_entries;
```

### 2. 정식 정책 4개 (신규)

```sql
-- supabase/migrations/20260512_rls_policies_til_entries.sql
-- 0023: til_entries RLS 정식 정책 적용 (사용자 격리)

-- SELECT: 본인 행만 조회 가능
CREATE POLICY "users_can_select_own_til" ON til_entries
  FOR SELECT
  TO authenticated
  USING (auth.uid() = user_id);

-- INSERT: 본인 user_id로만 작성 가능
CREATE POLICY "users_can_insert_own_til" ON til_entries
  FOR INSERT
  TO authenticated
  WITH CHECK (auth.uid() = user_id);

-- UPDATE: 본인 행만 수정 가능 + 다른 user_id로 변경 X
CREATE POLICY "users_can_update_own_til" ON til_entries
  FOR UPDATE
  TO authenticated
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

-- DELETE: 본인 행만 삭제 가능
CREATE POLICY "users_can_delete_own_til" ON til_entries
  FOR DELETE
  TO authenticated
  USING (auth.uid() = user_id);
```

### 3. 정책 검증 쿼리

```sql
SELECT policyname, cmd, roles, qual, with_check
FROM pg_policies
WHERE tablename = 'til_entries';
```

결과:

| policyname | cmd | roles | qual (USING) | with_check |
|---|---|---|---|---|
| users_can_select_own_til | SELECT | {authenticated} | auth.uid() = user_id | NULL |
| users_can_insert_own_til | INSERT | {authenticated} | NULL | auth.uid() = user_id |
| users_can_update_own_til | UPDATE | {authenticated} | auth.uid() = user_id | auth.uid() = user_id |
| users_can_delete_own_til | DELETE | {authenticated} | auth.uid() = user_id | NULL |
