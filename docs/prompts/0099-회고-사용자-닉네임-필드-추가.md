# 0099 회고: 사용자 닉네임 필드 추가

- 작성일: 2026-06-14
- 소요: 약 2시간

---

## 1. 한 줄 요약

User 모델에 nickname 필드를 NOT NULL로 추가하고, 기존 유저 전원에게 `여행자_` + UUID 앞 4자리 형태의 기본 닉네임을 백필했다. 신규 가입은 가입 액션에서 같은 형식으로 자동 부여한다. 마이그레이션은 0089처럼 Prisma 7 수동 방식으로 처리하고, 여러 번 실행해도 안전하도록 멱등성을 줬다.

---

## 2. 왜 / 목적 / 이유

### nickname을 NOT NULL + 기존 유저 백필

- 왜: nickname은 공개 피드(스토리·CostPlan 목록·상세)의 작성자 자리에 항상 표시돼야 하는 값이다. nullable로 두면 어떤 유저는 값이 있고 어떤 유저는 null이라, 작성자를 표시하는 모든 화면에 "null이면 어떻게 보여줄까" 분기를 넣어야 한다.
- 목적: "nickname은 무조건 있다"가 DB 레벨에서 보장돼서, 표시 코드 전체가 분기 없이 그냥 갖다 쓰는 상태.
- 이유: NOT NULL로 두면 null 가능성이 데이터 입구(DB)에서 막혀, 그 뒤의 모든 표시 코드가 단순해진다. 다만 NOT NULL 제약은 빈 행이 하나라도 있으면 걸 수 없으므로, 기존 유저를 먼저 백필해야 제약을 걸 수 있다 — NOT NULL과 백필은 한 묶음이다.

> 백필값 `여행자_A3F2`는 빈 임시값이 아니라 그 자체로 유효한 닉네임이라, 사용자가 바꾸지 않아도 화면이 정상 동작한다. 가입 시 기본 아바타를 자동 지정해두는 것과 같다 — 기본값을 주되 사용자가 원하면 마이페이지(0100)에서 교체할 수 있다.

### 백필값을 UUID 앞 4자리로 생성

- 왜: 기존 유저 전원에게 서로 다른 기본 닉네임을 줘야 하는데, 무작위로 만들면 마이그레이션을 다시 돌릴 때 값이 달라진다.
- 목적: 같은 유저에게는 항상 같은 기본 닉네임이 나오는 결정론적(deterministic) 상태.
- 이유: 각 유저의 UUID 앞 4자리를 대문자로 변환해 `여행자_A3F2` 형태로 만들었다. UUID는 유저마다 고정이라 몇 번 실행해도 같은 값이 나온다. 표시용 기본값이라 굳이 unique 제약은 걸지 않았다(중복 허용).

### Prisma 7 수동 마이그레이션 + 멱등성

- 왜: Prisma 7 + Supabase 조합에서 자동 마이그레이션이 매끄럽지 않아, 0089부터 SQL을 직접 작성해 Supabase에서 실행하는 수동 방식을 쓴다. 수동 SQL은 손이 미끄러져 두 번 실행될 수 있다.
- 목적: 마이그레이션 SQL을 두 번 실행해도 같은 결과가 나오는(멱등) 상태.
- 이유: 컬럼 추가에 `IF NOT EXISTS`, 백필 UPDATE에 `WHERE nickname = ''` 조건을 줘서, 이미 적용된 상태에서 다시 실행해도 중복 변경이 일어나지 않게 했다.

## 4. 코드 작성 & 수정

### 수정: `prisma/schema.prisma`

User 모델에 nickname 추가. NOT NULL이되 `@default` 없음 — 가입 액션이 항상 값을 제공하므로 DB default를 두지 않는다.

```prisma
model User {
  id        String   @id @db.Uuid
  email     String   @unique
  nickname  String   @db.VarChar(20)   // NOT NULL, @default 없음
  createdAt DateTime @default(now()) @map("created_at")
  // ...
}
```

### 신규: `prisma/migrations/20260611120000_add_nickname_to_users/migration.sql`

3단계. NOT NULL을 걸려면 기존 행을 먼저 채워야 하므로, 임시 DEFAULT로 컬럼을 추가해 NOT NULL을 만족시킨 뒤 백필하고, default를 제거한다.

```sql
-- Step 1: NOT NULL 만족용 임시 DEFAULT로 컬럼 추가 (멱등 보장)
ALTER TABLE "users" ADD COLUMN IF NOT EXISTS "nickname" VARCHAR(20) NOT NULL DEFAULT '';

-- Step 2: 기존 유저 백필 — UUID 앞 4자 대문자 조합
UPDATE "users"
SET "nickname" = '여행자_' || upper(substr(id::text, 1, 4))
WHERE "nickname" = '';

-- Step 3: DB default 제거 (이후 INSERT는 앱이 항상 nickname 제공)
ALTER TABLE "users" ALTER COLUMN "nickname" DROP DEFAULT;
```

> 결과 예시: `여행자_A3F2`. DROP DEFAULT가 안전한 근거 — supabase/migrations 전수 조회 결과 `handle_new_user` 트리거 미존재, public.users INSERT 경로는 signUp 단 하나라 앱이 항상 nickname을 제공한다.

### 수정: `lib/auth/actions.ts`

signUp의 user.create에 nickname 추가. 마이그레이션 백필과 동일한 포맷으로 일관성 유지.

```ts
await prisma.user.create({
  data: {
    id: data.user.id,
    email: data.user.email!,
    nickname: '여행자_' + data.user.id.slice(0, 4).toUpperCase(),
  },
});
```

### 적용 순서 (수동 마이그레이션)

1. schema.prisma 수정 (파일 변경만)
2. migration.sql 파일 생성
3. Supabase SQL 에디터에서 migration.sql 실행 (실제 컬럼 추가·백필·default 제거)
4. `prisma migrate resolve --applied 20260611120000_add_nickname_to_users`
5. `prisma generate`
6. `npx tsc --noEmit`

## 5. 결과 / 배운점

- 검증 통과: `SELECT COUNT(*) FROM users WHERE nickname IS NULL OR nickname = ''` 결과 0건(기존 유저 전원 백필), `SELECT id, nickname` 결과 `여행자_XXXX` 형태 확인, 신규 가입 시 nickname 자동 부여.
- 배운점 1: NOT NULL과 백필은 한 묶음이다. "값이 항상 있다"를 DB에서 보장하려면 빈 행을 먼저 채워야 제약을 걸 수 있고, 그 보장 덕에 표시 코드 전체가 null 분기 없이 단순해진다. 제약을 입구에 두면 그 뒤가 가벼워진다.
- 배운점 2: `prisma/migrations/`와 `prisma/sql/`는 역할이 다르다. migrations는 테이블·컬럼 구조 변경(DDL)을 기록하고, sql 폴더는 Prisma 스키마로 표현할 수 없는 RLS(Row Level Security, 행 단위 접근 보안) 정책을 따로 모은다. 비유하면 migrations는 집 구조(방·벽), sql은 출입 규칙(누가 들어올 수 있나)이다. 이번 nickname은 구조 변경뿐이라 migrations에만 있고, 닉네임을 공개로 읽되 이메일은 막는 규칙은 표시 단계에서 따로 처리한다(0093 원칙 연장).
- 배운점 3: 수동 SQL은 멱등성을 챙겨야 안전하다. `IF NOT EXISTS`와 `WHERE nickname = ''`로 두 번 실행해도 같은 결과가 나오게 했다.
