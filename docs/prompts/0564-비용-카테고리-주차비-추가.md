비용 카테고리를 5종 → 6종으로 확장(주차비 추가). DB enum·TS 유니온·라벨·배열 순서·색 토큰(라이트/다크)·색 맵 2곳을 한 벌로 갱신하고, 선행 작업으로 소비처 0인 사장된 맵 2종을 제거했다.

## 2. 왜 / 목적 / 이유

### 주차비를 독립 카테고리로
- **왜**: — 기존엔 주차비가 `ETC`(기타)로 들어갔고, 실제 DB에도 그렇게 들어간 행이 1건 있었다.
- **목적**: 기록 없음
- **이유**: 기록 없음
### 배열 위치 = 교통 다음
- **왜**: `CATEGORIES` 배열 순서가 폼 select 옵션(2곳)·소유자 뷰 카테고리 줄·요약 계산 순회를 동시에 정한다. 어디에 넣든 동작은 같아 순서는 순수하게 읽기 비용 문제.
- **목적**: 사용자가 실제로 훑는 두 곳(select·카테고리 줄)에서 스캔 비용을 낮춤.
- **이유**: 교통↔주차는 "이동에 드는 돈"으로 한 덩어리다. 의미가 인접한 항목이 물리적으로 인접해야 목록에서 눈이 덜 튄다. `ETC`는 "나머지"라는 성격상 관례대로 맨 뒤 유지.
  (누적 막대는 비중 내림차순 정렬이라 이 순서의 영향을 받지 않는다.)

### 색 = 라임(#cfe0a2 / #a8c85f)
- **왜**: 7번째 색이 필요한데, 누적 막대는 비중 순 정렬이라 **어떤 두 색이든 인접할 수 있다**. 특정 쌍만 피하는 선택이 성립하지 않는다.
- **목적**: 기존 6색 **전부**와 갈리는 색 하나.
- **이유**: 판정 기준선을 "이미 붙어도 갈린다고 확정된 쌍"에서 가져왔다 — 기존 6색끼리의 최소 색차(CIEDE2000) 라이트 10.7 / 다크 12.1(둘 다 교통/입장료 쌍). 후보 6종 중 **라이트·다크 양쪽에서 이 기준선을 넘긴 건 라임뿐**(12.5 / 17.5). 코랄은 다크 13.9로 항공과 아슬아슬한 데다 항공·숙박·주차가 전부 난색이 되고, 마젠타·틸·슬레이트는 라이트에서 기준선 미달(9.0 / 10.2 / 10.6).
  색상환으로도 같은 답이 나온다: 기존 hue 배치에서 항공 41° → 기타 152° 사이 111°가 유일한 큰 공백이고, 그 중앙이 라임 95°. 나머지 인접 간격(46~49°)과 동형이라 "한 자리가 비어 있어서 채웠다"에 가깝다.

### 사장된 맵을 먼저 지운 것
- **왜**: `CATEGORY_COLOR`·`CATEGORY_ICON`은 `Record<CostCategory, …>`라 소비처가 0인데도 카테고리를 추가할 때마다 값을 채워야 컴파일된다.
- **목적**: 이번 추가의 유지보수 비용을 미리 없앰.
- **이유**: 순서가 본질이다. 뒤로 미뤘으면 죽은 코드에 PARKING 값을 채워 넣은 뒤 지우게 된다. 0562에서 PlanTimeline·calc-cost-summary·화석 액션을 같은 이유로 정리한 것과 같은 판단.

## 4. 코드 작성 & 수정

### 사전 조사 — enum 소비처 전수

`CostCategory`는 **5종**이었다(TRANSPORT·ACCOMMODATION·FOOD·ENTRANCE·ETC).
프롬프트의 "6종(…항공…)"에서 항공(`FLIGHT`)은 enum 밖 — `PlanFlight` 별도 테이블에서
오고 UI에서만 `CostCategory | 'FLIGHT'` 합성 타입으로 붙는다.
따라서 이번 작업은 **enum 5→6종, 화면 색 6→7색**.

### 2. DB enum 확장 (`6769a91`)

```prisma
// 이 enum은 app/(protected)/my-plan/_lib/cost.ts의 CostCategory 유니온과 수기 복제 관계다
// (자동 파생 아님). 값을 고치면 그쪽 유니온·CATEGORIES·라벨·색 맵까지 같이 봐야 한다.
enum CostCategory {
  TRANSPORT
  ACCOMMODATION
  FOOD
  ENTRANCE
  ETC
  PARKING // 0564: 화면 순서는 CATEGORIES 배열이 정하므로 여기 위치는 무의미(맨 뒤 append)
}
```

```sql
-- prisma/migrations/20260808120000_add_cost_category_parking/migration.sql
-- 0564: 비용 카테고리 "주차비" 추가. 값 확장만 — 기존 행 무영향(백필 없음).
--   ALTER TYPE ... ADD VALUE는 트랜잭션 블록 안에서 실행할 수 없다. Prisma는 마이그레이션을
--   트랜잭션으로 감싸므로 migrate dev 경로로는 실패한다 → 수기 SQL + db execute +
--   migrate resolve --applied 경로로 반영했다(shadow DB 충돌 우회 관례와 동일).
ALTER TYPE "CostCategory" ADD VALUE 'PARKING';
```

반영 절차 (CLI는 nvm 22.22.3 — 레포 node는 20.9.0):

```bash
prisma db execute --file prisma/migrations/20260808120000_add_cost_category_parking/migration.sql
prisma migrate resolve --applied 20260808120000_add_cost_category_parking
prisma generate
prisma migrate status   # → 29 migrations found / Database schema is up to date!
```

`prisma db execute`에 `--schema` 플래그는 없다(Prisma 7 — datasource URL은 `prisma.config.ts`에서 읽음).

## 5. 결과 / 배운점

### 결과
- `npx tsc --noEmit` 통과.
- `npm test` — 6 스위트 / 8 테스트 실패. 기존 실패 목록(auth 5 스위트 + SpotPopup)과 **완전 일치** → 회귀 없음.
- `prisma migrate status` — 29 migrations, up to date.
- 실화면 7색 인접 판정: — 실 토큰 값으로 만든 대조 시안(라이트/다크 × 전체 인접 4종 + 주차비 1:1 6쌍 + 카테고리 점)을 별도 전달. 최종 판정은 플랜파인더 상세 실화면에서.

### 배운점
- **인접 판정의 기준선은 문헌이 아니라 레포 안에 있었다** — "ΔE 몇 이상이면 갈린다"는 일반 수치 대신, 이미 화면에서 붙어 쓰이며 확정된 최소 쌍(교통/입장료 10.7·12.1)을 기준선으로 삼았다. 같은 화면·같은 크기·같은 배경에서 나온 값이라 후보 비교가 곧 판정이 된다.
- **누적 막대는 "인접 쌍"을 고를 수 없다** — 비중 내림차순 정렬이라 어떤 두 색이든 붙을 수 있다. 그래서 새 색은 특정 이웃이 아니라 **기존 전부**와의 최소 색차로 평가해야 했다.
- **`Record<타입, …>`는 죽어도 유지보수 비용을 남긴다** — 소비처 0인 맵도 유니온이 늘면 값을 채워야 컴파일된다. 사장 시점에 지우지 않으면 확장할 때마다 세금이 붙는다. 그래서 삭제를 확장보다 **먼저** 했다.
