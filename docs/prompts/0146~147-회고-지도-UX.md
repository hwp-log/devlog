---

## 1. 한 줄 요약

스토리 작성의 여행동선 지도에서 "사용자 조작을 지도가 따라가게" 만들었다. 검색 결과를 고르면 그 위치로 지도가 이동·확대(0146), 여행순서를 드래그로 잡으면 그 항목의 마커로 지도가 이동(0147). 부모(mapRef)-자식(SpotList) 경계는 prop 콜백으로 연결했다.

---

## 2. 왜 / 목적 / 이유

### 0146 검색 선택 시 지도 이동

- **왜**: 검색해서 마커를 찍어도 지도가 그대로여서, 마커가 현재 보이는 영역 밖이면 안 보였다. 사용자는 "검색이 됐나?" 혼란스러웠다.
- **목적**: 검색 결과를 고르면 지도가 그 위치로 따라가 마커가 화면에 보이게 한다.
- **이유**: `handlePlaceSelect`에 `panTo` + `setLevel(3)`(동네 수준 확대)를 추가. 이 컴포넌트에 이미 있던 panTo 패턴(handleSpotSelect)을 재사용. 검색 즉시가 아니라 **항목 선택 시점**에 이동한다 — 검색하자마자 첫 결과로 튀면 안 고른 곳으로 흔들리기 때문.

### 0147 드래그 시작 시 마커로 이동

- **왜**: 여행순서를 드래그로 바꿀 때, 확대된 상태에서는 지금 잡은 항목이 어느 마커인지 지도에서 안 보였다.
- **목적**: 드래그로 항목을 잡으면 그 마커로 지도를 센터 이동해 "지금 이걸 만지는 중"을 시각적으로 연결한다.
- **이유**: 드래그 리스트는 자식(SpotList)에 있고 `mapRef`는 부모(SpotMap)에만 있다. 그래서 SpotList에 `onDragStart` 콜백 prop을 추가하고, 부모에서 그 콜백으로 `panTo`를 호출한다. 확대(level)는 건드리지 않고 센터 이동만 — 사용자가 이미 배치·확대해둔 상태를 유지한다.

## 3. 작성한 프롬프트

(요지. 실제 원문은 커밋 작업 기록에서 옮긴다.)

- **0146**: handlePlaceSelect에 panTo + setLevel. `[하지 말 것]` 제어형 center 전환 금지(sync 루프), 검색 즉시 이동 금지(선택 시점만), 좌표 순서 (lat, lng) 준수.
- **0147**: SpotList에 onDragStart 콜백 prop 추가, DndContext onDragStart 핸들러, 부모에서 panTo 전달. `[하지 말 것]` setLevel 금지(센터만), onDragEnd·순서 저장 무변경, readOnly에 콜백 미전달.

## 4. 코드 작성 · 수정

> 커밋 전 CC "읽고 보고만"으로 실제 파일과 대조 예정.

### 0146 (SpotMap.tsx)

```tsx
// handlePlaceSelect — 마커 찍은 뒤 지도 이동
mapRef.current?.panTo(new kakao.maps.LatLng(lat, lng));  // 좌표 순서 주의: (lat, lng)
mapRef.current?.setLevel(3);
```

### 0147 (SpotList.tsx → SpotMap.tsx)

```tsx
// SpotList: onDragStart 콜백 prop 추가
<DndContext
  onDragStart={(e) => {
    const s = spots.find((x) => x.id === e.active.id);
    if (s) onDragStart?.(s);
  }}
  onDragEnd={...}   // 기존 순서 저장 무변경
>

// SpotMap: 여행순서 모드에서만 전달 (readOnly엔 미전달)
<SpotList onDragStart={(spot) => mapRef.current?.panTo(new kakao.maps.LatLng(spot.lat, spot.lng))} />
```

## 5. 결과 · 배운점

### 결과
- 검색해도, 드래그해도 지도가 사용자 조작을 따라간다. 여행동선 편집 경험이 매끄러워졌다.

### 배운점 ① — 부모의 ref를 자식에서 쓰려면 콜백 prop으로 넘긴다

드래그(자식 SpotList)와 지도 제어(부모 mapRef)는 컴포넌트 경계가 다르다. 자식이 부모의 ref에 직접 접근할 수 없으므로, 기존 `onReorder`·`onDelete`처럼 `onDragStart` 콜백 prop을 추가해 "이벤트는 자식이 잡고, 동작은 부모가 수행"하게 나눴다. optional prop이라 콜백을 넘기지 않는 곳(readOnly 상세)에는 무영향.

### 배운점 ② — 카카오 좌표 순서 함정 (place.x=lng / y=lat vs LatLng(lat, lng))

카카오 place 객체는 `x=경도(lng)`, `y=위도(lat)`인데, `LatLng` 생성자는 `(위도, 경도)` 순이다. 이 둘을 혼동하면 좌표가 뒤바뀌어 엉뚱한 위치로 이동한다.

- 실제로 "서울특별시청"을 검색했을 때 마커는 서울에 정확히 찍히는데 지도만 시골로 이동하는 증상을 만났다. 마커(addSpot)와 지도 이동(panTo)이 서로 다른 좌표를 참조한 것이다.
- 이는 좌표 순서가 흐르는 지점(place.x/y 추출 → addSpot 인자 → panTo 인자)이 여러 곳이라, 그중 한 곳만 뒤바뀌어도 나머지와 어긋나기 때문이다. **마커는 맞고 지도는 틀리다**는 것이 원인을 좁히는 결정적 단서였다(추출은 정상, 특정 소비 지점만 순서 오류).
- (이 좌표 순서 정합은 별도로 추적·정리 중.)

### 한 줄 교훈
지도는 사용자의 조작(검색·드래그)을 따라가야 "됐다"는 피드백을 준다. 그리고 좌표는 라이브러리마다 x/y·lat/lng 순서 규약이 달라, 값이 흐르는 모든 지점에서 순서를 일관되게 맞춰야 한다 — "마커는 맞는데 지도는 틀리다"처럼 한쪽만 어긋나면 순서 불일치를 의심한다.
