## 이번 작업의 4가지 핵심 요소

### 1. 검증된 UX 패턴 탐색

**목적**

작성한 TIL을 다시 보고, 수정/삭제할 수 있는 페이지 추가.
"카드 클릭 → 상세 페이지 진입 → 수정/삭제" 흐름 구현.

**고민 — 어떻게 풀까?**

[케이스 A] TIL 작성 카드에 각각 [수정][삭제] 버튼 넣기
1. TIL 카드 옆에 수정, 삭제 버튼을 넣으면...
2. 수정의 경우 선택을 안 했을시, "카드를 선택하세요" 메시지 필요.
3. 카드 여러 개 선택하면? "하나만 선택" 메시지 필요.
4. 그러나 삭제의 경우는 하나가 아닌, 여러개의 선택도 필요 할 수 있음.
5. 위처럼 생각할 경우, 생각해야할 경우의 수가 많아져 다른 방법을 생각해보기로 함.

[케이스 B] TIL 카드 클릭 → 진입 후 수정, 삭제
1. 수정이나 삭제하고자 하는 카드를 클릭.
2. 선택된 카드의 내용에 상세페이지로 진입후, 상세 페이지에서 [수정]이나 [삭제] 버튼을 클릭.
3. 위처럼 생각할 경우, 생각할 경우의 수가 적어짐.

[결론]
현재 상황에서는 검증된 패턴을 가져오는 게 맞다고 판단함.
실제 서비스(Notion, GitHub Issues, Gmail 등) 조사 결과, [케이스 B] 패턴을 표준으로 사용하는 것을 확인하고 적용함.

**방법**

- 목록 페이지: 각 카드 클릭 시, 해당 TIL의 상세 페이지로 이동
- 상세 페이지: 본인이 작성한 TIL만 화면에 표시
- 상세 화면 전환: 처음엔 읽을수 있는 형태로만 보여주고, [수정] 버튼 클릭 시 입력창으로 바뀜 ([취소] 누르면 다시 읽기 화면으로 돌아감)
- 수정 폼 제출: DB 업데이트 후 TIL 목록 페이지로 이동
- 삭제 버튼 클릭: "정말 삭제할까요?" 확인 후 DB 삭제 + TIL 목록 페이지로 이동

**기술 적용**

- 목록 페이지: 각 카드를 `<Link href="/til/[id]">`로 감쌈 (클라이언트 사이드 라우팅)
- 상세 페이지: Server Component에서 `getTilEntry(id)` 호출 → 본인 글 아니면 `notFound()`로 404 처리
- 상세 화면 전환: `'use client'` + `useState(isEditing)`로 읽기/수정 화면 분기
- 수정 폼: `<form action={updateTilEntryAction}>` → 성공 시 `redirect('/til')`
- 삭제 폼: `<form action={deleteTilEntryAction}>` + `window.confirm` → 성공 시 `redirect('/til')`

> **Link**
> Next.js 컴포넌트. 클라이언트 사이드 라우팅 적용.
> 페이지 깜빡임 없이 부드럽게 이동.

> **Server Component**
> 서버에서 렌더링 후 클라이언트에 전달.
> 'use client' 지시어 없는 컴포넌트가 기본.
> DB 접근 등 서버 작업 직접 가능.

> **useState**
> React Hook. 컴포넌트 안에서 상태 관리.
> isEditing 같은 화면 전환 상태에 사용.

**배운점**: 새 UX를 만들면 많은 경우의 수 및 구조를 생각해 봐야함. 검증된 패턴은 이미 그 고민을 해결한 결과물이라, 가져와서 적용하는 것이 더 적합하다는 판단을 내림. 
단, 무작정 따라 하는 게 아니라 "왜 이 패턴이 충돌을 발생시키지 않는가"를 짚은 후 적용해야 함.

### 2. 테스트 환경에서 외부 함수 가짜로 대체하기

**목적**

수정/삭제 동작이 끝난 후 화면이 최신 데이터로 갱신되는지 테스트로 확인.
실제 갱신 함수를 호출하면 테스트 환경에서 에러 발생 → 가짜 함수로 대체해서 호출 여부만 검증.

**고민 — 어떻게 풀까?**

처음엔 기존 Mock 패턴 그대로 사용했음.

[케이스 A] 외부 변수 참조 패턴
1. `const mockRevalidatePath = jest.fn();` 작성.
2. `jest.mock('next/cache', () => ({ revalidatePath: mockRevalidatePath }))` 추가.
3. 테스트 실행 = `ReferenceError: Cannot access 'mockRevalidatePath' before initialization` 에러 발생.
4. 원인 분석: jest.mock이 파일 최상단으로 자동 이동(호이스팅)되는데, 그 시점엔 const 선언이 아직 안 된 상태라 접근 불가.

[케이스 B] jest.requireMock 패턴
1. `jest.mock('next/cache', () => ({ revalidatePath: jest.fn() }))` 작성 (외부 변수 참조 없음).
2. `const mockRevalidatePath = jest.requireMock('next/cache').revalidatePath` 추가.
3. 호이스팅 후에도 안전. 외부 변수 참조가 없으니 충돌 없음.

[결론]
케이스 A는 작성한 순서와 실제 실행 순서가 달라서 에러 발생.
케이스 B는 가짜 함수를 mock 안에 직접 넣고 그 다음 줄에서 꺼내오는 방식이라 안전.

**방법**

- 갱신 함수 자체를 가짜로 대체 (실제 호출 X)
- 테스트 코드에서는 "이 함수가 호출됐는지" + "어떤 인자로 호출됐는지"만 검증
- 수정 후 → `/til` 페이지 + 해당 상세 페이지 둘 다 갱신 호출 확인
- 삭제 후 → `/til` 페이지 갱신 호출 확인

**기술 적용**

- `jest.mock('next/cache', () => ({ revalidatePath: jest.fn() }))` 작성 (외부 변수 참조 X)
- `const mockRevalidatePath = jest.requireMock('next/cache').revalidatePath`로 꺼내옴
- 테스트에서 `expect(mockRevalidatePath).toHaveBeenCalledWith('/til')` 검증
- updateTilEntry 테스트 → 2번 호출 검증 (`/til` + `/til/${id}`)
- deleteTilEntry 테스트 → 1번 호출 검증 (`/til`)

> **호이스팅**
> 코드 실행 전 선언을 끌어올리는 동작.
> jest.mock은 파일 최상단으로 자동 이동.
> 작성한 순서와 실제 실행 순서가 다름.

> **TDZ (Temporal Dead Zone)**
> const/let 변수 선언 전 접근 시 ReferenceError 발생하는 영역.
> 변수가 "있긴 있지만 아직 접근 불가"한 상태.

> **jest.requireMock**
> Jest 내부 가짜 저장소에서 모듈을 꺼내오는 함수.
> 실제 모듈이 아닌 Mock 반환.

**배운점**: jest.mock은 일반 함수 호출처럼 보이지만 호이스팅 규칙이 다름. 외부 변수를 참조하면 TDZ 위험이 생기므로, mock 안에 직접 jest.fn()을 넣고 그 다음 줄에서 requireMock으로 꺼내는 패턴이 더 안전함. "왜 이 코드가 에러를 내는가"의 답이 코드 작성 순서가 아닌 실행 순서에 있음을 인지.

### 3. 수정 폼 동작 흐름과 타입 시스템 충돌

**목적**

수정 폼을 사용자가 제출하면 DB에 저장 후 목록 페이지로 이동.
실패 시 에러 메시지를 사용자에게 전달하려 했으나, 타입 시스템과 충돌 발생.

**고민 — 어떻게 풀까?**

처음엔 반환값으로 에러 정보를 전달하려 했음.

[케이스 A] 함수 끝에 `return result` 작성
1. 성공 시 redirect, 실패 시 에러 객체 반환 = `{ error: '...' }` 작성.
2. 타입 검사 실행 = `Type '(formData) => Promise<{ error: string }>' is not assignable to type '(formData) => void | Promise<void>'` 에러 발생.
3. 원인 분석: 폼의 action 속성은 "아무것도 반환하지 않는 함수"만 받음. 에러 객체 반환은 허용 X.

[케이스 B] `return result` 제거 (아무것도 반환하지 않음)
1. 함수 끝에서 return 줄 삭제.
2. 성공 시 = redirect로 페이지 이동, 실패 시 = 함수 그냥 종료.
3. 타입 검사 통과. 다만 에러 발생 시 사용자가 알 수 없는 트레이드오프 발생.

[결론]
폼의 action 속성은 "아무것도 반환하지 않는 함수"를 강제함. 객체 반환 불가.
return을 제거하면 타입은 안전하지만, 실패 시 사용자에게 에러 메시지가 전달되지 않음.
MVP 단계에서는 이 정도로 두고, 추후 useActionState Hook으로 개선 예정.

**방법**

- 수정 폼 제출 → 함수 안에서 DB 저장 시도
- 성공 시 → `/til` 페이지로 이동 (사용자가 결과 확인)
- 실패 시 → 함수 종료 (사용자에게 에러 메시지 전달 X, MVP 한계)

**기술 적용**

- `if (result && 'data' in result)` → `if ('data' in result)`로 단순화 (방어 코드 제거)
- 함수 끝에서 `return result` 삭제 (void 반환)
- 성공 시 `redirect('/til')` 호출
- 실패 시 함수 자연 종료
- 추후 개선: `useActionState` Hook으로 에러 메시지 전달 메커니즘 추가

> **Server Action**
> 'use server' 지시어가 있는 함수.
> 클라이언트에서 직접 호출 가능.
> 폼 action 속성에 직접 전달 가능.

> **`'data' in result`**
> `in` 연산자. 키 존재 여부 검증.
> 값이 falsy(null, 0, '')여도 키만 있으면 true.

> **useActionState**
> React 19 Hook. action 결과를 state로 관리.
> 에러 메시지 표시에 사용.
> action 시그니처가 `(prevState, formData) => state`로 변경됨.

**배운점**: React와 Next.js의 폼 action은 "아무것도 반환하지 않는 함수" 시그니처를 강제함. 에러 정보를 사용자에게 전달하려면 useActionState 같은 별도 메커니즘이 필요함. 타입 에러는 단순 컴파일 실패가 아니라 "이 시그니처가 강제되는 이유"를 알려주는 신호. 프레임워크가 강제하는 패턴에는 그 패턴을 따라야 하는 이유가 있음.

### 4. 타인 TIL 접근 차단 (다중 방어선)

**목적**

타인이 다른 사람의 TIL을 접근하지 못하게 차단.
DB 보안 한 겹만 두면 위험 → 코드 보안도 같이 적용해서 이중 방어선 구축.

**고민 — 어떻게 풀까?**

설계 단계에서 DB 보안만 사용할지, 코드 보안도 추가할지 결정이 필요했음.

[케이스 A] DB 보안(RLS)만 사용
1. til_entries 테이블에 RLS 정책 4개 적용 (0023에서 완료).
2. 함수에서는 `.update().eq('id', id)`만 사용 (본인 확인 없음).
3. DB 보안이 모든 책임을 짊어짐.
4. 위험: anon key가 실수로 service role key로 변경되면 DB 보안 우회 가능. 환경 변수 노출 시 즉시 위험.

[케이스 B] DB 보안 + 코드 보안 이중 사용
1. DB 보안 정책 적용 (0023에서 완료).
2. 함수에 `.eq('id', id).eq('user_id', user.id)` 추가.
3. DB 보안 비활성화나 key 변경 상황에서도 본인 확인이 살아있음.
4. 약간의 코드 중복이지만 보안이 우선.

[결론]
보안은 "다중 방어선" 원칙이 더 적합함.
DB 보안은 DB 레벨, 코드 보안은 함수 레벨에서 각각 작동.
한쪽이 무력화돼도 다른 쪽이 살아있음.
약간의 코드 중복 트레이드오프가 있지만 보안이 우선.

**방법**

- 본인 TIL만 조회 → 타인 글이면 404 페이지
- 본인 TIL만 수정 가능 → 타인 글이면 수정 불가
- 본인 TIL만 삭제 가능 → 타인 글이면 삭제 불가
- 브라우저 검증: 계정 B로 계정 A의 글 URL 직접 접근 → 404

**기술 적용**

- `getTilEntry`: `.eq('id', id).eq('user_id', user.id).single()` → 타인 글 = data null → `notFound()` 호출
- `updateTilEntry`: `.update(...).eq('id', id).eq('user_id', user.id)` → 타인 글 = update 매칭 X
- `deleteTilEntry`: `.delete().eq('id', id).eq('user_id', user.id)` → 타인 글 = delete 매칭 X
- 2계정 시나리오 브라우저 테스트로 실제 차단 확인

> **RLS (Row Level Security)**
> PostgreSQL의 행 단위 보안.
> 정책에 따라 행 접근 제어.
> DB 레벨에서 자동 적용.

> **anon key**
> Supabase 공개 키.
> 클라이언트에 노출되는 게 전제.
> RLS가 보안의 핵심.

> **service role key**
> Supabase 관리자 키.
> RLS 우회 가능.
> 서버 사이드 전용 (절대 클라이언트 노출 X).

**배운점**: DB 보안만으로 충분하다고 가정하는 것은 단일 실패 지점이 될 수 있음. 코드 보안을 추가하면 DB 보안이 일시 비활성화되거나 key가 잘못 사용되어도 안전. 보안에서는 "왜 중복하는가?"의 답이 "어느 한쪽이 무너져도 다른 쪽이 살아있어야 하기 때문". 단일 책임 원칙과 다중 방어선이 충돌할 때는 보안이 우선.

### 0025 TIL 상세/수정/삭제 페이지 plan을 받은 후 수정 요청 프롬프트

### 1. getTilEntry / updateTilEntry / deleteTilEntry Server Action (lib/til/actions.ts에 추가)

```typescript
// lib/til/actions.ts
import { revalidatePath } from 'next/cache';
import { createClient } from '@/lib/supabase/server';

export async function getTilEntry(id: string) {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();

  if (!user) {
    return { error: '로그인이 필요합니다' };
  }

  const { data, error } = await supabase
    .from('til_entries')
    .select()
    .eq('id', id)
    .eq('user_id', user.id)
    .single();

  if (error || !data) {
    return { error: '찾을 수 없습니다.' };
  }

  return { data: { entry: data } };
}

export async function updateTilEntry(id: string, title: string, content: string) {
  if (title.trim() === '') {
    return { error: '제목을 입력해주세요' };
  }
  if (content.trim() === '') {
    return { error: '내용을 입력해주세요' };
  }

  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();

  if (!user) {
    return { error: '로그인이 필요합니다' };
  }

  const { data, error } = await supabase
    .from('til_entries')
    .update({ title, content })
    .eq('id', id)
    .eq('user_id', user.id)
    .select()
    .single();

  if (error) {
    return { error: 'TIL 수정에 실패했습니다' };
  }

  revalidatePath('/til');
  revalidatePath(`/til/${id}`);
  return { data: { entry: data } };
}

export async function deleteTilEntry(id: string) {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();

  if (!user) {
    return { error: '로그인이 필요합니다' };
  }

  const { error } = await supabase
    .from('til_entries')
    .delete()
    .eq('id', id)
    .eq('user_id', user.id);

  if (error) {
    return { error: 'TIL 삭제에 실패했습니다' };
  }

  revalidatePath('/til');
  return { data: null };
}
```

// app/(protected)/til/[id]/TilDetail.tsx
'use client';
import { useState } from 'react';
import { updateTilEntryAction, deleteTilEntryAction } from './actions';

type TilEntry = {
  id: string;
  title: string;
  content: string;
  created_at: string;
};

export default function TilDetail({ entry }: { entry: TilEntry }) {
  const [isEditing, setIsEditing] = useState(false);

  if (isEditing) {
    return (
      <form action={updateTilEntryAction} className="flex flex-col gap-4">
        <input type="hidden" name="id" value={entry.id} />
        <input
          name="title"
          defaultValue={entry.title}
          className="border border-slate-300 rounded-lg px-3 py-2"
        />
        <textarea
          name="content"
          defaultValue={entry.content}
          rows={6}
          className="border border-slate-300 rounded-lg px-3 py-2 resize-none"
        />
        <div className="flex gap-2">
          <button type="submit" className="bg-slate-800 text-white rounded-lg px-4 py-2">
            저장
          </button>
          <button type="button" onClick={() => setIsEditing(false)} className="bg-slate-200 text-slate-700 rounded-lg px-4 py-2">
            취소
          </button>
        </div>
      </form>
    );
  }

  return (
    <div className="flex flex-col gap-4">
      <h1 className="text-2xl font-bold text-slate-800">{entry.title}</h1>
      <p className="text-slate-600 whitespace-pre-wrap">{entry.content}</p>
      <time className="text-xs text-slate-400">
        {new Date(entry.created_at).toLocaleDateString('ko-KR')}
      </time>
      <div className="flex gap-2">
        <button onClick={() => setIsEditing(true)} className="bg-slate-800 text-white rounded-lg px-4 py-2">

          >
            삭제
          </button>
        </form>
      </div>
    </div>
  );
}

'use server';
import { redirect } from 'next/navigation';
import { updateTilEntry, deleteTilEntry } from '@/lib/til/actions';

export async function updateTilEntryAction(formData: FormData) {
  const id = formData.get('id') as string;
  const result = await updateTilEntry(
    id,
    formData.get('title') as string,
    formData.get('content') as string,
  );
  if ('data' in result) {
    redirect('/til');
  }
}

export async function deleteTilEntryAction(formData: FormData) {
  const id = formData.get('id') as string;
  const result = await deleteTilEntry(id);
  if ('data' in result) {
    redirect('/til');
  }
}
