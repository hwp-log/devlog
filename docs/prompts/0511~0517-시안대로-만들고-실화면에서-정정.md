## 2. 왜 / 목적 / 이유

### 왜 (동기·문제)

플랜파인더 상세는 기능이 다 있는 화면이었고 남은 것은 표현이었다. 앞선 사이클에서 Claude Design에 시안을 맡겨 1열 구조를 확정했고, 그 시안(`docs/design/0512-plan-detail-final.html`)을 코드에 옮기는 일만 남아 있었다.

문제는 분량이었다. 상단부·일정·비용·항공·모바일까지 한 번에 던지면 검증할 것이 너무 많아지고, 중간에 어긋나도 어디서 어긋났는지 찾기 어렵다.

### 목적 (목표 상태·사용자 가치)

시안의 조판이 화면에 그대로 서는 것. 이 화면의 목적은 "남의 코스를 따라 할지" 판단하는 것이라, 섹션 위계가 뚜렷해야 총액·동선·항공을 순서대로 훑을 수 있다.

### 이유 (채택 근거·판단 기준)

**단계를 네 개로 나눈 기준은 "한 단계가 끝나면 화면이 돌아가고 커밋할 수 있는가"였다.** 상단부(0512) → 일정(0513) → 비용·항공(0514) → 모바일(0515). 모바일을 마지막에 둔 이유는 데스크톱이 확정되지 않은 상태에서 접으면 두 번 일하기 때문이다.

**시안 파일을 레포 안에 넣고 CC가 직접 읽게 했다.** 프롬프트에 파일명만 적으면 CC가 값을 스스로 상상해서 그릴 위험이 있다. 그래서 `docs/design/`에 두고 "각 단계 시작 전에 해당 섹션의 실측값을 읽고 그대로 적용, 파일에 없는 값은 지어내지 말고 기존 코드값 유지"를 명시했다.

**야간 무인 실행에는 안전장치를 넣었다.** 푸시 금지(아침에 되돌릴 수 있게), 단계마다 별도 커밋(부분 롤백 가능), `tsc` 실패 시 그 단계에서 중단, 스키마·마이그레이션 금지, 공용 컴포넌트 내부 수정 시 멈추고 보고.

**정정 국면에서 판단 기준이 한 번 갈렸다.** 아침에 실화면을 보고 다섯 가지를 지적했는데, CC가 시안을 실측해 보고하면서 그중 둘이 내 오류로 드러났다.

- 섹션 제목을 "17px"로 지시했는데 시안 실측은 22px이었다. 17px은 상단 로고 크기였다.
- 지표 밴드가 "균등이어야 한다"고 지적했는데 시안은 `max-content` 뭉침형이었고, 균등은 모바일 프레임의 값이었다.

제목은 시안이 이겼고, 지표 밴드는 실화면 판정으로 균등을 택했다. 시안이 항상 정답이 아니라 **실측값과 실화면 판정 중 어느 쪽이 그 항목의 근거인지**를 항목마다 갈랐다.

### 아침 정정 (참고치를 적되 시안이 이기게)

```
[배경]
0512~0515 야간 작업분 실화면 검수 결과 정정 6건.

각 항목의 실측값을 시안에서 다시 읽고 보고한 뒤 적용할 것.
아래 괄호 안 값은 확인용 참고치이며, 시안과 다르면 시안을 따르고 보고할 것.

① 섹션 제목 복원 — 가장 중요
현재 "여행 일정 / 예상 비용 / 왕복 항공편"이 12px 회색 라벨이다.
시안: 22px / weight 700 / letter-spacing -.015em / #17191a,
아래 2px 실선(#17191a) + padding-bottom 10px,
같은 줄 오른쪽에 13px #8b9196 보조 문구.

② 섹션 순서 교체 — 현재 일정 → 항공 → 비용. 시안은 일정 → 비용 → 항공.
   순수 JSX 이동으로 단독 커밋할 것.

③ 카테고리 색 막대 복원 — 각 줄 padding 8px 0 8px 11px에 왼쪽 3px 세로 색 막대.
   카테고리별 고정색: 교통 #a8c7f0 / 항공 #f2d9a0 / 식비 #c9b8ea /

④ 카테고리 2열 유지 — 시안 4a는 1열이지만 실화면 판정으로 2열을 유지한다.
```

### 4-2. 0516 — SectionHeader 신설 (이후 트랙의 뿌리)

정정 여섯 건 중 가장 컸던 자리다. 12px 회색 라벨뿐이라 섹션이 갈리지 않던 것을 22px 제목 + 2px 실선으로 되살렸다.

```tsx
// PlanFinderDetail.tsx (a9fa63a)
// 0516: 섹션 제목(시안 4a/4d) — 22px(모바일 19px) 굵은 제목 + 2px 실선, 우측 13px(12px) 보조.
//   섹션을 가르는 유일한 위계 장치라 세 섹션(일정·비용·항공) 공통.
function SectionHeader({ title, sub }: { title: string; sub?: string }) {
  return (
    <div className="flex items-baseline justify-between gap-3 border-b-2 border-fg pb-2 sm:pb-2.5">
      <h2 className="text-[19px] sm:text-[22px] font-bold tracking-[-0.015em] text-fg break-keep">{title}</h2>
      {sub && <span className="text-xs sm:text-[13px] text-muted shrink-0">{sub}</span>}
    </div>
  );
}
```

이 컴포넌트가 나중에 0527 작성 화면에서 두 번째로 만들어지고, 0531에서 공용으로 추출된다.

같은 커밋에서 브레이크포인트를 일괄 정정했다. 0512에서 `md:`로 적었던 것이 640~767px 구간에서 상단부만 모바일 크기로 렌더되는 원인이었다.

```tsx
// a9fa63a: md:* 전부 sm:* 로 치환 (히어로 높이·칩·제목·메타·지표 밴드)
<div className="relative w-full h-[200px] sm:h-[300px] rounded-[14px] overflow-hidden mb-4">
```

### 4-3. 0517 — 색 기준을 rank에서 카테고리 고정으로

```tsx

const RANK_BAR = ['bg-chart1-bg', 'bg-chart2-bg', 'bg-chart3-bg', 'bg-chart4-bg', 'bg-chart5-bg'];
const barByCategory = new Map(ratios.map((r, rank) => [r.category, RANK_BAR[Math.min(rank, 4)]]));
```

```tsx

//   비KRW는 시안에 형식이 없어 formatAmount. 합계 0이면 건수만(지어내지 않음).
const groupSummary = (items: Item[]): string | undefined => {
  if (items.length === 0) return undefined;
  const sum = items.reduce((acc, it) => acc + it.amount, 0);
  if (sum <= 0) return `${items.length}건`;
```

## 5. 결과 / 배운점

### 결과

- 시안 4a 조판이 화면에 섰다 — 섹션 제목 22px + 2px 실선, 지표 밴드 3열, 소개문 본문화, 일정 행 목록, 비용 3px 색 막대, 항공 4열, 모바일 하단 고정 바

- 여기서 만든 `SectionHeader`가 이후 0527(작성 화면)·0531(공용 추출)로 이어졌다

- 이 트랙의 조판은 **0534에서 본문 폭 860으로 편입**되고, **0538에서 스켈레톤이 재동기**됐다

### 배운점

**시안을 파일로 두고 CC가 직접 읽게 한 것이 정정의 절반을 막았다.** 내가 프롬프트에 적은 "17px"이 틀렸는데 CC가 시안 실측 22px로 정정했다. 내가 화면을 보고 눈대중한 값과 시안의 실제 값이 다를 수 있다는 것은, 프롬프트에 값을 적더라도 "참고치이며 시안과 다르면 시안을 따르라"를 함께 적어야 하는 이유다.

**시안이 항상 정답은 아니다.** 지표 밴드는 시안이 `max-content` 뭉침이었는데 실화면에서 균등이 나아 보였다. 여기서 갈린 기준은 "그 값이 어디서 왔는가"였다 — 제목 22px은 시안이 계산해 정한 값이고, 뭉침/균등은 보고 정하는 값이다. 계산에서 온 값은 시안이 이기고, 감각에서 온 값은 실화면이 이긴다.

**야간 무인 실행은 안전장치가 절반이다.** 푸시 금지·단계별 커밋·`tsc` 실패 시 중단·공용 컴포넌트 수정 시 보고. 이 넷이 있어서 아침에 "되돌릴 수 있는 상태"로 결과를 받았다. 실제로 정정이 여섯 건 나왔는데도 부담이 없던 것은 그 덕이다.

**같은 날 세 번 뒤집힌 결정이 있었다(카테고리 2열).** 도입 → 시안 근거로 1열 복원 → 실화면 근거로 2열 재복원. 이 왕복은 낭비였지만, 두 번째 복원 때 "시안 4a는 1열이지만 실화면 판정으로 2열을 유지한다"를 주석에 남겨서 세 번째 왕복은 없었다. 뒤집을 때는 이유를 코드에 남겨야 다음 사람이 되돌리지 않는다.

**한 번에 던지지 않고 넷으로 나눈 것이 정정 범위를 좁혔다.** 정정 여섯 건 중 다섯이 특정 단계에 국한됐고, 커밋이 단계별로 나뉘어 있어 어디를 고칠지 바로 찾았다. 한 덩어리로 만들었으면 diff에서 찾는 데 시간이 더 들었을 것이다.
