# 0089~95 회고: CostPlan 초기작업 및 비용표시 재처리 작업

- 날짜: 2026.6.11
- 소요: 약 6시간
- 관련 커밋: 0089 ~ 0095

---

## 1. 한 줄 요약

여행 플랜의 정밀 비용을 **비중%·총액 구간으로 가공해 공개**하는 CostPlan을, 데이터 구조부터 가공 함수·스토리 분기·목록 페이지·공개 토글·정렬/필터까지 한 줄기로 구현했다. 작업 중 발견한 공개 화면 이메일 노출(PII) hotfix를 함께 처리했다.

---

## 2. 왜 / 목적 / 이유

핵심 결정마다 **왜(동기·문제) / 목적(도달 상태·사용자 가치) / 이유(채택 근거)** 셋으로 나눠 적는다.

### 가. 비용 가공 공개 — 이 프로젝트의 뿌리

- **왜**: 정밀 지출액은 그 사람의 소비 수준·경제 상황을 정확히 드러내는 개인 경제 정보다. "이 여행에 정확히 253,844원 썼다"는 소득 추정·비교·판단의 대상이 된다. 곧 프라이버시 침해 정보다.
- **목적**: 정확한 액수는 가리되, 카테고리 비중(여행 컨셉)과 총액 구간(예산대)은 보여서 영감·비교가 되게 한다.
- **이유**: 영감·비교에는 "어떤 스타일·대략 얼마"면 충분하다. 가공이 내주는 것은 컨셉(비중) + 예산대(구간) 둘이고, 가리는 것은 정확한 액수 하나다. 비율·범주 표시를 원칙으로 삼았다.
- **파급**: 이 원칙 하나가 거의 모든 작업을 끌고 갔다. "가공해서 공개"가 원칙이면 정밀이 새는 모든 경로를 막아야 했고, 그것이 서버 차단·select 화이트리스트·스토리 가공·목록 가공으로 이어졌다.

### 나. 데이터 구조 — 무결성을 원천에서 보장

- **왜**: 공개·좋아요·복제 출처를 정합성 깨지지 않게 담아야 했다.
- **목적**: 좋아요는 중복 없이, 복제 출처는 원본이 삭제돼도 안 깨지게, 공개는 실수로 켜지지 않게.
- **이유**:
  - `PlanLike` 별도 테이블 + `@@unique([planId, userId])` → polymorphic nullable보다 무결성을 DB가 직접 보장.
  - `sourcePlanId`는 FK가 아닌 `String?` → 출처는 스냅샷(책임 경계). 원본이 사라져도 내 계획은 안 깨진다.
  - `isPublic` 기본 false(옵트인) → 기본 비공개라 실수 공개를 막는다.

### 다. 서버에서만 가공 — 사후처리보다 원천 방지

- **왜**: 가공값만 내보내려면 정밀이 클라로 새는 경로를 전부 막아야 한다.
- **목적**: 정밀 비용이 클라 번들·RSC payload·HTML 어디에도 없게 한다.
- **이유**:
  - `summarizePlanCost`에 `import 'server-only'` → 클라 컴포넌트가 import하면 빌드 타임 에러. 런타임 약속이 아니라 빌드 단계에서 차단.
  - `fetchPublicPlans`는 `include`가 아닌 `select` 화이트리스트 → `ownerId`·`startDate`·`endDate` 같은 민감 필드를 조회조차 안 한다. 정밀 `costs/flight`는 가공 입력으로만 쓰고 반환에서 제거.

### 라. 스토리 상세도 작성자까지 가공 — 분기 기준은 페이지 성격

- **왜**: 스토리는 공개되는 기록이다. 작성자도 "공개되면 어떻게 보이나"를 리뷰할 수 있어야 한다.
- **목적**: 마이플랜(편집 공간)=정밀, 스토리·목록(공개 뷰)=가공으로 가른다.
- **이유**: 처음엔 isOwner로 정밀/가공을 갈랐으나, 가르는 기준은 *소유 여부*가 아니라 *페이지 성격*이었다. 정밀은 편집 공간에서, 공개 화면이면 작성자에게도 가공. isOwner 비용 분기를 걷어내고 스토리 상세는 무조건 가공으로 바꿨다.

### 마. 이메일 노출 hotfix — 가린 것보다 민감한 것이 새고 있었다

- **왜**: 비용을 가리는 작업 중에, 정작 더 민감한 작성자 이메일(PII)이 로그인 없이 공개 노출되고 있었다(스토리 목록·상세 2곳).
- **목적**: 타인 이메일을 즉시, 프로덕션에서 차단한다.
- **이유**: 렌더만 빼면 payload에 남을 수 있어 `include`에서 `user`를 통째로 제거해 조회 자체를 끊었다. 작성자 표시 복원은 `User` 닉네임 필드 도입(별도 트랙)으로 미뤘다.

## 3. 작성한 프롬프트 (핵심 발췌)

작업 프롬프트는 `[배경]/[목표]/[하지 말 것](❌)/[검수 모드]/plan 요청.` 형식으로 통일했다.

### 가공 함수 (2단계)

```
[배경]
CostPlan에서 제3자에게 보여줄 비용 가공 함수를 만든다.
정밀 비용(PlanCost + 항공)을 카테고리 비중%와 총액 구간으로 변환한다.
정의는 한 곳 — _lib/cost.ts에 두고 3·4단계가 공유. 서버에서만 호출돼
클라 번들에 정밀 로직·정밀값이 새지 않아야 한다.

[목표]
... 비중%: 카테고리별 / 총액. 항공은 "항공" 카테고리로 합류.
    반올림 후 합이 100이 아니면 잔차를 최대 항목에 더해 100 맞춤.
    총액 구간(계단식 가변 폭): ~50만=10만 / 50~100만=25만 / 100만~=50만

[하지 말 것]
❌ 클라 컴포넌트에서 import 가능하게 두기 (서버 전용 보장)
❌ 본인/제3자 분기 (함수는 변환만)

[검수 모드]
★★★ (로직): 반환에 정밀 금액이 안 섞이는지 / 비중 합 100% / 구간 경계.
plan 요청.
```

> 검수 과정에서 "cost.ts에 두자"던 전제가 틀렸음을 CC가 코드로 잡아냈다(cost.ts는 이미 클라 컴포넌트가 import 중). → 신규 `lib/plan/summarize-plan-cost.ts`로 옮기고 `server-only` 적용.

### 스토리 상세 가공 전환 (3단계)

```
[목표]
page.tsx에서 isOwner 비용 분기 제거. story.plan이면 무조건
summarizePlanCost → PublicCostSection.
PublicCostSection: PublicCostSummary만 입력, 비중% 막대 + 범례 + 구간,
정밀 금액 표시 없음.

[하지 말 것]
❌ 제3자 경로에 정밀 totals/flightAmount/total 전달
❌ 여행 일자(startDate/endDate) 작업
❌ 작성 날짜(createdAt) 표시 변경 (비용 유효 시점 정보라 유지)
```

> "작성 날짜는 오히려 살려야 한다"는 통찰: 물가가 변하므로 "언제 기준 비용인지"가 없으면 가공값도 해석이 어긋난다.

## 4. 코드 작성 & 수정

### 가공 함수 — 최대 잔여법 + 계단식 구간 (서버 전용)

```ts
// lib/plan/summarize-plan-cost.ts
import 'server-only';

export type PublicCostSummary = {
  ratios: Array<{ category: CostCategory | 'FLIGHT'; label: string; ratio: number }>;
  band: { lower: number; upper: number } | null; // KRW 전용, 비-KRW는 null
  currency: 'KRW' | 'USD' | 'JPY';
};
// 반환에 정밀 amount 없음. 비중 합 100은 최대 잔여법(소수점 큰 순 +1).
// computeBand를 먼저 계산해 total=0 조기 반환에도 재사용 → 비-KRW면 band=null 일관.
```

### 공개 토글 — 소유권 검증이 핵심

```ts
// app/(protected)/my-plan/[id]/actions.ts
export async function togglePlanPublicAction(planId: string, isPublic: boolean) {
  // getUser() → 없으면 redirect
  const plan = await prisma.myPlan.findFirst({
    where: { id: planId, ownerId: user.id }, // ← 본인 것일 때만
    select: { id: true },
  });
  if (!plan) return;                          // 타인 플랜이면 업데이트 없음

  revalidatePath(`/my-plan/${planId}`); revalidatePath('/my-plan'); revalidatePath('/cost-plan');
}
```

## 5. 결과 / 배운 점

### 결과

- CostPlan 코어 완성: **공개 토글 → 목록 노출 → 가공 열람**이 사용자 손으로 처음부터 끝까지 동작.
- 가격구간 필터 + 최신순·가격순 정렬(비-KRW는 정렬 끝·필터 전체에만).
- 가공 함수 단위 테스트 11케이스 통과(합 100·경계·total=0·비-KRW·항공 합류).
- 공개 화면 이메일 노출 차단(프로덕션 반영).

### 배운 점

- **원칙 하나가 구조를 결정한다.** "가공해서 공개"라는 원칙이 server-only·select 화이트리스트·페이지별 분기를 전부 끌고 왔다. 기능이 아니라 원칙에서 출발하면 누락이 줄어든다.
- **사후처리보다 원천 방지.** 렌더에서 빼는 것(사후)이 아니라 조회/import 단계에서 끊는 것(원천)이 진짜 차단이다. select 화이트리스트, include 제거, server-only가 같은 결.
- **분기 기준을 다시 의심하기.** isOwner로 가르려던 것을 "페이지 성격"으로 바꾼 순간 설계가 단순해졌다. 처음 잡은 축이 항상 옳지는 않다.
- **추측보다 코드.** "cost.ts에 두면 된다", "스토리 비용 구조가 호환될 것이다" 같은 전제를 CC의 "읽고 보고만"이 코드로 잡아줬다. 작업 중 이메일 노출도 그 흐름에서 발견됐다.
- **가린 것 옆의 더 큰 구멍.** 비용을 가리는 작업이 오히려 더 민감한 PII(이메일) 노출을 드러냈다. 한 곳을 보안 관점으로 보면 인접한 구멍도 보인다.
