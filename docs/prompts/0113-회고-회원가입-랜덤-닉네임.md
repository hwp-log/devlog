# 0113 회고: 회원가입 시 랜덤 닉네임 자동 부여

- 작성일: 2026-06-24
- 소요: 약 1시간
- 관련 커밋: cb62f92

## 1. 한 줄 요약

닉네임이 필수 필드인데 가입 시점엔 값이 없어, 가입 즉시 랜덤 닉네임을 자동 부여해 null을 원천 차단했다. 컬럼 제약(VARCHAR 20)을 넘는 후보는 컬럼을 늘리지 않고 재추첨으로 걸러, DB를 건드리지 않고 제약을 지켰다.

## 2. 왜 / 목적 / 이유

### 닉네임 자동 부여 — null 원천 차단

- 왜: 닉네임은 필수 필드인데 가입 시점엔 입력값이 없다. 가입 폼에 닉네임 칸을 추가하면 가입 단계가 늘고, 비워두면 닉네임이 null인 사용자가 생긴다.
- 목적: 가입하는 순간 닉네임이 항상 채워져, 데이터가 늘 완전한 상태인 것. 변경은 나중에 마이페이지에서.
- 이유: nullable로 두면 null 사용자가 생겨 무결성이 깨지고, 닉네임을 화면에 뿌릴 때마다 null 분기를 타야 한다. 가입 즉시 임시 닉네임을 자동 부여하면 null이 애초에 존재할 수 없고, 수정 경로(마이페이지)만 열어두면 사용자 자율성도 보장된다. 데이터를 입구에서 완전하게 유지하는 쪽을 택했다.

### 재추첨 루프 — 컬럼 제약을 양보하지 않음

- 왜: `User.nickname`은 VARCHAR(20) 제약인데, 라이브러리가 만드는 닉네임이 "레고를 밟은 긴꼬리원숭이"처럼 20자를 넘을 때가 있었다.
- 목적: 제약(20자)을 어기지 않으면서, DB는 건드리지 않고 자동 부여를 성립시키는 것.
- 이유:
  1. 20자 제약은 닉네임이 너무 길면 카드·헤더·목록 UI가 깨지므로 둔 의도된 규칙이다. 라이브러리 출력이 길다고 컬럼을 늘리면, 라이브러리에 내 데이터 규칙을 양보하는 본말전도다.
  2. 컬럼 길이 변경은 마이그레이션(스키마 변경·기존 데이터 영향·롤백 리스크)이라 신중해야 하는 ★★★★급 작업이다. "닉네임 자동 부여"라는 작은 기능을 위해 DB 스키마를 바꾸는 건 과하다.
  3. 재추첨은 메모리에서 20자 이하가 나올 때까지 거르고 확정값 하나만 INSERT하므로, DB 무결성·성능에 영향이 없다. 재추첨 처리 시간도 짧아 실용적으로 부담이 없었다.

### 폴백 — 무한 루프 방지

- 왜: 재추첨이 매번 20자를 넘으면 무한 루프에 빠질 수 있다.
- 목적: 최악의 경우에도 항상 보장된 닉네임이 부여되는 것.
- 이유: 재추첨에 상한(최대 5회)을 두고, 그래도 실패하면 `여행자_{userId 앞 4자}` 폴백으로 떨어지게 했다. 재추첨은 하되 무한정은 아니라는 방어적 설계.

## 3. 작성한 프롬프트

```
[배경]
회원가입 시 닉네임 자동 부여. User.nickname은 VARCHAR(20). 라이브러리
@woowa-babble/random-nickname의 getRandomNickname('animals')이 가끔 20자 초과.

[목표]
1. types/random-nickname.d.ts — 타입 정의 없는 라이브러리라 declare module 추가.
2. lib/auth/nickname.ts — generateNickname(userId) 신규:
   - 20자 이하 나올 때까지 최대 5회 재추첨(MAX_TRIES=5, MAX_LEN=20).
   - 실패 시 '여행자_' + userId 앞 4자 대문자 폴백.
3. lib/auth/actions.ts — 기존 signUp 흐름에서 nickname 한 줄만 교체.

[하지 말 것]
❌ signUp 흐름·다른 로직 건드리지 마 — nickname 생성 부분만.
❌ User 스키마(컬럼 길이) 변경 금지 — 재추첨으로 제약 안에서 해결.
❌ import 경로 주의: '@woowa-babble/random-nickname' (README의 @babble/... 는 오타).

[검수] tsc 통과 / 단위 호출 10회 모두 20자 이하 / 실제 가입해 마이페이지 표시 확인.
```

## 4. 코드 작성 & 수정

### 타입 정의 (declare module)

```ts
// types/random-nickname.d.ts — 타입 정의 없는 CJS 라이브러리
declare module '@woowa-babble/random-nickname' {
  export function getRandomNickname(
    type: 'animals' | 'characters' | 'heros' | 'monsters'
  ): string;
}
```

### 재추첨 + 폴백

```ts
// lib/auth/nickname.ts (전체 12줄)
import { getRandomNickname } from '@woowa-babble/random-nickname';

const MAX_LEN = 20;   // User.nickname VARCHAR(20)
const MAX_TRIES = 5;

export function generateNickname(userId: string): string {
  for (let i = 0; i < MAX_TRIES; i++) {
    const n = getRandomNickname('animals'); // "형용사 명사" 예: "술 마시는 햄스터"
    if (n && n.length <= MAX_LEN) return n;  // 제약 만족분만 채택 (n && 로 undefined 방어)
  }
  return '여행자_' + userId.slice(0, 4).toUpperCase(); // 폴백 (UUID 앞 4자 대문자)
}
```

### 가입 흐름 한 줄 교체

```ts
// lib/auth/actions.ts — signUp 내부, 기존 흐름 무수정
nickname: generateNickname(userId),
```

## 5. 결과 / 배운점

- 실제 가입(resublimity@naver.com) 후 "레고를 밟은 긴꼬리원숭이"가 마이페이지에 표시됐고, 단위 호출 10회 모두 20자 이하였다. 마이페이지 닉네임 수정 input도 이미 있어 변경 경로가 보장된다.
- null은 입구에서 막는다: 필수 필드가 가입 시점에 값이 없다면, nullable로 두고 화면마다 분기하기보다 자동 부여로 null 자체를 없애는 편이 데이터를 완전하게 유지한다.
- 제약은 양보하지 않는다: 외부 라이브러리 출력이 내 제약(20자)을 넘을 때, 제약을 늘리는 게 아니라 제약에 맞는 값만 받아들이는 게 맞다. 꼬리(라이브러리)가 몸통(데이터 규칙)을 흔들게 두지 않는다.
- DB는 건드릴수록 비싸다: 같은 문제를 컬럼 길이 변경(마이그레이션, ★★★★)으로도 풀 수 있었지만, 메모리에서 거르고 확정값만 INSERT하면 DB 영향 0으로 해결된다. 작은 기능에 비싼 변경을 매칭하지 않는다.
- 방어적 설계: 재추첨에는 상한과 폴백을 둬 무한 루프를 막았다.
