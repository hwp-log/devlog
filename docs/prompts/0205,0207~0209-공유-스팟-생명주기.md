# 0205·0207~0209 회고: 공유 스팟 생명주기

작성일: 2026-08-10
소요 시간: 약 3시간
관련 커밋: 1223d72(0205) · 11e2d35(0207) · 3213fb8(0208) · 0209(SQL 실행, 코드 커밋 없음)

---

## 1. 한 줄 요약

스팟이 공유 자산이 되면서 깨진 전제 위에서 Cascade가 계속 옳게 동작해 남의 여행동선을 지우고 있었고, 그 경로를 닫은 뒤 반대편(아무도 안 쓰는 스팟)까지 함께 처리해 생명주기를 닫았다.

---

## 2. 왜 / 목적 / 근거

### 왜 (동기·문제)

S3-a(0201)에서 스팟 재사용을 도입했다. 같은 장소를 여러 스토리가 함께 쓰게 된 것이다. 그런데 삭제 로직은 그대로였다.

```
스토리 A 삭제
  → A가 만든 스팟 X 하드삭제
  → Spot → StorySpot onDelete: Cascade 발동
  → X를 재사용하던 스토리 B의 여행동선까지 사라짐
```

**사용자는 자기 글에서 장소가 왜 없어졌는지 영영 모른다.** 복구도 안 되고 원인 추적도 어렵다. 프로덕션 사고가 나기 전에 닫아야 했다.

문제의 성격이 특이했다. 스키마도 Cascade 설정도 잘못된 게 없다. `StorySpot.spot`의 `onDelete: Cascade`는 0183에서 신설된 그대로이고, 지금도 그대로다. **바뀐 건 "한 스팟을 참조하는 스토리는 하나뿐"이라는 전제였다.** S3-a가 그 전제를 깼고, Cascade는 낡은 전제 위에서 계속 정확히 동작했다.

그리고 0205로 삭제를 막고 나니 반대편 문제가 드러났다. 주인이 나가고 아무도 안 쓰게 된 스팟이 지도에 그대로 남는다. 사용자가 늘면 이런 스팟이 쌓이는데, **나중에는 어느 게 실제 촬영지고 어느 게 잔재인지 구분할 수 없게 된다.** 지금은 시딩을 직접 했으니 파악되지만, 사용자 데이터가 섞이면 청소가 불가능해진다.

### 목적 (도달 상태)

- 스토리를 지우거나 편집해도 남이 쓰고 있는 스팟은 사라지지 않는다. 삭제·편집 자체는 정상 성공한다.
- 아무도 안 쓰게 된 사용자 생성 스팟은 자동으로 정리된다. 단 시딩 촬영지는 참조가 0이어도 남는다.
- 이미 쌓인 잔재도 한 번 청소한다.

### 근거 (결정 기준)

**Cascade를 고치지 않았다.** 관계 정의를 바꾸는 대신, Cascade가 발동하기 **전에** 지켜야 할 대상을 빼내는 방식을 택했다. 스키마 변경은 되돌리기 어렵고, `onDelete: Cascade` 자체는 "스팟이 없어지면 그 방문 기록도 없어진다"는 의미로 여전히 옳다. 틀린 건 "스팟을 없앤다"는 판단 쪽이었다.

**차단이 아니라 orphan 전환을 골랐다.** 두 안이 있었다.

| 안 | 내용 | 대가 |
|---|---|---|
| 차단 | 남이 쓰고 있으면 삭제 거부 | 즉시 가능. 단 "내 스토리를 못 지운다"는 UX |
| orphan 전환 | `storyId=null`로 공유 스팟 편입 | 올바른 종착지. 표지 검증 필요 |

차단은 데이터를 지키는 대신 사용자에게 대가를 떠넘긴다. orphan 전환을 택하되, 그 전에 `storyId=null`이 안전한지 조사부터 했다.

**조사 결과가 결정을 바꿨다.** 처음엔 orphan 도입이 큰 문을 여는 줄 알았다. 인수인계서 표지에 `s.story!` 비-null 단언과 RLS 소유자 검사가 걸린다고 적혀 있었다. 그런데 실제로 확인하니:

```
spot.storyId를 non-null로 취급하는 코드   0곳  (표지의 s.story!는 오독, 실제는 ss.story)
storyId=null 행                          이미 45/66 live (시딩 스팟)
스키마·RLS 변경                          둘 다 불필요
```

**두 달 전부터 열려 있던 문이었다.** 시딩(0190)이 이미 45행을 null로 만들어놨고, 정상 동작 중이었다. 표지 목록이 오래 적혀 있었다는 이유로 검증 없이 믿고 있었던 것이다.

**청소는 `source` 컬럼으로 갈랐다.** "참조 0이면 삭제"만으로는 시딩 스팟 45개가 함께 날아간다. 걔들도 `story_spots=0`이기 때문이다. 시딩과 사용자 생성을 구분할 표식이 없어서 컬럼으로 만들었다.

**청소 범위는 전체 스캔이 아니라 국소로 잡았다.** 전체 스캔은 삭제할 때마다 전 스팟을 훑는다. 지금은 67개지만 늘어난다. 국소는 다른 경로로 생긴 orphan을 못 잡지만, 그건 0209에서 한 번 쓸면 된다.

## 4. 작성·수정한 코드

### 0205 — orphan 전환 (+35 −2)

공용 헬퍼를 하나 만들었다. **`storyId: { not: thisStoryId }`가 핵심**이다. 자기 자신의 참조를 세면 모든 owned 스팟이 orphan화된다.

```ts
// app/(protected)/story/[id]/actions.ts
// S3-a 후속: owned 스팟 삭제 전, "다른 스토리(storyId≠this)의 story_spots가 참조 중"인 spotId를 찾는다.
// 참조 있으면 하드삭제 대신 storyId=null로 orphan(공유 스팟 편입) — Spot→StorySpot Cascade로 타 스토리
// 여행동선이 사라지는 소실 방지.
async function findSharedOwnedSpotIds(
  tx: Prisma.TransactionClient,
  ownedSpotIds: string[],
  thisStoryId: string,
): Promise<string[]> {
  if (ownedSpotIds.length === 0) return [];
  const refs = await tx.storySpot.findMany({
    where: { spotId: { in: ownedSpotIds }, storyId: { not: thisStoryId } },
    select: { spotId: true },
    distinct: ['spotId'],
  });
  return refs.map((r) => r.spotId);
}
```

삭제 경로. **전환이 `story.delete`보다 먼저**여야 한다.

```ts
// app/(protected)/story/[id]/actions.ts  (deleteStoryAction)
- await prisma.story.delete({ where: { id: storyId } });
+ // owned 스팟 중 "다른 스토리가 재사용 중"인 것은 story.delete cascade 전에 orphan(storyId=null)으로 전환.
+ // 전환은 반드시 delete보다 먼저(같은 tx).
+ await prisma.$transaction(async (tx) => {
+   const owned = await tx.spot.findMany({ where: { storyId }, select: { id: true } });
+   const shared = await findSharedOwnedSpotIds(tx, owned.map((s) => s.id), storyId);
+   if (shared.length > 0) {
+     await tx.spot.updateMany({ where: { id: { in: shared } }, data: { storyId: null } });
+   }
+   await tx.story.delete({ where: { id: storyId } });
+ });
```

편집 경로. `deleteMany`가 `where: { storyId }` 스코프라 **orphan된 스팟은 자동으로 제외된다.**

```ts
// app/(protected)/story/[id]/actions.ts  (updateStoryAction)
+ // 제출 목록에서 빠진 owned spot 중 "다른 스토리가 재사용 중"인 것은 삭제 대신 orphan(storyId=null).
+ // orphan은 아래 deleteMany({storyId})·재도출 derived(storyId) 스코프에서 자동 제외(실측 확인).
+ const removedOwned = await tx.spot.findMany({ where: { storyId, id: { notIn: ownedRealIds } }, select: { id: true } });
+ const sharedRemoved = await findSharedOwnedSpotIds(tx, removedOwned.map((s) => s.id), storyId);
+ if (sharedRemoved.length > 0) {
+   await tx.spot.updateMany({ where: { id: { in: sharedRemoved } }, data: { storyId: null } });
+ }
  await tx.spot.deleteMany({ where: { storyId, id: { notIn: ownedRealIds } } });
```

### 0207 — source 컬럼 (+70)

```prisma
// prisma/schema.prisma
// 0207: Spot 프로비넌스. 'seed'=시딩 촬영지(청소 보호)/'user'=사용자 생성. 0208 청소 로직 분기축
enum SpotSource {
  seed
  user
}

model Spot {
  // ...
  source      SpotSource @default(user)
}
```

마이그레이션은 수동 4단계로 넣었고, 멱등하게 짰다. 백필 매칭 키는 **시딩 스크립트 자신의 dedup 키(`name` + 좌표 4자리)를 재사용**했다. `id`는 dev/prod마다 달라 마이그레이션에 넣으면 깨진다.

```sql
-- prisma/migrations/20260714160000_add_spot_source/migration.sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'SpotSource') THEN
    CREATE TYPE "SpotSource" AS ENUM ('seed', 'user');
  END IF;
END $$;

ALTER TABLE "spots" ADD COLUMN IF NOT EXISTS "source" "SpotSource" NOT NULL DEFAULT 'user';

-- 백필: seed-spots.json 45개를 name+좌표(4자리)로 매칭해 'seed' 전환. 나머지는 default 'user' 유지.
UPDATE "spots" s SET "source" = 'seed'
FROM (VALUES
  ('덕수궁 돌담길', 37.5659, 126.975),
  ('경원재 앰배서더 인천', 37.3916, 126.6372),
  …(45개)…
  ('북촌로6길', 37.58, 126.9855)
) AS seed(name, lat, lng)
WHERE s.name = seed.name
  AND round(s.lat::numeric, 4) = seed.lat
  AND round(s.lng::numeric, 4) = seed.lng;
```

### 0208 — 자동 청소 (+28)

**후보를 삭제 전에 캡처한다.** cascade가 `story_spots`를 지우고 나면 "이 스토리가 뭘 참조했었는지" 알 수 없다.

```ts
// app/(protected)/story/[id]/actions.ts  (편집 경로)
+ // 0208: 이 스토리에서 떨어져 나갈 storySpot의 spotId를 deleteMany 전에 캡처 (참조 0 청소 후보).
+ const droppedRefSpotIds = (
+   await tx.storySpot.findMany({
+     where: { storyId, spotId: { notIn: [...derivedSpotIds, ...reusedSpotIds] } },
+     select: { spotId: true },
+     distinct: ['spotId'],
+   })
+ ).map((r) => r.spotId);
  await tx.storySpot.deleteMany({ where: { storyId, spotId: { notIn: [...derivedSpotIds, ...reusedSpotIds] } } });
```

**청소는 트랜잭션 마지막에.** orphan 전환과 cascade가 끝난 최종 상태를 읽어야 한다. 그리고 삭제 판정은 **미리 센 숫자가 아니라 `storySpots: { none: {} }`로 삭제 시점에** 한다.

```ts
// app/(protected)/story/[id]/actions.ts  (편집 경로)
+ // 0208: 모든 storySpot 재도출 뒤 마지막에 실행. 편집에서 빠져 참조 0이 된 user orphan 스팟만 삭제.
+ // seed·타 스토리 참조(방금 재사용 포함, story_spots none 판정)·소유 스팟은 조건에서 탈락.
+ if (droppedRefSpotIds.length > 0) {
+   await tx.spot.deleteMany({
+     where: { id: { in: droppedRefSpotIds }, storyId: null, source: 'user', storySpots: { none: {} } },
+   });
+ }
```

삭제 경로도 같은 구조다.

```ts
// app/(protected)/story/[id]/actions.ts  (deleteStoryAction)
+ // 0208: 청소 후보 = 이 스토리가 참조하던 spotId. story.delete cascade로 story_spots가 0이 될 수 있어 delete 전 캡처.
+ const refSpotIds = (
+   await tx.storySpot.findMany({ where: { storyId }, select: { spotId: true }, distinct: ['spotId'] })
+ ).map((r) => r.spotId);

  await tx.story.delete({ where: { id: storyId } });

+ // 0208: orphan 전환·cascade 뒤에만 실행. 참조 0 + 주인 없음 + user 인 후보만 삭제.
+ if (refSpotIds.length > 0) {
+   await tx.spot.deleteMany({
+     where: { id: { in: refSpotIds }, storyId: null, source: 'user', storySpots: { none: {} } },
+   });
+ }
```

| 참조 0이 된 user 스팟 | 자동 삭제 (전체 53→52) |
| 참조 0인 seed 스팟 | 잔존 (45개 보호) |

**두 번째가 이번 작업의 본체다.** 0205 이전이었으면 도깨비_2의 여행동선이 통째로 사라졌을 것이다.

0209는 코드가 아니라 SQL 한 번이었다. 0208은 국소 스코프라 이미 생긴 orphan은 트리거를 못 만난다. 0208과 **같은 세 조건**(`storyId=null`, `story_spots=0`, `source='user'`)을 조건절로 써서 한 번 쓸었고, 광화문 1건이 정리됐다(52→51). id를 하드코딩하지 않고 조건절로 쓴 이유는 **코드와 SQL의 논리를 같게 유지**하기 위해서다.

### 배운 것 1 — 관계는 그대로인데 의미가 바뀐다

이번 버그의 한 줄이다.

```
schema는 안 바뀌었다. Cascade도 그대로다.
바뀐 건 "한 스팟을 참조하는 스토리는 하나뿐"이라는 전제였다.
S3-a가 그걸 깼고, Cascade는 낡은 전제 위에서 계속 옳게 동작했다.
```

**코드 리뷰로는 안 잡히는 종류다.** `onDelete: Cascade` 줄을 아무리 들여다봐도 틀린 게 없다. 관계 정의는 여전히 맞다. 잘못된 건 그 관계가 서 있는 세계 쪽이다.

기능을 추가할 때 "무엇이 바뀌었나"만 보면 놓친다. **"이 변경으로 어떤 전제가 깨졌나"**를 따로 물어야 한다. S3-a는 스팟 재사용을 추가했을 뿐인데, 그 순간 삭제·편집·평점·표시 경로의 전제가 동시에 무효가 됐다.

### 배운 것 2 — 오래 적혀 있다고 사실이 되지 않는다

인수인계서 표지에 이렇게 적혀 있었다.

```
lib/spot/queries.ts 의 s.story! 비-null 단언  → storyId=null 생기면 크래시
spots_insert RLS 소유자 검사                 → storyId=null 이면 깨짐
```

이걸 믿고 "orphan을 도입하면 S3-b를 앞당겨 해야 한다"고 판단했다. 그런데 실제로 조사하니 **`s.story!` 단언은 존재한 적이 없었고**(실제는 `ss.story`, 오독이었다) **`storyId=null` 행은 이미 45개가 정상 동작 중**이었다.

더 나쁜 건, 0201 커밋 메시지에 "storyId=null이 생기지 않아 표지 전부 무관"이라고 적어뒀다는 것이다. 그때 이미 시딩(0190)이 45행을 null로 만든 뒤였다. **틀린 서술이 커밋 메시지에 박혀서 다시 근거로 쓰였다.**

표지 목록은 "확인해야 할 것"이지 "확인된 것"이 아니다. 그 구분이 흐려지면 검증 없이 결정 근거가 된다.

### 배운 것 3 — 순서가 만드는 안전

편집 경로에서 `spot_movies`와 촬영 장면 설명이 무접촉으로 살아남는다. 처음엔 왜인지 몰랐는데, 코드 순서를 보니 이유가 있었다.

```
:98   orphan 전환 (storyId=null)      ← 먼저 실행
:151  derived = where { storyId }     ← orphan은 여기서 이미 빠진다
:179  spot_movies 재도출 (derived 스코프)
```

**orphan이 derived 산출보다 먼저 일어나므로, 재도출 집합에 애초에 안 잡힌다.** 우연이 아니라 순서가 만든 안전이고, orphan 전환을 한 줄만 뒤로 옮겼어도 `description` 54건이 날아갈 수 있었다.

같은 원리가 0208에도 있다. 청소 후보를 `deleteMany` **전에** 캡처하는 이유, 청소 실행을 트랜잭션 **마지막에** 두는 이유가 다 순서다. 트랜잭션 안에서는 "무엇을 하는가"만큼 "언제 하는가"가 정확해야 한다.

### 배운 것 4 — 검증에서 논증을 받지 않는다

0205 plan의 검증안이 "실 DB 파괴 없이 로직·조건으로 논증하겠다"였다. 되돌려 보내고 롤백 트랜잭션 실측을 요구했다.

이유가 있다. 이 세션에서 "같아 보인다"가 두 번 틀렸다. 편집 경로가 삭제 경로와 같은 시퀀스로 보였지만 실제로는 확증이 필요했고, 조사 시점의 코드와 구현된 코드가 같아 보였지만 실행해봐야 알았다.

특히 **(c) seed 스팟 보호**는 논증으로 넘어갈 수 없었다. 여기가 틀리면 시딩 촬영지 45개가 통째로 날아간다. 실제로 롤백 tx로 돌려보니 `story_spots=0`인데도 `source='user'` 필터에서 걸러져 생존했다.

한 가지 더. 브라우저 실전 검증에서 **X(orphan될 스팟)와 Y(그냥 삭제될 스팟)를 한 스토리에 같이 넣고** 테스트했다. 하나만 넣으면 "전부 살린다"는 잘못된 코드도, "전부 지운다"는 원래 버그도 통과해버린다. **갈라지는지를 봐야 한다.**

### 배운 것 5 — 남은 부채

orphan 전환은 "주인 없는 스팟"을 만든다. 이 스팟은 이름·좌표를 아무도 고칠 수 없다. RLS상 소유자가 없고, 스팟 편집 UI는 스토리 안에만 있기 때문이다.

원래 시딩 스팟 45개가 같은 상태였으니 새로 생긴 문제는 아니다. 다만 **orphan이 그 수를 늘린다.** 위키형 편집 설계 부채가 커졌다.

그리고 사용자 입장에서 어색한 순간이 하나 남는다.

```
내가 만든 스팟 X를 편집에서 뺐다  →  성공
그런데 X는 지도에 그대로 남아 있다  →  "왜 안 지워지지?"
```

데이터는 지켰지만 기대와 어긋난다. 안내가 없다. 이건 UI 작업이라 이번 범위에서 열지 않았다.
