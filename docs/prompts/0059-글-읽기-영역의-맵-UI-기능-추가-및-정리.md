## 1. 한 줄 요약

보는 방([id])에 여행 동선을 읽기 전용으로 띄웠다. 새 UI를 만들지 않고 작성/수정 방의 리스트↔마커 카드 전환을 그대로 채용하되 편집 기능·안내만 전부 끄는 방식으로, 통일감·모바일 대응·작성자 혼동 방지를 한 번에 잡았다. 마커/항목 클릭 시 지도 panTo + 펄스 강조 + 사이드가 리스트↔카드로 fade 전환된다.

## 2. 왜 / 목적 / 이유

### 핵심 A — 새 UI가 아니라 "작성 UI를 읽기 전용으로 채용"

- **왜(동기/문제)**: 처음엔 보는 방 전용으로 예쁜 새 레이아웃(지도 위 팝업 등)을 목업까지 만들었다. 근데 모바일 사용 빈도가 높을 텐데 팝업은 좁은 화면을 다 덮어 답답하고, 작성/수정과 다른 UI라 작성자가 혼동할 수 있었다.
- **목적(도달할 상태)**: 작성·수정·읽기가 같은 화면으로 통일돼, 보는 사람도 작성자도 헷갈리지 않고, 모바일은 작성 방 동작을 그대로 물려받아 따로 손 안 대도 되는 상태.
- **이유(채택 근거)**: 새로 만들면 (1) 모바일 대응을 또 해야 하고 (2) 통일감이 깨지고 (3) 컴포넌트가 늘어난다. 기존 SpotList/SpotPopup/SpotMap에 `readOnly` prop만 더해 *편집 손잡이만 떼면*, 보여주는 건 다 두고 손대는 것만 끄는 가벼운 길이 된다.

> 면접용 한 문장: "보는 방을 새로 만들지 않고, 작성 UI에 readOnly를 더해 편집 기능·안내만 끄는 방식으로 세 화면 통일감과 모바일 대응을 동시에 얻었다."

### 핵심 B — 마커 전환 시 카드가 안 갱신된 진짜 원인은 `key` (★ 면접 카드)

- **왜**: 카드가 떠 있을 때 *다른* 마커를 누르면 카드 내용이 새 마커로 안 바뀌고 이전 내용이 남았다.
- **목적**: 마커를 바꿀 때마다 사진·이름·리뷰가 그 마커 기준으로 갱신되는 상태.
- **이유(원인과 해결)**: SpotPopup이 `useState(spot.name)`처럼 *props를 초기값으로만* state에 넣는 구조였다. props(spot)는 바뀌어도, 리액트는 같은 위치·같은 컴포넌트를 *재활용*하느라 내부 state를 이전 spot 그대로 보존한다 — props와 state는 첫 마운트 때 한 번 복사된 뒤 연결이 끊기기 때문. (이건 편집 UI엔 올바른 설계 — props를 계속 따라가면 사용자 입력이 매번 덮어써진다.) 해결은 `key={displayedSpot.id}` — id가 바뀌면 리액트가 다른 컴포넌트로 보고 강제 재마운트해 state를 새 spot 기준으로 초기화한다.

> 면접용 한 문장: "props를 초기값으로만 받은 state는 props가 바뀌어도 안 따라온다(리액트가 컴포넌트를 재활용해 state를 보존). 같은 컴포넌트로 다른 데이터를 보여줄 땐 `key`를 데이터 id로 줘 강제 재마운트한다."

### 핵심 C — fade에서 useEffect 대신 핸들러 동기 업데이트

- **왜/이유**: 카드 fade-out 중에도 내용을 유지하려 `displayedSpot`(마지막 spot 기억) state를 뒀는데, 이걸 `useEffect`로 갱신하면 한 프레임 늦어(렌더 후 실행) A 닫고 B 누를 때 A가 잠깐 번쩍이는 깜빡임이 생긴다. 그래서 useEffect 없이 클릭 핸들러에서 `setDisplayedSpot`을 직접 동기 호출해, 늦는 프레임 자체를 없앴다.

### 핵심 D — readOnly면 @dnd-kit 자체를 안 켬

- **왜/이유**: 읽기 전용에서 드래그 핸들만 숨기고 @dnd-kit은 켜두면 "안 보이는데 드래그는 되는" 이상한 상태가 된다. 그래서 `readOnly`일 때 DndContext/SortableContext를 *아예 감싸지 않고* plain `<ul>`로 렌더 — 드래그가 *동작 자체를 안 하게* 구조로 차단했다.

## 5. 결과 / 배운점

### 결과
- 보는 방에 동선 리스트(좌측 고정) + 지도. 항목/마커 클릭 → panTo + 펄스 + 좌측이 카드로 fade 전환, × 누르면 리스트 복귀.
- 편집 요소·안내 전부 숨김(읽기 전용). 작성/수정 방은 그대로 동작.
- 펄스 색이 마커 색(시작 초록/끝 빨강/중간 파랑) 따라감.

### 배운점
1. **props를 초기값으로만 받은 state는 props가 바뀌어도 안 따라온다.** 리액트가 같은 위치·타입 컴포넌트를 재활용해 state를 보존하기 때문. 같은 컴포넌트로 다른 데이터를 보여줄 땐 `key`를 데이터 id로 줘 강제 재마운트한다. (편집 UI엔 props 미추종이 오히려 올바른 설계 — 입력이 덮어써지지 않게.)
2. **useEffect는 한 박자 늦다.** fade-out 중 내용 유지를 useEffect로 하면 1프레임 깜빡임이 생긴다. 클릭 핸들러에서 state를 직접 동기 호출하면 그 틈이 없다. (key 재마운트가 useEffect 갱신보다 깔끔한 이유와 같은 결.)
3. **읽기 전용은 "숨김"이 아니라 "동작 자체를 안 켜기"로.** 드래그 핸들만 숨기면 안 보이는데 동작은 되는 상태가 된다. readOnly면 DndContext 자체를 안 감싸 구조로 차단.
4. **추측은 빗나갈 수 있고, 진짜 원인은 코드를 봐야 안다.** 갱신 안 됨의 원인을 처음엔 "토글 로직"으로 추측했지만 실제는 key 부재였다. 코드를 읽어 진단한 뒤 고친 게 맞았다. (Prisma·라이브러리 버전 때와 같은 교훈.)
5. **새로 만드는 것보다 "끄기"가 가벼울 때가 있다.** 보는 방을 새 UI로 짜는 대신 작성 UI에 readOnly만 더해, 통일감·모바일 대응·코드량을 한 번에 잡았다.

### 남긴 것 (다음 작업)
- **0060 fade 통일은 안 하기로 판단** — 작성 방은 unmount/mount 구조라 fade에 JSX 구조 변경(★★★)이 필요한데, 업계 기준(iOS 가이드·NN/g)상 빠른 도구 조작(pinning/search/edit)엔 fade가 오히려 방해다. "읽기=fade, 작성=빠릿"은 비일관이 아니라 맥락에 맞춘 일관(Figma Dev Mode 등 기업도 모드별 차등이 정상). 별도 회고로 남길 가치 있음.
- 모바일 작성/수정 방 레이아웃(글씨 위로 뜸) — 작성 방도 같이 가진 문제라 양쪽 한 번에. ★★★.
