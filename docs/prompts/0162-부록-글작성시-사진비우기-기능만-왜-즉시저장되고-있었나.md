## 부록 — 글 작성 시, 사진 비우기 기능만 왜 즉시 저장되고 있었나? (git 이력 발굴)

### 발견의 계기

0161(SpotPopup 상태 재배치) 완료 후 브라우저 수동 검증 중 위화감이 있었다. 이 앱의 편집은 2단 저장이다 — 팝업의 [저장]은 화면 임시 반영까지, 실제 DB 반영은 페이지 상단 [수정] 제출이 담당한다. 실제로 스팟을 삭제해도 상단 [수정] 없이 새로고침하면 마커가 되살아난다. 그런데 **사진 비우기만 팝업 [저장] 시점에 즉시 서버 반영**되고 있었다 — 그것도 Storage 파일 물리 삭제라 새로고침으로도 복구 불가. 모든 조작 중 이것 하나만 원칙 밖에서 움직이고 있었고, 이 비대칭의 수리가 본론(§1~5)이다.

수리를 마치고 질문이 남았다 — 2단 저장 구조를 스스로 만든 프로젝트에 왜 이 예외가 존재했나. git 이력과 당시 회고를 발굴한 결과를 부록으로 남긴다. 결론부터: 예외는 구조 전환에서 살아남은 잔재가 아니라, **전환 완료 52분 뒤에 새로 태어난 회귀**였다.

### 왜 회귀했나

당시 회고(0053)는 defer 원칙을 스스로 세워 두었다: "비우기를 즉시 실행하면 [취소]가 의미 없어짐 → 실제 삭제는 [저장] 시점으로 연기." 원칙은 정확했으나 **적용 범위를 팝업 한 층(취소 대비)까지만 설정** — "팝업 저장 = 확정"으로 모델링했고, 상단 제출까지의 2단은 tmp_ 스팟에서만 실현했다.

회귀의 배경 추정(이력에 명시 근거 없음): 추가·교체는 pendingPhotos Map에 파일을 싣는 지연 채널이 자연스러웠지만, 비우기는 실을 파일이 없어 의도 채널이 없어 보였고 가장 짧은 길이 개별 액션이었을 것. 실제로는 그 채널이 photoUrl:null로 이미 존재했으나 당시 그렇게 읽지 못했다 — 이번 사이클의 서버 파생 판정이 그 읽기를 6주 늦게 수행한 셈이다.

### 배운점 — 원칙의 사정거리

- 결함의 성격은 "원칙 부재"도 "원칙 위반"도 아닌 **원칙의 적용 범위 미달**이었다. 원칙을 세우는 것과 그 원칙이 닿아야 할 층을 전부 짚는 것은 다른 작업이다.
- 전환 완료 52분 뒤의 새 기능에서 회귀가 일어났다 — 작업 중의 판단과 원칙 수립 시의 판단은 같은 사람 안에서도 분리된다. 완료 시점의 원칙 정합 자가점검(CLAUDE.md §8 신설)이 이 간극의 대응책이다.
- 모순은 6주간 어떤 문서에도 잡히지 않았고, 발견 경로는 실기기 수동 검증의 위화감이었다 — 테스트와 문서가 놓치는 층을 수동 검증이 잡는다.
