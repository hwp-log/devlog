## 1. 한 줄 요약

세 목록 화면의 로딩 표시를 하나의 원칙으로 정리하고, 플랜파인더에 페이지네이션을 넣으면서 번호바를 스토리와 공유하도록 뽑아냈다.

## 2. 왜 / 목적 / 이유

### 왜 (동기·문제)

카드 교체(0406)까지 끝나고 나니 화면의 **빈 상태**가 남아 있었다. 플랜파인더에는 로딩 표시가 아예 없었고, 필터 결과가 0건이면 `이 가격대 플랜이 없습니다`라는 문장 한 줄이 회색 박스에 떠 있었다. 다음 행동을 안내하지 않는 막다른 화면이었다.

그리고 로딩을 넣으려다 더 큰 문제를 봤다. **세 목록 화면이 서로 다른 순간에만 로딩을 보여주고 있었다.**

| 화면 | 진입 로딩 | 화면 내 로딩 |
|---|---|---|
| 플랜파인더 | 없음 | 불필요(필터가 동기 연산) |
| 스토리 | 없음 | `useTransition` 있음 |
| 스팟파인더 | 없음 | 있음 |

스토리·스팟파인더는 화면 안에서 뭘 누를 때는 스켈레톤이 뜨는데 그 화면으로 **이동해 올 때는 아무것도 안 떴다.**

### 목적 (도달하려는 상태)

- 빈 상태가 막다른 골목이 아니라 다음 행동을 안내한다
- 세 화면이 같은 대기 길이에 같은 표시를 한다
- 목록이 길어져도 한 번에 다 그리지 않는다

### 이유 (채택 근거)

**로딩을 한 방식으로 통일하지 않은 이유** — 진입 로딩(`loading.tsx`)과 화면 내 로딩(`useTransition`)은 경쟁 관계가 아니라 **다른 순간을 맡는다.** 한쪽으로 몰면 반드시 구멍이 생긴다. `loading.tsx`만 쓰면 화면 안 상호작용에 표시가 없고, `useTransition`만 쓰면 진입할 때 흰 화면이다.

그래서 통일할 대상은 메커니즘이 아니라 **생김새와 판단 기준**이라고 봤다. 판단 기준은 "서버를 거치느냐"가 아니라 **"지금 화면에 있는 걸로 답할 수 있느냐"**다. 플랜파인더 필터는 이미 받아둔 배열을 거르는 동기 연산이라 대기가 0이고, 여기에 스켈레톤을 띄우면 깜빡임만 생긴다.

**스켈레톤을 화면 전체에 씌우지 않은 이유** — 눈썹·타이틀은 서버 응답과 무관한 정적 텍스트다. 셔머로 덮었다가 같은 자리에 같은 글자가 나타나면 깜빡임이다. **"아직 모르는 것에만 씌운다"**를 원칙으로 잡았다.

**폭 규칙을 스토리 열 구성으로 복사하지 않은 이유** — 플랜 카드는 메타 줄(`서울 용산구 이태원 · 3일 · 스팟 4곳 · 1인`)이 길어 **320px 밑에서 잘린다.** 스토리 카드는 제목 + 지역 + 좋아요라 좁아도 버틴다. 카드가 담는 정보량이 다르므로 열 구성을 그대로 가져오면 안 된다.

**페이지네이션을 서버가 아니라 클라이언트 슬라이스로 한 이유** — 정렬·필터 기준인 가격대 `band`가 **비용 합산에서 나오는 파생값**이지 DB 컬럼이 아니다. SQL `where`/`order by`로 쓸 수가 없다. 서버로 가려면 플랜 총액을 `MyPlan` 컬럼으로 저장하는 게 선행 조건이고, 그건 별건이다. 그리고 실제 통증은 데이터 전송량이 아니라 **이미지 34장 동시 로드**였는데, 클라이언트 슬라이스만으로도 그건 해결된다.

## 4. 작성·수정한 코드

### 0412 — 상태 3종

`plan-finder/loading.tsx`를 신설했다. **이 시점 버전은 화면 전체를 셔머로 덮었다.**

```tsx
// 플랜파인더 첫 진입(서버 페치 중) 로딩 스켈레톤.
// 헤더 행 + 카드 그리드를 실제 레이아웃과 동일 치수로 채운다.
export default function Loading() {
  return (
    <div aria-hidden>
      <div className="flex flex-col gap-3 sm:flex-row sm:items-end sm:justify-between mb-4 sm:mb-6">
        <div>
          <div className="skeleton-shimmer h-[11px] w-16 rounded" />       {/* 눈썹 */}
          <div className="skeleton-shimmer h-5 w-36 rounded mt-3" />       {/* 타이틀 */}
          <div className="skeleton-shimmer h-[14px] w-44 rounded mt-4" />  {/* 요약 */}
        </div>
        <div className="flex flex-wrap gap-2">
          <div className="skeleton-shimmer h-8 w-[72px] rounded-full" />
          <div className="skeleton-shimmer h-8 w-[64px] rounded-full" />
        </div>
      </div>
      <div className="grid grid-cols-1 sm:grid-cols-3 gap-[11px] sm:gap-[14px]">
        {Array.from({ length: 3 }).map((_, i) => (
          <div key={i} className="bg-card border border-border rounded-[14px] h-[240px] sm:h-[280px]
                                  flex flex-col justify-end gap-2.5 p-4">
            <div className="skeleton-shimmer h-3 w-3/5 rounded" />
            <div className="skeleton-shimmer h-3 w-[45%] rounded" />
            <div className="skeleton-shimmer h-[26px] w-2/5 rounded" />
            <div className="skeleton-shimmer h-3 w-[35%] rounded" />
          </div>
        ))}
      </div>
    </div>
  );
}
```

**눈썹·타이틀까지 전부 셔머고, 카드는 `bg-card` 위에 텍스트 바 4줄이다.** 둘 다 0414에서 뒤집힌다.

빈 상태는 안내 카드로 바꿨다. 필터 0건은 고스트 버튼, 전체 0건은 프라이머리 버튼으로 무게를 달리했다.

```diff
- className="bg-card border border-border rounded-[14px] p-12 text-center text-fg2"
- 이 가격대 플랜이 없습니다
+ className="border-[1.5px] border-dashed border-border rounded-[14px] p-[22px]
+            flex flex-col items-center text-center gap-3"
+ <span className="w-2 h-2 rounded-full bg-primary" />
+ <p className="text-[13px] leading-[1.6] text-fg2 break-keep">
+   이 가격대의 코스가 아직 없어요.<br />첫 코스의 점을 찍어보세요.
+ </p>
+ <Link href="/my-plan/new" className="... border border-border ...">내 플랜 공개하기</Link>
```

점선 테두리와 파란 점은 "여긴 아직 비어 있고 채울 수 있다"는 신호다. 실선 카드는 완결된 정보처럼 보인다.

### 0413 — 진입 로딩 두 화면

`story/loading.tsx`에 원칙을 주석으로 명시했다.

```tsx
// 스토리 목록 첫 진입(서버 페치 중) 로딩 스켈레톤 — 0413.
// 다른 화면에서 이동해 올 때의 진입 표시. 화면 내 useTransition 로딩(StoryListPaged)과는 별개 층.
// 스켈레톤은 "아직 모르는 것"에만 씌운다:
//  · 눈썹·타이틀은 서버 응답과 무관한 정적 텍스트 → 실제 StoryHeader 그대로 렌더
//    (셔머로 덮으면 같은 글자 재출현 = 깜빡임).
//  · 검색바는 셔머로 — 실제 input을 그리면 입력 가능해 보이나 핸들러가 없어 입력이 유실됨.
//  · 카드 그리드는 StorySkeletonGrid 재사용, count=STORY_PAGE_SIZE로
//    초기 페인트 스켈레톤과 동일 치수(전환 시 시프트 없음).
export default function Loading() {
  return (
    <div>
      <div className="flex flex-col md:flex-row md:items-end md:justify-between gap-4 mb-6">
        <StoryHeader />
        <div className="skeleton-shimmer h-10 w-full md:w-70 rounded-full" aria-hidden />
      </div>
      <StorySkeletonGrid count={STORY_PAGE_SIZE} />
    </div>
  );
}
```

**루트의 `aria-hidden`이 사라지고 셔머 요소별로 옮겨간 것**이 이 원칙의 결과다. 실제 헤더가 안에 있으니 통째로 숨기면 안 된다.

스팟파인더는 `SpotFinderLoadingSkeleton`이 이미 있었다. `SpotFinderMapWrapper`의 dynamic import 폴백으로만 쓰이던 것이라 `loading.tsx`에서 그대로 재사용했고, 결과적으로 **진입 로딩과 청크 로딩이 같은 화면**이 돼 이음새가 사라졌다.

### 0414 — 스켈레톤 컴포넌트 분리

`PlanSkeletonGrid`를 뽑고 `loading.tsx`를 0413 원칙에 맞췄다. 두 가지가 뒤집혔다.

- **눈썹·타이틀을 셔머에서 실제 `PlanFinderHeader` 렌더로** — 요약 줄과 필터만 셔머로 남겼다(데이터 의존)
- **카드 내부의 텍스트 바 4줄을 없애고 표면 전체를 셔머 블록 하나로** — 커버 카드는 표면 전체가 사진이라, 셔머 위에 셔머 바를 그리면 겹쳐서 지저분해진다

카드 스켈레톤이 컴포넌트가 되면서 `PlanCard` 치수가 바뀔 때 고칠 자리가 한 곳으로 줄었다.

```diff
-const WIDE_ROUTES = ['/story'];
+const WIDE_ROUTES = ['/story', '/plan-finder'];
```

`WIDE_ROUTES`는 정확 매칭이라 **목록만 풀폭이 되고 `/plan-finder/[id]` 상세는 `max-w`를 유지**한다. 상세는 읽는 화면이라 폭이 넓으면 오히려 나쁘다.

```diff
-className="grid grid-cols-1 sm:grid-cols-3 gap-[11px] sm:gap-[14px]"
+className="grid grid-cols-[repeat(auto-fill,minmax(320px,1fr))] gap-[11px] sm:gap-[14px]"
```

브레이크포인트로 열 수를 정하는 대신 **카드 최소 폭 320px을 정하고 열을 자동으로 채우게** 했다. 1280이면 3열, 1920이면 5열이 되면서 카드 폭이 늘 320~450 사이에 머문다. 브레이크포인트를 안 쓰니 초광폭 대응도 따로 필요 없다.

```diff
-sizes="(max-width: 767px) 100vw, 33vw"
+sizes="(max-width: 767px) 100vw, 400px"
```

**열 수가 가변이 되면서 `33vw`가 의미를 잃었다.** 3열 기준으로 계산된 값인데 이제 열이 3~7개로 변하기 때문이다. 실제 카드 폭 범위에 맞춰 고정값으로 바꿨다.

### 0416 — 페이지네이션과 번호바 공용화

`lib/plan/pagination.ts`를 따로 만든 이유가 주석에 있다.

```ts
// 플랜파인더 한 페이지 크기 — 스토리(STORY_PAGE_SIZE=15)와 동일.
// lib/plan/queries.ts는 'server-only'라 클라이언트(PlanListClient)가 import 불가 →
// 무-server-only 파일에 상수만 분리해 클라·서버 양쪽이 쓴다.
export const PLAN_PAGE_SIZE = 14;
```

**이 세 줄에 오류가 두 개 있다.** 주석은 "스토리와 동일"이라 하고 커밋 메시지는 "15개씩"이라 했는데 값은 `14`다. 당시에는 아무도 못 봤고 0425에서 12로 바꾸면서 자연히 없어졌다.

`Pagination.tsx`는 스토리에서 그대로 뽑아냈다. 핵심은 `buildPages`다.

```ts
/** 첫·현재·마지막 고정, 중간 …생략. 반환 길이 = slots(total>slots일 때). */
function buildPages(current: number, total: number, slots: number): (number | 'ellipsis')[] {
  if (total <= slots) return Array.from({ length: total }, (_, i) => i + 1);
  const inner = slots - 2;                                   // 1·total 제외 중간 예산
  let left = Math.max(2, current - Math.floor((inner - 1) / 2));
  const right = Math.min(total - 1, left + inner - 1);
  left = Math.max(2, right - inner + 1);                     // 우측 경계 보정
  const showLeft = left > 2;
  const showRight = right < total - 1;
  // …가 슬롯 1칸 차지 → 숫자 창을 한 칸씩 축소해 총 길이 유지
  const from = showLeft ? left + 1 : left;
  const to   = showRight ? right - 1 : right;
  // [1, …?, from..to, …?, total]
}
```

추출하면서 인터페이스를 범용화했다.

| 스토리 전용 | 공용 |
|---|---|
| 소비처의 `{totalPages > 1 && …}` | 컴포넌트 내부 `if (totalPages <= 1) return null` |
| `isPending` | `disabled` prop |
| `goTo` 직접 호출 | `onGo` 콜백 |

```tsx
// 번호 페이지네이션 UI 공용 컴포넌트 — 스토리(0307)에서 추출, 플랜파인더(0416)와 공유.
// 데이터 소스(URL 재요청이냐 클라 슬라이스냐)는 소비처가 onGo에서 결정한다.
// 이 컴포넌트는 "몇 페이지가 있고 지금 몇 페이지인가"만 그린다.
```

이 주석이 추출의 기준이다. **번호바는 페이지 수와 현재 위치만 알면 되고, 그 페이지를 어떻게 가져오는지는 몰라도 된다.** 그래서 서버 재요청을 쓰는 스토리와 클라이언트 슬라이스를 쓰는 플랜파인더가 같은 컴포넌트를 쓸 수 있다.

`StoryListPaged`에서는 80줄이 빠지고 한 줄이 들어갔다.

```diff
-{totalPages > 1 && ( <nav aria-label="페이지 네비게이션" …> …47줄… </nav> )}
+<Pagination page={page} totalPages={totalPages} onGo={goTo} disabled={isPending} />
```

`PlanListClient` 상단에는 이 방식의 한계를 명기했다.

```ts
// 페이지네이션(0416): 클라이언트 슬라이스 방식.
// ⚠️ 이건 "이미지 로딩"만 해결한다 — page.tsx가 fetchPublicPlans로 공개 플랜을 여전히 전량 수신하고,
//    여기서 정렬·필터·슬라이스한다. 데이터 전송량은 그대로. 현재 페이지 카드만 마운트돼
//    next/image가 그만큼만 요청하는 게 이득의 전부.
// 서버 페이지네이션으로 전환하려면 선행 조건: 정렬·필터 기준인 가격대 band가 비용 합산 "파생값"이라
//    SQL where/order로 못 쓴다 → 플랜 총액을 MyPlan 컬럼으로 저장(생성·수정 시 집계)해야
//    DB LIMIT/OFFSET + 총액 필터/정렬이 가능해진다. 그 전엔 서버 전환 이득이 없다.
```

슬라이스 자체는 짧다.


필터·정렬 변경 시 `setPage(1)`을 붙였고, 페이지 이동 시 문서 최상단으로 스크롤한다(첫 마운트는 skip).

## 5. 결과 / 배운 것

### 결과

- 세 목록 화면 모두 진입 로딩이 생겼고 스켈레톤 원칙이 같아졌다
- 빈 상태가 안내 카드로 바뀌어 다음 행동(`내 플랜 공개하기`)으로 이어진다
- 번호바가 공용 컴포넌트가 되면서 `StoryListPaged`에서 80줄이 지워졌다
- 34개 목록이 세 페이지로 나뉘고 한 번에 마운트되는 카드가 줄었다

### 배운 것

**통일할 대상은 메커니즘이 아니라 판단 기준이었다.** 처음에는 "로딩 방식을 하나로 통일한다"로 접근했는데, 진입과 상호작용은 다른 순간이라 한쪽으로 몰면 반드시 구멍이 생긴다. 검색해보니 표준도 같은 얘기였다 — 1초 미만 대기에는 로딩 표시를 쓰지 말고, 이미 불러온 콘텐츠를 스켈레톤으로 덮는 건 안티패턴이다. **지켜야 할 일관성은 "같은 대기 길이에 같은 표시"이지 "모든 화면에 같은 애니메이션"이 아니다.**

**스켈레톤은 모르는 것에만 씌운다.** 정적 텍스트를 셔머로 덮으면 같은 자리에 같은 글자가 다시 나타나 깜빡임이 된다. 실제 input을 그리면 입력이 가능해 보이는데 핸들러가 없어 유실된다. 이 두 경우가 원칙의 양쪽 근거다.

**추출의 기준은 "무엇을 몰라도 되는가"다.** 번호바는 페이지 수와 현재 위치만 알면 되고 데이터를 어떻게 가져오는지는 몰라도 된다. 그 경계를 주석에 적어두니 서버 재요청(스토리)과 클라이언트 슬라이스(플랜파인더)가 같은 컴포넌트를 쓸 수 있었다. 반대로 `goTo`·스크롤 처리·크로스페이드는 소비처마다 달라 스토리에 남겼다.

**해결이 아니라 유예라면 그렇게 적어야 한다.** 클라이언트 슬라이스는 이미지 로딩만 해결하고 데이터는 여전히 전량 내려온다. 34개면 무시할 만하지만 500개면 아니다. 그 한계와 서버 전환의 선행 조건(총액을 컬럼으로 저장)을 코드 주석에 남겨두면, 나중에 이 코드를 보는 사람이 "왜 서버로 안 했지"를 다시 파지 않아도 된다.

**문서와 코드가 어긋난 채로 커밋됐다.** `PLAN_PAGE_SIZE = 14`인데 주석은 "스토리와 동일(15)", 커밋 메시지는 "15개씩"이었다. 셋 중 어느 것도 서로 안 맞았고 당시엔 아무도 못 봤다. **주석에 숫자를 적으면 코드와 따로 늙는다** — 다른 상수를 참조하거나 아예 안 적는 게 낫다.
