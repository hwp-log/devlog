## 1. 한 줄 요약

결제 승인 라우트(`app/(protected)/payment/confirm/route.ts`)에 테스트가 0건이었다. 스위트 전수 판독 → 승인 경로 구현 판독 → 테스트 작성의 3단계로 진행해 금액 검증·이중 승인·지급 실패 보존·인증 네 가지 방어와 승인 후의 담기 실패 보존·승인 실패 기록 두 경로를 검사하는 6건을 신설했다. 구현 수정 0, 전체 213/213 통과.

## 2. 왜 / 목적 / 이유

왜: 0616에서 CI를 붙였지만 CI가 돌리는 테스트 207개 중 결제는 0건이었다.
구현과 테스트를 같은 쪽인 CC가 만들어 맹점을 공유할 가능성을 걱정했는데
판독해보니 실제 문제는 그게 아니라 207건 중 158건의 검사가 유틸·렌더링에
몰려 있던 것이었다. ★★★★★ 등급인 결제는 비어 있었다.

목적: 테스트를 짜기 전에 구현부터 판독했다. 네 가지 방어가 전부 있음을
확인한 뒤 그 방어가 실제로 도는지를
검사하는 쪽으로 케이스를 잡았다.

이유 — assert 통일: 매 케이스의 핵심 assert를 "confirmPayment가
불렸는가"로 통일했다. 상태만 보면 FAILED가 됐다는 것만 알 수 있고
돈이 나갔는지는 그 호출 여부로만 갈린다.

## 4. 코드 작성 & 수정

신규 1파일: `app/(protected)/payment/confirm/__tests__/route.test.ts` (157줄)

구성: 파일 상단 `@jest-environment node` 독블록, Supabase·Prisma·
confirmPayment·copyPublicPlanAction의 mock 4벌, PENDING 주문 공통 픽스처,
그리고 승인 차단 4건과 승인 이후 2건의 describe 2그룹.

### mock 선언 — 호이스팅 회피

```ts
// jest.mock은 import·const 위로 호이스팅되므로 factory에서 바깥 const를 참조하면
// 초기화 전 접근이 된다 — factory 안에서 jest.fn()을 만들고 requireMock으로 꺼낸다.
jest.mock('@/lib/prisma', () => ({
  prisma: { order: { findUnique: jest.fn(), update: jest.fn() } },
}));
jest.mock('@/lib/payment/confirm', () => ({ confirmPayment: jest.fn() }));

const mockFindUnique = jest.requireMock('@/lib/prisma').prisma.order.findUnique as jest.Mock;
```

첫 실행은 factory 밖에서 만든 `const mockFindUnique = jest.fn()`을 factory
안에서 참조하는 형태로 썼다가 "Cannot access before initialization"으로
죽었다. 참고한 til 테스트가 같은 형태로 통과하는 이유는 그쪽 factory가
mock 변수를 클로저 안에서 지연 참조하기 때문이었다.

### 케이스 4 — 담기 실패 시 PAID 보존

```ts
mockCopyPlan.mockResolvedValue({ error: '담기 실패' });

const res = await GET(callbackRequest(1500));

expect(mockConfirmPayment).toHaveBeenCalledTimes(1);
// 마지막 상태 갱신이 PAID — 이후 FAILED 덮어쓰기가 없어야 승인 사실이 DB에 남는다
const lastUpdate = mockUpdate.mock.calls.at(-1)?.[0];
expect(lastUpdate?.data?.status).toBe('PAID');
expect(
  mockUpdate.mock.calls.some((call) => call[0]?.data?.status === 'FAILED')
).toBe(false);
```

### 케이스 6 — 로그인 안 함은 DB 조회 전에 차단

```ts
mockGetUser.mockResolvedValue({ data: { user: null }, error: null });

const res = await GET(callbackRequest(1500));

expect(mockConfirmPayment).not.toHaveBeenCalled();
expect(mockFindUnique).not.toHaveBeenCalled();
const url = locationOf(res);
```

## 5. 결과 / 배운점

### 결과

- 신규 6건 전부 통과. 전체 스위트는 213/213이고 기존 207건도 그대로다
- 구현 코드 수정 0 — 테스트 파일만 추가
- 첫 실행은 jest.mock 호이스팅으로 실패했고 requireMock 방식으로 해소
- `@jest-environment node` 독블록은 필요한지 실측했다. 빼고 돌리니
  jsdom에서 `next/server` import 시점에 죽었다. fetch API의
  Request/Response 전역이 없기 때문이다. 확인 후 복원했다

### 배운점

**실패 원인을 구현 결함과 이름 차이로 갈라야 한다.** 지시한 에러 코드는
UNAUTHORIZED였는데 구현의 실제 값은 UNAUTHENTICATED였다. 그대로 assert
했으면 테스트가 빨간불이 됐겠지만 코드는 멀쩡했을 것이다.

진짜 DB에 남의 주문을 넣지 않고도 "남의 주문"이라는 상황을 만들 수
있었다. mock에게 그런 주문이 있다고 답하게 시키면 되기 때문이다.
돈이 안 나가게 막는 것 말고도 이런 쓸모가 있다.

남은 공백이 있다. `payment/failed/route.ts`의 PENDING 가드는 이미
PAID인 주문을 실패로 덮지 않는 updateMany 조건인데 여기에는 아직
테스트가 없다.

## 결정 (Decisions)

- 금액 불일치 케이스의 위조값은 9999가 아니라 100이다. 실제 위조는
  적게 보내는 쪽이고 그게 이 검증이 막으려는 것이다.
- 로그인 케이스에서 confirmPayment 미호출뿐 아니라 prisma.findUnique
  미호출까지 확인했다. 첫 관문에서 막히면 DB 조회조차 안 가야 한다.
- 지시한 에러 코드는 UNAUTHORIZED였으나 구현의 실제 값은
  UNAUTHENTICATED였다. 구현을 고치지 않고 테스트가 실제 값을 따랐다.
- jest.mock 호이스팅으로 첫 실행이 실패했다. factory 밖에서 만든
  jest.fn을 안에서 참조하려 했기 때문이다. factory 안에서 만들고
  requireMock으로 꺼내는 방식으로 바꿔야 했다.
- @jest-environment node 독블록은 실제로 필요한지 빼고 돌려 확인했다.
  jsdom에서 next/server import 시점에 죽는다.
