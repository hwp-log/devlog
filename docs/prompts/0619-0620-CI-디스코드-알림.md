## 3. 작성한 프롬프트

### ① 웹훅 붙이기 (0619)

```
[배경]
CI 결과가 Actions 탭에만 남아서 열어봐야 안다. 디스코드로 결과를 받게 한다.
#dotrip 채널 웹훅 URL은 GitHub Secrets에 넣어뒀다.
  Secret 이름: DOTRIP_DISCORD_CI_WEBHOOK_URL

[목표]
.github/workflows/ci.yml 의 ci job 마지막에 알림 단계를 추가.

- 서드파티 액션 대신 curl로 직접 POST할 것 (외부 액션은 공급망 위험이 있고
  이 정도는 curl 한 줄이면 된다)
- if: always() 를 붙일 것. 앞 단계가 실패하면 기본적으로 건너뛰는데,
  정작 알림이 필요한 게 실패한 순간이다
- 웹훅 URL은 반드시 secrets에서 읽을 것. 파일에 직접 적지 말 것
- 보낼 내용
  - 성공/실패 구분 (job status)
  - 커밋 메시지 첫 줄
  - 커밋한 사람
  - 해당 실행 결과 페이지 링크
- 성공과 실패 문구를 다르게 할 것

[하지 말 것]
❌ 서드파티 액션 사용
❌ 웹훅 URL을 파일에 하드코딩
❌ ci.yml 외 파일 수정
❌ 기존 네 단계(lint·typecheck·test·build) 수정
❌ 커밋·push (검수 후)

[검수 모드]
diff를 먼저 보고할 것.
그리고 아래를 함께 보고:
- 실패 시에도 이 단계가 실행되는 근거
- 로그에 웹훅 URL이 노출될 여지가 있는지

plan 요청.
```

검수 보고에서 두 항목이 확인됐다.

첫째, 실패했을 때도 알림이 나가는 이유. CI의 각 단계(step)에는 "앞
단계가 다 성공했으면 실행한다"는 조건이 기본으로 걸려 있다. 그 조건의
이름이 success()다. 그래서 테스트가 깨지면 그 뒤 단계는 실행되지 않는다.
알림 단계에 붙인 always()는 이 기본 조건을 "무조건 실행"으로 바꾼다.
앞이 깨져도 알림은 나간다.

둘째, 웹훅 주소가 로그에 노출될 여지. 네 겹으로 막혀 있다. 주소를
명령문에 직접 적지 않고 환경변수로만 넘겼다. 셸이 실행하는 명령을
로그에 한 줄씩 찍는 기능(set -x)을 켜지 않았다. curl이 화면에 찍는
응답·진행 표시를 껐다. 마지막으로 GitHub이 Secret에 등록된 값을 로그에서
\*\*\*로 가려준다.

CC가 여기에 하나를 더 짚었다. 커밋 메시지를 명령문 안에 글자로 그대로
끼워 넣으면 그 글자가 명령의 일부가 된다. 메시지에 특수문자를 섞어
명령을 주입할 수 있다는 뜻이다. 그래서 커밋 메시지도 주소와 같이
환경변수로만 넘기게 설계했다. 자세한 근거는 결정 섹션에 있다.

### ② --fail 추가 (0620)

```
[배경]
0619에서 붙인 디스코드 알림 단계의 curl에 --fail이 없다.
curl은 서버가 4xx를 돌려줘도 "요청은 보냈다"로 보고 정상 종료한다.
그러면 웹훅 주소가 만료되거나 채널이 지워졌을 때 알림은 안 오는데
CI는 초록으로 남는다. 고장을 알 수 없는 상태다.

[목표]
.github/workflows/ci.yml 의 notify discord 단계에서
curl에 --fail 옵션 추가.

- 왜 붙이는지 한 줄 주석도 함께
- 다른 옵션(-sS -o /dev/null -w)은 그대로 둘 것

커밋 후 push:
  ci: 0620 디스코드 알림 실패를 CI가 잡도록 --fail 추가

[하지 말 것]
❌ ci.yml 외 파일 수정
❌ 기존 네 단계 수정
❌ Co-Authored-By

[검수 모드]
diff를 먼저 보고할 것.
--fail을 붙였을 때 fork PR에서 어떻게 되는지도 함께 보고
(secrets 미주입으로 빈 URL이 되는 경우).

plan 요청.
```

**②의 plan 검수에서 내 판단 하나가 틀렸다.** 남이 fork에서 보낸
PR에는 저장소의 Secrets가 주입되지 않는다. 그러면 웹훅 주소 자리에 빈
문자열이 들어간다. 나는 --fail을 붙이면 이 경우가 새로 빨간불이 된다고
봤는데 조사 결과 전후 동일했다.

이유는 이렇다. 프로그램은 끝날 때 exit code라는 숫자를 남긴다. 0이면
성공이고 그 밖의 숫자는 전부 실패로 친다. CI는 이 숫자가 0이 아니면 그
단계를 실패로 표시한다. 그런데 curl은 주소가 아예 비어 있으면 --fail이
있든 없든 0이 아닌 숫자로 끝난다. 즉 fork PR의 빈 주소는 0619
시점부터 이미 실패였다. --fail이 새로 잡는 것은 주소가 유효한데 서버가
4xx·5xx로 거절하는 경우뿐이다.

## 4. 코드 작성 & 수정

변경 파일 1개: `.github/workflows/ci.yml` (0619 +26줄, 0620 +2/-1줄)

### 0619 — notify discord 단계 신설

먼저 알림에 쓸 값을 준비하는 부분이다.

```yaml
      - name: notify discord
        if: always()
        env:
          # 시크릿은 env로만 주입 — run 본문에 ${{ secrets… }}를 직접 보간하지 않는다
          WEBHOOK_URL: ${{ secrets.DOTRIP_DISCORD_CI_WEBHOOK_URL }}
          JOB_STATUS: ${{ job.status }}
          # push 이벤트엔 head_commit이 있고 pull_request 이벤트엔 없다 — PR은 제목·actor로 폴백.
          # 값을 run에 직접 보간하지 않는 것은 커밋 메시지발 스크립트 인젝션 차단용
          COMMIT_MSG: ${{ github.event.head_commit.message || github.event.pull_request.title }}
          COMMIT_AUTHOR: ${{ github.event.head_commit.author.name || github.actor }}
          RUN_URL: ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}
```

env: 아래에 적은 값들은 환경변수가 된다. 명령문이 실행되기 전에 값이
먼저 확정되는 통이라 웹훅 주소와 커밋 메시지를 여기 담으면 명령문에
글자로 들어가지 않는다. `||`는 앞 값이 없으면 뒤 값을 쓴다는 뜻이다.

다음은 실제로 알림을 보내는 명령문이다.

```yaml
        run: |
          FIRST_LINE="${COMMIT_MSG%%$'\n'*}"
          if [ "$JOB_STATUS" = "success" ]; then
            TEXT="✅ CI 통과 — ${FIRST_LINE} (${COMMIT_AUTHOR})"$'\n'"${RUN_URL}"
          else
            TEXT="❌ CI 실패 (${JOB_STATUS}) — ${FIRST_LINE} (${COMMIT_AUTHOR})"$'\n'"확인: ${RUN_URL}"
          fi
          # jq --arg: 커밋 메시지의 따옴표·역슬래시를 JSON 안전하게 이스케이프
          jq -n --arg content "$TEXT" '{content: $content}' \
            | curl -sS -o /dev/null -w "discord: %{http_code}\n" \
                -H 'Content-Type: application/json' -d @- "$WEBHOOK_URL"
```

FIRST_LINE 줄은 커밋 메시지에서 첫 줄만 잘라낸다. if는 job 결과가 성공인지에
따라 문구를 가른다. jq는 JSON을 다루는 명령줄 도구다. 여기서는 그
문구를 디스코드가 받는 JSON 형식의 전송 본문(payload)으로 감싼다.
마지막의 curl이 그 본문을 웹훅 주소로 보낸다.

### 0620 — --fail 추가

```diff
           # jq --arg: 커밋 메시지의 따옴표·역슬래시를 JSON 안전하게 이스케이프
+          # --fail: 웹훅이 4xx를 돌려줘도 curl은 기본 정상 종료라 고장이 초록으로 묻힌다 — HTTP 에러를 비0 종료로 승격
           jq -n --arg content "$TEXT" '{content: $content}' \
-            | curl -sS -o /dev/null -w "discord: %{http_code}\n" \
+            | curl -sS --fail -o /dev/null -w "discord: %{http_code}\n" \
                 -H 'Content-Type: application/json' -d @- "$WEBHOOK_URL"
```

주석의 "비0 종료"는 프로그램이 끝날 때 남기는 숫자(exit code)를 말한다.
0이면 성공이고 그 밖의 숫자는 전부 실패로 친다. --fail이 없으면 서버가
거절해도 curl은 0으로 끝나 CI가 이 단계를 초록으로 표시한다.

- push 후 #dotrip에 "✅ CI 통과 — ci: 0619 CI 결과를 디스코드로 알림
  (hwp2024dev)" 도착 확인. 실행 링크 포함
- 0620 push 후에도 알림 단계가 성공으로 표시됐다. --fail을 붙인 뒤에도
  정상 경로가 깨지지 않았다는 확인이다
- 실패 경로의 ❌ 문구는 실전 검증 전이다. CI가 실제로 깨질 때 확인 예정

### 배운점

**알림을 붙이는 일인데 실제로 손이 간 건 "실패했을 때 어떻게
도는가"였다.** always()도 --fail도 인젝션 차단도 전부 실패 쪽 이야기다.
성공 경로는 처음부터 문제가 없었다. 알림이 필요한 순간이 곧 실패한
순간이라 그렇다.

실패에 두 종류가 있다는 것을 --fail을 붙이면서 갈랐다. 주소가 비어서
아예 못 보낸 경우와 보냈는데 서버가 거절한 경우는 다르다. 앞은 0619
시점부터 이미 CI에서 실패로 표시됐고 --fail이 새로 잡는 것은 뒤쪽뿐이다.

공개 저장소라는 조건이 설계를 바꿨다. 남이 PR 제목을 쓸 수 있다는
사실이 값을 전부 환경변수로만 넘기게 한 이유다.

남은 한계가 하나 있다. fork에서 온 PR은 secrets가 주입되지 않아 이
단계가 빈 주소로 실패한다. 그 경우 알림을 건너뛰게 하는 처리는 넣지
않았다.

## 결정 (Decisions)

- if: always()는 알림 단계에만 붙였다. 각 단계에는 앞이 다 성공했을
  때만 실행한다는 기본 조건(success())이 걸려 있어 앞 단계가 하나라도
  실패하면 뒤를 건너뛴다. 그러면 정작 깨졌을 때만 알림이 안 온다. 다만
  되살리는 것은 알림 하나뿐이다 — lint가 깨졌는데 test를 굳이 돌릴
  이유는 없다.
- 커밋 메시지와 웹훅 URL은 명령문 안에 글자로 끼워 넣지 않고 환경변수로
  넘긴다. 명령문에 박힌 글자는 셸이 명령으로 읽는다. 커밋 메시지에
  따옴표를 닫고 세미콜론을 찍으면 그다음이 새 명령이 된다. 공개
  저장소라 PR 제목으로 누구나 그 자리에 문자열을 넣을 수 있다.
  환경변수에 담으면 셸이 시작할 때 이미 값이 정해져 있어 명령으로
  해석되지 않는다.
- JSON 조립은 jq --arg다. jq는 JSON을 다루는 명령줄 도구이고 --arg는
  값을 안전하게 끼워 넣는 옵션이다. 커밋 메시지의 따옴표·역슬래시가
  전송 본문을 깨뜨리지 않게 하기 위해서다.
- push로 도는 CI에는 커밋 정보(head_commit)가 실려 오는데 PR로 도는
  CI에는 없다. 그래서 없을 때는 PR 제목을 대신 쓰게 했다. 이런 대체를
  폴백이라 부른다.
- 0620에서 --fail을 붙였다. curl은 서버가 4xx를 돌려줘도 "요청은
  보냈다"로 보고 정상 종료한다. 그러면 로그에는 discord: 400이 찍히는데
  step은 초록으로 남는다. 웹훅이 만료되거나 채널이 지워지면 알림만
  조용히 끊기고 그걸 알 방법이 없다.
- 주석에 exit 코드 숫자를 적지 않기로 했다. 처음에는 "exit 22로 승격"
  으로 쓰려 했으나 로컬에서 404를 실측하니 exit 56이 나왔다. 상황에
  따라 코드가 다르므로 "비0 종료"로 적었다.
