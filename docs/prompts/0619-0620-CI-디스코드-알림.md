## 2. 왜 / 목적 / 이유

왜: 0616에서 CI를 붙였지만 결과가 Actions 탭에만 남아 열어봐야 알 수
있었다. 0616 첫 실행이 실패했을 때도 탭을 열어보고 알았다. 검사는

계기: 멘토가 8/20에 남긴 액션 아이템이었다. #dotrip 채널 편집 권한을

이유 — curl 직접 POST: 서드파티 액션 대신 curl로 직접 보냈다. 알림
하나에 외부 액션을 물리면 그 저장소가 바뀔 때 CI가 같이 흔들린다.
curl은 러너에 기본으로 들어 있다.

### ② --fail 추가 (0620)

```
[배경]

그러면 웹훅 주소가 만료되거나 채널이 지워졌을 때 알림은 안 오는데
CI는 초록으로 남는다. 고장을 알 수 없는 상태다.

[목표]

curl에 --fail 옵션 추가.

- 왜 붙이는지 한 줄 주석도 함께
- 다른 옵션(-sS -o /dev/null -w)은 그대로 둘 것

커밋 후 push:
  ci: 0620 디스코드 알림 실패를 CI가 잡도록 --fail 추가

[하지 말 것]

❌ 기존 네 단계 수정
❌ Co-Authored-By

[검수 모드]
diff를 먼저 보고할 것.
--fail을 붙였을 때 fork PR에서 어떻게 되는지도 함께 보고
(secrets 미주입으로 빈 URL이 되는 경우).

```

**②의 plan 검수에서 내 판단 하나가 틀렸다.** fork PR에서 --fail이
새로 빨간불을 만든다고 봤는데 조사 결과 전후 동일했다. secrets
미주입으로 빈 URL이 되면 curl은 --fail과 무관하게 비0으로 종료해
0619 시점부터 이미 step 실패였다. --fail이 새로 잡는 것은 주소가
유효한데 서버가 4xx·5xx를 돌려주는 경우뿐이다.

## 4. 코드 작성 & 수정

변경 파일 1개: `.github/workflows/ci.yml` (0619 +26줄, 0620 +2/-1줄)

### 0619 — notify discord 단계 신설

env 주입부. 시크릿과 커밋 메시지를 run 본문에 보간하지 않는다.

```yaml
      - name: notify discord
        if: always()
        env:
          # 시크릿은 env로만 주입 — run 본문에 ${{ secrets… }}를 직접 보간하지 않는다
          WEBHOOK_URL: ${{ secrets.DOTRIP_DISCORD_CI_WEBHOOK_URL }}
          JOB_STATUS: ${{ job.status }}
          # push 이벤트엔 head_commit이 있고 pull_request 이벤트엔 없다 — PR은 제목·actor로 폴백.
          # 값을 run에 직접 보간하지 않는 것은 커밋 메시지발 스크립트 인젝션 차단용
          COMMIT_MSG: ${{ github.event.head_commit.message || github.event.pull_request.title }}
          COMMIT_AUTHOR: ${{ github.event.head_commit.author.name || github.actor }}
          RUN_URL: ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}
```

run 본문. 메시지 첫 줄만 잘라 성공·실패 문구를 가르고 jq로 payload를
조립한다.

```yaml
        run: |
          FIRST_LINE="${COMMIT_MSG%%$'\n'*}"
          if [ "$JOB_STATUS" = "success" ]; then
            TEXT="✅ CI 통과 — ${FIRST_LINE} (${COMMIT_AUTHOR})"$'\n'"${RUN_URL}"
          else
            TEXT="❌ CI 실패 (${JOB_STATUS}) — ${FIRST_LINE} (${COMMIT_AUTHOR})"$'\n'"확인: ${RUN_URL}"
          fi
          # jq --arg: 커밋 메시지의 따옴표·역슬래시를 JSON 안전하게 이스케이프
          jq -n --arg content "$TEXT" '{content: $content}' \
            | curl -sS -o /dev/null -w "discord: %{http_code}\n" \
                -H 'Content-Type: application/json' -d @- "$WEBHOOK_URL"
```

### 0620 — --fail 추가

```diff
           # jq --arg: 커밋 메시지의 따옴표·역슬래시를 JSON 안전하게 이스케이프
```

## 5. 결과 / 배운점

### 결과

- 0619 로컬 검증 3종: YAML 파싱, bash -n 문법 검사, 실제 발송 없이
  메시지 조립까지만 돌리는 dry run으로 성공·실패 두 문구의 JSON 확인
- push 후 #dotrip에 "✅ CI 통과 — ci: 0619 CI 결과를 디스코드로 알림
  (hwp2024dev)" 도착 확인. 실행 링크 포함
- 0620 push 후에도 discord step success, 정상 경로 회귀 없음
- 실패 경로의 ❌ 문구는 실전 검증 전이다. CI가 실제로 깨질 때 확인 예정

### 배운점

**알림을 붙이는 일인데 실제로 손이 간 건 "실패했을 때 어떻게
도는가"였다.** always()도 --fail도 인젝션 차단도 전부 실패 쪽 이야기다.
성공 경로는 처음부터 문제가 없었다. 알림이 필요한 순간이 곧 실패한
순간이라 그렇다.

실패에 두 종류가 있다는 것을 --fail을 붙이면서 갈랐다. 주소가 없어서
못 보낸 것(fork PR의 빈 URL)과 보냈는데 거절당한 것(4xx)은 다르다.
앞은 0619 시점부터 이미 step 실패였고 --fail이 새로 잡는 것은 뒤쪽뿐이다.

공개 저장소라는 조건이 설계를 바꿨다. 남이 PR 제목을 쓸 수 있다는
사실이 env 경유를 선택한 이유다.

남은 한계가 하나 있다. fork에서 온 PR은 secrets가 주입되지 않아 이
단계가 빈 URL로 실패한다. 스킵 가드는 넣지 않았다.

## 결정 (Decisions)

- if: always()는 알림 단계에만 붙였다. step의 기본 조건은 success()라
  앞 단계가 하나라도 실패하면 뒤를 건너뛴다. 그러면 정작 깨졌을 때만
  알림이 안 온다. 다만 되살리는 것은 알림 하나뿐이다 — lint가 깨졌는데
  test를 굳이 돌릴 이유는 없다.
- 커밋 메시지와 웹훅 URL은 run 블록에 직접 보간하지 않고 env로 넘긴다.
  run에 박힌 글자는 셸이 명령문으로 읽는다. 커밋 메시지에 따옴표를 닫고
  세미콜론을 찍으면 그다음이 새 명령이 되고 공개 저장소라 PR 제목으로
  누구나 그 자리에 문자열을 넣을 수 있다. env에 담으면 셸이 시작할 때
  이미 값이 정해져 있어 명령으로 해석되지 않는다.
- JSON 조립은 jq --arg다. 커밋 메시지의 따옴표·역슬래시가 payload를
  깨뜨리지 않게 하기 위해서다.
- PR 이벤트에는 head_commit이 없어 pull_request.title로 폴백했다.
- 0620에서 --fail을 붙였다. curl은 서버가 4xx를 돌려줘도 "요청은
  보냈다"로 보고 정상 종료한다. 그러면 로그에는 discord: 400이 찍히는데
  step은 초록으로 남는다. 웹훅이 만료되거나 채널이 지워지면 알림만
  조용히 끊기고 그걸 알 방법이 없다.
- 주석에 exit 코드 숫자를 적지 않기로 했다. 처음에는 "exit 22로 승격"
  으로 쓰려 했으나 로컬에서 404를 실측하니 exit 56이 나왔다. 상황에
  따라 코드가 다르므로 "비0 종료"로 적었다.
