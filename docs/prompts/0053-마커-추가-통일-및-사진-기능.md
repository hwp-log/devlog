## 2. 왜 / 목적 / 이유

### (a) 작성 시 마커 추가 불가 → tmp_ 전략으로 통일

- **이전 상태**: 마커 추가는 수정 페이지에서만 가능. 작성 시 storyId가 없어 DB에 바로 저장 불가.
- **왜 안 됐나**: Spot 테이블의 `storyId`는 NOT NULL 외래 키. story가 아직 없는 시점에 `INSERT INTO spot` 불가.
- **해결**: `tmp_${randomUUID()}`를 로컬 ID로 부여해 클라이언트 상태에만 보관. 글 제출 시 `prisma.$transaction` 안에서 Story → Spot 순으로 생성하며 realId를 확보.
- **면접 답**: "ID 의존성이 있는 레코드를 어떻게 임시 관리하고 일괄 저장하나" → 로컬 ID + 트랜잭션 one-shot 패턴

### (b) 사진을 트랜잭션 밖에서 처리 → 분산 시스템 정합성

- **이유**: `prisma.$transaction`은 Prisma(PostgreSQL)에만 적용. Supabase Storage는 별도 시스템이라 트랜잭션 범위 밖.
- **해결**: 트랜잭션으로 Story + Spot만 생성(photoUrl = null). 이후 별도 루프에서 Storage 업로드 → `prisma.spot.update({ photoUrl })`.
- **핵심 문제**: tmp_ ID가 트랜잭션 후에야 realId로 확정. `tmpToReal: { tmpId, realId }[]` 매핑으로 트랜잭션 결과를 루프에 전달.
- **부분 실패 허용**: Storage 업로드 실패 시 `continue` (사진만 없는 채로 글은 저장). 완전 실패보다 낫다는 판단.
- **면접 답**: "DB 트랜잭션과 외부 스토리지를 어떻게 동기화하나" → 순차 처리 + 부분 실패 허용

### (c) 사진 비우기를 defer로 → 취소 가능한 편집 UX

- **이유**: 통합 편집 모드에서 [저장]/[취소] 버튼을 붙인 이상, [비우기]를 즉시 실행하면 [취소]가 의미 없어짐.
- **해결**: `pendingPhotoCleared = true` 플래그만 올리고 실제 삭제는 [저장] 시점으로 연기. `originalPhotoUrl`로 [취소] 시 복원.
- **real spot 비우기**: [저장] 클릭 → `clearSpotPhoto(spotId)` Server Action 호출 → Storage `remove()` + DB null.
- **tmp_ spot 비우기**: [저장] 클릭 → `onFileSelect(null)` → `pendingPhotos.delete(spotId)`. Storage 없으므로 로컬만 처리.
- **면접 답**: "낙관적 UI와 실제 반영을 언제 나눠야 하나" → 취소 가능성이 있으면 defer

### (d) hasPendingFile 체크 → blob URL DB 저장 방지

- **문제**: 수정 폼 제출 시 `spotsData`(JSON)에 real spot의 `photoUrl`이 `blob:...`로 들어있을 수 있음. 트랜잭션이 그대로 `UPDATE spot SET photoUrl = 'blob:...'`을 실행하면 무효 URL이 DB에 저장됨.
- **이유**: SpotPopup에서 [저장] 시 `pendingPhotoPreview`(blob URL)을 `onUpdate({ photoUrl })`로 올려보내고, `setSpotsJson(JSON.stringify(next))`로 직렬화하기 때문.
- **해결**: `const hasPendingFile = formData.get(\`spotPhoto_${spot.id}\`) instanceof File;` → 파일이 있으면 트랜잭션에서 `photoUrl: undefined`(스킵). 이후 루프에서 Storage 업로드 후 실제 URL로 덮어씀.
- **blob URL이 DB에 저장되면 안 되는 이유**: `blob:` URL은 브라우저 메모리 참조. 서버나 다른 클라이언트에서 접근 불가. 페이지 새로고침 시에도 무효.
- **면접 답**: "클라이언트 임시 객체 URL이 서버에 도달하는 경로를 어떻게 막나" → FormData 파일 존재 여부 확인 + 트랜잭션 photoUrl skip

### (e) clearSpotPhoto에서 Storage remove → 고아 파일 방지

- **이유**: DB `photoUrl = null`만 하면 Storage 파일은 남음. Storage 요금 누적 + 접근 불가 파일 방치 = 업계 표준 위반.
- **해결**: `new URL(spot.photoUrl).pathname`에서 Storage path 역산 → `supabase.storage.from('story-photos').remove([path])` 후 DB null.
- **고아 파일 완전 방지 여부**: 사진 교체 시 기존 파일 삭제는 MVP 스코프 외로 제외. timestamp 경로라 충돌 없음. 추후 정리 예정.
- **면접 답**: "분산 시스템에서 한쪽 삭제가 실패하면 어떻게 되나" → Storage 삭제 실패는 고아 파일만 남고 기능 동작에 영향 없음. DB null은 성공했으므로 UX는 정상.

## 4. 코드 작성 & 수정

### 1. tmp_ 전략 + 트랜잭션 (app/story/new/actions.ts)

```typescript
const tmpToReal: Array<{ tmpId: string; realId: string }> = [];

const story = await prisma.$transaction(async (tx) => {
  const s = await tx.story.create({
    data: { title, content, photoUrl: null, userId: user.id, tags: { connectOrCreate: ... } },
  });

  for (const [i, spot] of spotsData.entries()) {
    const created = await tx.spot.create({
      data: { storyId: s.id, name: spot.name, lat: spot.lat, lng: spot.lng, order: i + 1, photoUrl: null },
    });
    tmpToReal.push({ tmpId: spot.id, realId: created.id });
  }
  return s;
});

// 트랜잭션 후: Storage 업로드 (부분 실패 허용)
for (const { tmpId, realId } of tmpToReal) {
  const file = formData.get(`spotPhoto_${tmpId}`);
  if (!(file instanceof File)) continue;
  // ... upload → prisma.spot.update({ photoUrl })
}

redirect(`/story/${story.id}`);
```

### 3. clearSpotPhoto Storage remove (app/story/[id]/spots/actions.ts)

```typescript
export async function clearSpotPhoto(spotId: string): Promise<{ error: string } | { ok: true }> {
  // ... auth + ownership 확인

  if (spot.photoUrl) {
    const url = new URL(spot.photoUrl);
    const prefix = '/storage/v1/object/public/story-photos/';
    const storagePath = url.pathname.startsWith(prefix)
      ? url.pathname.slice(prefix.length)
      : null;
    if (storagePath) {
      await supabase.storage.from('story-photos').remove([storagePath]);
    }
  }

  await prisma.spot.update({ where: { id: spotId }, data: { photoUrl: null } });
  revalidatePath(`/story/${spot.story.id}`);
  return { ok: true };
}
```

## 5. 결과 / 배운점

### 결과
- 작성/수정 마커 추가 기능 통일 (tmp_ 전략으로 storyId 의존성 해소)
- 사진 추가/교체/비우기 CRUD 완성
- SpotPopup 개별 인라인 편집 → 통합 편집 모드로 UX 개선
- Storage 고아 방지 패턴 적용 (clearSpotPhoto)

### 배운점

**1. 트랜잭션 경계**
DB 레코드끼리는 한 트랜잭션. 외부 시스템(Storage)은 트랜잭션 범위 밖. 순서: 트랜잭션으로 ID 확보 → 트랜잭션 후 Storage 처리. 실패해도 DB 데이터는 안전.

**2. createMany vs 개별 create**
`createMany`는 생성된 레코드의 ID를 반환하지 않음. tmpId → realId 매핑이 필요한 경우 반드시 개별 `create` 루프. Prisma 문서 확인 필요한 부분.

**3. useActionState + startTransition (React 19)**
`formAction`은 `useActionState`가 반환한 액션. 직접 호출 가능하나, React transition 밖에서 호출하면 "async function called outside of transition" 에러. `startTransition(() => formAction(fd))`으로 감싸야 함.

**4. redirect 함정 2개**
- `redirect('/story')`: 목록으로 이동. 트랜잭션이 story를 반환하도록 하고 `redirect(\`/story/${story.id}\`)`로 수정.
- `useActionState`의 `formAction`을 onSubmit에서 수동 호출 시 transition 필요.

**5. blob URL = 브라우저 메모리 참조**
`URL.createObjectURL(file)`은 해당 브라우저 탭에서만 유효한 임시 URL. 서버로 전달되면 무의미. DB에 저장되면 다른 기기/탭/새로고침에서 모두 broken image. FormData에는 File 객체 자체를 넣어야 함.

**6. Storage remove = 업계 표준**
DB null만으로는 파일이 Storage에 남아 "고아 파일(orphan)" 발생. 비용 + 정합성 문제. 삭제 전 path 역산(publicUrl → storagePath) 패턴 필요.

**7. 다음 공부 주제 (이번 작업에서 드러난 빈 곳)**
- 트랜잭션 격리 수준 / 데드락 가능성 분석
- useMemo vs useState vs useRef 적합 시점
- 부분 실패 시 사용자 알림 / 재시도 패턴

### 함정 (디버깅)

| 증상 | 원인 | 해결 |
|---|---|---|
| 마커 클릭 시 저장한 정보 안 보임 | `setActiveSpot(spot)` 시 stale closure — `el.addEventListener`의 `spot`이 렌더 당시 값 고정 | `setActiveSpot((prev) => ...)` + localSpotsRef로 최신값 참조 |
| 마커 무한 재렌더 | `StoryWriteForm`의 `initialLocalSpots` 매 렌더마다 새 배열 생성 → `useEffect([localSpots])` 루프 | `useMemo(() => ..., [])` 고정 |

| 글 등록 후 목록으로 이동 | `redirect('/story')` 하드코딩 | 트랜잭션이 `story` 반환 → `redirect(\`/story/${story.id}\`)` |

## 결정 (Decisions)

- tmp_ prefix = 로컬 임시 ID 규약 (DB 저장 전 클라이언트 상태 관리)
- 트랜잭션 범위 = Story + Spot 생성/수정만. Storage는 항상 트랜잭션 후 별도 처리
- 사진 업로드 부분 실패 허용 = Storage 실패 시 `continue` (글 자체는 저장)
- 비우기 = defer (pendingPhotoCleared 플래그) + [저장] 시 clearSpotPhoto 호출
- 교체 시 기존 파일 삭제 생략 (MVP) = timestamp 경로라 충돌 없음, 추후 정리
- hasPendingFile = 트랜잭션에서 blob URL DB 저장 방지 (photoUrl: undefined)
