## 1. 한 줄 요약

마이플랜 상세를 읽기 전용으로 정리하고, 수정은 작성 편집기를 재사용해 기존 계획을 불러와 통째 교체 저장하도록 만들었으며, 삭제는 확인 한 번 거치는 상세의 버튼 한 곳으로 일원화했다.

## 2. 왜 · 목적 · 이유

### 2-1. 상세는 읽기 전용, 수정은 작성 편집기 재사용
- **왜(동기/문제):** 상세에 옛 추가 폼이 남아 읽기와 쓰기가 섞여 있었고, 수정 전용 화면이 없었다.
- **목적(가치):** 상세는 보기만 하고, 수정은 작성 때 쓰던 편집기를 그대로 불러와 고친다. 작성·수정 경험이 같다.
- **이유(결정):** 수정 폼을 새로 만들지 않고 작성 편집기에 `mode`('create'/'edit')와 `initialState`를 추가해 재사용했다. 화면을 두 벌 유지할 필요가 없다.

### 2-2. 수정 저장을 "통째 교체"로 (핵심)
- **왜(동기/문제):** 저장을 "바뀐 행만 골라 고치기(diff)"로 하면, 편집기 항목과 DB 행을 짝지어 추가/수정/삭제로 나누는 분기가 필요하다. 같은 날 항목을 짝짓는 부분이 틀어지기 쉽다(0063에서 겪은 매칭 문제와 같은 자리).
- **목적(가치):** 저장 결과가 항상 편집기 화면과 똑같도록(정합성) 보장하면서, 저장 코드를 단순하게 유지한다.
- **이유(결정) — 두 층으로 나뉜다:**
  - **층1 (작성 편집기, 0064에서 이어짐):** 변경마다 DB를 건드리지 않고 마지막에 한 번 모아 저장한다. → DB 접근 비용을 줄이는 건 이 층의 이득이다.
  - **층2 (이번 update):** 그 한 번의 저장에서 diff 대신 통째 교체 — 기존 `PlanSpot`·`PlanCost`를 다 지우고 편집기 상태대로 다시 생성한다. 작성(create)과 같은 `buildPlanRows`를 공유한다. 쓰기는 오히려 약간 더 많지만, 여행 계획은 항목 수가 적어 그 비용은 무시할 수준이다. 대신 **단순함**과 **정합성("저장 결과 = 화면")**을 얻는다. 데이터가 커지면 diff로 전환할 여지는 남긴다.
  - **안전:** 갱신·삭제·재생성을 한 트랜잭션으로 감싸 원자적이다. 재생성이 실패하면 삭제가 롤백돼 "반쯤 지워진" 상태가 생기지 않는다(무결성).

### 2-3. 삭제를 상세 한 곳으로 일원화
- **왜(동기/문제):** 목록 카드의 인라인 × 삭제는 카드를 누르다 잘못 닿으면 바로 지워질 위험이 있었고, 상세에도 삭제가 생겨 경로가 둘로 갈렸다.
- **목적(가치):** 삭제를 확인 한 번 거치는 상세의 버튼 한 곳으로 모아 실수 삭제를 줄인다.
- **이유(결정):** 목록 카드의 ×를 제거하고 카드 전체를 상세 링크로 두었다. 기존 `deleteMyPlanAction`은 상세에서 그대로 재사용한다.

## 3. 작성한 프롬프트

Claude Code에 넘긴 단계별 프롬프트(큰 단계 3개 + 작은 후속 2개).

**1단계 — 상세 읽기 전용 + 버튼**
```
[배경] 상세에 옛 추가 폼이 남아 읽기/쓰기 혼재.
[목표] 상세를 읽기 전용으로, 하단에 "수정"(→ /my-plan/[id]/edit 링크)·"삭제" 버튼.
[하지 말 것] ❌ 편집기 edit 모드/update(다음 단계) ❌ deleteMyPlanAction 새로 만들기(기존 재사용) ❌ 스키마 변경 ❌ 커밋
[검수 모드] 추가 폼 사라짐 / 삭제 본인 것만 / 수정 → /edit 링크(라우트는 다음 단계라 404 정상)
plan 요청.
```

**2단계 — 수정 화면(편집기 재사용 + 역매핑)**
```
[배경] 상세 읽기 전용 + 수정 버튼까지 완료.
[목표] /my-plan/[id]/edit 라우트 + 작성 편집기가 기존 계획을 EditorState로 역매핑해 채워진 채로 열림.(저장 연결은 다음 단계)
[하지 말 것] ❌ update/저장 연결(다음 단계) ❌ edit 모드 저장이 create 호출(중복 생성) ❌ 스키마 변경 ❌ 커밋
[참조 패턴] 편집기에 initialState·mode prop 추가 / 비용-장소 연결은 planSpotId 기준 / 메타까지 전부 채움
[검수 모드] schema CostCategory enum과 cost.ts 일치 확인 / 값 정확히 채워짐 / 같은 Day 2개 planSpotId 묶임 / edit 모드 저장 비활성
plan 요청.
```

**3단계 — 수정 저장 활성화(공유 헬퍼 + update)**
```
[배경] 수정 화면이 채워 열리지만 저장 비활성.
[목표] 행 빌드 로직을 공유 헬퍼(buildPlanRows)로 추출(create·update 공용) / update 액션(한 트랜잭션: 스칼라 갱신 → 기존 행 삭제 → 재생성) / 저장 후 /my-plan/[id] redirect / 저장 버튼 활성화.
[하지 말 것] ❌ 빌드 로직 복붙(헬퍼 하나로) ❌ ownerId 클라값(세션 고정) ❌ redirect를 트랜잭션/try 안 ❌ 옛 항목 id 강제 재사용 ❌ 스키마 변경 ❌ 커밋
[검수 모드] 같은 Day 2개 planSpotId 안 엉킴 / 저장 → 상세 반영·비용 합산 / buildPlanRows 공유 / 남의 계획 update 차단
plan 요청.
```

작은 후속: (a) 수정 화면 카드 폭을 작성 화면과 통일(래퍼 className 일치), (b) 목록 카드 × 제거 + 카드 전체 상세 링크.

```ts
// 신규: create·update가 같이 쓰는 행 생성 로직
async function buildPlanRows(tx: Prisma.TransactionClient, planId: string, items: SaveItem[]) {
  for (const item of items) {
    const spot = await tx.planSpot.create({
      data: { planId, day: item.day, order: item.order, name: item.name, lat: 0, lng: 0 },
    });
    if (item.amount > 0) {
      const category: CostCategory = item.category === '' ? 'ETC' : item.category;
      await tx.planCost.create({
        data: { planId, planSpotId: spot.id, day: item.day, category, label: item.name, amount: item.amount },
      });
    }
  }
}
```

```ts
export async function updatePlanWithItemsAction(planId: string, payload: SavePayload) {
  // 인증 + 소유 검증 (트랜잭션 전)
  const existing = await prisma.myPlan.findFirst({ where: { id: planId, ownerId: user.id } });
  if (!existing) return { error: '수정 권한이 없습니다' };

  await prisma.$transaction(async (tx) => {
    await tx.myPlan.update({ where: { id: planId }, data: { /* 스칼라 + 메타 */ } });
    await tx.planCost.deleteMany({ where: { planId } });   // cost 먼저 (planSpotId가 SetNull)
    await tx.planSpot.deleteMany({ where: { planId } });
    await buildPlanRows(tx, planId, payload.items);        // 화면대로 재생성
  });
  redirect(`/my-plan/${planId}`);  // 트랜잭션 바깥(Next redirect는 throw)
}
```

## 5. 결과 / 배운점

- **결과:** 상세는 읽기 전용, 수정은 작성 편집기를 불러와 통째 교체 저장, 삭제는 상세 한 곳. 같은 날 항목 2개도 planSpotId로 정확히 묶이고, 날짜는 저장 round-trip에서 안 밀린다.
- **배운점:**
  - 수정 저장 "diff vs 통째 교체"는 정답이 하나가 아니라 **트레이드오프**다. 데이터가 작고 가끔 저장되는 도메인이면 통째 교체가 단순함·정합성으로 이긴다. diff가 교과서적이지만 이 규모엔 과설계다.
  - **비용 절감과 정합성은 다른 층의 이득이다.** 비용은 "변경마다 안 하고 모아 저장(층1)", 정합성·단순함은 "통째 교체(층2)". 면접에선 두 결정을 분리해 답할 수 있어야 한다.
  - 트랜잭션 **원자성**으로 "다 지우고 다시 만들기"가 안전해진다 — 중간 실패 시 롤백, 반쯤 지워진 상태 없음.
  - create와 update가 같은 `buildPlanRows`를 공유해 행 생성 규칙이 한 곳에 모인다.
  - **한계(다음 작업 주의):** 통째 교체는 EditorState에 없는 칸(예: 좌표)을 round-trip에서 잃는다. 지금은 좌표가 늘 0이라 무해하나, 지도 작업이 들어가면 그 칸을 EditorState에 담거나 update에서 보존해야 한다.
