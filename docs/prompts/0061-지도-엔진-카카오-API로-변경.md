---

## 1. 한 줄 요약

지도 엔진을 Mapbox에서 카카오로 이관해 **한국 POI 검색 정확도**와 **마커-선 정렬**을 동시에 확보하고, 동선 직선 + 구간 중앙 방향 화살표 + 3페이지 레이아웃 폭을 다듬었다.

---

## 2. 왜 / 목적 / 이유

**왜 (동기 · 문제)**
Mapbox의 두 한계가 기록 앱의 완성도를 직접 해쳤다.
- 한국 POI 검색이 부정확 — "서울시청"을 검색해도 "원주시"가 나오는 수준. *촬영지를 검색·기록*하는 앱에서 핵심 기능이 깨진 상태.
- DOM 마커(HTML 오버레이) vs WebGL 선이 서로 다른 좌표계 → 마커가 동선에서 어긋나 보임(약 28px). pitch·backdrop-filter·box-shadow 등 픽셀 보정으로 며칠 싸웠지만 *증상*만 건드렸을 뿐 원인은 그대로였다.

**목적 (도달할 상태 · 사용자 가치)**
한국 촬영지를 정확히 검색·표시하고, 마커가 동선에 정확히 붙는 지도. 사용자가 신뢰하고 직관적으로 쓰는 *기록* 경험.

**이유 (채택 근거 · 의사결정)**
- 카카오는 한국 POI 데이터가 강함 (`services` 라이브러리 `keywordSearch`).
- 마커·폴리라인이 *같은 projection*을 써서 정렬이 구조적으로 맞음 — DOM-vs-WebGL 어긋남 자체가 사라짐.
- 트레이드오프: 카카오 웹은 다크 테마 커스터마이징을 지원하지 않아 *다크 지도를 포기*. 그래도 기록 앱엔 검색 정확도·정렬 완성도가 훨씬 중요하다고 판단해 이관.

> 면접용 한 문장: "Dotrip은 한국 촬영지를 기록하는 앱이라 장소 검색·표시의 정확도가 제품 완성도의 핵심이었다. Mapbox는 한국 POI 검색이 부정확했고('서울시청'→'원주시'), DOM 마커와 WebGL 선의 좌표계가 달라 마커가 동선에서 어긋났다 — 둘 다 완성도를 직접 해치는 문제. 카카오는 한국 POI 데이터가 강하고 마커·폴리라인이 같은 projection이라 정렬이 구조적으로 맞는다. 다크 테마는 포기했지만 기록 앱엔 검색 정확도·정렬 완성도가 우선이라 판단해 이관했다."

## 4. 코드 작성 & 수정

**(가) 좌표 순서 변환 — 가장 중요한 함정 (★★★)**
Mapbox는 `[lng, lat]` 배열, 카카오는 `{lat, lng}` / `LatLng(lat, lng)`. 값은 같고 *순서가 반대*.

```ts
// components/SpotMap.tsx — panTo 예시
// 변경 전 (Mapbox, lng first)
mapRef.current?.panTo([spot.lng, spot.lat]);
// 변경 후 (Kakao, lat first)
mapRef.current?.panTo(new kakao.maps.LatLng(spot.lat, spot.lng));
```

**(나) 마커 — 명령형 DOM → 선언형 CustomOverlayMap**

```tsx
// 변경 전 (Mapbox): document.createElement + appendChild + new mapboxgl.Marker(...).addTo(map)
//   - markersRef / markerElemsRef로 수동 관리, 펄스도 raw appendChild

// 변경 후 (Kakao, components/SpotMap.tsx)
<CustomOverlayMap position={{ lat: spot.lat, lng: spot.lng }} zIndex={1}>
  <div style={{ position: 'relative', width: 28, height: 28 }}>
    <div onClick={() => handleMarkerClick(spot)} style={{ /* 색원 + 숫자, getSpotColor 그대로 */ }}>
      {i + 1}
    </div>
    {pulsingIds.has(spot.id) && (
      <div style={{ /* 펄스 링 */ animation: 'spot-pulse 0.6s ease-out forwards' }}
           onAnimationEnd={() => setPulsingIds(prev => { const s = new Set(prev); s.delete(spot.id); return s; })} />
    )}
  </div>
</CustomOverlayMap>
```
- 펄스: raw `appendChild` → `pulsingIds: Set<string>` state로 React가 관리. `markerElemsRef` 제거.

**(다) 동선 — 흰 케이싱 + 주황 코어 2겹 (라이트 지도 대비)**

```tsx
// components/SpotMap.tsx — 구간별 Polyline 2겹
<Polyline path={seg} strokeColor="#ffffff" strokeWeight={7} strokeOpacity={0.9} zIndex={0} /> {/* 케이싱 */}
<Polyline path={seg} strokeColor="#f97316" strokeWeight={4} strokeOpacity={1}   zIndex={1} /> {/* 코어 */}
```

**(라) 구간 중앙 방향 화살표 — Mercator 보정 각도 (★★★)**

```tsx
// components/SpotMap.tsx — 구간 중점에 회전된 '›'
const midLat = (a.lat + b.lat) / 2;
const midLng = (a.lng + b.lng) / 2;
// cos(midLat) 보정으로 Mercator 위도 왜곡 제거 — 없으면 위도 따라 각도가 틀어짐
const angle = Math.atan2(
  -(b.lat - a.lat),
  (b.lng - a.lng) * Math.cos(midLat * Math.PI / 180)
) * 180 / Math.PI;

<CustomOverlayMap position={{ lat: midLat, lng: midLng }} zIndex={0}>
  <div style={{
    pointerEvents: 'none', color: '#f97316', fontSize: 20, fontWeight: 'bold',
    transform: `rotate(${angle}deg)`,
    textShadow: '0 0 2px #fff, 0 0 4px #fff', // 라이트 배경용 흰 halo
  }}>›</div>
</CustomOverlayMap>
```

**(마) 로딩 게이팅 + 2D 기본**


## 5. 결과 / 배운점

**결과**
- 마커-선 정렬 완벽 (28px 오프셋 해소) — 직선 + 같은 projection의 구조적 효과.
- 한국 POI 표시 정확 (상효교회, 상효1동마을복지회관 등 빽빽한 지명).
- 동선 직선 + 구간 중앙 방향 화살표(흰 halo) + 흰 케이싱 주황 선으로 라이트 지도에서도 가시.
- 세 페이지 콘텐츠 폭 통일.

**배운점**
- **증상을 덮지 말고 원인 계층을 바꿔라.** Mapbox에서 pitch·backdrop-filter·box-shadow로 픽셀 보정만 반복했지만, 진짜 해법은 *DOM-vs-WebGL 구조 자체*를 단일 projection 엔진으로 교체하는 것이었다. 한 발 물러나 구조를 본 판단이 핵심.
- **좋은 추상화는 교체 비용을 낮춘다.** 좌표가 보편 표준(WGS84)이고 데이터 계약과 렌더링 구현이 분리돼 있어서, *엔진만 갈아도 데이터·페이지·DB는 안 흔들렸다.* "같은 API라서"가 아니라 "관심사 분리 덕"이라는 점이 정확한 이해.
- **선의 *의미*가 기술 선택을 결정한다.** 도로 스냅(내비)은 마커를 다시 동선에서 띄운다 — 기록 앱의 선은 "점을 잇는" 직선이어야 정렬과 의미가 둘 다 맞는다. 도로 경로 옵션을 검토하고 *의식적으로 직선을 유지*한 트레이드오프.
- **추측보다 코드·런타임.** 원인은 매번 코드·DOM·측정값을 읽어 찾았고, 직관적 추측은 여러 번 빗나갔다.
