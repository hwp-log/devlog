# 0206·0211~0212 회고: 재사용 스팟 경로에서 값이 사라지는 문제

작성일: 2026-08-10
소요 시간: 약 2시간
관련 커밋: 05bc99e(0206) · 59896ad(0211) · 5f6d692(0212)

---

## 1. 한 줄 요약

스팟 재사용을 도입하면서 "값을 실어 나르는 경로"가 하나 더 늘었는데, 그 경로에 값을 안 실어서 같은 병이 하루 동안 세 번 다른 얼굴로 나왔다.

---

## 2. 왜 / 목적 / 근거

### 왜 (동기·문제)

세 증상이 따로 발견됐다. 처음엔 별개 버그로 보였다.

**0206 — 후보 카드엔 작품이 있는데 폼엔 없다.**
근접 후보 카드에 "롯데월드몰 [도깨비][호텔 델루나]"가 뜬다. 눌러서 폼에 올리면 "연결된 작품 없음"이다. 저장하고 편집으로 다시 들어가면 정상으로 나온다. **방금 고른 재사용만 빈칸인 비대칭.**

**0211 — 편집 모드엔 보이는데 읽기 모드엔 없다.**
같은 폼 안에서 갈렸다. 수정을 누르면 "수리남"이 나오는데, 읽기 모드에선 "작품 연결..." 자리표시자가 뜬다. 리뷰·별점은 양쪽 다 정상이고 작품만 그랬다.

**0212 — 새 스팟은 사진이 되는데 재사용은 안 된다.**
직접 찍은 스팟은 사진 업로드가 반영된다. 시딩 스팟을 재사용한 경우 올려도 반영이 안 된다.

세 번째쯤 되니 패턴이 보였다. **전부 "재사용 경로에서 값이 안 실린다"**였다.

### 목적 (도달 상태)

- 후보 카드에서 본 작품이 폼에서도 보인다.
- 읽기 모드와 편집 모드가 같은 값을 보여준다.
- 재사용 스팟도 편집에서 사진을 저장·교체·삭제할 수 있다. 단 공유 스팟의 장소 사진은 덮어쓰지 않는다.

### 근거 (결정 기준)

**세 건 모두 표시·저장 경로만 고쳤다.** 0203의 작품 편집 잠금(공유 스팟의 작품은 수정 불가)은 유지했고, 스키마도 안 건드렸다. 문제는 데이터 모델이 아니라 값이 전달되지 않는 것이었다.

**0206에서 `movieId`를 일부러 안 채웠다.** 정확히는 채울 수가 없었다. 후보 카드가 쓰는 타입이 제목만 갖고 있다.

```ts
// lib/spot/nearby.ts
export type NearbySpot = {
  spotId: string;
  name: string;
  distanceM: number;
  movies: string[];    // ← 제목 문자열 배열. id 없음
  storyCount: number;
};
```

조회 자체가 `movie: { select: { title: true } }`라 id를 안 가져온다. 그래서 "표시 전용이니 제목만 있으면 된다"고 판단했다. 편집 모드가 `movieTitle`만으로 잘 그렸으니 확인도 됐다고 봤다.

**그 판단이 0211을 만들었다.** 읽기 모드는 `movieId`로 판정하고 있었다.

```
리뷰   게이트: spot.review      표시: spot.review       ← 같은 필드
별점   게이트: spot.rating      표시: spot.rating       ← 같은 필드
작품   게이트: spot.movieId     표시: spot.movieTitle   ← 다른 필드
```

**"보여줄지 말지"를 A로 판단하고 "무엇을 보여줄지"는 B에서 가져왔다.** 원래는 두 필드가 항상 짝으로 세팅돼서 문제가 없었는데, 0206이 `movieTitle`만 채우면서 짝이 깨졌다. 게이트를 값 필드로 정렬하는 쪽을 골랐다. `movieId`를 억지로 채우는 건 타입을 바꿔야 하고, 저장 경로에 영향이 갈 수 있다.

**0212는 버그가 아니라 미구현이었다.** 코드에 그렇게 적혀 있었다.

```
// 재사용 스팟은 공유 Spot.photoUrl 미수정 (per-visit 사진은 S3-b)
```

0201에서 재사용을 만들 때 신규 작성만 완성하고 편집은 미뤄둔 자리다. 신규 작성은 이미 `StorySpot.photoUrl`에 기록하고 있었으므로, **그 패턴을 편집에 대칭 적용**하면 됐다.

모델은 이미 맞게 서 있었다는 것도 확인했다.

| 필드 | 층 |
|---|---|
| `StorySpot.rating` / `photoUrl` / `review` | per-visit (방문 기록) |
| `Spot.photoUrl` / `coverUrl` | per-place (장소 대표) |
| `SpotMovie` | 장소↔작품 다대다 |

표시 경로가 전부 `StorySpot.photoUrl`을 읽고 있었다. **per-visit으로 정합하게 서 있고 쓰기 한 곳만 비어 있었다.**

### 0212 — 편집에 재사용 사진 루프 추가 (+43 −1)

신규 작성 경로에 이미 있던 패턴을 편집에 대칭 적용했다. 핵심은 **공유 `Spot.photoUrl`을 건드리지 않고 `StorySpot.photoUrl`에만 기록**하는 것이다.

```ts
// app/(protected)/story/[id]/actions.ts
+ // 재사용 스팟 per-visit 사진 — 공유 Spot.photoUrl 미수정, story_spots.photoUrl에만 기록(NEW 대칭).
+ // replace/clear 판정은 owned와 동일(resolvePhotoIntent). keep은 무동작 — 재사용 upsert가 update에서 photoUrl 생략해 기존값 보존.
+ for (const spot of spotsData) {
+   if (!spot.reusedSpotId) continue;
+   const reusedId = spot.reusedSpotId;
+   const file = formData.get(`spotPhoto_${spot.id}`);
+   const oldUrl = oldReusedPhotoBySpotId.get(reusedId) ?? null;
+   const intent = resolvePhotoIntent(oldUrl, spot.photoUrl, file instanceof File);
+
+   if (intent === 'replace') {
+     const ext = (file as File).name.split('.').pop() ?? 'jpg';
+     const path = `${user.id}/spot/${reusedId}/${Date.now()}.${ext}`;
+     const { data: uploadData, error: uploadError } = await supabase.storage
+       .from('story-photos').upload(path, file as File, { upsert: true });
+     if (uploadError) continue;
+     const { data: { publicUrl } } = supabase.storage.from('story-photos').getPublicUrl(uploadData.path);
+     await prisma.storySpot.updateMany({ where: { storyId, spotId: reusedId }, data: { photoUrl: publicUrl } });
+     // 교체 성공 후에만 구 per-visit 파일 삭제
+     if (oldUrl) {
+       const oldPath = extractStoragePath(oldUrl);
+       if (oldPath) await supabase.storage.from('story-photos').remove([oldPath]);
+     }
+   } else if (intent === 'clear') {
+     await prisma.storySpot.updateMany({ where: { storyId, spotId: reusedId }, data: { photoUrl: null } });
+     const oldPath = extractStoragePath(oldUrl!);
+     if (oldPath) await supabase.storage.from('story-photos').remove([oldPath]);
+   }
+ }
```

구 사진 URL을 **별도로 스냅샷**해야 했다. 기존 조회가 `where: { storyId }` 기준이라 공유 스팟(`storyId ≠ this`)은 안 잡힌다. 이걸 안 하면 사진을 교체할 때마다 옛 파일이 storage에 고아로 쌓인다.

```ts
+     where: { storyId, spotId: { in: reusedIds } },

```

## 5. 결과 / 배운 것

### 결과

세 건 다 표시·저장이 정상화됐다. 재사용 스팟을 고르면 폼에 "호텔 델루나 +1"이 뜨고, 읽기 모드에서도 같은 값이 보이고, 편집에서 사진을 올리면 마커와 카드 썸네일에 반영된다. 저장 경로와 0203 잠금은 무접촉이다.

### 배운 것 1 — 경로가 늘면 원칙도 다시 적용해야 한다

0199에서 "새 per-visit 필드는 편집 로드 / 폼 payload / 저장 upsert 세 경로에 다 실어야 한다"는 원칙을 세웠다. 그리고 지켰다고 생각했다.

**그런데 S3-a가 경로를 하나 더 만들었다.** 후보 카드 → 폼이라는 경로다. 원칙에 그게 없었다.

```
0199 당시 경로   편집 로드 · 폼 payload · 저장 upsert
S3-a 이후        + 후보 카드 → 폼 (재사용 선택)
                 + 편집에서의 재사용 저장
```

원칙이 틀린 게 아니라 **원칙이 쓰인 시점의 지도가 낡았다.** 이건 0205 회고의 "관계는 그대로인데 의미가 바뀐다"와 같은 구조다. 기능을 추가할 때 "무엇이 늘었나"만이 아니라 "기존 원칙의 적용 범위가 어떻게 넓어졌나"를 물어야 한다.

### 배운 것 2 — 게이트와 값은 같은 필드를 봐야 한다

0211의 원인이 이거다.

```
"보여줄지 말지"  →  movieId 로 판정
"무엇을 보여줄지" →  movieTitle 에서 가져옴
```

두 필드가 항상 짝으로 세팅되던 동안에는 아무 문제가 없었다. **그래서 이 설계 결함이 몇 달간 숨어 있었다.** 0206이 한쪽만 채우는 순간 드러났다.

리뷰와 별점은 게이트와 표시가 같은 필드라 애초에 이런 일이 안 생긴다. 세 필드를 나란히 놓고 보니 작품만 어긋나 있었고, 그 대조가 원인을 짚어줬다.

**"이 값이 있으면 보여준다"는 판정은 그 값 자체로 해야 한다.** 대리 필드로 판정하면, 그 대리 관계가 깨지는 날 조용히 틀린다.

### 배운 것 3 — 합리적 판단이 다음 버그의 원인이 된다

0206에서 `movieId`를 안 채운 건 근거 있는 판단이었다.

- `NearbySpot` 타입에 id가 없다. 조회가 title만 가져온다
- 표시 전용이므로 id가 필요 없다
- 편집 모드가 `movieTitle`만으로 정상 렌더된다 (확인함)
- 저장 경로는 0203·0204에서 서버까지 차단돼 있어 값이 실려도 DB에 못 들어간다

**네 근거 다 맞았다.** 그런데 읽기 모드가 다른 소스를 본다는 걸 몰랐다. 편집 모드만 확인하고 넘어갔기 때문이다.

교훈은 "판단이 틀렸다"가 아니라 **"확인 범위가 좁았다"**다. 값을 하나만 채우기로 했으면, 그 값을 읽는 곳을 전부 세어봤어야 했다. 0212 조사에서 "지금 photoUrl을 읽는 화면이 각각 무엇을 읽는가 — 표로 정리하라"를 넣은 건 이 경험 때문이다.

### 배운 것 4 — 같은 값이 화면마다 따로 조립된다

하루에 세 번 터지고 나니 이게 구조 문제라는 게 보였다.

```
rating(0199)      편집로드 / 폼payload / 저장  — 세 경로 다 채워야 했다
작품(0206)        후보카드 → 폼               — 한 군데 빠져서 빈칸
작품(0211)        읽기모드가 다른 필드를 봄
photoUrl(0212)    편집 경로에서 재사용을 통째로 건너뜀
```

**한 값이 화면마다 다른 이름·다른 소스로 존재한다.** 작품 하나만 봐도 이렇다.

```
DB           spot_movies (다대다)
서버 쿼리     movies: [{ title }]
LocalSpot    movieId · movieTitle · extraMovieCount
읽기 렌더     movieTitle (0211 이후)
편집 렌더     movieTitle
```

**한 번은 우연이고 세 번이면 구조다.** 화면마다 각자 조립하는 대신 표시용 모양을 한 번 만들어 공유하는 게 맞는 방향이겠지만, 이번엔 열지 않았다. 리팩토링 범위를 감으로 정하지 않으려면 먼저 "작품·사진·별점이 각각 어느 화면에서 무엇을 읽는가"를 표로 만들어야 하고, 그건 별도 작업이다. 그리고 취업 일정상 동작하는 기능이 하나 더 있는 게 낫다고 판단했다.

### 배운 것 5 — 커밋 번호가 코드 주석과 어긋났다

회고를 쓰며 diff를 다시 읽다 발견했다. **0212 커밋이 넣은 주석 두 곳이 `0214`로 적혀 있다.**

```
// real spot 사진 교체 ... (per-visit 사진은 story_spots.photoUrl에 별도 미러 — 아래 재사용 루프, 0214)
// 0214: 재사용 스팟 per-visit 사진 — 공유 Spot.photoUrl 미수정, story_spots.photoUrl에만 기록
```

커밋 메시지와 파일명은 0212인데 코드 주석만 0214다. 이유는 추측하지 않는다. 다만 이게 이 세션에서 두 번째다. 0222에서도 커밋 메시지·주석은 "z15"인데 실제 상수는 13이었다.

**둘 다 "설계 단계에서 정한 것과 코드에 박힌 것이 다른데 아무도 안 봤다"는 같은 형태다.** 승인할 때 보고서와 커밋 메시지는 읽었지만, 정작 diff의 그 줄을 대조하지 않았다. 상수 하나·주석 한 줄짜리일수록 diff에서 그 줄을 직접 보는 게 빠르다.
