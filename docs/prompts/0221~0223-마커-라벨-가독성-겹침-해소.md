## 1. 한 줄 요약

지도 마커의 이름 라벨이 안 읽히는 문제를, 색 대비 → 고정 임계 분기 → 거리 기반 연속 계산 순으로 세 번에 걸쳐 풀었다.

## 2. 왜 / 목적 / 근거

### 왜 (동기·문제)

SpotFinder 지도에서 마커 이름이 두 가지 이유로 안 읽혔다.

**하나, 색이 묻혔다.** 비선택 마커 라벨의 배경(`--surface2` = #26292b)이 다크 지도 배경과 너무 비슷했다. 테두리가 흰색 12%로 있긴 했으나 너무 흐려서 분리가 안 됐다.

**둘, 겹쳤다.** 스팟 클릭 시 지도가 항상 줌 11로 이동했는데, 도심(종로 일대)처럼 스팟이 밀집한 곳에서는 라벨끼리 포개져 어느 게 무엇인지 알 수 없었다.

### 목적 (도달 상태)

- 비선택 라벨이 다크 배경에서 분리되어 보인다. 단 선택 라벨(파란 배경·흰 글자)보다 도드라지지 않아 위계가 유지된다.
- 스팟을 클릭하면 그 주변 라벨이 읽을 수 있을 만큼 벌어진다. 동시에 한적한 지역에서는 불필요하게 확대되지 않아 주변 맥락이 유지된다.

### 근거 (결정 기준)

**색 대비(0221)** — 배경색을 밝히는 대신 테두리만 12% → 30%로 올렸다. 배경을 밝히면 선택 마커와의 대비가 약해져 위계가 무너지고, 다크 팔레트 5단 중 이미 제일 밝은 값을 쓰고 있어 새 값을 만들어야 했다. 테두리 한 값만 바꾸는 게 최소 변경이면서 목적을 달성한다.

**겹침 해소(0222·0223)** — 임계값과 줌 레벨을 감으로 정하지 않았다. 실제 DB 좌표 65개의 최근접 거리를 전부 계산하고, 라벨 폭을 픽셀로 측정해 줌별 겹침 해소 거리를 도출했다. 그 숫자에서 임계를 뽑았다.

측정 결과(정제본 56개 기준):

| 최근접 거리 | 개수 | 성격 |
|---|---|---|
| 1km 이내 | 13 | 밀집 |
| 1~6km | 16 | 중간 |
| 6km 이상 | 27 | 고립(z11에서 안 겹침) |

줌별 라벨 비겹침 최소거리(라벨 폭 중앙값 92px 기준):

| 줌 | 비겹침 거리 |
|---|---|
| z11 | 5,575m |
| z14 | 697m |
| z15 | 349m |
| z16 | 175m |

도심 실제 거리: 덕수궁↔시청 336m, 마로니에↔낙산 443m, 광화문↔국제금융공사 507m.

이 표에서 **z14(697m)로는 종로가 안 풀리고, z16(175m)은 주변 맥락이 사라진다**는 판단이 나왔다.

### 0223 — 연속 계산 (+28 −14)

라벨 폭 근사 헬퍼를 새로 만들었다. 렌더에는 영향이 없고 줌 계산에만 쓴다.

```tsx
// components/SpotFinderMapNaver.tsx
// 0223: 미선택 라벨(pill) 폭 px 근사 — markerContent의 pill 파라미터 미러(font 12px, padding 9+9, border 1+1).
// 한글 12px(1em)·라틴/숫자 6.7·공백 4. 클릭 줌 계산의 겹침 폭에만 쓰임(렌더에는 무영향).
function labelWidthPx(name: string): number {
  let g = 0;
  for (const ch of name) g += ch === ' ' ? 4 : /[가-힣]/.test(ch) ? 12 : /[0-9A-Za-z]/.test(ch) ? 6.7 : 8;
  return g + 18 + 2;
}
```

상수를 임계·단계형에서 하한·상한·물리상수로 바꿨다.

```tsx
// components/SpotFinderMapNaver.tsx (상수)
- const DENSE_NEARBY_M = 1000;
- const CLICK_ZOOM_DENSE = 13;
- const CLICK_ZOOM_SPARSE = 11;
+ // 0223: 클릭 목표 줌을 최근접 이웃 거리에서 연속 계산(단계·임계 제거).
+ // z = round(log2(156543·cos(lat)·gapPx / D)), [z11, z16] 클램프. (줌 1↑ = 비겹침 거리 절반)
+ const SPOT_CLICK_ZOOM_MIN = 11; // = STAGE2_MAX_ZOOM (하한·분해 임계·맥락)
+ const SPOT_CLICK_ZOOM_MAX = 16; // 상한 — z16 비겹침 175m로 실 도심 전부 분리
+ const EQUATOR_MPP_Z0 = 156543;  // z0 적도 m/px (Web Mercator). mpp(z) = EQUATOR·cos(lat)/2^z
```

```tsx
// components/SpotFinderMapNaver.tsx (handleSpotSelect)
    // 0223: 최근접 이웃까지 거리에서 "라벨이 안 겹치는 최소 줌"을 연속 계산.
    let nearest = Infinity, nearestSpot: SpotFinderSpot | null = null;
    for (const other of visibleSpots) {
      if (other.id === spot.id) continue;
      const d = haversineM(spot.lat, spot.lng, other.lat, other.lng);
      if (d < nearest) { nearest = d; nearestSpot = other; }
    }
    let targetZoom = SPOT_CLICK_ZOOM_MIN; // 이웃 없음 → 하한(z11) 맥락
    if (nearestSpot) {
      // 비겹침: 중심거리(px) ≥ 두 라벨 half폭 합 = (Wa+Wb)/2. px = m/mpp, mpp = 156543·cos(lat)/2^z.
      // ⇒ z = log2(156543·cos(lat)·gapPx / D). 라벨 폭은 실제 이름 길이.
      const gapPx = (labelWidthPx(spot.name) + labelWidthPx(nearestSpot.name)) / 2;
      const mppZ0 = EQUATOR_MPP_Z0 * Math.cos((spot.lat * Math.PI) / 180);
      const zReq = Math.log2((mppZ0 * gapPx) / nearest); // nearest=0(중복좌표) → +Inf → 상한 클램프
      targetZoom = Math.max(SPOT_CLICK_ZOOM_MIN, Math.min(SPOT_CLICK_ZOOM_MAX, Math.round(zReq)));
    }
    mapInstance.morph(new naver.maps.LatLng(spot.lat, spot.lng), targetZoom, STAGE2_TRANSITION);
```

## 5. 결과 / 배운 것

### 결과

실기기·브라우저 확인 결과, 도심(종로·세운전자상가)에서는 라벨이 벌어져 읽히고, 구룡포처럼 초밀집인 곳은 상한 z16까지 들어가며, 한적한 지역은 z11에 머물러 맥락이 유지된다. 검산도 표와 일치했다.

| 최근접 거리 | 계산된 줌 |
|---|---|
| 5,575m | z11 |
| 1,058m (와룡공원) | z13 |
| 336m (덕수궁↔시청) | z15 |
| 4m (구룡포) | z21 → 상한 z16 |

한 가지는 못 풀었다. 구룡포 가옥거리와 계단은 4m 거리라 **어떤 줌으로도 라벨이 안 벌어진다.** 상한에서 멈추게 하고 주석으로 남겼다.

### 배운 것 1 — 고정 임계는 경계 바깥을 놓친다

0222에서 "1km 안이면 밀집"이라고 잘랐다. 도심·구룡포·월정사가 다 잡혀서 잘 됐다고 생각했다.

그런데 와룡공원 ↔ 북촌로6길이 **1,058m**였다. 임계를 58m 차이로 넘어 "한적"으로 판정됐고, z11로 갔고, z11은 5,575m 이상 떨어져야 안 겹치니 당연히 겹쳤다. 같은 문제를 겪는 스팟이 1~5.5km 구간에 16개나 있었다.

**임계값 자체가 문제가 아니라, "임계를 둔다"는 발상이 문제였다.** 필요한 줌은 거리에 따라 연속적으로 변하는데, 그걸 두 단계로 뭉갠 것이다. 줌이 1 오를 때마다 비겹침 거리가 정확히 절반이 된다는 관계가 이미 표에 있었는데, 그 관계를 쓰지 않고 표에서 값 두 개만 뽑아 썼다.

0223에서 임계와 단계를 다 지우고 거리를 넣으면 줌이 나오는 식으로 바꿨다. 지역·이름 길이와 무관하게 동작하고, 스팟이 늘어도 코드를 안 건드려도 된다.

### 배운 것 2 — 결정과 구현이 어긋난 채로 다음 커밋에 묻혔다

회고를 쓰려고 diff를 다시 읽다가 발견했다.

```
0222 커밋 메시지    "최근접 이웃이 1km 안에 있으면 z15"
0222 코드 주석      "z15 = 349m↑ 쌍 겹침 해소"
0222 실제 상수      CLICK_ZOOM_DENSE = 13
```

**설계 단계에서 z15로 정했는데 코드엔 13이 들어갔다.** 메시지와 주석은 전부 z15를 말하는데 값만 13이다. 즉 0222는 실제로는 z13으로 동작하고 있었다.

그리고 이걸 아무도 못 잡았다. 이유가 있다. 0223에서 이 상수 자체를 지우고 연속 계산으로 갈아엎었기 때문에, **잘못된 값이 드러날 기회 없이 사라졌다.** 겹침이 안 풀린 걸 보고 "임계가 빡빡하다"고 진단했는데, 실은 목표 줌도 의도보다 두 단계 낮았던 것이다. 진단이 완전히 틀린 건 아니지만(임계 문제도 실재했다), 원인의 절반만 본 셈이다.

**교훈은 "검증할 때 값을 눈으로 확인하라"에 가깝다.** 당시 CC 보고와 커밋 메시지를 읽고 승인했는데, 둘 다 z15라고 적혀 있었으니 통과했다. 정작 코드에 박힌 숫자를 직접 대조하지 않았다. 상수 하나짜리 변경일수록 diff의 그 줄을 보는 게 빠르다.

그리고 이 사례가 회고를 쓰는 이유이기도 하다. **커밋 당시에는 몰랐던 걸 나중에 diff를 다시 읽으며 발견했다.**

### 배운 것 3 — 실측이 판단을 대신한다

이 작업에서 감으로 정한 숫자가 거의 없다.

- 임계 1km → 최근접 거리 분포의 자연 경계(13/16/27 분할)
- z14 기각 → 697m라 종로(336~507m)를 못 푼다
- z16 상한 → 175m면 실 도심 전부 분리, 그 아래는 어떤 줌으로도 불가
- 라벨 폭 → 중앙값 92px이 아니라 실제 이름으로 계산

특히 마지막이 중요했다. 고정 92px은 평균이지 실제가 아니다. "제주국제공항"과 "1"이 같은 폭일 리 없는데, 평균으로 계산하면 긴 이름끼리 붙어 있을 때 여전히 겹친다. 클릭한 스팟과 최근접 스팟 **두 개만** 재면 되므로 비용도 없다.

비교 대상을 전체 스팟이 아니라 `visibleSpots`로 잡은 것도 같은 결이다. 라벨 겹침은 **실제로 그려진 마커 사이에서만** 발생한다. 작품 칩으로 걸러진 상태면 화면에 몇 개 없는데 전체 기준으로 재면 안 보이는 이웃 때문에 불필요하게 깊이 들어간다.
