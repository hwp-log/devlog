## 1. 한 줄 요약

[여행순서 바꾸기]를 활성화해 `'reorder'` mode를 추가하고, 사이드 카드에 SpotList(드래그 정렬 + × 삭제)를 띄웠다. 삭제는 청사진의 "길게 눌러 삭제" 대신 **× 버튼**으로 — 드래그와 입력·위치가 안 겹치게 분리했다.

---

## 2. 왜 / 목적 / 이유

### 핵심 A — `'reorder'` mode 추가

- **왜**: [여행순서 바꾸기] 버튼이 0055부터 비활성으로 배포돼 있던 미완성 노출. 하던 걸 마무리해야 했다.
- **목적**: 메뉴 → reorder 진입 → 드래그로 순서를 바꾸면 마커 번호·색·폴리라인·목록 번호가 다 따라 갱신되는 상태.
- **이유**: 0056의 `'search'` mode 추가 패턴(타입에 mode 추가 → 버튼 활성화 → 사이드 카드 분기)을 그대로 재사용. SpotList·드래그 정렬·`onReorder`가 이미 동작해 연결만 하면 됐고, 새 의존성 0개.

### 핵심 B — 삭제는 "길게 눌러 삭제" 대신 × 버튼 (이번 핵심 결정)

- **왜**: 청사진은 "길게 눌러 삭제(아이폰 패턴)"였다. 그런데 `@dnd-kit`의 PointerSensor는 "누르고 끌면 = 드래그"인데, 길게누르기도 "누르고 시작"이라 *같은 입력을 두고 싸운다* → (a) 끌다가 실수 삭제, (b) 충돌 조율(delay 튜닝·별도 제스처 처리)로 구현이 무거워진다.
- **목적**: 되돌리기 힘든 동작(삭제)이 이미 있는 동작(드래그)과 안 싸우는 상태.
- **이유**: 기준 = **"삭제 ↔ 드래그 분리."** × 버튼은 별개 `<button>`이라 dnd-kit 포인터 이벤트와 안 섞이고, 가볍고, 접근성(`aria-label`)도 공짜. 0057b에서 ×를 드래그 핸들과 **양 끝으로** 떼어 물리적으로도 분리(실수 삭제 더 줄임). 길게누르기를 감수할 수도 있었지만, 0057은 "하던 거 마무리"가 목표라 무거운 제스처 작업을 끼우면 늘어진다고 판단해 보류. **삭제 확인 단계도 같은 이유로 의도적으로 뺐다**(나중에 폴리시로).

> 면접용 한 문장: "삭제는 되돌리기 힘드니 드래그와 입력·위치를 모두 분리한다 — 길게누르기는 드래그와 포인터 입력이 겹쳐 실수·구현 부담이 커서 별개 × 버튼으로 갔다."

### 핵심 C — 마커 색은 "통일" 대신 방향성 유지

- **왜**: 2번 마커 빨강이 거슬린다는 메모(원래 "파랑 계열로 통일" 검토).
- **목적**: 마커 색이 시각 노이즈가 아니라 *동선 정보*를 담는 상태.
- **이유**: 동선 기능엔 출발/도착 색 구분이 의미 있다(신호등 관습: 초록=출발, 빨강=도착)고 판단 → "통일"이 아니라 **방향성 유지**로 결정. 시작=초록 / 끝=빨강 / 중간=파랑, 단일 마커만 파랑. 즉 진짜 목표는 "빨강 제거"가 아니라 "*의미 없는* 색 노이즈 제거"였고, 의미 있는 빨강(도착)은 남겼다.

### components/SpotMap.tsx — 'reorder' mode + 삭제 연결

```tsx
// Mode 타입 (6개)
type Mode = 'menu' | 'pinning' | 'search' | 'reorder' | 'edit' | 'view';

// 삭제 후 2곳 미만이면 자동으로 menu 전환
function handleDeleteInReorder(spotId: string) {
  handleDelete(spotId);                                  // 기존 삭제(order 재정렬 포함)
  if (localSpots.filter((s) => s.id !== spotId).length < 2) {
    setMode('menu');                                     // 1곳이면 순서 편집 의미 없음
  }
}

// [여행순서 바꾸기] 버튼: 2곳 미만이면 disabled, 이상이면 onClick setMode('reorder')
// 사이드 카드 reorder 분기: <SpotList onReorder={handleReorder} onDelete={handleDeleteInReorder} />
// 하단 SpotList 블록: 0057b에서 통째 제거 (reorder 사이드 카드로 역할 이전)
```

> `handleDeleteInReorder`의 2→1 자동 전환은 React 이벤트 배칭에 기댄다 — 화면에서 reorder가 1곳짜리로 깜빡이는지 확인 항목(깜빡이면 `setMode`를 effect로 이동).

## 5. 결과 / 배운점

### 결과
- [여행순서 바꾸기] 활성화 — 2곳 미만 잠김, 이상이면 reorder 진입.
- 드래그 순서 변경 → 마커 번호·색·폴리라인·목록 번호 다 갱신.
- × 삭제 → 재정렬. 핸들 왼쪽 / × 오른쪽으로 분리해 실수 삭제 줄임.
- 마커 색: 출발 초록 / 도착 빨강 / 중간 파랑.

### 배운점
1. **제스처 위에 제스처를 얹지 말 것.** dnd-kit 포인터 위에 길게누르기를 더하면 입력이 겹쳐 충돌·실수가 난다. 별개 버튼이 충돌 0 + 접근성 공짜.
2. **위험한 동작은 입력·위치 둘 다 분리.** 삭제(되돌리기 힘듦)를 × 별개 버튼 + 핸들과 양 끝 거리로 떼었다.
3. **"통일" 의도가 한 바퀴 돈 케이스.** 진짜 목표는 "빨강 제거"가 아니라 "의미 없는 색 노이즈 제거"였고, 의미 있는 빨강(도착)은 남겼다. 결정의 *기준*을 다시 확인.
4. **자동 모드 전환은 배칭 의존.** 2→1 삭제 시 reorder→menu 전환을 React 이벤트 배칭에 기댔는데, 화면 테스트에서 깜빡임 없이 동작 확인.
