## 2. 왜 / 목적 / 이유

### 사이드 카드 패턴 선택 (Mapbox Popup 폐기)
- **왜**: Mapbox Popup이 근처 마커를 가리는 문제가 있다. offset + maxWidth 조정은 미봉책이다.
- **목적**: 마커 클릭 시 정보 카드를 지도 옆에 표시해 마커 가림을 원천 차단한다.
- **이유**: Mapbox Github issue #4676 (2017~2026 미해결). 라이브러리 한계를 확인한 후 사이드 패널 전환을 결정했다. Airbnb / Google Maps 모두 동일한 패턴을 사용한다.

### Server Actions bodySizeLimit 5mb 설정
- **왜**: 사진 업로드 FormData가 기본 1MB 제한을 초과해 `Body exceeded 1 MB limit` 에러가 발생한다.
- **목적**: 5MB 이하 사진 업로드를 허용한다.
- **이유**: Server Actions 기본 1MB는 DDoS 방지 목적이다. 사진 업로드는 명시적으로 파일 크기 검증(`MAX_SIZE = 5 * 1024 * 1024`)을 서버 액션 내에서 직접 수행하므로 5MB로 상향해도 보안상 문제가 없다.

### onUpdate 콜백 패턴 (revalidatePath + reconciliation 충돌 해결)
- **왜**: 제목 저장 후 카드에 옛 이름이 유지된다. `setDisplayName` 호출은 정상이지만 UI에 반영되지 않는다.
- **목적**: 저장 성공 후 부모 SpotMap의 `activeSpot`과 `localSpots`를 즉시 동기화한다.
- **이유**: `revalidatePath` → `router.refresh()` → RSC payload 재전송 → React reconciliation 중 SpotPopup이 리마운트될 수 있다. 리마운트 시 `useState(spot.name)`이 stale `activeSpot.name`으로 재초기화된다. `onUpdate` 콜백으로 부모 상태를 갱신하면 리마운트 후에도 올바른 초기값을 읽는다.

// 삭제 + 순서 재정렬
export async function deleteSpot(spotId: string) {
  await prisma.$transaction(async (tx) => {
    await tx.spot.delete({ where: { id: spotId } });
    const remaining = await tx.spot.findMany({
      where: { storyId },
      orderBy: { order: 'asc' },
    });
    // 중간 조회가 필요해 배열 형식 대신 함수 형식 사용 (0048과 다름)
    await Promise.all(
      remaining.map((s, i) => tx.spot.update({ where: { id: s.id }, data: { order: i + 1 } }))
    );
  });
}

## 5. 결과 / 배운점

### 결과

- 마커 클릭 시 Airbnb/Google Maps 패턴의 사이드 카드 표시. 지도와 카드가 2/5 비율로 반응형 배치된다.
- 사진 업로드 / 이름 편집 / 리뷰 편집 / 삭제 기능 전체 완성.
- transition duration-200으로 카드 show/hide 시 지도 크기 전환이 부드럽다.
- 함정 7개 직면 + 갈음으로 학습 자산 12개 확보.

### 배운점

**1. Next.js Server Actions 1MB 제한**
기본 1MB는 DDoS 방지 목적이다. 파일 업로드 기능이 있으면 `experimental.serverActions.bodySizeLimit`을 명시적으로 설정해야 한다. 서버 액션 내에서 파일 크기를 재검증하면 보안을 유지하면서 제한을 상향할 수 있다.

**2. Mapbox Popup 한계 — 라이브러리 한계 수용 결정**
offset + maxWidth는 미봉책이다. 마커를 가리는 근본 원인은 Popup 위치 계산 방식에 있고, 2017년부터 미해결 이슈다. 라이브러리 한계를 확인하면 대안 패턴(사이드 카드)으로 전환하는 결정이 빠를수록 낫다.

**3. Prisma shadow DB + Supabase storage 스키마 충돌**
`prisma migrate dev`는 shadow DB에서 마이그레이션을 검증한다. Supabase 전용 스키마(`storage.objects`)가 shadow DB에 없으면 `P3006` 에러가 발생한다. 개발 단계에서는 `prisma db push`로 우회할 수 있지만, 마이그레이션 파일이 생성되지 않으므로 Production 배포 시점에 별도 마이그레이션 처리가 필요하다.

**4. revalidatePath + router.refresh + React reconciliation 충돌**
`revalidatePath` 호출 → Next.js `router.refresh()` 자동 트리거 → RSC payload 재전송 → 클라이언트 컴포넌트 reconciliation. 이 과정에서 `startTransition` async 콜백의 setState가 언마운트된 컴포넌트에 적용되면 React가 폐기한다. 부모 상태(`activeSpot`)를 동기화하는 `onUpdate` 콜백 패턴으로 해결했다.

**5. useState 초기값 + props 변경 함정**
`useState(spot.name)`은 마운트 시점에 한 번만 설정된다. props.spot이 변경돼도 같은 컴포넌트 인스턴스를 재사용하면 상태는 갱신되지 않는다. `key={activeSpot.id}` 추가로 id 변경 시 리마운트해 useState가 재초기화되도록 했다.

**6. $transaction 함수 형식 vs 배열 형식**
0048 `reorderSpots`는 중간 조회가 없어 배열 형식을 사용했다. 0049 `deleteSpot`은 삭제 후 남은 항목을 조회(`findMany`)해서 순서를 재정렬하므로 함수 형식이 필요하다. 트랜잭션 형식 선택 기준: 중간 조회 필요 여부.

**7. CSS transition 이중 구조**
width transition을 위해 외부 컨테이너는 항상 DOM에 존재해야 한다. `display: none`이나 조건부 렌더만으로는 width transition이 작동하지 않는다. 외부 div는 항상 렌더(transition 담당), 내부 SpotPopup은 조건부 렌더(콘텐츠 담당)로 역할을 분리했다.

**8. 권한 검증 공통 유틸 분리 (DRY)**
3개 서버 액션(uploadSpotPhoto / updateSpot / deleteSpot)이 같은 패턴(인증 → 소유권 확인)을 사용한다. `getSpotWithOwnership` 유틸로 공통화해 코드 중복을 제거했다. 0048 reorderSpots 시점에는 인라인으로 처리했는데, 3개 이상 액션이 같은 패턴을 쓰는 시점에 유틸 분리를 결정하는 게 합리적이다.

**9. readOnly prop으로 같은 컴포넌트 다중 모드**
SpotPopup이 수정 페이지(편집 가능)와 상세 페이지(읽기 전용)에서 같은 컴포넌트로 동작한다. `readOnly={!canAddSpot || !storyId}` 조건으로 모드를 결정한다. 편집 버튼 / 삭제 버튼 / 사진 업로드 input은 readOnly=false일 때만 렌더링한다. Airbnb / Google Maps 같은 서비스가 사용하는 공통 카드 컴포넌트 패턴.

## 결정 (Decisions)

- **Mapbox Popup 폐기 → 사이드 카드**: 라이브러리 미해결 이슈 확인 후 Airbnb/Google Maps 패턴 채택
- **prisma db push 우회**: shadow DB 충돌로 migrate dev 불가 → Production 마이그레이션은 별도 시점에 처리
- **bodySizeLimit 5mb**: 서버 액션 내 파일 크기 재검증이 있으므로 상향 적용
- **onUpdate 콜백 패턴**: revalidatePath 충돌 해결을 위한 부모 상태 동기화 표준 패턴
- **key={activeSpot.id}**: props 변경 시 리마운트가 필요한 컴포넌트의 표준 해결 패턴
