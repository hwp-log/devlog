# 0071 회고: 공항편 선택 드롭다운 변경 및 메뉴 디자인 통일

- 작성일: 2026-06-05
- 소요: 약 1.5시간
- 관련 커밋: `feat: 0071 공항 선택 드롭다운 적용, 카드 디자인 통일 (글래스·모서리)`

## 한 줄 요약

IATA 코드 직접 입력을 한일 공항 13개 드롭다운으로 교체하고, 직항 노선 매트릭스(ROUTES)로 도착지 목록을 필터링해 직항이 없는 조합은 선택 자체가 불가능하게 만들었다. 소개 박스와 항공편 카드를 글래스 톤·14px 모서리로 통일했다.

## 왜 / 목적 / 이유

### 1. 자유 입력 → 닫힌 드롭다운

- 왜: IATA 코드(ICN, NRT)는 개발자에게는 익숙하지만 일반 사용자에게는 낯설다. 한글 입력, 오타, 없는 코드 같은 오입력이 빈 검색 결과의 주요 원인이었고, 그때마다 정제 로직과 안내 문구를 덧붙이는 대응을 반복하고 있었다.
- 목적: 타이핑 없이 고르기만 하면 되는 입력. 오입력이라는 원인 자체가 존재하지 않는 상태.
- 이유: v1의 대상이 한일 노선이라 공항이 13개(한국 6 + 일본 7)로 유한하다. 선택지가 닫혀 있으면 자유 입력이 아니라 선택이 맞다. 스카이스캐너식 자동완성(searchAirport API 활용)도 검토했지만, 전 세계 공항이 필요해지는 시점에 가치가 생기는 기능이고 타이핑마다 API 호출이 발생해 호출량·구현 비용 대비 이득이 없어 백로그로 보류했다.

### 2. ROUTES 직항 노선 매트릭스 — 사전 차단

- 왜: 직항이 없는 조합(예: 청주-하네다)은 언제 검색해도 빈 결과다. 기존 안내 문구("출발일을 바꾸거나 직항 노선인지 확인해보세요")는 검색이 실패한 뒤에 사용자가 추측하도록 돕는 사후 처리라, 원인이 여러 개(오타·노선·날짜)인 상황에서는 정확한 안내가 불가능했다.
- 목적: 잘못된 조합은 화면에서 고를 수 없는 상태. 오류를 처리하는 것이 아니라 오류가 발생할 수 없게 만드는 것.
- 이유: `ROUTES: Record<string, string[]>`로 직항 노선을 정의하고, 출발 공항을 선택하면 도착 드롭다운에 연결 가능한 공항만 남긴다. 한국발 6개 키만 직접 정의하고 일본발은 역방향으로 자동 도출했다 — 노선표 자체도 정의는 한 곳이라, 노선 하나를 추가하면 양방향에 동시에 반영된다. 부수효과로 빈 결과의 원인이 사실상 날짜 하나로 수렴해, 기존 안내 문구가 비로소 정확한 말이 됐다. 노선은 취항·단항으로 변하므로 "2026-06 기준 정기 직항" 주석을 달고 확실한 노선만 보수적으로 넣었다.

### 3. 카드 디자인 통일 (글래스·모서리)

- 왜: 한 화면에 흰색이 두 종류(불투명 흰색 카드 / 반투명 글래스 카드), 모서리 반경이 두 종류(14px / glass-outer의 큰 반경) 섞여 있어 미세하게 어긋나 보였다. 소개 박스는 주황 배경이라 전체 톤과도 달랐다.
- 목적: 상세·편집기·소개·비용·항공편 카드가 하나의 디자인 규칙을 따르는 상태.
- 이유: 개별 카드에 스타일을 덧붙이지 않고 glass-outer 클래스 정의 한 곳에서 모서리를 14px로 변경하고, 항공편 카드(FlightLeg·SkeletonCard)의 불투명 흰색을 glass-outer로 교체했다. 글래스는 반투명 흰색 + 배경 블러라 단색을 따라 찍는 방식으로는 채도를 맞출 수 없고, 같은 클래스를 쓰는 것이 맞는 방법이다. 전역 클래스 변경이므로 다른 화면(스토리·랜딩)도 함께 바뀌는 양면이 있어, 전 화면 점검을 후속 항목으로 남겼다.

## 코드 작성 & 수정

직항 노선 정의와 역방향 자동 도출 — 한국발만 적으면 일본발은 따라온다:

```typescript
// app/(protected)/my-plan/new/FlightSearchSection.tsx
// 2026-06 기준 정기 직항 노선 (한국 출발 기준 정의)
const KR_ROUTES: Record<string, string[]> = {
  ICN: ['NRT', 'HND', 'KIX', 'FUK', 'CTS', 'NGO', 'OKA'],
  GMP: ['HND', 'KIX', 'CJU', 'PUS'],
  PUS: ['NRT', 'KIX', 'FUK', 'NGO', 'GMP', 'CJU'],
  CJU: ['GMP', 'PUS', 'TAE', 'CJJ'],
  TAE: ['CJU'],
  CJJ: ['CJU'],
};

// 일본발 노선은 역방향으로 자동 도출 — 노선표도 정의는 한 곳
const ROUTES: Record<string, string[]> = { ...KR_ROUTES };
for (const [origin, dests] of Object.entries(KR_ROUTES)) {
  for (const dest of dests) {
    (ROUTES[dest] ??= []).push(origin);
  }
}
```

출발 선택에 따라 도착 목록이 좁아지는 select:

```tsx
// 도착 드롭다운 — ROUTES[origin]에 있는 공항만 옵션으로 표시
const destOptions = ROUTES[origin] ?? [];
<select value={dest} disabled={!origin} onChange={...}>
  <option value="">공항 선택</option>
  {destOptions.map((code) => (
    <option key={code} value={code}>{AIRPORT_NAME[code]} ({code})</option>
  ))}
</select>
```

출발 변경 시 무효해진 도착 초기화:

```typescript
function handleOriginChange(value: string) {
  setOriginIata(value);
  if (destIata && !(ROUTES[value] ?? []).includes(destIata)) {
    setDestIata(''); // 새 출발지에서 갈 수 없는 도착지면 초기화
  }
}
```

## 결과 / 배운점

- 직항 없는 조합은 화면에서 고를 수 없게 됐고, 같은 공항 선택도 노선표에 자기 자신이 없으므로 자동으로 차단된다. 빈 결과의 원인이 날짜 하나로 수렴했다.
- **오류는 발생 후 안내하는 것보다 발생 자체를 차단하는 것이 낫다.** 안내 문구는 사용자가 실수한 뒤에 추측을 돕는 사후 처리고, 선택지 제한은 실수가 일어나기 전에 작동한다. 도메인이 유한할 때(공항 13개) 자유 입력을 닫힌 선택지로 바꾸면 잘못된 상태는 표현 자체가 불가능해진다.
- **단일 출처 원칙은 코드만이 아니라 데이터에도 적용된다.** 노선표를 양방향으로 두 번 적었다면 노선 하나 바꿀 때 두 곳을 고쳐야 했다. 한 방향만 정의하고 역방향을 도출하는 구조로, 0070의 "정의는 한 곳" 원칙이 상수 데이터에서도 반복됐다.
- 기능의 범위 결정도 설계다. 자동완성이 더 화려하지만, v1 사용자 동선(한일 노선)에는 닫힌 드롭다운이 더 정확하고 빠르고 싸다. "안 만들기로 한 것"과 그 근거를 남기는 것이 면접에서 기능 자체보다 좋은 답이 된다.
- 시각 통일은 색을 따라 찍는 게 아니라 같은 정의(클래스)를 쓰는 것으로 달성한다. 전역 클래스 수정은 일관성을 공짜로 주는 대신 점검 범위도 전역이 된다.
