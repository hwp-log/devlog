## 1. 한 줄 요약

영속 스팟의 사진 비우기가 팝업 저장 시점에 Storage를 물리 삭제하던 것을, 교체 경로와 대칭인 지연 반영(상단 "수정" 제출 시 반영)으로 전환 — 의도는 새 상태 없이 서버가 DB 스냅샷과 제출 payload의 diff로 파생 판정.

---

## 2. 왜 / 목적 / 이유

### 비가역 소실의 비대칭
- **왜**: story 편집은 2단 저장(팝업 저장 = 화면 임시 / 상단 수정 = DB 영속)인데, 영속 스팟의 사진 비우기만 `clearSpotPhoto`를 즉시 호출해 Storage 파일까지 삭제. 상단 수정 없이 이탈하면 다른 필드는 새로고침으로 복구되지만 사진만 비가역 소실.
- **목적**: 모든 편집이 같은 시점(제출)에 영속화되는 대칭 구조. 삭제의 비가역성 대응은 unapproveMovie 때와 같은 문제의식.
- **이유**: 사용자의 머릿속 모델("수정 누르기 전엔 확정 아님")과 시스템 동작의 일치. 예외 1개가 전체 모델을 배신한다.

### 의도 전달 = 서버 파생 (클라이언트 상태 추가 0개)
- **왜**: 실측 결과 `updateStoryAction` L85가 이미 제출 spotsJson의 `photoUrl ?? null`을 DB에 쓰고 있었음 — 비우기 의도의 절반(DB null)은 이미 구현돼 있었고, 빠진 것은 Storage 물리 삭제뿐.
- **이유**: 의도가 기존 payload에 이미 실려 있으므로 명시 payload(Map 확장/Set)는 spotsJson과 이중 소스가 된다. 파생 가능한 것을 저장하지 않는 0161 원칙과 동일 — 서버가 DB 스냅샷 vs 제출 diff로 판정.

## 4. 코드 작성 & 수정

### 1. 판정 유틸 (신규, `lib/story/photo-cleanup.ts`) — 판정표를 코드로

```typescript
export function resolvePhotoIntent(
  oldUrl: string | null,
  submittedUrl: string | null | undefined,
  hasPendingFile: boolean,
): PhotoIntent {
  if (hasPendingFile) return 'replace';
  // photoUrl:null + 파일 부재 = 비우기 의도의 파생 판정 (DB 스냅샷 vs 제출 payload의 diff 기반)
  if (oldUrl && !submittedUrl) return 'clear';
  return 'keep';
}
```

| 케이스 | DB | 제출 | 파일 | 판정 → 동작 |
|---|---|---|---|---|
| ① 비우기 | non-null | null | 없음 | clear → DB null(기존 L85) + 트랜잭션 후 Storage 삭제 (신규) |
| ② 교체 | non-null | blob(무시됨) | 있음 | replace → 기존 업로드 로직 불변 + 성공 후 구 파일 삭제 (신규) |
| ③ 무변경 | X | X | 없음 | keep → 무동작 |
| ④ 연속 조작 | — | 최종값만 | 최종값만 | 클라이언트에서 수렴: 비우기→교체=② / 교체→비우기=① |

`extractStoragePath`는 구 clearSpotPhoto의 URL→경로 추출 로직 이관본 (+ URL 파싱 try/catch 가드). 테스트 12케이스로 판정표 고정.

### 2. updateStoryAction 편입 (`app/story/[id]/actions.ts`)

- 트랜잭션 **전**: `findMany`로 구 photoUrl 스냅샷 확보

- **실패 방침**: Storage 삭제 부분 실패 허용 (기존 업로드 실패 정책과 동일 리듬)

## 5. 결과 / 배운점

### 결과
- 팝업 저장 시 서버 접촉 0 — 2단 저장 원칙에 예외 없음. 비우기 저장 후 상단 수정 없이 새로고침하면 사진 복원 (기존엔 소실)
- 부수 개선: 교체 시 구 파일이 무조건 고아로 남던 누수 해소 (성공 후 구 파일 삭제)
- 코드 175줄 삭제 (죽은 액션 6개), 신규는 순수 함수 2개 + 테스트
- 테스트: photo-cleanup 12 + SpotPopup 14 = 26 Green, tsc 클린

### 배운점
- **의도는 이미 payload에 있었다**: "비우기 의도를 어떻게 전달할까"로 시작했지만, 실측하니 L85가 이미 절반을 하고 있었음. 새 상태·새 필드 추가 전에 기존 데이터 흐름에 의도가 실려 있는지부터 확인 — 파생 가능한 것은 만들지 않는다.
- **삭제 순서 = 안전의 방향**: DB 확정 → Storage 물리 삭제. 실패의 최악이 "고아 파일(가역 누수)"이 되도록 순서를 설계하면, 비가역 소실은 구조적으로 불가능해진다.
- **죽은 코드는 무리지어 있다**: 요청은 2개 제거였지만 같은 파일의 6개 전부가 고아였음 — 구조 전환(개별 액션→일괄 동기화)이 일어난 파일은 전수 조사 가치가 있다.

### 미해결 / 범위 밖 보고
- **스팟 삭제 시 Storage 고아**: `deleteMany`는 사진 파일을 지우지 않음 (기존 동작, 이번 범위 밖) — 같은 파생 판정 리듬(스냅샷에 있고 제출 목록에 없는 spot)으로 확장 가능
- 기존 auth 테스트 7개 실패, `.next` validator tsc 오류 — 기존 이슈 (0161 보고와 동일)

## 결정 (Decisions)

- **비우기 의도 = 서버 파생 판정**: 클라이언트 상태 추가 없이 DB 스냅샷 vs 제출 spotsJson의 diff로 판정 (`photoUrl:null + 파일 부재 = 비우기`). 명시 payload는 spotsJson과 이중 소스라 기각.
- **Storage 삭제는 DB 확정 후, 부분 실패 허용**: 기존 업로드 실패 정책(continue)과 동일 리듬. 원자성보다 "비가역 소실 불가능" 보장을 우선.
- **판정 로직은 순수 함수로 분리** (`lib/story/photo-cleanup.ts`): 판정표를 테스트로 고정, 서버 액션 본문은 수집·실행만.
- **spots/actions.ts 파일 전체 삭제**: 6개 액션 전수 grep 0건 근거. 개별 spot CRUD 액션 시대의 유물 — 필요 시 git 이력 복원.

### 발견의 계기

0161(SpotPopup 상태 재배치) 완료 후 브라우저 수동 검증 중 위화감이 있었다. 이 앱의 편집은 2단 저장이다 — 팝업의 [저장]은 화면 임시 반영까지, 실제 DB 반영은 페이지 상단 [수정] 제출이 담당한다. 실제로 스팟을 삭제해도 상단 [수정] 없이 새로고침하면 마커가 되살아난다. 그런데 **사진 비우기만 팝업 [저장] 시점에 즉시 서버 반영**되고 있었다 — 그것도 Storage 파일 물리 삭제라 새로고침으로도 복구 불가. 모든 조작 중 이것 하나만 원칙 밖에서 움직이고 있었고, 이 비대칭의 수리가 본론(§1~5)이다.

수리를 마치고 질문이 남았다 — 2단 저장 구조를 스스로 만든 프로젝트에 왜 이 예외가 존재했나. git 이력과 당시 회고를 발굴한 결과를 부록으로 남긴다. 결론부터: 예외는 구조 전환에서 살아남은 잔재가 아니라, **전환 완료 52분 뒤에 새로 태어난 회귀**였다.

### 왜 회귀했나

당시 회고(0053)는 defer 원칙을 스스로 세워 두었다: "비우기를 즉시 실행하면 [취소]가 의미 없어짐 → 실제 삭제는 [저장] 시점으로 연기." 원칙은 정확했으나 **적용 범위를 팝업 한 층(취소 대비)까지만 설정** — "팝업 저장 = 확정"으로 모델링했고, 상단 제출까지의 2단은 tmp_ 스팟에서만 실현했다.

회귀의 배경 추정(이력에 명시 근거 없음): 추가·교체는 pendingPhotos Map에 파일을 싣는 지연 채널이 자연스러웠지만, 비우기는 실을 파일이 없어 의도 채널이 없어 보였고 가장 짧은 길이 개별 액션이었을 것. 실제로는 그 채널이 photoUrl:null로 이미 존재했으나 당시 그렇게 읽지 못했다 — 이번 사이클의 서버 파생 판정이 그 읽기를 6주 늦게 수행한 셈이다.

### 배운점 — 원칙의 사정거리

- 결함의 성격은 "원칙 부재"도 "원칙 위반"도 아닌 **원칙의 적용 범위 미달**이었다. 원칙을 세우는 것과 그 원칙이 닿아야 할 층을 전부 짚는 것은 다른 작업이다.
- 전환 완료 52분 뒤의 새 기능에서 회귀가 일어났다 — 작업 중의 판단과 원칙 수립 시의 판단은 같은 사람 안에서도 분리된다. 완료 시점의 원칙 정합 자가점검(CLAUDE.md §8 신설)이 이 간극의 대응책이다.
- 모순은 6주간 어떤 문서에도 잡히지 않았고, 발견 경로는 실기기 수동 검증의 위화감이었다 — 테스트와 문서가 놓치는 층을 수동 검증이 잡는다.
