---

## 1. 한 줄 요약

스토리에 좋아요 기능을 추가했다. likes 테이블과 RLS를 작성하고(1단계), 상세 페이지에 낙관적 업데이트 토글 버튼을, 피드에 좋아요 수와 내 좋아요 상태 표시를 적용했다(2단계). 같은 작업에서 피드 카드 UI를 velog 구조로 정비했다.

---

## 2. 왜 / 목적 / 이유

### likes 테이블 + 복합 unique 설계
- 왜: 한 사람이 한 스토리에 좋아요를 한 번만 적용할 수 있어야 한다.
- 목적: 중복 좋아요가 데이터 차원에서 불가능한 상태.
- 이유: 애플리케이션 코드가 아니라 DB 제약 `@@unique([storyId, userId])`이 규칙을 보장한다. 코드 검증은 누락될 수 있으나 제약은 항상 작동한다.

### 카운트를 비정규화 컬럼 없이 _count로 조회
- 왜: 좋아요 수를 화면에 표시하고 정렬에도 사용해야 한다.
- 목적: 카운트가 항상 실제 좋아요 행 수와 일치하는 상태.
- 이유: 카운터 컬럼을 따로 두면 증가·감소 동기화 버그 위험이 생긴다. 관계 카운트(`_count`)는 항상 실제 값과 일치하고, 포트폴리오 트래픽에서 성능도 충분하다.

### 좋아요에 낙관적 업데이트(useOptimistic) 적용
- 왜: 서버 응답(약 400ms)을 기다린 뒤 하트가 켜지면 앱이 느리게 느껴진다.
- 목적: 클릭 즉시 반응하는 체감 성능.
- 이유: 좋아요는 실패 비용이 낮고(롤백이 하트 하나) 즉각 반응이 기능의 전부다. 화면을 먼저 변경하고 서버는 뒤에서 확정하거나 실패 시 자동 롤백한다. 호출 횟수를 줄이는 디바운스와 다르다. 호출 횟수는 동일하고 체감 지연만 없앤다.

### 피드 하트는 표시 전용, 토글은 상세에서만
- 왜: 좋아요 수(통계)와 좋아요 행동(토글)은 성격이 다르다.
- 목적: 피드는 둘러보는 곳, 상세는 행동하는 곳으로 역할을 구분한다.
- 이유: 카드 UI 관례상 숫자는 하단 메타(통계), 누르는 액션은 별도 위치다. 피드 카드마다 토글을 두면 카드별 내 좋아요 상태 조회가 필요해 복잡해진다.

### 피드 하트 색을 내 좋아요 기준으로 수정 (fix)
- 왜: 처음에는 좋아요 1개 이상이면 빨갛게(인기색) 표시했는데, 이 경우 남이 누른 글도 빨갛게 보여 "내가 눌렀다"로 오해된다.
- 목적: 색은 "내가 누른 글"에만, 숫자는 중립 통계.
- 이유: 유튜브 관례 그대로다. 색은 내 행동, 숫자는 중립. 에러는 없었으나 의도와 다른 동작(시맨틱 버그)이라 fix로 처리했다. 배치 쿼리(`storyId IN`) 한 번으로 내 좋아요 storyId를 Set으로 가져와 N+1을 회피한다.

### 날짜를 필름 카메라 각인 스타일로
- 왜: 일반 타임스탬프는 "작성 시각(데이터)"으로 읽힌다.
- 목적: 날짜를 "다녀온 추억"으로 읽히게 해 제품 정체성(여행 기억)을 강화한다.
- 이유: 필름 사진의 주황 날짜 각인은 노스탤지어 코드다. 가독성(밝은 사진 대비) 문제로 순수 각인 대신 앰버 글래스 칩으로 절충했다.

## 4. 코드 작성 & 수정

```prisma
// prisma/schema.prisma
model Like {
  id        String   @id @default(cuid())
  storyId   String   @map("story_id")
  userId    String   @map("user_id") @db.Uuid
  createdAt DateTime @default(now()) @map("created_at")

  story     Story    @relation(fields: [storyId], references: [id], onDelete: Cascade)
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@map("likes")
  @@unique([storyId, userId])
}
```

```sql
-- prisma/sql/likes-rls.sql
ALTER TABLE "likes" ENABLE ROW LEVEL SECURITY;

CREATE POLICY "likes_select" ON "likes"
FOR SELECT TO public USING (true);

CREATE POLICY "likes_insert" ON "likes"
FOR INSERT TO authenticated WITH CHECK (user_id = (select auth.uid()));

CREATE POLICY "likes_delete" ON "likes"
FOR DELETE TO authenticated USING (user_id = (select auth.uid()));
-- UPDATE 정책 없음 (의도)
```

```typescript
// app/story/[id]/actions.ts
export async function toggleLikeAction(storyId: string): Promise<{ liked: boolean; count: number }> {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) throw new Error('로그인이 필요합니다'); // throw → LikeButton catch에서 롤백

  const existing = await prisma.like.findUnique({
    where: { storyId_userId: { storyId, userId: user.id } },
  });

  let liked: boolean;
  if (existing) {
    await prisma.like.delete({ where: { storyId_userId: { storyId, userId: user.id } } });
    liked = false;
  } else {
    try {
      await prisma.like.create({ data: { storyId, userId: user.id } });
      liked = true;
    } catch (e) {
      if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002') liked = true;
      else throw e;
    }
  }

  const count = await prisma.like.count({ where: { storyId } });
  revalidatePath('/story');
  return { liked, count };
}
```

// lib/format-date.ts
export function formatRelativeDate(date: Date): string {
  const diffMs = Date.now() - date.getTime();
  const diffMin = Math.floor(diffMs / 60_000);
  const diffHour = Math.floor(diffMs / 3_600_000);
  const diffDay = Math.floor(diffMs / 86_400_000);

  if (diffMin < 1) return '방금 전';
  if (diffHour < 1) return `${diffMin}분 전`;
  if (diffDay < 1) return `${diffHour}시간 전`;
  if (diffDay < 7) return `${diffDay}일 전`;

  const y = date.getFullYear();
  const m = String(date.getMonth() + 1).padStart(2, '0');
  const d = String(date.getDate()).padStart(2, '0');
  return `${y}.${m}.${d}`;
}

## 5. 결과 / 배운점

- useOptimistic의 dispatch는 반드시 `startTransition` 안에서 호출한다. 밖에서 호출하면 즉시 롤백되는 React 19의 알려진 동작이 있다.
- 낙관적 업데이트와 디바운스는 다르다. 낙관적 업데이트는 체감 지연을 없애고(호출 횟수 동일), 디바운스는 호출 횟수를 줄인다. 좋아요에는 전자를 적용했고, 연타는 펜딩 중 버튼 비활성화로 막았다.
- 좋아요의 시각 문법: 색은 "내 행동", 숫자는 "중립 통계"다(유튜브 관례). 에러가 없어도 의도와 다른 동작은 버그다. 인기색은 남의 좋아요까지 빨갛게 표시해 fix로 수정했다.
- N+1 회피: 카드별 조회 대신 `storyId IN` 배치 쿼리 한 번으로 내 좋아요 목록을 Set으로 가져온다.
- Prisma 스키마에 모델을 추가한 뒤 `prisma generate`를 실행하지 않으면 `_count` 타입이 누락된다.
- ON DELETE 참조 설계: likes는 CASCADE다. 스토리가 삭제되면 부속물인 좋아요도 함께 사라지는 것이 맞다.
- 한계: 피드의 상대 시간("방금 전")은 서버 렌더 시점에 계산되므로, 페이지를 오래 열어둔 경우 갱신되지 않는다. 새로고침 시 정상 표시된다.
