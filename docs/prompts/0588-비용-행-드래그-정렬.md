# 0588 회고: 비용 행 드래그 정렬

**작성일**: 2026-08-17
**관련 커밋**: `fb2f2b8`(스키마·마이그레이션·백필) · `6710341`(저장·복원) · `783207b`(드래그용 id) · `c9f3297`(고정 비용 드래그) · `cbee76f`(일자별 드래그)

---

## 1. 한 줄 요약

비용 행에 드래그 정렬을 붙이면서, 순서의 정본이 없던 `PlanCost`에 `order` 필드를 추가하고 (planId, day) 그룹별 순번 공간으로 저장·복원·복사 경로를 전부 맞췄다.

## 2. 왜 / 목적 / 이유

- 여행 일정 항목은 드래그로 순서를 바꿀 수 있는데 비용 행에는 그 기능이 없었다. 고정 비용·일자별 비용 둘 다.
- 조사해 보니 기능만 없는 게 아니라 **순서를 저장할 필드 자체가 없었다.** `PlanSpot`은 `order`를 갖는데 `PlanCost`는 `createdAt`(삽입 순서)에 기대고 있었다.

## 3. 작성한 프롬프트

이번 사이클의 형태는 **"조사 → 결정 세 개 → 실행 → 중간 검수"** 였다.

```
[검수 모드] 착수 전 확인:
- PlanCost에 순서를 저장할 필드가 있는지
  · 없으면 스키마 변경이 필요하니 먼저 보고
[하지 말 것] ❌ 스키마 변경을 조사 없이 진행
```

조사 후 사용자가 세 가지를 확정했다: ⓐ 스키마 변경 승인 ⓑ 순번 공간은 `(planId, day)` 그룹별 ⓒ 백필은 `createdAt` 순. 그리고 폼 상태는 "id는 드래그 전용, 기존 index 기반 CRUD는 유지".

실행 단계에서도 하네스가 걸렸다: **`❌ 마이그레이션을 백업 확인 없이 실행`**, **`커밋 1 완료 후 결과 보고하고 멈출 것`**.

## 4. 코드 작성 & 수정

### 조사에서 정정한 것

0588 1차 보고에서 "같은 트랜잭션 행들이 동일 `created_at`을 받아 정렬이 임의가 된다"고 했는데 **실측은 반대였다.**

```
'렌트카 정비비용'   08:44:50.564
'서귀포호텔 2박'    08:44:50.713   ← 0.15초 차이
```

DDL은 `DEFAULT CURRENT_TIMESTAMP`지만 **Prisma가 `@default(now())`를 행마다 클라이언트 측에서 생성해 보내** DB 기본값이 쓰이지 않았다. 중복 그룹 0건. 즉 기존 정렬이 깨져 있진 않았고, `order` 도입 근거는 "드래그로 정한 순서는 삽입 순서와 다르다" 쪽만 유효하다. 사용자가 ⓐ의 근거로 들었던 사실이라 정정해 보고했고, 마이그레이션 SQL 주석에도 실측을 남겼다.

조사 중 "중복 데이터"처럼 보인 것도 확인해 보니 **같은 제목의 서로 다른 플랜 2건**이었다(하나는 전날 담기 검증용 비공개 사본). 한 플랜 안 중복은 0건.

### 커밋 1 — 스키마·마이그레이션·백필

```sql
ALTER TABLE "plan_costs" ADD COLUMN "order" INTEGER NOT NULL DEFAULT 0;

UPDATE "plan_costs" c SET "order" = s.rn
FROM (SELECT id, row_number() OVER (PARTITION BY plan_id, day ORDER BY created_at, id) - 1 AS rn
      FROM "plan_costs") s
WHERE c.id = s.id;

ALTER TABLE "plan_costs" ALTER COLUMN "order" DROP DEFAULT;
CREATE INDEX "plan_costs_plan_id_day_order_idx" ON "plan_costs"("plan_id", "day", "order");
```

- `PARTITION BY plan_id, day`에서 **`day`가 NULL인 행들은 Postgres가 한 그룹으로 묶는다** — ⓑ 결정(고정 비용 = 한 그룹)이 별도 분기 없이 성립한다.
- `DEFAULT 0`은 기존 행을 NOT NULL로 채우기 위한 것이라 백필 후 떼어냈다 — `PlanSpot.order`와 형태를 맞춘다(저장 경로가 항상 명시적으로 넣는다).
- 실행 전 `plan_costs` 19행을 JSON으로 덤프해 뒀다. 롤백은 `DROP COLUMN "order"` 한 줄.

검증 3항목 전부 통과: 그룹 안 `order` 중복 0건 / 그룹별 `0..n-1` 연속성 전 10그룹 정상 / **덤프(`created_at` 순) 대비 불일치 0건**(현재 순서 그대로 굳음).

**이 커밋 시점에 `tsc`가 실패한다**는 사실도 함께 보고했다 — `order`가 필수가 되며 쓰기 지점 4곳이 오류였고, 그중 **담기(`copyPublicPlanAction`)와 더미 시드 2곳은 내가 계획에서 빠뜨렸던 지점**이다. 스키마 변경이 드러냈다.

### 커밋 2 — 저장·복원

`order`는 **그룹(day) 안의 러닝 카운터**다. 배열 인덱스를 쓰면 안 되는 이유가 둘 있다: 금액 0인 행을 건너뛰므로 인덱스에 구멍이 생기고, 폼의 `dayCosts`는 전 Day가 한 배열이라 인덱스가 Day 경계를 넘는다.

```ts
  const orderByDay = new Map<number, number>();
  for (const cost of dayCosts) {
    if (cost.amount <= 0) continue;
    const order = orderByDay.get(cost.day) ?? 0;
    orderByDay.set(cost.day, order + 1);
    …
  }
```

읽기는 `orderBy: [{ day: 'asc' }, { order: 'asc' }]`로. 담기는 **원본 `order`를 그대로 복사**한다(사용자 확정 — 원본 작성자가 정한 순서를 유지). 행을 걸러내지 않고 전량 복사하므로 재번호 없이도 그룹별 `0..n-1`이 보존된다.

### 커밋 3 — 드래그용 id

dnd-kit은 고유·안정 id를 요구하는데 비용 행은 `key={index}`였고, `localId`는 연결 장소 id라 **여러 행이 같은 값이거나 null**(기타 지출)이라 쓸 수 없었다.

두 타입에 `id: string`을 추가하되 **복원 시에는 `PlanCost.id`를 그대로 쓴다** — 이미 고유·안정이고, 서버 컴포넌트에서 난수를 만들면 값이 매 렌더 달라진다. 새 행만 클라에서 `crypto.randomUUID()`.

기존 index 기반 CRUD는 유지(사용자 확정). id는 드래그 키와 React key로만 쓴다.

### 커밋 4·5 — 드래그

일정 항목의 패턴을 그대로 따랐다: `useSortable({ id })` / 핸들에만 `attributes`·`listeners`(행 전체에 걸면 입력·드롭다운 조작이 드래그로 먹힌다) / `isDragging`은 `opacity-50` / `sensors`·`collisionDetection`·`strategy` 동일 값 재사용.

조판은 **2줄 스택을 유지**하면서 핸들을 첫 줄에 붙였다. `sm:contents`로 래퍼를 지워 핸들·이름이 그리드의 1·2열이 되게 했고, 그래서 `grid-cols`가 `[1fr_150px_120px_32px]` → `[20px_1fr_150px_120px_32px]`로 한 열 늘었다. 일자별 행은 조건부 라벨 줄이 위에 하나 더 있어 **핸들을 장소 드롭다운과 같은 줄**에 뒀다.

**Day 안에서만** 재배열하는 게 커밋 5의 핵심이다. `dayCosts`가 전 Day 한 배열이라 전역 `arrayMove`는 다른 Day를 밀어낸다.

```ts
      const slots = prev.dayCosts.map((cost, i) => ({ cost, i }))
        .filter(({ cost }) => cost.day === clampedCostDay);
      const reordered = arrayMove(slots.map(({ cost }) => cost), oldPos, newPos);
      const next = [...prev.dayCosts];
      slots.forEach(({ i }, k) => { next[i] = reordered[k]; });
```

**그날 행이 원래 점유하던 전역 슬롯에 순서대로 되꽂는** 방식이다. 검산:

```
전:   A/d1 B/d2 C/d1 D/d2 E/d1 F/d3   order: A(d1 o0) C(d1 o1) E(d1 o2) …
후:   E/d1 B/d2 A/d1 D/d2 C/d1 F/d3   order: E(d1 o0) A(d1 o1) C(d1 o2) …
day2 불변 ✓ (B,D)   day3 불변 ✓ (F)   각 슬롯의 day 보존 ✓
```

## 5. 결과 / 배운점

- `npx tsc --noEmit` 통과. `npx next build` 컴파일 성공(새 그리드 클래스가 CSS에 생성된 것도 확인). `npm test` 실패 목록 기존과 동일(6스위트/8테스트) — 회귀 없음.
- **실화면으로만 판정 가능한 것** : ① 고정 비용 드래그 ② 일자별 드래그가 **그날 안에서만** 되는지 ③ 저장 후 다시 열었을 때 순서 유지 ④ 담은 플랜이 원본 순서를 갖는지 ⑤ 모바일 360px에서 핸들이 붙은 2줄 스택 조판 ⑥ 드래그 중 입력·드롭다운이 잘못 잡히지 않는지.
- 배운점 초안 1: **기능을 붙이려다 없던 정본을 발견했다.** "드래그 좀 붙이자"였는데 순서를 저장할 곳이 아예 없었고, `createdAt`이 그 역할을 대신하고 있었다. 삽입 순서와 사용자가 정한 순서는 지금까지 우연히 같았을 뿐이다(재저장이 전량 재삽입이라). 드래그가 그 우연을 깬다 — **기능 추가가 데이터 모델의 빈 곳을 드러내는 경로**다.
- 배운점 초안 2: **타입 오류가 조사보다 정확했다.** 커밋 1 후 `order`를 필수로 만들자 컴파일러가 쓰기 지점 4곳을 정확히 짚었고, 그중 둘(담기·시드)은 내가 계획에서 빠뜨린 곳이었다. 스키마를 먼저 조이고 컴파일러에게 호출부를 물어보는 순서가, 내가 grep으로 세는 것보다 나았다.

## 결정 (Decisions)

- **`PlanCost.order` 도입** — 순서의 정본. `createdAt`은 삽입 순서일 뿐이다.
- **순번 공간은 `(planId, day)` 그룹별** — `day=null` 고정 비용이 한 그룹. Postgres `PARTITION BY`가 NULL을 한 그룹으로 묶어 별도 분기가 필요 없다.
- **백필은 `createdAt` 순** — 현재 화면 순서를 그대로 굳힌다.
- **`order`는 그룹 안 러닝 카운터** — 배열 인덱스 금지(0원 행 스킵·Day 경계).
- **담기는 원본 `order`를 그대로** — 원본 작성자가 정한 순서도 담기의 일부다.
- **폼 `id`는 드래그 전용** — 기존 index 기반 CRUD 유지. 복원 시엔 `PlanCost.id` 재사용.
- **Day 안에서만 재배열** — 그날 행이 점유하던 전역 슬롯에 되꽂는다.

## 남은 것 (별건)

- **드래그 핸들 터치 타겟이 14px**로 §5 44px에 미달한다. 일정 항목과 같은 값을 쓴 것이라(패턴 준용 지시) 여기만 고치면 갈린다 — 접근성 정리 사이클에서 **함께**.
- **읽기 화면은 여전히 금액 내림차순 정렬**이다(`summarizePlanCost`). 작성자가 정한 순서가 읽기에는 반영되지 않는다 — 의도인지 미판정.
- 0579~0587에서 넘어온 것: 담긴 플랜 소급 복구 / 목록 카드와 상세의 일수 폴백 불일치 / 축소 확인 문구에 비용 미포함 / 항공권 초기화에 확인 없음 / 검색 결과 카드의 1인 요금 표기 / 확인 UI 세 갈래 통일 / 스토리→플랜 복사 경로 점검 / `todayStr()` 통합.
