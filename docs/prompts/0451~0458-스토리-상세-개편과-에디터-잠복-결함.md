## 2. 왜 / 목적 / 이유

### 왜 (동기·문제)

스토리 상세 화면이 세 토막으로 읽혔다. 위쪽 절반은 사진·소제목·불릿·인용의 **글**인데, SPOTMAP부터는 카드·지도·차트의 **UI**였다. 그 전환이 예고 없이 일어났고, 눈썹 라벨(STORY / SPOTMAP / PLAN)은 "여기가 새 섹션"까지만 말할 뿐 "성격이 바뀐다"는 말은 못 했다.

여기에 비용 비율 트리맵과 파란 채움 버튼이 페이지에서 유일하게 채도 높은 덩어리로 남아, 정작 봐야 할 PLAN 블록보다 시선을 먼저 가져갔다.

에디터 쪽은 별개 문제였다. 글자 크기를 조절할 수단이 아예 없어 작성자가 캡션이나 부연을 표현할 방법이 없었다.

### 목적 (목표 상태·사용자 가치)

읽는 사람이 순례기를 다 읽고 나서 **"이 코스로 나도 가볼까"**로 자연스럽게 넘어가는 화면. 그 목적 하나로 판단하면 무엇을 빼고 무엇을 키울지가 정해진다.

- 비용 비율은 "갈까 말까" 단계에 필요 없는 정보 → 뺀다
- PLAN 블록이 페이지에서 가장 눈에 띄어야 한다 → 커버 사진을 넣는다
- 글과 도구 사이의 경계가 읽기를 방해하지 않아야 한다

### 이유 (채택 근거·결정 기준)

**트리맵을 뺀 근거**는 "틀린 정보"가 아니라 **"한 화면 이른 정보"**라는 판단이다. 비율이 궁금해지는 시점은 이미 플랜 상세에 들어간 뒤고, 스토리 독자에게 필요한 건 총액과 기간뿐이다. 정보를 없애는 게 아니라 제 화면으로 돌려보내는 것이라 손실이 없었다.

**커버 배치**는 미디어 오브젝트 패턴을 따랐다. MDN이 이 패턴의 정의 첫 줄로 "모바일에서 쌓이고 데스크톱에서 2열"을 꼽고 있어, 데스크톱 좌측 썸네일 140×105 / 모바일 세로 스택이 표준 동작 그대로다.

**컨테이너 쿼리는 검토 후 기각**했다. 검색으로는 "재사용 컴포넌트에는 컨테이너 쿼리" 권고가 나왔으나, 조사해보니 세 화면의 폭 체인이 전부 동일했다(데스크톱 860px 고정, 모바일 뷰포트−48). 폭이 뷰포트의 함수라 컨테이너 쿼리 이득이 0이었고, 코드베이스에 `@container` 선례도 0건이었다. 검색 결과보다 우리 조건이 먼저였다.

### 0456 — "작게" 커스텀 Mark

```ts
// app/(protected)/story/new/SizeMark.ts
// 명령 타입 확장 — 툴바·버블이 부르는 toggleSmall()의 출처
declare module '@tiptap/core' {
  interface Commands<ReturnType> {
    size: {
      /** "작게" 마크 토글 — 캡션·부연용 보조 크기(13px, globals.css 파생) */
      toggleSmall: () => ReturnType;
    };
  }
}

export const SizeMark = Mark.create({
  name: 'size',
  addAttributes() {
    return {
      size: {
        default: 'sm',
        parseHTML: (el) => (el.getAttribute('data-size') === 'sm' ? 'sm' : null),
        renderHTML: (attrs) => ({ 'data-size': attrs.size }),
      },
    };
  },
  // 파싱 화이트리스트 — sm 외 값·타 span은 마크 미적용
  parseHTML() {
    return [{ tag: 'span[data-size="sm"]' }];
  },
  renderHTML({ HTMLAttributes }) {
    return ['span', mergeAttributes(HTMLAttributes), 0];
  },

  addCommands() {
    return {
      toggleSmall:
        () =>
        ({ commands }) =>
          commands.toggleMark(this.name, { size: 'sm' }),
    };
  },
});
```

```css
/* app/globals.css — 값은 CSS가 정한다 */
.tiptap-content [data-size='sm'] { font-size: 13px; }

/* 인라인 코드(StarterKit Code) — 규칙 부재 시 preflight 모노스페이스만 적용돼 칩 식별 불가.

.tiptap-content code {
```

13px은 새 값이 아니다. 이 프로젝트가 이미 보조 텍스트에 13px을 쓰고 있어("본문 16 / 보조 13") 기존 어휘를 따랐다.

툴바 배선은 세 버튼이다 — 작게(`toggleSmall` / `AArrowDown`)는 헤딩 옆에 `ToolbarDivider`
양쪽 샌드위치로 격리, 취소선(`toggleStrike` / `Strikethrough`)·인라인 코드(`toggleCode` / `Code`)는
StarterKit 기등록 마크의 UI 노출이라 B·I 옆. 버블 메뉴에도 "작게"를 추가해 B/I/H2/작게/링크가 됐다.

### 0457 — extensions 고정

```tsx
// app/(protected)/story/new/TiptapEditor.tsx
const extensions = useMemo(() => [
  StarterKit.configure({ link: false }),
  Image,
  Link.configure({ openOnClick: false }),
  Callout,
  SizeMark,
  createSlashCommand(() => fileInputRef.current?.click()),
  GlobalDragHandle, // 기본 옵션(dragHandleWidth 20) — 아래 sm:pl-[38px]와 파생 관계
], []);
```

배열에서 매 렌더 새 객체를 만드는 항목은 `StarterKit.configure()`·`Link.configure()`·
`createSlashCommand()` 셋이고, 나머지(`Image`·`Callout`·`SizeMark`·`GlobalDragHandle`)는
모듈 참조라 원래 안정이다. `compareOptions`는 배열 자체가 아니라 **항목을 인덱스별로** 비교하므로,
불일치를 만든 건 정확히 저 셋이다.

의존성 `[]`가 성립하는 근거: `createSlashCommand`에 넘기는 콜백이 `fileInputRef`를 **호출 시점에** 읽는 지연 참조이고, ref 객체는 렌더 간 안정이라 1회 생성한 클로저가 영구 유효하다.

## 5. 결과 / 배운 점

### 결과

- SPOTMAP·PLAN 눈썹 제거로 세 토막 나던 화면이 하나로 붙었다 (본문 머리의 STORY 눈썹은 존치 — 글의 시작 표지라 성격이 다르다)
- 트리맵 제거로 페이지에서 채도 높은 덩어리가 사라지고, 커버가 들어간 PLAN 카드가 자연스럽게 시선의 종착점이 됐다
- 태그·좋아요를 본문 직후에서 PLAN 카드 뒤로 옮겨 글의 마침표 역할을 하게 했다 (그 아래 "다른 이야기 보기"가 다음 행동을 받는다)
- **extensions 고정 후 타이핑 체감 속도가 눈에 띄게 빨라졌다** — 체감 서술, 계측값 없음

### 배운 점

**1. 메이저 업그레이드는 관용구를 조용히 깬다.**

tiptap v3의 `useEditor`는 기본적으로 트랜잭션에 React 리렌더를 하지 않는다(v2의 기본값이 v3에서 뒤집혔다). 그래서 **선택만 바꾸는 조작은 `isActive`가 재평가되지 않았다.** 문서가 바뀌는 조작은 `onUpdate → onChange → 부모 setState` 경로로 **우연히** 리렌더가 걸려서 동작하는 것처럼 보였을 뿐이다.

즉 B·I·H2·취소선·인라인 코드 **전부 같은 잠복 버그**였고, 새로 넣은 "작게"에서 처음 가시화됐다. 텍스트를 선택만 하면 볼드 버튼도 활성이 안 됐는데 아무도 눈치채지 못했다.

**2. 증상만 고치려다 앱을 죽였고, 그 사고가 더 깊은 원인을 드러냈다.**

`shouldRerenderOnTransaction: true` 한 줄로 v2 동작을 복원하려 했더니 `Maximum update depth exceeded`로 edit 페이지가 죽었다. 원인 조사에서 진짜 결함이 나왔다 — **`extensions` 배열이 렌더마다 재생성되고 있었다.**

`StarterKit.configure()`·`Link.configure()`·`createSlashCommand()`를 렌더 안에서 호출하니 매번 새 객체이고, `useEditor`의 `compareOptions`는 extensions를 항목 동일성(`!==`)으로 비교하므로 **항상 불일치 → 매 렌더 `setOptions()` → `view.updateState()`로 뷰 전체 재갱신**이었다. 무한 루프는 그 고리에 트랜잭션 리렌더를 얹어서 닫힌 것이었다.

성급한 수정이 없었다면 이 결함은 계속 잠들어 있었을 것이다. **실패한 수정에서도 정보가 나온다.**

**3. 고리를 끊고 나면 같은 처방이 안전해진다.**

0457로 `setOptions` 쪽이 끊긴 뒤에는 `useEditorState` 셀렉터로 `트랜잭션 → 리렌더` 방향을 추가해도 고리가 안 닫혔다. 순서가 중요했다 — 근본 원인을 먼저 제거하고 공식 권장 경로를 얹는 것.

**4. 저장 규약은 sanitize 부재를 전제로 정해야 한다.**

이 프로젝트는 저장 HTML을 `dangerouslySetInnerHTML`로 그대로 렌더하고 sanitize 계층이 없다. 그래서 "작게"를 `TextStyle`(=`<span style>`)로 만들지 않고 `<span data-size="sm">` 화이트리스트로 갔다. 인라인 style을 여는 순간 방어선이 얇아지기 때문이다. Callout이 이미 같은 규약을 쓰고 있어 어휘도 맞았다.

**5. 검색 결과보다 우리 조건이 먼저다.**

컨테이너 쿼리 권고는 "같은 컴포넌트가 서로 다른 폭의 자리에 놓일 때" 성립하는 것이었는데, 우리는 세 화면 폭 체인이 동일해 이득이 0이었다. 조사 항목에 "선례가 있는지"를 넣어둔 덕에 적용 직전에 걸렀다.

**6. 커밋 번호 순 ≠ 시간 순.**

이 트랙에서 **0452가 0451보다 2분 먼저 커밋됐다**(03:25 vs 03:27). 상세 화면을 먼저 손보고
그 마크업을 폼 쪽에 옮기면서 번호를 되돌려 붙인 결과다. 그래서 0452 커밋 안에 `(0451)` 주석이
달린 코드가 들어 있고, 이번 검수에서 "0451 커버 마크업"을 0451 diff에서 찾다가 못 찾는 일이 실제로 났다.

회고를 나중에 쓸 때 번호만 믿고 커밋을 특정하면 이렇게 어긋난다. CLAUDE.md §7이 회고 번호를
`ls docs/prompts/`와 `git log --oneline` **둘 다** 대조해 확정하라고 못 박은 이유의 실례다 —
번호는 작업의 이름이지 시간축이 아니다.
