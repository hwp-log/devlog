```typescript
export async function signIn(email: string, password: string) {
```

### 작업4 - Supabase 호출 도입 및 실패 케이스 추가

```typescript
import { createClient } from '@/lib/supabase/server';
import { isValidEmail } from './validators';

export async function signIn(email: string, password: string) {
  if (!isValidEmail(email)) {
    return { error: '이메일 형식이 올바르지 않습니다' };
  }
  if (password === '') {
    return { error: '비밀번호를 입력해주세요' };
  }

  const supabase = await createClient();
  const { error } = await supabase.auth.signInWithPassword({ email, password });

  if (error) {
    return { error: '이메일 또는 비밀번호가 올바르지 않습니다' };
  }
}
```

```typescript
/**
 * 이메일/비밀번호로 로그인 처리
 * 이메일 형식 검증 후 Supabase Auth 호출
 */
export async function signIn(email: string, password: string) {
  if (!isValidEmail(email)) {
    return { error: '이메일 형식이 올바르지 않습니다' };
  }
  if (password === '') {
    return { error: '비밀번호를 입력해주세요' };
  }

  const supabase = await createClient();
  const { data, error } = await supabase.auth.signInWithPassword({ email, password });

  if (error) {
    return { error: '이메일 또는 비밀번호가 올바르지 않습니다' };
  }

  return { data: { user: data.user } };
}
```

## 작업 근거

### lib폴더의 구조 및 역할

- `lib/auth/`는 인증 관련 **비즈니스 로직을 모아 두는 영역**으로,  
  - 이메일 검증, signIn / 로그인, signOut, 유틸 함수 등의  
  - “인증 처리 로직”을 한 곳에 모아서 관리.

- 반면  
  - `app/(auth)/`는  
    - 라우팅, 페이지 구성, 폼 UI 등  
    - **“인증 화면/라우팅”**을 담당.

- 즉,  
  - `lib/auth/` → **로직(비즈니스)**  
  - `app/(auth)/` → **화면/라우팅(UI)**  
  이렇게 **책임을 분리**하기 위해,  
  `signIn` 같은 함수는 `lib/auth/actions.ts`에 작성.

- 또한, 이전에 만든 `lib/auth/validators.ts`(이메일 형식 검증 등)도 같은 폴더에 있어서,  
  - 검증 로직과 액션 로직을  
    한 폴더 안에서 자연스럽게 재사용할 수 있고,  
  - import 경로도 간단하게 유지가능.

## Supabase 호출 후 인증성공시, user 데이터 반환에서 session을 제외한 이유
Supabase의 `signInWithPassword`는  
이메일·비밀번호로 로그인한 뒤,  
`{ data: { user, session }, error }` 형태로 결과를 반환하는 메서드.  
이 응답에서 `session`까지 같이 반환하는 대신, `user`만 반환하기로 함. 
이유는 아래와 같음.

1. **session은 쿠키로 자동 관리됨**  
   - `@supabase/ssr` 환경에서 `createServerClient`가  
     - `session`을 `httpOnly` 쿠키로 자동 저장·갱신.  
   - 따라서 클라이언트가 `session` 객체를 직접 다룰 필요가 없어,  
     - 응답에 포함시키지 않음.

2. **응답 구조 단순화**  
   - `{ data: { user, session } }`보다  
     - `{ data: { user } }`가 더 단순해서,  
   - 호출 측 코드에서 불필요한 `session` 처리를 피할 수 있음.

3. **보안 강화**  
   - `session` 안에는 `access_token` 같은 민감한 토큰이 들어 있음.  
   - 이 토큰을 클라이언트에 응답으로 노출하면,  
     - 실수로 처리하거나,  
     - 의도치 않게 로그에 남길 위험이 존재.  
   - 반대로,  
     - `session`은 서버에서 쿠키로만 관리하고,  
     - 응답에서는 `user` 정보만 노출하면,  
     - 토큰 노출을 줄여 보안을 강화할 수 있다.

### 2. Supabase Mock 패턴

```typescript
const mockSignInWithPassword = jest.fn();

jest.mock('@/lib/supabase/server', () => ({
  createClient: jest.fn(() =>
    Promise.resolve({
      auth: { signInWithPassword: mockSignInWithPassword },
    })
  ),
}));
```

핵심:
- `mock` 접두사 변수명 사용 (Jest 호이스팅 충돌 회피)

이 패턴은 이후 signUp, signOut에도 동일하게 재사용 예정.

1. **비동기 함수 시그니처의 일관성** — 형식 검증만 하는 경로도 async로 두는 이유는 호출 측에서 항상 await로 일관되게 받기 위함. 미래에 외부 호출 로직이 추가되어도 호출 측 코드 변경 불필요.

4. **Server Action** — 인증 자체는 Supabase가 담당. 이외 로직 및 책임영역 내용은 입력 검증 + 에러 처리 + 응답 형태 통일.

6. **CLAUDE.md만으로 일관성 보장 가능** — 새 세션에서도 패턴 유지 (Anthropic 공식 권장).
7. **코드 자체가 일관성의 원천** — 작동하는 코드 = 일관된 코드. 기존 코드 보고 패턴 추출하면 충돌 없음.
8. **검수자 마인드셋** — AI가 코드 짜고 사람이 의도 일치 검증. "구현"보다 "검수" 능력이 핵심.
9. **레이어 인식 (역할 + 위치 + 흐름 + 이유)** — 코드 이해의 4요소. 면접 답변 골격으로 활용 가능.
