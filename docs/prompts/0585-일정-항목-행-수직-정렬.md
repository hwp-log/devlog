# 0585 회고: 일정 항목 행 수직 정렬

**작성일**: 2026-08-17
**관련 커밋**: `7c04a34`(일정 항목 행 컨트롤 수직 정렬)

---

## 1. 한 줄 요약

플랜 편집 화면 일정 항목 행에서 주소가 붙은 항목만 컨트롤이 10~12px 내려가 보이던 것을, 행 정렬을 `items-start`로 바꾸고 좌우 컨트롤 셋을 입력 필드 높이(42px) 박스 안에서 중앙 정렬시켜 맞췄다.

## 2. 왜 / 목적 / 이유

담기·날짜 작업으로 편집 화면을 계속 들락날락하는 중에 눈에 걸렸다.
기능을 보러 열어둔 화면인데, 오래 보고 있으니 조판이 보였다.

- 우측 ✕ 버튼이 옆 입력 필드와 수평이 안 맞았고, **항목마다 아래 주소 한 줄이 붙어
  행 높이가 달라지는 것**이 원인으로 지목됐다.
- 조사 결과 지목이 맞았고, 범위가 하나 더 넓었다 — **좌측 드래그 핸들·번호도 같은
  원인으로 같은 만큼 어긋나 있었다.** 왼쪽 끝이라 눈에 덜 띄었을 뿐이다.

## 3. 작성한 프롬프트

```
- 현재 정렬이 어떻게 잡혀 있는지 먼저 보고할 것 (flex 정렬 값, 각 요소의 높이·여백)
- 주소 유무와 무관하게 일관되게 보이도록 할 것
- 좌측 드래그 핸들·번호도 같은 축에 있는지 함께 확인
[하지 말 것] ❌ 행 구조 자체 재설계 ❌ 버튼 크기·색 변경 ❌ 다른 화면의 유사 행 손대기
```

"현재 값을 먼저 보고하라"가 이번 하네스였다. 조판 문제는 눈으로 보고 값을 바꿔 맞추는 유혹이 큰데, 값을 세면 원인이 산수로 나온다.

## 4. 코드 작성 & 수정

### 조사 — 어긋남은 산수로 떨어졌다

행 컨테이너가 `flex items-center gap-2`라 **모든 자식이 행 전체 높이 기준 중앙**이었다.

| 요소 | 높이 |
|---|---|
| 드래그 핸들 (`GripVertical size={14}`, 패딩 없음) | 14px |
| 번호 (`text-sm`) | 20px |
| 썸네일 (조건부) | 72px |
| ✕ 버튼 (`w-7 h-7`) | 28px |
| 내용 열 | **가변** |

내용 열이 가변인 게 원인이다.

| 구성 | 계산 | 높이 |
|---|---|---|
| 입력만 | py-2(8×2) + border(1×2) + text-base lh 24 | **42px** |
| + 주소 줄 | 42 + gap-1(4) + text-xs lh 16 | **62px** |
| + 작품 칩 | 42 + 4 + (16 + py-[2px]×2) | **66px** |

어긋남 = `(내용 열 − 42) / 2` → **0 / 10 / 12px**. 썸네일이 있어도 값은 같다 — 썸네일이 최대 높이가 되면 내용 열과 컨트롤이 함께 밀려 상대 차이가 보존된다.

### 수정 — 기준을 행이 아니라 입력으로

```ts
// 42px = ITEM_INPUT_CLASS 실측: py-2(8×2) + border(1×2) + text-base lh 24.
const ITEM_CTRL_ALIGN = 'h-[42px] flex items-center shrink-0';
```

- 행: `items-center` → **`items-start`**
- 핸들·번호·✕: 위 상수로 입력 높이 박스 안 중앙
- 썸네일: **`self-center`** — `items-start` 전환에도 현행(중앙) 유지

세 가지를 판단했다.

- **핸들·✕는 래퍼로 감쌌다.** 버튼에 직접 높이를 주면 ✕는 `w-7 h-7`(크기 변경 금지)이 깨지고, 핸들은 드래그 잡히는 영역이 14px → 42px로 넓어져 **동작이 바뀐다.** 조판 수정이 상호작용을 바꾸면 안 된다.
- **썸네일 `self-center`의 실제 이동량은 0이다**(72px이 항상 최대 — 내용 열 최대 66px). 그래도 붙인 이유는 의도를 코드에 남기기 위해서다 — 내용이 더 길어지는 날 이 한 줄이 판단을 대신한다.
- **좌측도 같이 고쳤다.** ✕만 맞추면 좌우가 서로 어긋난다.

### 검산 — Tailwind JIT

CLAUDE.md §5에 "arbitrary 값은 완전 리터럴만 JIT 스캔됨"이 있어, 상수로 뺀 `h-[42px]`가 실제로 생성되는지 프로덕션 빌드로 확인했다.

```
.h-\[42px\]{height:42px}
```

**생성됐다.** 경고 대상은 `h-[${x}px]` 같은 **조립식**이고, 소스에 온전한 문자열로 있으면 스캐너가 찾는다.

## 5. 결과 / 배운점

- `npx tsc --noEmit` 통과. `npx next build` 통과. `npm test` 실패 목록 기존과 동일(auth 5스위트 + SpotPopup = 6스위트/8테스트) — 회귀 없음.
- **실화면 확인 완료** — ① 썸네일 있는 행과 주소만 있는 행이 섞인 목록에서
  ✕·드래그 핸들·번호가 모두 입력 필드와 한 축에 있다. 행 높이가 두 종류로 갈리는데도
  컨트롤이 흔들리지 않는다 ② 썸네일 행(대표 배지·이미지·작품 태그·주소)이 이전과 같다
  ③ 좁은 폭에서도 주소가 접히지 않는다 — 작품 태그가 붙은 행까지 한 줄 유지
- 배운점 초안 1: **`items-center`는 "가운데"가 아니라 "무엇의 가운데"다.** 자식이 서로 높이가 다르면 정렬 기준은 가장 큰 자식이 되고, 그 자식이 가변이면 축이 데이터에 따라 움직인다. 여기서 기준이어야 했던 건 행이 아니라 입력 필드였다 — **정렬은 무엇에 맞출지를 먼저 정하는 일**이고, `items-center`는 그 질문을 건너뛴다.
- 배운점 초안 2: **눈에 띄는 곳만 고치면 축이 둘로 갈린다.** 보고된 건 ✕ 하나였지만 핸들·번호가 같은 원인으로 같은 만큼 어긋나 있었다. ✕만 맞췄다면 어긋남의 총량은 줄되 **서로 다른 축 두 개**가 생겨 더 이상해졌을 것이다. 증상이 하나로 보여도 원인을 공유하는 형제를 먼저 세야 한다.

## 결정 (Decisions)

- **항목 행의 정렬 기준은 입력 필드(42px)** — 행 전체가 아니다. 주소·칩이 붙어도 축이 고정된다.
- **좌우 컨트롤 셋은 같은 축** — ✕만 고치지 않는다.
- **버튼은 래퍼로 감싼다** — 크기·히트 영역을 조판 수정이 바꾸지 않게.
- **42px은 `ITEM_INPUT_CLASS` 파생값** — 입력 패딩·글자 등급을 바꾸면 이 상수도 함께(양쪽 주석에 명시).
