## 2. 왜 / 목적 / 이유

- **왜**: Story가 늘어나면 목록이 길어지는데, 전체를 한 번에 렌더하면 저사양·구형 기기에서 성능이 나빠지고 푸터에 닿기 어려움. 페이지 분할이 필요.
- **목적**: 데이터가 늘어도 (1)DOM을 고정해 저사양 기기 성능 보존 (2)푸터 접근 유지 (3)특정 페이지 공유·복원 가능 (4)로딩 중 레이아웃 안정.
- **이유**: 아래 판단 여정 참조 — 각 선택마다 근거를 세움.

---

## 3. 판단 여정 (핵심 자산)

### 방식 선택: 무한스크롤·더보기 배제 → 번호(교체)
- **무한스크롤 배제**: 푸터에 영영 못 닿음, DOM이 계속 쌓임. (Etsy 사례: 무한스크롤 도입 후 조회 -50%·전환 -23%)
- **더보기(누적) 배제**: DOM이 쌓여 저사양·구형 기기 성능 저하. "저사양 기기가 최대 변수 — 관심 없는 사람은 2~3세대 전 기기를 씀"이라는 판단.
- **가상 스크롤 검토 후 배제**: 성능은 되지만 무한스크롤과 같은 약점(푸터 못 닿음).
- **번호 페이지네이션(교체) 채택**: 페이지를 넘기면 이전 페이지를 교체 → DOM 고정, 저사양 안전, 푸터 유지. "예상 가능한 표준 UX를 미리 구현하는 게 실무 정석이고, 배포 후 전환 비용 > 지금 구현 비용, 번호 페이징은 표준 기본기라 과설계가 아님"이라는 논거로 확정.
  - (초기엔 "이전/다음 버튼 + URL"로 기울었으나, 위 논거가 더 타당해 정정)

### 생략(…) 방식
- 묶음 넘기기가 아니라 **첫·현재·마지막은 항상 노출 + 중간은 …** 방식. web_search로 Louisiana 정부 디자인시스템 표준 확인(최대 7칸, 마지막 페이지 바로 접근 우수).
- 반응형: 모바일 5칸 / 데스크톱 7칸, 터치 44px+, aria-current.

### URL ?page 동기화
- 껐다 켜거나 새로고침해도 페이지 유지 + 공유 가능.
- 서버 주도 단일 경로(router.replace scroll:false → RSC 재요청)로 **이중 fetch 회피**.
- 메뉴 이동 후 1페이지 리셋은 정상(표준).

### 높이 상수화 (번호바·푸터 안 튐)
- 그리드 높이를 items.length가 아니라 **STORY_PAGE_SIZE 상수**로 고정 → 결과 개수가 달라도 높이 일정 → 번호바·푸터 위치 고정.
- web_search로 AG Grid `autoPageSize`·MUI `autoPageSize` 표준 확인("페이지당 높이 고정 + 데이터 채움"). 마지막/검색 결과 적을 때 아래 빈 공간은 표준이 용인(위치 안정 > 빈 공간 없애기).
- (초기 `max(items.length, 2*cols)`가 결과 개수에 연동돼 튀었고, 상수로 바꿔 해결)

### 로딩: shimmer 스켈레톤 + 크로스페이드
- pulse 대신 shimmer("흐르는 느낌" 선호). shimmer가 짧은 로딩에 끊기는 문제는 **크로스페이드**(스켈레톤·카드 레이어를 겹쳐 opacity 전환, 빈 프레임 없이 스르륵)로 해결.
- 일부러 지연 넣지 않음(사용자 시간 존중) — 데이터 오면 바로 전환.

### 검색 로딩 연결 (A-ii → A-i)
- 처음엔 A-ii(keyword 변경 감지, post-hoc 타이밍)로 갔으나, "검색 스켈레톤이 fetch 완료 후에 뜨는" 문제 → **A-i(공유 트랜지션 StoryBrowser 래퍼)**로 전환. 검색·페이지 넘김이 한 useTransition을 공유해 fetch 중 스켈레톤 표시.

### 검색 유도
- 결과가 없을 때 "검색하기" 링크 → 상단 검색창으로 스크롤 + focus(별도 글로우가 아니라 브라우저 기본 포커스). 탐색형·목적형 동선 모두 커버.

## 5. 결과 / 배운점

### 결과
- 번호 페이지네이션 + 생략 + 반응형 + URL 동기화 + 검색 유도 + 스켈레톤/크로스페이드 로딩 + 높이 상수화까지 한 커밋으로 완결.
- 검색·페이지 넘김이 같은 로딩 흐름을 공유(StoryBrowser).

### 배운점
- **"버튼 몇 개"로 보이는 페이지네이션이 실제로는 UX·로직·접근성·성능이 얽힌 트랙**: 방식 선택(무한스크롤/더보기/번호)부터 생략 방식·URL·높이·로딩까지 각각 근거가 필요했다.
- **표준을 검색으로 확인하고 따르되, 근거를 말할 수 있게**: 생략 방식(Louisiana), 높이 고정(AG Grid/MUI) 모두 web_search로 표준을 확인하고 채택. "표준이라서"가 아니라 "왜 표준인지"를 근거로.
- **높이 상수화 = 위치 안정 > 빈 공간**: 데이터에 높이를 맞추면 번호바가 튀고, 상수로 고정하면 빈 공간이 생긴다. 후자를 택한 건 업계 표준(위치 안정 우선)과 일치.
- **저사양 기기를 최대 변수로 둔 판단**: 더보기(누적)를 배제하고 교체를 택한 근본 이유. 포트폴리오지만 실사용 관점의 성능 고려.

- **번호 페이지네이션(교체) 채택** — 무한스크롤·더보기·가상스크롤 배제. 저사양 기기 DOM 고정 + 푸터 접근 + 표준 UX.
- **생략(…) 방식** — 첫·현재·마지막 항상 노출, 중간 …. Louisiana 표준 확인. 반응형 5/7칸.
- **URL ?page 동기화** — 유지·공유. 서버 주도 단일 경로로 이중 fetch 회피.
- **높이 상수화(STORY_PAGE_SIZE)** — 번호바·푸터 위치 고정. AG Grid/MUI 표준. 빈 공간은 용인.
- **shimmer 스켈레톤 + 크로스페이드** — 끊김 없는 전환. 일부러 지연 안 넣음.
- **검색 로딩 = A-i 공유 트랜지션** — StoryBrowser 래퍼로 검색·페이지 넘김이 로딩 흐름 공유.
