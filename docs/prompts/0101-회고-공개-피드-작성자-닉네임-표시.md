## 1. 한 줄 요약

공개 피드 4곳(스토리 목록·상세, CostPlan 목록·상세)의 작성자 자리에 닉네임을 표시했다. 각 쿼리에서 `select: { nickname: true }`로 닉네임만 집어, user를 통째로 가져오면 딸려 나오는 email이 payload에 애초에 실리지 않게 했다(0093 이메일 노출 재발 방지). 마이(본인 공간) 화면에는 작성자를 표시하지 않는다.

---

## 2. 왜 / 목적 / 이유

### user 통째 include가 아니라 nickname만 select

- 왜: 공개 피드에 작성자 닉네임만 띄우면 되는데 `include: { user: true }`로 user 행을 통째로 가져오면, email이 우려가 아니라 실제로 payload에 실려 네트워크에 노출된다. 화면에서 nickname만 보여줘도 email은 이미 클라에 도착해 있다. 0093에서 바로 이 경로로 이메일이 새서 막은 적이 있다.
- 목적: 작성자 자리에 닉네임이 뜨되, email은 쿼리 결과에 애초에 들어오지 않는 상태.
- 이유: 4곳 쿼리 모두 `select: { nickname: true }`로 필요한 컬럼만 집었다. 보따리(user 행)를 통째로 가져오는 게 아니라 필요한 것 하나만 꺼내, email이 가져오는 단계에서 원천 차단된다. 0097에서 짚은 "화면 숨김 vs 서버 미전송"과 같은 원리 — 진짜 보호는 데이터 입구(select)에서 일어난다. 0093은 같은 실수를 한 번 겪은 지점이라, 0101은 그 자리를 닉네임으로 채우면서 반대 방향으로 재발하지 않게 select로 구조를 잡았다.

### 마이(본인 공간)에는 작성자 미표시

- 왜: 마이플랜·마이스토리는 본인이 본인 것을 보는 공간이라, 작성자가 "나"임이 자명하다. 거기에 닉네임을 띄우면 군더더기다.
- 목적: 작성자 닉네임은 공개 피드(남의 것을 구경하는 곳)에만 뜨고, 본인 공간에는 안 뜨는 상태.
- 이유: 작성자 표시는 공개 피드 4곳 쿼리·컴포넌트에만 추가하고, 마이 화면 쿼리는 건드리지 않았다. "닉네임은 공개 피드용"이라는 0099 때의 방향과 일치.

## 5. 결과 / 배운점

- 검증 통과: 네트워크 payload에 email 없음(`@`·email 검색 0건, nickname만 실림), 스토리·CostPlan 목록·상세 4곳에 작성자 닉네임 표시, 마이(본인 공간) 화면엔 작성자 없음(변화 없음), tsc 통과.
- 배운점 1: `include`는 보따리(행)를 통째로 가져오고 `select`는 필요한 것만 집는다. 닉네임만 보여주면 되는데 user를 통째로 include하면 email이 payload에 실려 네트워크에 노출된다 — 화면에서 숨겨도 이미 클라에 도착해 있다. select로 nickname만 집어 가져오는 단계에서 차단했다.
- 배운점 2: 0093에서 이메일 노출을 막았던 그 자리를 0101에서 닉네임으로 채우면서, 같은 실수를 반대 방향으로 되풀이할 위험이 있었다. "작성자 보여주자"는 무심코 user 통째 include로 가기 쉬운데, select로 명시하니 0093에서 막은 노출이 구조적으로 부활하지 않는다. 한 번 데인 지점은 다음 작업에서 같은 함정을 의식적으로 피해야 한다.
