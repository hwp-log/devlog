# 0281 회고: 모바일 지도 카메라 프레이밍 (시트 half 파생 동조)

**작성일**: 2026-07-18
**소요 시간**: 약 1시간
**관련 커밋**: `8553873` fix: 0281 모바일 지도 padding을 시트 half와 동조 (카드 블록 중앙)

---

## 1. 한 줄 요약

선택 스팟 카드(72.5px 마커)가 브라우저 모바일 뷰에서 가시 영역 중앙보다 위로
치우치던 것을, 원인이 "지도 하단 padding 200px 고정"과 "시트 half 높이 svh 비례"의
파생 페어 어긋남임을 확증하고, padding을 시트 half 공칭 산식에서 파생 계산하도록
정합화. 실기기(작은 뷰포트)에선 우연히 근사해 안 보였던 잠재 부패를 잡음.

---

## 2. 왜 / 목적 / 이유

### 지도 카메라 padding을 시트 half와 동조

- **왜 (표면 동기)**: 실사용자는 브라우저 창 크기를 바꿔가며 지도를 보지 않는다 —
  이 어긋남을 실제로 겪는 사람은 사실상 없다. 다만 채용 담당자는 데스크탑
  브라우저를 줄여서(반응형으로) 볼 가능성이 높고, 그때 카드가 어정쩡하면
  "모바일 대응이 덜 됐다"고 오해받는다. 실기기에선 완벽한데도. 포폴은 "잘 되느냐"
  만큼 "잘 되어 보이느냐"가 중요하므로, 평가자 시야를 고려해 손대기로 판단.
- **왜 (진짜 발견)**: 원인을 코드로 확증하니 "브라우저에서만 삐끗하는 현상"이
  아니라 파생 페어 부패였다. 시트 half는 `max(58svh, 359px+safe-area)`로
  뷰포트에 비례해 커지는데, 지도 하단 padding은 `200px 고정`. 시트 높이라는
  한 사실이 두 곳에 다른 형태로 박혀 있었고, 실기기 크기(660~850px)에선 200이
  우연히 근사해 안 보였을 뿐 큰 뷰포트에선 체계적으로 이탈하는 잠재 버그였다.
- **목적**: 카드 블록(사용자가 보는 실체 = 카드+라벨+점)의 중심이 시트 위
  가시 영역 수직 중앙에 오게. 모든 뷰포트 높이에서 성립하게.
- **이유**: 이미 0280에서 로딩 안내를 "가시 영역 = 100svh − 시트높이" 산식
  (`SLOT_TOP`)으로 배치했다. 지도 padding도 같은 논리를 따라야 하는데 200px
  고정이라 어긋난 것 → 같은 파생 페어로 정합화하면 근본 해결. 포폴 대비가
  계기였으나, 결과적으로 숨어 있던 단일 소스 위반을 잡았다.

### 중앙 기준 = 좌표(점)가 아니라 카드 블록

- **왜**: 사용자가 "중앙에 있길" 기대하는 건 좌표 점이 아니라 눈에 보이는
  72.5px 카드 블록이다. 점을 중앙에 놓으면 그 위에 얹힌 카드가 위로 떠 보여,
  고치려던 "위로 치우침"을 다른 형태로 재현한다.
- **이유**: 카드 블록 중앙 기준은 실기기 이동이 ≈40px 소폭에 그쳐(현재 실기기가
  이미 이 상태에 가까움) 회귀 위험이 작다. 좌표 점 중앙은 실기기 ≈97px 이동으로
  체감 변화가 커 기각. 고정 오프셋(실기기 완전 무변)은 브라우저 정확한 중앙에
  미달이라 기각. 브라우저를 고치되 실기기는 거의 안 건드리는 선택.

## 4. 코드 작성 & 수정

> 코드 블록은 커밋된 실제 파일에서 확증.

### components/SpotFinderMapNaver.tsx — 고정 상수 → 파생 계산

```typescript
// 0281: 모바일 지도 하단 패딩 — 고정 200px는 시트 half(svh 비례)와 파생 페어가 어긋나
// 큰 뷰포트(브라우저 모바일 뷰) 중앙을 이탈 → 시트 half 공칭 산식에서 파생 계산으로 대체.
// SHEET_MAX_H.half(58svh·359px) ↔ SLOT_TOP(SpotFinderMapSlot) ↔ computeMapPadBottom
// 3자 페어 — 한쪽만 바꾸면 어긋남.
// MARKER_BLOCK_CENTER_OFFSET = 좌표(점 중심)에서 (카드+pill+점) 블록 중심까지 위쪽 거리.
// 유도: 점 위 5.5(dot/2) + 4(pill 간격) + pill≈31 + 5(카드 간격) + 카드 72.5 ≈ 블록 118
//   → 중심 ≈ 좌표 −56. MARKER_CARD_SIZE·MARKER_DOT_SIZE 파생.
const MARKER_BLOCK_CENTER_OFFSET = 56;

// pad = 시트half − 2×블록보정 → 좌표 안착점 = 가시영역중앙 + 56 = 블록 중심이
// 가시 영역 수직 중앙(모든 뷰포트 높이에서 성립).
// svh는 지도 div clientHeight로 역산(innerHeight는 iOS 주소창에 흔들림).
// safe-area는 지도 div 인라인 --sab를 computed로 읽음(0279 --card·0261 env 선례). 브라우저=0 자동.
function computeMapPadBottom(mapEl: HTMLElement): number {
  const svh = mapEl.clientHeight;
  const sab = parseFloat(getComputedStyle(mapEl).getPropertyValue('--sab')) || 0;
  const sheetHalf = Math.max(0.58 * svh, 359 + sab);
  return Math.max(0, sheetHalf - 2 * MARKER_BLOCK_CENTER_OFFSET);
}
```

### 생성 옵션 반영 (초기 featuredSpot 프레이밍)

```typescript
// 0281: 초기 자동 선택(featuredSpot)은 morph 미경유·생성 center 시작이라
// 생성 옵션에서 padding을 함께 반영 — 첫 프레임부터 카드 블록 중앙.
...(window.matchMedia(MOBILE_MQ).matches
  ? { padding: { bottom: computeMapPadBottom(mapDivRef.current) } }
  : {}),
```

### 재적용 effect + resize 구독

```typescript
// 0224→0281: 고정 200 → 동일 산식. resize 구독 추가(브라우저 창 높이 변경 재계산 —
// 실기기는 svh·safe-area 불변이라 동일값 재적용 = 무해).
const apply = () => {
  const el = mapDivRef.current;
  mapInstance.setOptions('padding', { bottom: mq.matches && el ? computeMapPadBottom(el) : 0 });
};
apply();
mq.addEventListener('change', apply);
window.addEventListener('resize', apply);
```

## 5. 결과 / 배운점

### 결과 (사실)
- 정적: `tsc --noEmit` 통과 · eslint 0 errors · jest 기준선(8f/86p) 유지.
- 브라우저 모바일 뷰: 창 높이와 무관하게 선택 카드 블록이 시트 위 가시 영역
  수직 중앙에 정렬. 창 높이 변경 시 resize 재계산으로 유지.
- 실기기: 기존 대비 좌표 ≈40px 상향, 카드 위치 자연스러움 확인(회귀 없음).
- 수평 치우침: 수직 교정 후 육안 판정 → 잔존 없음. "왼쪽 치우침"으로 느껴졌던
  것은 카드가 위로 뜬 데서 온 착시였고, 수직을 맞추니 자동 해소.

### 배운점
- **같은 사실이 두 곳에 다른 형태로 박히면 특정 조건에서만 어긋난다.** 시트 높이
  라는 한 사실이 "svh 비례"(시트)와 "200px 고정"(패딩)으로 이원화돼 있었다.
  실기기 크기에선 우연히 근사해 안 보였을 뿐 뷰포트가 커지면 체계적으로 어긋나는
  잠재 부패였다. 단일 소스는 "지금 안 틀어짐"이 아니라 "파생 관계가 명시됐는가"로
  판단해야 한다.
- **실기기 정상 = 전체 정상이 아니다.** 브라우저 어긋남을 "물리적 차이(safe-area
  없음)"로 넘길 뻔했으나, 원인을 코드로 확증하니 고칠 수 있는 계산 문제였다.
  "실기기가 정상이니 됐다"로 멈췄으면 잠재 버그를 방치했을 것.
- **추측 대신 (A)/(B) 판정을 먼저 요구했다.** 원인이 고칠 수 있는 것인지, 물리적
  차이라 못 고치는 것인지를 코드 근거로 가른 뒤에야 손댔다. 이 판정이 없었으면
  "브라우저용 보정"을 넣다가 실기기를 틀어뜨렸을 수 있다(safe-area 계층).
- **한 축을 고치면 다른 축 착시가 드러난다.** 수직·수평을 동시에 파지 않고 수직만
  먼저 교정한 뒤 수평을 재판정했다. 결과적으로 수평은 착시였고 별도 작업이
  불필요했다 — 싸게 한 축부터 고쳐 판정 비용을 줄였다.

## 결정 (Decisions)

- **지도 하단 padding = 시트 half 파생 계산**: 고정 200px 폐기.
  `computeMapPadBottom(mapEl)` = `max(0.58×svh, 359+safe-area) − 2×블록오프셋`.
  svh는 지도 div clientHeight 역산, safe-area는 `--sab` computed 읽기(브라우저=0).
- **중앙 기준 = 카드 블록**(좌표 점 아님): `MARKER_BLOCK_CENTER_OFFSET=56`.
  실기기 이동 최소(≈40px), 사용자가 보는 실체를 중앙에.
- **초기 featuredSpot도 생성 옵션 padding 반영**: morph 미경유라 첫 프레임부터 동일.
- **resize 재계산 구독**: 브라우저 창 높이 변경 대응. 실기기는 svh·safe-area
  불변이라 무해.
- **3자 페어 주석**: SHEET_MAX_H.half ↔ SLOT_TOP(0280) ↔ computeMapPadBottom
  상호 참조 — 한쪽만 바꾸면 어긋남(Tailwind JIT 제약으로 코드 공유 불가, 주석 동기).
- **수평은 비수정**: 수직 교정으로 착시 해소 확인 → 별도 작업 없음.
