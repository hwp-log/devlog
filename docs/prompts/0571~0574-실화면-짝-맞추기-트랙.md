- 0571(잘못된 것이 보임)과 0572(아무것도 안 보임)는 증상이 다르다.

## 4. 코드 작성 & 수정

### 0571 — 1벌 공유 + 대표형 판정

`my-plan/new/MyPlanFormSkeleton.tsx` 1벌을 `new/loading.tsx`·`[id]/edit/loading.tsx`가 공유(0491 구조 그대로). new·edit이 같은 `MyPlanNewForm`을 쓰고 초기값 차이가 골격에 안 남는다.

**갈린 판정 하나**: 지표 밴드는 **포함**, 예상 비용 요약은 **생략**.

| 블록 | 판정 | 근거 |
|---|---|---|
| 지표 밴드 | 포함 | 값이 없어도 `—`로 **항상** 뜬다 |
| 예상 비용 요약 | 생략 | **0570부터 전부 0이면 `CostSection`이 `null`** — new 대표형은 "안 뜸" |

둘 다 "값이 있어야 뜨는 것 아니냐"로 물었는데 답이 갈렸다. 0570을 방금 만들지 않았으면 요약을 넣었을 것이다.

### 0572 — 만들기 전에 "그려지긴 하나"를 먼저

0571에서 `new`가 안 그려진 걸 뒤늦게 안 대가로, 이번엔 조회 유무를 먼저 쟀다. 어드민은 `layout.tsx`(권한) → `page.tsx`(목록)가 직렬이고 둘 다 실 조회다.

`glass-outer`를 스켈레톤에도 쓴 이유: **스켈레톤은 실화면의 짝이지 개선안이 아니다.** 안 쓰면 전환 시 카드 면이 갑자기 생긴다.

### 0573 — 매핑과 "거의 무변"

새 판단을 만들지 않고 같은 역할의 다른 화면을 따랐다: `fg` / `fg2` / `muted` / `hint` / `hairline` / `field-border` / `danger` / `primary`(눈썹 — 0441).

**라이트는 "무변"이 아니라 "거의 무변"이다.** 델타:

| 자리 | 변화 |
|---|---|
| 본문 `#1A1A1A` → `fg #191a1c` | 거의 동일 |
| h2·버튼 `slate-700 #334155` → `fg2 #55565c` | **밝아짐 + 청색기 제거** |
| 메타 `slate-500` → `muted` / 건수 `slate-400` → `hint` | 밝아짐 + 무채화 |
| 에러 `rose-500/600` → `danger #ef4444` | **핑크 → 정적색 빨강** |
| 눈썹 `sky-500` → `primary #4d9eff` | **하늘 → 브랜드 파랑** |

`btn-elevated`는 다크 오버라이드를 신설했다(면 `surface2`, 그림자 완화 — 다크에선 큰 드롭섀도가 얼룩으로 보인다). 소비처가 어드민뿐이라 부수 영향 없음.

### 0574 — 겹침의 원인과 4곳 동시 수정

겹침은 절대 위치도 음수 마진도 아니었다:

```jsx
<div className="… min-w-0">          {/* 박스는 0까지 줄어듦 */}
  <span className="shrink-0">{createdAtLabel}</span>   {/* 안 줄어듦 */}
</div>                                {/* overflow-hidden 없음 → 새어 나감 */}
```

0559 주석의 **"min-w-0 = 넘침 방지"는 안쪽에 `shrink-0`이 있으면 성립하지 않는다** — 넘침을 막는 게 아니라 잘리지 않고 새어 나오게 만든다. `overflow-hidden`을 함께 보강했다.

밴드는 **4파일 동시**:
```diff
- grid-cols-[auto_auto_auto_1fr] sm:grid-cols-4 gap-x-2
+ grid-cols-2 sm:grid-cols-4 gap-x-2 gap-y-3 sm:gap-y-0
```
마지막 칸만 `sm:items-end sm:text-right`(모바일 2×2에선 오른쪽 열이 [장소/총 비용]이라 여기만 우측 정렬하면 열 안에서 정렬이 갈린다 → `sm:`만).

### 0574 후속 — 2행이 양끝을 쓰도록 (`3a2b5df`)

겹침은 `c8e06a6`으로 해소됐지만 **액션 4개가 2행에 좌측 정렬로 뭉쳐 오른쪽 94px이 비었다.** 스토리 상세(`/story/[id]`)가 이미 답을 갖고 있어 그 배치를 따랐다 — 좌측 메타 + **우측 끝** 관리 아이콘.

```
1행: [아바타 · 작성자 · 날짜] ········· [수정][삭제]
2행: [비공개 pill] ················· [♥ 0]
```

**`PlanOwnerActions`를 두 조각으로 쪼갠 경위.** 구 컴포넌트는 pill + 수정 + 삭제를 **한 덩어리**로 렌더했다. 이번 배치는 pill(2행 왼쪽)과 아이콘(1행 오른쪽)이 **서로 다른 줄**에 놓이므로 덩어리째로는 나눌 수 없다. CSS만으로 풀려던 시도(`sm:contents` + `order`)는 **데스크톱 순서와 gap이 갈려** 접었다 — 한 flex 컨테이너에서 두 종류의 gap(좌측↔묶음 20px / 묶음 내부 8px)을 낼 수 없다.

→ `PlanPublicToggle` + `PlanManageIcons({ planId, className })`로 분리. 구 `PlanOwnerActions`는 **소비처가 `PlanFinderDetail` 하나뿐**이라 합쳐진 래퍼를 남기지 않고 폐기했다(소비처 0 래퍼 = 화석 — 0564·0566에서 사장 코드를 지운 기준).

**복제해도 되는 것과 안 되는 것.** 아이콘은 모바일·데스크톱 **두 벌**을 그리고 `sm:hidden`/`max-sm:hidden`으로 가른다. 근거가 갈린다:

| 조각 | 상태 | 복제 판정 |
|---|---|---|
| `PlanPublicToggle` | `useOptimistic` 공개 상태 | **절대 복제 금지** — 두 인스턴스면 optimistic 상태가 갈려 한쪽만 "공개 중"이 된다 |
| `PlanManageIcons` | 삭제 `isPending`뿐 | **복제 안전** — 수정=이동, 삭제=redirect로 **두 동작 다 렌더 후 이탈**이라 갈릴 상태가 없다 |

그래서 pill은 2행에 **한 번만** 존재하고, 데스크톱에서는 그 2행 컨테이너가 통째로 우측 묶음이 된다. 아이콘만 두 벌이다.

**데스크톱 무변 근거**: 2행 컨테이너가 `sm:` 이상에서 `[pill][수정·삭제][좋아요]` 전부 `gap-2` — 구 구조(`PlanOwnerActions` 내부 `gap-2` + 바깥 `gap-2`)와 **같은 8px**. `ml-auto`는 `sm:ml-0`으로 해제.

`className`을 prop으로 받는 게 "조판을 variant로 가르지 않는다"(0518)와 어긋나지 않는 이유도 주석에 남겼다 — **variant가 아니라 위치 클래스 전달**이고, 내부 조판(gap·칩 크기)은 컴포넌트가 고정한다.

- 0574는 **실화면 검수가 한 라운드 더 돌았다** — 겹침을 고치고 나니 액션이 좌측에 뭉쳐 오른쪽 94px이 비는 게 드러나 `3a2b5df`로 재배치
- 실화면 확인: — 0574 두 행이 각각 양끝을 쓰는지 · 닉네임 20자+에서 아이콘이 안 밀리는지 · 밴드 격자 · 모바일 밴드 세로 +55px 수용 여부 / 0573 라이트 델타 3건 / 전환 시프트

### 배운점
- **짝의 개수를 세는 것이 이 트랙의 반복 작업이었다.** 0574에서 밴드가 2곳(실화면·폼)인 줄 알았는데 **4곳**이었다 — 스켈레톤 2개가 같은 클래스 문자열을 복제하고 있었다. 하나라도 빠지면 전환 시프트가 생긴다. 조판을 고칠 때 "이 조판을 복제한 곳이 몇 곳인가"를 먼저 세는 게 작업의 절반이었다.
- **판정을 뒤집을 때는 당시 검산 대상이 무엇이었는지를 봐야 한다.** 0562(B)의 "모바일도 4열 유지"는 **"가로로 넘치는가"만 검산**했고 "격자로 읽히는가"는 판정 대상이 아니었다. 결론만 보면 "왜 이렇게 했지"가 되지만, 검산 대상을 보면 **뒤집는 게 아니라 안 본 축을 추가하는 것**이 된다. 과거 판정을 존중하면서 바꾸는 방법이다.
- **`loading.tsx`는 파일이 있다고 뜨는 게 아니다.** 세그먼트가 실제로 suspend해야 그려지고(0571 `new`), `layout.tsx`의 await 구간은 **그 안쪽 loading이 못 덮는다**(0572).
- **정정을 적는 것과 다음 측정에 적용하는 것은 다르다.** 0571에서 "0ms를 노출 시간으로 읽었다"를 정정해 놓고 0572에서 "45.8ms를 노출 시간으로 읽는" 같은 종류의 오류를 반복했다. 두 번 다 *서버가 일한 시간*과 *경계가 pending인 시간*을 같은 것으로 취급했다.
- **유틸의 생사는 소비처 grep으로 확인해야지 회고 문구로 추정하면 안 된다.** 0572에서 `glass-outer`를 "폐기된 카드 유틸"로 본 게 틀렸다(지금도 랜딩·auth·my-story가 쓴다). 0513·0527의 "카드 제거"는 그 화면의 사실이지 유틸의 사실이 아니었고, 잘못된 전제가 **코드 주석까지 갔다.**
- **스켈레톤은 실화면보다 좋으면 안 된다.** `glass-outer`를 쓸지 고민한 지점이 그것이다 — 폐기 방향이라 안 쓰고 싶었지만, 안 쓰면 전환 시 카드 면이 갑자기 생긴다. 짝을 맞추는 게 우선이고 개선은 실화면 쪽에서 한다.
- **컴포넌트를 쪼갤지 말지는 "상태가 있는가"가 가른다.** 0574 후속에서 `PlanOwnerActions`를 나누며 아이콘은 두 벌 그리고 토글은 한 벌만 뒀다. 기준이 조판이 아니라 **상태의 성격**이었다 — optimistic 상태는 두 인스턴스가 갈리지만, "렌더 후 이탈"뿐인 pending은 갈릴 창이 없다. 반응형에서 같은 UI를 두 벌 그리는 건 흔한 손인데, **무엇을 복제해도 되는지는 DOM이 아니라 상태를 봐야** 판단된다.
- **CSS로 풀리는 한계를 먼저 확인하는 게 빨랐다.** 0574 후속은 `sm:contents` + `order`로 컴포넌트를 안 건드리고 풀 수 있을 것처럼 보였지만, 한 flex 컨테이너가 두 종류의 gap(20px/8px)을 못 내서 접었다. 그 확인이 "컴포넌트를 쪼개야 한다"는 결론의 근거가 됐다.
