## 1. 한 줄 요약

플랜 상세 두 벌(/my-plan/[id], /plan-finder/[id])을 한 벌로 — 일정 행 공용화(0556)에서
출발해, 공개 축의 뿌리 원칙을 "금액 가공"에서 "글 자체를 가림"으로 재정의(0557 접근 제어
→ 0558 금액 실값 통일)하고, 그 위에서 관리 버튼 공용화(0559)·라우트 통합(0560)·작성 폼
조판 정합(0561)까지 완결.

## 2. 왜 / 목적 / 이유 (트랙의 서사)

1. **발단은 스크린샷 두 장.** 같은 플랜의 일정 행이 공개 상세엔 썸네일·작품 칩·주소가
   있는데 소유자 상세엔 이름뿐이었다. 원인은 조판이 아니라 조회 층 — 소유자 page에
   Spot 조인이 없었다 (0556).
2. **스토리를 선례로 봤더니, 거긴 축이 없어서 단순했던 것.** 스토리가 /story/[id]
   한 화면으로 사는 이유는 설계가 좋아서가 아니라 Story 모델엔 isPublic이 아예 없기
   때문이었다. 플랜은 공개 축이 있어서 화면이 갈라진 것 — 그래서 축 자체를 파고들었다.
3. **축을 파니 근거 없는 완화가 나왔다.** 뿌리 원칙 0089("정밀 지출액 = 개인 경제
   정보")를 0492가 금액 공개로 완화했는데, 그 근거가 어느 회고에도 없었다.
4. **근거를 다시 세우니 원칙이 바뀌었다.** 지키려던 것은 금액 프라이버시가 아니라
   **작성자의 통제권** — 미완성이거나 보이고 싶지 않으면 안 보이면 되는 것이다.
   그러면 "어중간하게 가공"이 아니라 "보이거나 안 보이거나"여야 한다. 그래서 1단계
   접근 제어(0557: visiblePlanWhere, 비공개 = 남에게 404)가 먼저 섰다.
5. **접근 제어가 서자 도미노가 쓰러졌다.** 보이면 안 되는 것은 아예 안 보이므로 금액
   근사·구간 가공의 존재 이유가 소멸(0558 실값 통일). 두 화면의 마지막 실질 차이가
   금액 표현이었으므로, 이것이 다시 라우트 통합(0559~0560)의 장벽을 없앴다.
   **순서를 바꾸면 못 푸는 문제였다** — 통합을 먼저 시도했다면 "실값 화면과 가공
   화면을 어떻게 한 벌로?"에 막힌다.
6. **작성 폼은 컴포넌트가 아니라 조판으로 맞췄다(0561).** 스토리 0459 방식 — 섹션
   순서·용어·제목 급만 정합하고 마크업은 공유하지 않는다. 비용↔항공 순서는 의도적으로
   어긋나게 뒀다: 읽기는 훑는 순서, 폼은 입력 흐름 — 합산(예상 비용)은 입력이 아니라
   파생이라 모든 입력 뒤 "저장 직전 확인" 자리가 맞다. 완전 정합(B안)은 0537 헤더 폭
   전례처럼 정합을 위해 없던 불편을 만드는 것이라 기각.

### 0557 — 접근 제어 (원칙 재정의 1단계)

```ts
// lib/plan/queries.ts — 가시성 정본
export function visiblePlanWhere(viewerId?: string | null) {
  return { OR: [{ isPublic: true }, ...(viewerId ? [{ ownerId: viewerId }] : [])] };
}
```

적용 3곳: 공개 상세 page(소유자는 자기 비공개도 열람 — 남은 404 유지)·좋아요·담기 액션.

## 5. 결과 / 배운점

### 결과

- 플랜 상세는 /plan-finder/[id] 한 벌 — 소유자는 관리 버튼(공개 전환·수정·삭제)·원본
  링크 포함, 비소유자는 좋아요·담기만. 구 URL은 redirect 스텁이 보호.
- 금액은 전 화면 실값, 비공개는 글 자체가 가려짐(남에게 404·목록 미노출·스토리 카드
  통째 생략).
- 전 커밋 `npx tsc --noEmit` 통과. npm test 기존 실패 목록(auth 5스위트+SpotPopup)
  외 회귀 없음(0558에서 전수 확인, 이후 관련 스위트 통과 유지).
- 잔여(별도 사이클): isDraft 컬럼 drop, /my-plan/[id] 스텁 제거(진입 0 확인 후),
  읽기 SectionHeader 공용화(모바일 19→20px 시각 변경 수반), "왕복 항공편" 편도 표기.

### 배운점

- **"화면이 다르다"의 원인은 조판 층이 아닐 수 있다** — 0555(조판 정합)에서 행 내용이
  안 따라온 이유는 select 한 줄이었다 (0556).
- **선례를 옮기기 전에 선례가 성립한 조건을 확인할 것** — 스토리의 한 화면 구조는
  설계 선택이 아니라 공개 축(isPublic) 부재의 결과였다. 조건이 다르면 같은 구조를
  베낄 게 아니라 조건 차이(축)를 먼저 다뤄야 한다.
- **완화된 원칙에 근거가 없으면 완화를 되돌리는 게 아니라 근거를 다시 세운다** —
  0089→0492의 무근거 완화를 파니 지킬 것은 금액이 아니라 통제권이었고, 원칙이 서자
  구현 결정(가공 폐기→통합)이 도미노로 따라왔다. 순서를 바꾸면(통합 먼저) 못 푸는
  문제였다.
- **상위 층이 서면 하위 층의 존재 이유를 재심사할 것** — 접근 제어와 표현 가공은 같은
  목적(통제권)의 두 층. 상위(접근)가 서자 하위(가공)는 폐기 대상이 됐다 (0558).
- **정합에도 예외 근거를 명문화할 것** — 비용↔항공 순서처럼 의도적으로 어긋나게 둔
  자리는 주석에 근거를 남겨야 다음 정합 사이클이 "누락"으로 오인해 재제안하지 않는다
  (0537 헤더 폭 전례의 재적용).

## 결정 (Decisions)

- 플랜 공개의 원칙 재정의: 지키는 것은 금액 프라이버시가 아니라 **작성자의 통제권** —
  비공개는 금액 가공이 아니라 글 자체를 가린다 (0089→0492 무근거 완화의 근거 재수립)
- 플랜 가시성 정본 = `visiblePlanWhere`(공개이거나 내 것) — 소비처는 상세·좋아요·담기.
  공개 목록은 진열 기준(isPublic 단독)이라 미적용
- 금액은 전 화면 실값(formatAmount) — 근사·구간 폐기. 필터·정렬 기준 = total(0 = 제외/말단)
- isDraft는 코드에서 폐기 — 실효 의미는 isPublic=false가 담음. 컬럼 drop은 별도 사이클
- 플랜 상세 정본 = /plan-finder/[id] 한 벌 — /my-plan/[id]는 redirect 스텁(진입 0 확인
  시 제거). 삭제 후 이동은 /my-plan 공통

  달라도 원칙은 하나: 두 벌 관리 금지
- 일정 행 우측 실값 금액(0556 잠정)은 미편입 확정 — 총액은 지표 밴드, 항목별은 비용
  섹션에 있어 세 번째 등장
- 작성 폼 정합은 0459 방식(조판·용어만, 컴포넌트 공유 금지) — 단 비용↔항공 순서는
  입력 흐름 예외(읽기는 훑는 순서, 폼은 입력 흐름). 완전 정합을 위해 없던 불편을 만들지
  않는다(0537 전례)
