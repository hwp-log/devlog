# 0314~0315 회고: Story 썸네일 이미지 최적화

**작성일**: 2026-07-23
**관련 커밋**:
- `0314` feat: Story 카드 썸네일 next/image 전환 (c193cc6)
- `0315` feat: StoryCard next/image 적용 — 0314 잔여분 (e185ada)

> 0314는 next.config 설정만, 0315는 컴포넌트 교체와 회귀 수정이라 한 작업이 두 커밋으로 갈라진 케이스. 갈라진 경위 자체가 기록할 값어치가 있어 묶어 회고.

---

## 1. 한 줄 요약

Story 목록에서 사진이 제각각 튀며 뜨는 어수선함을, "로딩 화면을 3~4초 보여줘 가리는" 방향으로 풀려다가 원인 조사로 전환해 next/image 전환 하나로 해결. 체감 2~3초 들쭉날쭉이 0.2초 일괄로 바뀌었고, 원래 넣으려던 지연 연출은 필요 자체가 사라졌다.

---

## 2. 왜 / 목적 / 이유

- **왜**: Story 목록에서 레이아웃(스켈레톤)은 즉시 뜨는데 사진만 순서 없이 한 장씩, 각각 끊기며 나타남. 시각적으로 어수선하고 완성도가 낮아 보임.
- **목적**: 목록 진입 시 사진이 한 번에, 안정적으로 채워지는 경험. 사용자가 "로딩 중"을 인지할 틈이 없게.
- **이유**: 처음 떠올린 해법은 "로딩 애니메이션을 2초(원하는 건 3~4초) 강제로 보여주고 그 뒤에 사진을 한꺼번에 노출"이었다. 실제로 그렇게 하면 어수선함이 사라져 보였기 때문. 그러나 이 방향은 원인을 없애는 게 아니라 **가리는** 접근이라 재검토했다.

---

## 3. 판단 여정

### 출발점 — 잘못된 가설 두 개

1. **"Vercel 무료 플랜이라 느린 것 아닌가"** → 퍼플렉시티에 문의. 답은 "호스팅이 아니라 프론트 로딩·레이아웃 설계 문제"로 정확했고, Pro 업그레이드로는 해결되지 않는다는 것도 맞았다.
2. **"지연을 넣어 가리자"** → 3~4초 강제 지연은 이탈률·만족도 기준에서 위험 구간이라는 지적을 받고 보류.

다만 퍼플렉시티가 제시한 비교 목업 코드에는 결함이 있었다. `leftReady`가 true일 때만 `<img>`를 마운트하는 구조라 **2초 동안 이미지 다운로드가 시작조차 되지 않는다.** 설명("스피너 도는 동안 미리 로딩")과 코드가 반대로 동작한 것. 이 지점에서 "실제 우리 코드는 어떻게 돼 있나"를 확인하는 쪽으로 방향을 틀었다.

### 원인 조사 — 세 겹이 겹쳐 있었다

CC에 "읽고 보고만" 모드로 조사를 맡긴 결과:

| 층 | 문제 |
|---|---|
| ① 파일 자체 | 확장자만 `.png`인 **무압축 BMP 1.77MB**가 그대로 저장·서빙 중 (940×627×3바이트로 용량 계산 일치). 업로드 시 포맷 검증 없음 |
| ② 전송 | `next/image` 미사용. 카드 표시 폭 대비 수 배 크기 원본을 15장 전부 eager 동시 다운로드. 업로드 시 `cacheControl: '3600'`을 지정했으나 실제 응답 헤더는 `cache-control: no-cache` |
| ③ 공개 시점 | 스켈레톤 크로스페이드가 **"데이터(HTML) 도착" 기준**이지 "이미지 로드 완료" 기준이 아님. 코드 전체에 `onLoad` 핸들러 없음 → 스켈레톤이 걷힌 뒤 각 이미지가 완료 순서대로 제각각 나타남 |

"순서 없이"는 ③, "각각 끊기며"는 ①+②였다. 즉 하나의 증상처럼 보였지만 원인이 둘이었다.

### 처방 순서 — 무거운 것부터, 그리고 나중 것은 유보

- **A. next/image 전환** — ② 해결
- **B. `decode()` 기반 일괄 공개 게이트** — ③ 해결
- **C. 업로드 포맷 검증·캐시** — ① 해결

셋을 한 커밋에 묶지 않고 **A만 먼저 넣고 실화면을 보기로** 결정했다. 근거는 "A가 충분히 빨라지면 B가 불필요해질 수 있고, 필요 없는 코드를 미리 넣는 것보다 실화면을 보고 판단하는 게 낫다"였다. 결과적으로 이 판단이 맞았다 — **B는 끝내 넣지 않았다.**

### 사고 1 — 커밋에 파일이 빠졌다

0314 커밋 직후 로그를 보니 `1 file changed`. next.config만 들어가고 StoryCard 변경이 없었다. CC 플랜의 ②단계(컴포넌트 교체)가 실행되지 않은 상태에서 커밋한 것.

- 신호는 두 개나 있었다: `git status`의 "ahead of origin by 1 commit"(0313이 푸시 안 된 상태), 그리고 `1 file changed`.
- 게다가 이 시점에 실화면을 보고 "깔끔해졌다"고 판단했는데, 실제로는 **브라우저 캐시** 때문이었다. remotePatterns만으로는 아무것도 변하지 않는다.
- 이후 커밋 전 `git show --stat`으로 파일 수를 확인하는 절차를 넣었다.

### 사고 2 — 0314가 만든 테스트 회귀

next.config에 넣은 `new URL(process.env.NEXT_PUBLIC_SUPABASE_URL!)`가 **jest config 평가 시점에 던졌다.** next/jest가 config를 파싱할 때는 `.env.local`이 로드되기 전이라 env가 undefined → 테스트 전체가 실행 불가.

"env가 없으면 조용히 와일드카드로 새는 것보다 시끄럽게 죽는 게 낫다"고 판단해 넣은 `!` 단언이 테스트까지 죽인 것. 0315에서 폴백 호스트로 수정했다. **와일드카드 폴백은 채택하지 않았다** — 이미지가 안 뜨는 상태로 빌드가 통과해버리기 때문.

### 예측이 빗나간 지점 — BMP

"프리빌드 sharp/libvips에는 BMP 로더가 없으니 해당 카드는 변환 실패로 깨질 것"이라 예상했으나, 실제로는 **변환만 건너뛰고 원본을 그대로 서빙**했다(200, image/bmp, 1.77MB). 깨지지 않는 대신 그 카드만 최적화 혜택이 없다.

## 4. 코드 작성 & 수정

### 0314 — next.config remotePatterns

```ts
// next.config.ts
images: {
  remotePatterns: [
    {
      protocol: 'https',
      hostname: new URL(process.env.NEXT_PUBLIC_SUPABASE_URL!).hostname,
      port: '',
      pathname: '/storage/v1/object/public/**',
      search: '',
    },
  ],
},
```

- `protocol`/`port`/`pathname`/`search`를 전부 명시 — 생략 시 와일드카드로 풀린다는 문서 경고에 따름.
- 호스트는 하드코딩 대신 env에서 파생(환경 간 이식성).

### 0315 — StoryCard 교체 + 회귀 수정

```tsx
// app/(protected)/story/_components/StoryCard.tsx
{thumbnail ? (
  <Image
    src={thumbnail}
    alt=""
    fill
    sizes="(max-width: 767px) 50vw, (max-width: 1023px) 33vw, (max-width: 1279px) 25vw, (max-width: 1535px) 20vw, 17vw"
    className="object-cover"
  />
) : (
  /* "이미지 없음" 폴백 유지 */
)}
```

`sizes` 5구간은 그리드 컬럼 정의(`grid-cols-2 md:3 lg:4 xl:5 2xl:6`, gap 24px)에서 실제 카드 폭을 계산해 도출:

| 뷰포트 | 컬럼 | 실제 카드 폭 | sizes |
|---|---|---|---|
| <768px | 2 | 50vw − 36px | 50vw |
| 768–1023 | 3 | 33.3vw − 32px | 33vw |
| 1024–1279 | 4 | 25vw − 30px | 25vw |
| 1280–1535 | 5 | 20vw − 28.8px | 20vw |
| ≥1536 | 6 | 16.7vw − 28px | 17vw |

```ts
// next.config.ts — jest 회귀 수정
hostname: process.env.NEXT_PUBLIC_SUPABASE_URL
  ? new URL(process.env.NEXT_PUBLIC_SUPABASE_URL).hostname
  : 'placeholder.supabase.co', // jest 등 env 없는 평가용, 실서빙 불가 호스트
```

## 5. 결과 / 배운점

### 결과

- **dev 실측**: 시드 이미지 1.20MB → w=384에서 54KB, webp 협상 시 w=256에서 5.7KB. Supabase 업로드 PNG 662KB → 57KB.
- **배포본 체감**: 2~3초 들쭉날쭉 → **약 0.2초에 전부 일괄 표시.**
- `next/image` 기본 lazy 덕에 뷰포트 밖 카드의 동시 다운로드 경쟁도 해소.
- **B(공개 게이트)는 폐기.** 전송이 빨라지자 팝인이 인지되지 않아 필요가 사라졌다.
- 테스트는 기존 실패 8건과 동일, 회귀 없음.

### 배운점

- **어수선함의 정체는 "느림의 편차"였다.** 각 이미지가 느리니 완료 순서가 갈렸고, 그게 튀는 것처럼 보인 것. 전송을 빠르게 만들자 "들쭉날쭉할 시간" 자체가 없어졌다. 연출로 가리는 것과 원인을 없애는 것의 차이가 여기서 갈린다.
- **가리는 해법을 먼저 떠올린 이유는, 증상을 UI 문제로 규정했기 때문이다.** "사진이 튀어 보인다"를 시각 현상으로만 보면 답이 연출로 좁혀진다. 전송량이라는 층을 의심하려면 증상을 "왜 늦게 오는가"로 다시 물어야 했다.
- **필요 없어진 개선은 넣지 않는 것도 결과다.** B를 미리 구현했다면 효과를 확인할 수 없는 코드가 남았을 것. A → 확인 → B 판단 순서가 그걸 막았다.
- **체감 판정에도 조건 통제가 필요하다.** "깔끔해졌다"는 첫 인상은 브라우저 캐시였고, 로컬 dev는 이미지 최적화를 타지 않는다. 판정은 시크릿 창 + 배포본에서.
- **커밋 직전 `git show --stat`으로 파일 수 확인.** CC가 단계 중간에 멈춘 걸 못 보고 커밋해 한 작업이 두 커밋으로 갈라졌다. `git status`의 "ahead by N"과 `N file changed` 두 줄만 읽었어도 잡혔다.
- **"시끄럽게 죽는" 설계도 죽는 범위를 봐야 한다.** env 부재 시 빌드를 세우는 건 의도대로였지만 테스트 실행까지 막을 줄은 계산하지 못했다. 다만 조용한 와일드카드 폴백으로 되돌리지는 않았다.

## 결정 (Decisions)

- **처방을 A(전송) → B(공개 시점) → C(파일)로 분리하고 A만 먼저 커밋** — 어느 변경이 체감을 고쳤는지 판별 가능하게. 결과적으로 B 불필요 판정.
- **B(decode 게이트) 폐기** — A 이후 팝인이 인지되지 않아 필요 소멸.
- **3~4초 강제 지연 미채택** — 이탈률 위험 구간이고, 원인 제거로 지연 자체가 불필요해짐.
- **env 부재 시 폴백 호스트** — 와일드카드 폴백은 배제(이미지가 안 뜨는 채로 빌드 통과 위험).
- **BMP 파일은 이번 범위 밖** — 변환 스킵되어 원본 서빙 상태로 남음. 업로드 포맷 검증(C)에서 처리 예정.
- **C(업로드 매직바이트 검증 + cacheControl 미적용 원인 규명)는 백로그** — 스토리지·데이터 층이라 화면 작업과 분리.
- **첫 화면 카드 eager 지정은 백로그** — LCP 경고가 뜨지만 그리드 첫 행이 뷰포트마다 달라 후보가 고정되지 않음. 실사용 체감이 이미 충분해 유보.
