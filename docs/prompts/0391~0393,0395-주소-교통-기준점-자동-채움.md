## 1. 한 줄 요약

"주소가 어떤 스팟에는 나오고 어떤 스팟에는 안 나온다"는 관찰에서 출발해, 채우는 로직이 이미 있는지 데이터로 확인하고 없는 쪽(주소)만 신설한 뒤, 작성 중에 즉시 보이도록 배선했다.

## 2. 왜 / 목적 / 이유

**왜(문제)** — 스팟 시트에 주소와 "교통 기준점"이 나오는 스팟과 안 나오는 스팟이 있었다. 롯데월드몰은 주소("서울특별시 송파구 올림픽로 300")와 교통("잠실역에서 도보 약 4분")이 둘 다 나오는데 다른 스팟은 둘 다 없었다.

**목적** — 어떤 경로로 추가하든 주소와 교통이 채워지고, 등록 후가 아니라 **작성 중에** 보이는 상태.

**이유** — 새로 만들기 전에 기존 로직을 확인하기로 했다. 값이 나오는 스팟이 있다는 것은 채우는 코드가 어딘가 있고 경로에 따라 갈린다는 뜻이기 때문이다. 조사 결과 예상과 달랐고, 그 결과가 처방을 완전히 바꿨다(§4 참조).

작성 중 노출을 택한 이유는 요청이 "내용 작성시 주소도 들어갈 수 있도록"이었기 때문이다. 교통처럼 저장 시 서버에서 채우면 등록 후 상세에서야 보인다.

## 4. 코드 작성 & 수정

### 조사 결과 — 예상이 뒤집힌 지점

"주소 로직이 이미 있으니 갖다 쓰자"는 전제로 시작했으나, 실제로는 **교통에만 있고 주소에는 없었다.**

| | 값을 만드는 곳 | user 스팟 채움률 |
|---|---|---|
| 교통 | 저장 시 `actions.ts`에서 `findNearestTransit`이 좌표만으로 자동 계산 | 15/18 (83%) |
| 주소 | 시딩 스크립트(`seed-spots.ts`)뿐 | **0/18 (0%)** |

*(채움률은 조사 시점 프로덕션 DB 집계로, 코드에는 남아 있지 않다. seed 스팟은 45개 주소 100%.)*

주소는 "있는데 안 타는" 것이 아니라 **싣는 코드가 없었다.** `addSpot(name, lng, lat)`에 `address` 파라미터가 없어서, 검색으로 추가할 때 `place.address`를 손에 들고도 버리고 있었다.

교통 null 3건도 함수 실패가 아니었다. 자동 계산이 0178(2026-07-13)에 도입됐는데 그 3개는 5/31·6/18·7/2 생성이라 코드가 없던 시절 저장된 것이고, 백필(0191)은 시드 45개만 대상이라 이들을 건드리지 않았다. 그 좌표로 실제 호출하면 전부 정상값이 나온다("서울특별시청이 시청역 바로 위인데 null"이라는 조합 자체가 실패가 아니라 미실행의 증거였다).

### 0391 — 검색 경로 배선

스키마·`LocalSpot`·payload·`actions.ts` 저장은 이미 `address`를 지원하고 있었다. 빠진 것은 `addSpot`이 값을 받아 싣는 것 하나뿐이라 변경 범위가 작았다.

```ts
// address는 optional — 검색 경로만 전달, 찍기·재사용은 미전달(기존 동작)
function addSpot(name: string, lng: number, lat: number, address?: string | null)
```

표기 체계도 통일했다. 카카오 `address_name`은 지번인데 시드 주소는 도로명이라 같은 자리에 두 체계가 섞인다.

```ts
// 도로명 우선, 빈 문자열이면 || 로 지번 폴백
address: d.road_address_name || d.address_name
```

도로명은 그때까지 아예 버려지고 있었다 — `KakaoDoc` 타입에 `road_address_name`이 없어 매핑에서 참조조차 안 됐다. 검색 목록과 시트가 같은 `PlaceResult.address`를 소비하므로 소스 한 곳만 고쳐 양쪽이 일치했다.

### 0392 — 좌표 한 왕복으로 주소·교통

신규 2파일.

| 파일 | 역할 |
|---|---|
| `lib/spot/reverseGeocode.ts` | server-only. 카카오 `coord2address`, 도로명 우선 지번 폴백, 실패 null |
| `lib/spot/spotMeta.ts` | `'use server'` `getSpotMeta` — 인증 가드 + 좌표 검증 + `Promise.all`로 역지오코딩·`findNearestTransit` 병렬, 각 실패 독립 null |

세 가지 판단:

| 쟁점 | 결정 | 근거 |
|---|---|---|
| `requireUser` 공용 추출 | 보류, 인라인 가드 | 테스트 있는 `nearby`와 값반환형 `searchPlaces`까지 마이그레이션해야 함. 호출부 1개만 쓰는 반쪽 추출은 오히려 나쁨 |
| 검색 경로 역지오코딩 | 스킵(`includeAddress` 옵션) | `place.address`가 POI에 붙은 실제 주소라 좌표를 되돌려 얻는 것보다 정확 |
| 재사용 경로 | `nearby` select에 4필드 추가 | 공유 Spot의 저장값이 정본. 재계산은 drift 위험 |

리뷰에서 두 가지를 고쳤다.

```ts
// ① 하드코딩 false면 주소 빈 POI에서 폴백이 사라진다
void fetchAndApplyMeta(id, lat, lng, !place.address);
// 짝으로 병합도 ?? 가 아니라 || — 빈 문자열도 폴백돼야 성립
address: s.address || meta.address
```

```ts
// ② 폐기 가드 — 삭제됐거나 재사용으로 전환된 스팟에는 적용하지 않는다.
// 찍기 → 인플라이트 → chooser에서 재사용 선택 → 응답 도착 순서에서
// 역지오코딩이 공유 Spot 정본을 덮는 것을 막는다.
if (!target || target.reusedSpotId) return;
```

실 API로 검증했다: 롯데월드몰 → "올림픽로 300"(시드 주소와 문자 그대로 일치), 서울시청 → "세종대로 110", 바다 좌표 → null(graceful).

### 0393 — 편집 폼 렌더

실기기에서 데이터는 도착하는데 편집 폼에만 안 보였다. 서울특별시청(DB상 교통 null)을 검색으로 추가했더니 보기 팝업에 "시청역에서 도보 약 4분"이 떴다 — `getSpotMeta`가 새로 채운 값이므로 데이터 경로는 정상이라는 증거였다.

원인은 렌더 누락이었다. 교통 블록의 게이트에 `!isEditing`이 걸려 있었다.

```diff
- {!isEditing && spot.nearestStation && spot.transitMinutes != null && (
+ {spot.nearestStation && spot.transitMinutes != null && (
```

게이트에서 `!isEditing &&`만 걷어낸 한 줄이다. (이 블록이 삼항으로 바뀌는 것은 0395에서 `metaPending` 대기 표시를 넣으면서다.)

편집용 블록을 따로 만들지 않았다. 마크업을 이중화하면 두 화면이 갈릴 수 있고, 게이트 완화는 보기 모드 렌더 결과를 바이트 단위로 바꾸지 않는다.

### 0395 — 찍기 경로 레이스

찍기만 전부 비고 검색은 주소만 뜨는 상태였다. 두 증상이 하나의 원인으로 설명된다.

```
addSpot → fetchAndApplyMeta 발사(병렬) → await findNearbySpots
→ 메타 도착, applySpotMeta가 localSpots에 병합
   (이 시점 activeSpot이 아직 null → 함수형 패치는 no-op)
→ setActiveSpot(리터럴 객체)  ← 메타 없는 객체로 확정
→ 시트는 activeSpot을 렌더 → 누락
```

검색은 리터럴에 `place.address`가 들어 있어 주소만 떴고, 찍기는 baseline 주소조차 없어 전무했다.

```ts
// 리터럴로 덮지 말고 최신 목록에서 세팅 — 도착 순서 양쪽 커버
setActiveSpot(
  localSpotsRef.current.find(s => s.id === id)
    ?? { id, name: '', lat, lng, order: localSpots.length + 1 }
);
```

같은 수정을 찍기(`addSpotFromMapRef`)와 검색(`handlePlaceSelect`) 양쪽에 적용했다. 검색 경로는 리터럴에 `place.address`가 있어 증상이 가벼웠을 뿐 같은 레이스를 갖고 있었고, 데스크톱 찍기에도 있던 잠재 버그가 함께 교정됐다.

대기 표시는 `metaPendingIds: Set<string>`으로 관리하고 `finally`에서 제거했다 — 값 도착·null 확정·실패 모두 대기 종료여야 영구 "확인 중"이 남지 않는다.

**전제 정정** — 이 작업의 배경에 "찍기가 `findNearbySpots`를 await한 뒤 `getSpotMeta`를 부른다(직렬)"고 적었으나, 실제 코드는 이미 `void fetchAndApplyMeta`로 await 전에 발사하는 병렬 구조였다. 병렬화 수정은 불필요했고 코드 확인이 전제를 뒤집었다. 커밋 메시지의 "조회 속도 개선"은 실제 변경이 아니라 확인 결과에 해당한다.

## 5. 결과 / 배운점

### 결과

- 검색·찍기 어느 경로로 추가해도 작성 중 시트에 주소와 교통 기준점이 표시된다. 실기기 확인 완료(광화문 "서울 종로구 사직로 161" / "경복궁역에서 도보 약 5분").
- 주소 표기가 도로명으로 통일됐다.
- 조회 중에는 "확인 중"이 표시되고, 값이 오거나 없음이 확정되면 사라진다.
- `getSpotMeta` 실측: 도심 약 77ms(지하철 1콜), 외곽 약 120ms(지하철 miss → 기차역 2콜).

### 배운점

- **"이미 있는 로직을 갖다 쓰자"는 전제부터 확인한다.** 값이 나오는 스팟이 있다는 관찰은 맞았지만, 결론은 정반대였다 — 교통에는 있고 주소에는 없었다. 실데이터 통계(seed 100% vs user 0%)를 갈라 보지 않았다면 잘못된 처방으로 갔다.
- **"실패"와 "미실행"은 다르다.** 교통 null 3건을 API 실패나 캐스케이드 결함으로 의심했으나, 기능 도입 이전에 저장된 데이터였다. 그 좌표로 실제 호출해보는 것이 판정을 갈랐다. 서울특별시청이 시청역 바로 위인데 null이라는 조합 자체가 단서였다.
- **두 증상이 하나의 원인으로 설명되면 그게 근본 원인이다.** "찍기는 전무 / 검색은 주소만"이라는 비대칭이 `setActiveSpot` 리터럴 하나로 설명됐다. 증상별로 따로 고쳤다면 각각에 덧대는 수정이 됐을 것이다.
- **비동기 응답을 상태에 병합할 때는 폐기 조건을 먼저 정한다.** 삭제됐거나 다른 것으로 전환된 대상에 늦게 온 응답을 적용하면, 앞서 정한 원칙("공유 Spot 저장값이 정본")이 그 경로에서만 조용히 깨진다.
- **`??`와 `||`는 폴백 의미가 다르다.** 빈 문자열을 유효값으로 볼지 아닐지에 따라 갈리며, 짝이 되는 두 지점을 함께 고쳐야 폴백이 성립한다.
- **UX 판단은 실기기가 뒤집을 수 있다.** 0392에서 "값이 오면 나타나는 것으로 충분"으로 판단했으나 실기기에서 느리게 느껴져 0395에서 대기 표시를 넣었다. 서버가 빠른 것(77ms)과 체감이 빠른 것은 다르다 — 차이는 모바일 RTT였다.

### 남은 것 / 후속

- 기존 user 스팟 18개 주소 백필 — `backfill-transit.ts`(0191) 선례대로 별건 스크립트.
- `requireUser()` 공용 추출은 계속 보류 중.
- 0391 커밋이 남긴 `// 0391: 검색 주소(지번, address_name)` 주석은 같은 커밋에서 도로명 우선으로 바꾼 것과 모순이었다. 0392에서 "도로명 우선"으로 정정됐다 — 한 커밋 안에서 코드를 바꾸면 그 코드를 설명하던 주석도 같이 봐야 한다는 사례.
- `getSpotMeta` 실측치(도심 77ms / 외곽 120ms)와 채움률은 조사 시점 측정으로, 코드에는 남아 있지 않다.
