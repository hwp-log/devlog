## 1. 한 줄 요약

마이페이지(`/mypage`)를 신규로 만들어, 본인 이메일은 읽기 전용으로 표시하고 닉네임은 수정할 수 있게 했다. 닉네임 수정 액션은 서버에서 본인(user.id)만 대상으로 고정하고, 길이 검증을 클라·서버 양쪽에 뒀다. 진입은 헤더 프로필 드롭다운의 MyPage 링크로 연결했다.

---

## 2. 왜 / 목적 / 이유

### 이메일은 표시만, 닉네임은 수정 열기

- 왜: 이메일은 Supabase Auth의 로그인 식별자(identifier)라 단순 프로필 값이 아니다. 바꾸려면 새 주소 확인 메일·소유권 검증 같은 인증 플로우가 필요하고, 잘못 건드리면 로그인 자체가 막힐 수 있다. 반면 닉네임은 표시용 이름이라 입력값을 저장하면 끝이고 계정에 영향이 없다.
- 목적: 한 화면에서 이메일은 "이 계정이 누구인지" 확인용으로 보여주고, 닉네임은 가볍게 바꿀 수 있는 상태.
- 이유: 이메일은 `<p>{email}</p>` 읽기 전용으로 두고, 닉네임만 입력·저장 폼을 열었다. 이메일 수정은 인증 플로우가 필요한 별도의 큰 작업이라 이번 범위에서 제외했다. 0093에서 이메일을 공개 피드 payload에서 뺀 PII 보호의 연장선 — 0093은 타인 이메일 노출 차단이었고, 0100은 본인에게만 표시하되(공개 아님) 수정은 막은 것. "이메일은 민감 식별자"라는 같은 원칙이 양쪽을 관통한다.

### 닉네임 수정은 본인(user.id)만

- 왜: 닉네임 값과 함께 user id를 클라가 보내게 하면, 악의적 클라이언트가 다른 사람 id를 넣어 타인 닉네임을 바꿀 수 있다.
- 목적: 클라가 무엇을 보내든 본인 닉네임만 바뀌는 상태.
- 이유: 액션은 nickname 값만 인자로 받고, 수정 대상은 서버에서 세션의 `where { id: user.id }`로 고정했다. 클라가 타인 id를 주입할 자리 자체가 없다. 0094 togglePlanPublicAction의 본인 검증 패턴 그대로.

### 길이 검증 클라·서버 이중

- 왜: 클라 검증만 두면 개발자도구로 우회해 빈 값이나 과도하게 긴 값을 보낼 수 있다.
- 목적: 빈 값·공백·21자 이상이 어떤 경로로도 저장되지 않는 상태.
- 이유: 클라 input에 `maxLength={20}`로 입력을 1차 제한하고, 서버 액션에서 `trim()` 후 0자 거부·20자 초과 거부로 2차 검증한다. 클라는 사용성(즉시 막힘), 서버는 신뢰 경계(우회 차단)를 담당한다. 이 빈 값 거부가 0099의 NOT NULL과 맞물려, 닉네임이 어느 경로로도 비지 않게 이중으로 보장된다.

### 신규: `app/(protected)/mypage/NicknameForm.tsx` (client)

이메일 읽기 전용, 닉네임 입력·저장. input에 `maxLength={20}`로 1차 제한.

```tsx
// 이메일: <p>{email}</p> (읽기 전용)
// 닉네임: <input maxLength={20} ... /> + 저장 버튼
// 저장 시 updateNicknameAction(nickname) 호출
```

### 신규: `app/(protected)/mypage/actions.ts`

본인만 수정 + 서버 길이 검증.

```ts
// app/(protected)/mypage/actions.ts (신규)
'use server';

export async function updateNicknameAction(nickname: string) {
  const user = await getUser();
  if (!user) return;

  const trimmed = nickname.trim();
  if (trimmed.length === 0) return { error: '닉네임을 입력해주세요' };
  if (trimmed.length > 20) return { error: '닉네임은 20자 이하' };

  await prisma.user.update({
    where: { id: user.id },        // 본인만 — 클라가 타인 id 주입 불가
    data: { nickname: trimmed },
  });

  revalidatePath('/mypage');
}
```

## 5. 결과 / 배운점

- 검증 통과: 드롭다운 MyPage → /mypage 진입, 이메일 표시(수정 불가), 닉네임 변경·저장 후 새로고침해도 유지, 빈 값/공백·21자 이상 거부, 타인 닉네임 수정 불가(서버 where 고정).
- 배운점 1: 같은 화면에 나란히 있는 값이라도 수정의 무게는 다르다. 닉네임은 표시용이라 입력값 저장이면 끝이지만, 이메일은 로그인 식별자라 수정에 인증 플로우가 필요하다. "표시"와 "수정"의 비용 차이를 인식해, 이번엔 닉네임만 수정을 열고 이메일은 표시에 그쳤다.
- 배운점 2: 검증은 클라(사용성)와 서버(신뢰 경계) 양쪽에 둔다. 클라 maxLength는 사용자 편의용이고, 우회 가능하므로 서버 trim·길이 검사가 진짜 방어선이다. 수정 대상도 클라 입력이 아니라 서버 세션의 user.id로 고정해 권한 경계를 코드 구조로 막았다.
- 배운점 3: 0099의 NOT NULL과 0100의 빈 값 거부가 맞물려 닉네임이 어느 경로로도 비지 않는다. 데이터 구조(0099)와 입력 검증(0100)이 같은 보장을 두 겹으로 만든다.
