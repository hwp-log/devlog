## 1. 한 줄 요약

모바일 대응의 첫 단계로 데스크톱 전용 헤더 네비를 하단 탭바로 전환했다. 햄버거 드로어를 검토했다가 발견성 데이터를 근거로 기각했고, 탭 개수 고정을 위해 Admin 링크를 아바타 드롭다운으로 먼저 이동(0151)한 뒤 탭바를 도입(0152)했다.

## 2. 왜 / 목적 / 이유

### 결정 1: 햄버거 드로어 기각, 하단 탭바 채택

- **왜 (문제):** 헤더 네비가 데스크톱 전용 flex 한 줄 배치였다. 모바일(390px)에서 링크 3개 + Write 버튼 + 로고 + 아바타가 한 줄에 들어가지 못해 깨졌다. 모바일 네비 패턴이 필요했다.
- **목적 (목표 상태):** 모바일 사용자가 주요 화면(Story / SpotFinder / PlanFinder / Write) 사이를 한 손으로, 배우지 않고 이동할 수 있는 상태.
- **이유 (채택 근거 / 비교):**
  1. **발견성.** 햄버거처럼 숨긴 메뉴는 실제 사용률이 낮은데 그 안에 중요한 목적지가 들어간다. NN Group 조사 기준으로 숨긴 메뉴는 작업 완료율을 약 21% 낮춘다 — "보이지 않으면 잊는다". 드로어 기각은 취향이 아니라 측정된 비용 때문이다.
  2. **엄지 도달성.** 화면은 길어지는데 엄지 도달 범위는 그대로다. 주요 목적지는 엄지가 닿는 하단에 두는 것이 원칙이고, 상단 햄버거는 물리적으로 가장 먼 위치다.
  3. **조건 분기.** 포탈처럼 항목이 많으면 드로어가 맞다. Dotrip은 최상위 목적지가 4개로 적고 고정이라 탭바 조건에 맞았다.
  4. **디자인 언어 정합.** 기존 Liquid Glass(`glass-header`) 미학을 하단으로 연장하는 것이라 새 패턴 도입 비용이 없다.
- **감수한 비용:** SpotFinder가 `calc(100vh-200px)`로 뷰포트 높이를 쓰고 있어, 탭바 도입 시 이 계산의 재조정이 필요하다는 것을 알고 진행했다 (→ 0153에서 처리). 참고: 최초에는 구현 비용이 낮은 드로어를 추천받았으나, "LLM 추천은 평균으로 회귀해 모든 포트폴리오가 비슷해진다"는 문제의식으로 최신 트렌드를 web_search로 재검증했고, 검색 결과가 추천을 뒤집었다.

### 결정 2: Admin 링크를 탭이 아닌 아바타 드롭다운으로 (0151 선행)

- **왜:** 탭바는 사용자마다 같은 개수의 슬롯을 유지해야 레이아웃이 안정된다. Admin은 관리자에게만 조건부 노출되는 링크라 탭에 넣으면 관리자/일반 사용자 간 탭 개수가 달라진다.
- **목적:** 탭 항목을 4개로 고정할 수 있는 상태.
- **이유:** Admin은 사용 빈도가 낮고 권한 기반 항목이라 성격상 계정 메뉴(아바타 드롭다운)에 속한다. 데스크톱에도 동일 적용해 모바일/데스크톱 구조를 통일했다. 권한 로직(layout 가드, requireAdmin)은 무변경 — 링크 노출 위치만 이동이므로 검수 등급 ★★로 진행했다.

### 결정 3: 4번째 탭은 MyPage가 아닌 Write

- **왜:** 탭 후보가 Story / SpotFinder / PlanFinder + 1이었다.
- **이유:** Write는 서비스의 핵심 행동이고, MyPage는 아바타 드롭다운에 이미 있다. FAB(떠 있는 버튼)가 지고 주요 행동을 내비 바 안에 통합하는 것이 현재 방향이기도 하다.

### 결정 4: /story vs /story/new 활성 판정 분기

- **왜:** Write 탭의 href가 `/story/new`인데 Story 탭이 `startsWith('/story')`로 판정하면 두 탭이 동시에 활성이 된다.
- **이유:** CC가 plan 단계에서 이 겹침을 스스로 발견해 명시 분기를 제안했다. 프롬프트에 없던 케이스를 plan 검토에서 잡은 사례.

## 4. 작성 및 수정한 코드

### BottomTabBar 신규 — 탭 배열과 활성 판정

```tsx
// app/(protected)/_components/BottomTabBar.tsx
const TABS = [
  { href: '/story', label: 'Story', Icon: BookOpen },
  { href: '/spot-finder', label: 'SpotFinder', Icon: Map },
  { href: '/plan-finder', label: 'PlanFinder', Icon: Compass },
  { href: '/story/new', label: 'Write', Icon: PenSquare },
] as const;

function isActive(href: string) {
  if (href === '/story/new') return pathname === '/story/new';
  if (href === '/story') return pathname.startsWith('/story') && pathname !== '/story/new';
  return pathname.startsWith(href);
}
```

### BottomTabBar — 컨테이너 (Liquid Glass + safe-area)

```tsx
// app/(protected)/_components/BottomTabBar.tsx
<div
  className="fixed bottom-0 left-0 right-0 z-40 md:hidden glass-header border-t border-slate-200/50"
  style={{ paddingBottom: 'env(safe-area-inset-bottom)' }}
>
  <nav aria-label="주요 메뉴" className="flex items-stretch h-14">
```

- `glass-header`는 border-bottom만 정의된 클래스라 탭바용 상단 경계(`border-t`)를 별도로 얹었다.
- z-40: 헤더(z-10)보다 위.

### BottomTabBar — 탭 항목

```tsx
// app/(protected)/_components/BottomTabBar.tsx
<Link
  key={href}
  href={href}
  aria-current={active ? 'page' : undefined}
  className={`flex-1 flex flex-col items-center justify-center gap-0.5 transition-colors ${
    active ? 'text-[#1A1A1A] font-semibold' : 'text-slate-500 hover:text-slate-800'
  }`}
>
  <Icon size={20} strokeWidth={active ? 2.25 : 1.75} />
  <span className="text-[10px] leading-none">{label}</span>
</Link>
```

- 각 탭이 `flex-1`로 균등 분할되고 세로 전체(h-14 + safe-area)가 터치 영역이라 44px 터치 타겟을 충족한다.

### UserDropdown — Admin 조건부 항목 (0151)

```tsx
// app/(protected)/_components/UserDropdown.tsx
{isAdmin && (
```

### layout 두 곳 — 탭바 렌더와 본문 여백

```tsx
// app/(protected)/layout.tsx — protected라 user 보장, 무조건 렌더
<main className="max-w-7xl mx-auto px-6 pt-8 pb-24 md:pb-8">
  {children}

<BottomTabBar />
```

```tsx
// app/story/layout.tsx — 비로그인 접근 가능 페이지라 user 조건부
```

## 5. 결과 / 배운 점

- **결과:** 390px에서 탭바 4항목 노출·이동·활성 표시 정상. 데스크톱 회귀 없음. /story(별도 layout)와 (protected) 페이지 모두 적용, 비로그인 시 탭바 미노출.
- **배운 점:**
  1. **표준 패턴 채택은 실력 부족이 아니라 관례가 왜 관례가 됐는지 아는 것이다.** 사용자는 다른 앱에서 이미 "하단 탭 = 이동"이라는 학습 비용을 지불했다. 여기서 독창성을 부리면 창의가 아니라 마찰이 된다. 차별화는 구조(뼈대)가 아니라 도메인과 디테일(살)에서 한다.
  2. **AI 추천은 평균으로 회귀한다 — 근거를 요구하면 뒤집힌다.** 최초 추천(드로어)은 구현 비용 기준으로는 합리적이었지만, web_search 재검증에서 발견성 데이터가 나오며 뒤집혔다. 도구의 첫 답을 결론이 아니라 가설로 다루는 것.
  3. **조건부 항목은 고정 슬롯 UI의 적이다.** 탭바 도입 전에 Admin을 옮긴 것(0151 선행)처럼, 구조 변경은 그 구조가 요구하는 불변 조건을 먼저 확보하고 들어간다.
  4. **plan 검토는 프롬프트의 빈틈을 잡는다.** /story vs /story/new 활성 겹침은 프롬프트에 없던 케이스인데 CC가 plan에서 발견했다. plan 단계를 형식이 아니라 검토로 쓰는 이유.
