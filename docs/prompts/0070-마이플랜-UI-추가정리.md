# 0070 회고: 마이플랜 UI 추가정리 (편집기·상세 통일)

- 작성일: 2026-06-04
- 소요: 약 2.5시간
- 관련 커밋: `feat: 0070 마이플랜 UI 추가정리 (카테고리-아이콘 반영, 항공편-검색 및 정산금액에 반영)`

## 한 줄 요약

작성/수정 편집기와 상세 페이지에 두 벌씩 있던 항공편 카드·비용 섹션을 공용 컴포넌트 하나로 모으고, 항공편 검색 폼을 결과 카드와 같은 모양(스켈레톤 카드)으로 바꿔 두 화면의 UI를 통일했다.

## 왜 / 목적 / 이유

### 1. FlightLeg·CostSection 공용 컴포넌트 추출

- 왜: 항공편 카드와 비용 섹션이 상세 페이지와 편집기에 한 벌씩, 총 두 벌 있었다. 0068에서 시간 표시 버그를 고칠 때 상세 쪽만 고쳐졌고, 편집기 쪽 복사본은 그대로 남아 21:10 항공편이 12:10으로 표시되는 버그가 오늘 발견됐다. 코드가 두 곳에 있으면 수정할 때 두 곳을 모두 기억해야 하는데, 사람은 한쪽을 잊는다.
- 목적: 정의는 한 곳(`_components/FlightLeg.tsx`, `_components/CostSection.tsx`), 사용은 여러 곳(import). 한 번 고치면 상세와 편집기에 동시에 반영되는 상태.
- 이유: 항공편 데이터가 두 형태(DB는 Date 객체, 검색 API는 ISO 문자열)로 들어오므로, 컴포넌트가 받는 정규화 타입 `FlightLegData`를 정의하고 양쪽에서 변환하는 컨버터 2개(`planFlightToLegData`, `flightOfferToLegData`)를 두는 방식을 채택했다. 컴포넌트는 입력 형태를 모르고, 호출부가 변환을 책임진다.

### 2. 시간 표시의 시간대 고정 (UTC 함정 변종)

- 왜: 0068에서 `toISOString().slice(11, 16)`(UTC 시각을 그대로 자름)을 `toLocaleTimeString('ko-KR')`로 고쳤지만, 이 함수는 시간대를 지정하지 않으면 실행 환경의 시간대를 쓴다. 내 맥은 KST라 정상으로 보였지만, Vercel 서버는 UTC라 프로덕션에서만 9시간 어긋날 수 있는 상태였다.
- 목적: 로컬과 프로덕션에서 같은 시각이 표시되는 상태.
- 이유: `timeZone: 'Asia/Seoul'`을 명시했다. 현재 검색 대상이 한국·일본 노선이고 두 나라 모두 UTC+9라 단일 시간대 고정으로 정확하다.

### 3. 스켈레톤 카드 검색 폼

- 왜: 검색 폼(입력창 나열)과 선택 후 표시되는 항공편 카드의 모양이 완전히 달라, 검색 전후로 화면이 튀어 보였다.
- 목적: 검색 전 화면이 결과 화면의 예고편이 되는 상태. 사용자가 입력하는 자리와 결과가 채워질 자리가 같다.
- 이유: 결과 카드(FlightLeg)와 같은 4열 골격에 입력만 심었다. 출발·도착 IATA 자리는 입력 필드, 시간·소요·편명·가격 자리는 '?' 표시. 왕복이면 오는편 카드가 가는편 입력의 역방향으로 자동 미러된다(입력 두 번 받지 않음). 표시용 FlightLeg는 손대지 않고 편집기 전용 SkeletonCard를 두되, 공항명·아이콘은 FlightLeg에서 export해 재사용했다.

### 4. 입력 보조 정리 (배지·날짜 강조·통화 제거)

- 왜: Day 항목 입력 줄에 카테고리 시각 피드백이 없고, 항공 검색 시 날짜가 비면 문구만 떠서 어느 필드를 채울지 시선 유도가 없었다. 통화 선택은 항공 가격이 KRW 고정인 것과 어긋났다.
- 목적: 입력 화면에서도 상세 화면과 같은 카테고리 색·아이콘이 보이고, 비어 있는 필드가 직접 강조되는 상태. 통화는 KRW 하나로 단순한 상태.
- 이유: 배지는 타임라인과 같은 CATEGORY_ICON을 재사용했다(미선택은 빈 원, 선택 시 색 전환). 날짜 강조는 IATA 입력 상태를 부모로 끌어올리지 않고, "날짜 누락 여부"만 콜백으로 부모에 알려 부모가 자기 소유의 날짜 input에 빨간 테두리를 적용하는 방식을 채택했다 — 0068의 검색 상태 분리 설계를 유지하면서 신호만 전달한다. 통화는 UI에서 제거하고 'KRW' 고정값으로 저장한다(DB 컬럼은 유지).

## 코드 작성 & 수정

정규화 타입과 컨버터 — 두 데이터 형태를 한 컴포넌트로 모으는 접점:

```typescript
// app/(protected)/my-plan/_components/FlightLeg.tsx
export type FlightSegmentData = {
  origin: string; destination: string
  departsAt: string; arrivesAt: string  // ISO 문자열로 통일
  airline: string; flightNo: string
}
export type FlightLegData = {
  tripType: 'ONE_WAY' | 'ROUND_TRIP'
  totalAmount: number
  out: FlightSegmentData
  ret?: FlightSegmentData
}

// 상세에서: PlanFlight(Date 객체) → FlightLegData
export function planFlightToLegData(f: PlanFlight): FlightLegData
// 편집기에서: FlightOffer(ISO 문자열) → FlightLegData
export function flightOfferToLegData(f: FlightOffer): FlightLegData
```

시간 표시 — 실행 환경과 무관하게 한국 시간으로 고정:

```typescript
// app/(protected)/my-plan/_components/FlightLeg.tsx
function fmtTime(iso: string) {
  return new Date(iso).toLocaleTimeString('ko-KR', {
    hour: '2-digit',
    minute: '2-digit',
    hour12: false,
    timeZone: 'Asia/Seoul', // 미지정 시 실행 환경 시간대 사용 — Vercel 서버는 UTC
  });
}
```

날짜 누락 신호 — IATA 상태는 검색 컴포넌트 내부에 유지하고 신호만 부모로:

```typescript
// app/(protected)/my-plan/new/FlightSearchSection.tsx
const bothIata = showForm && originIata.length === 3 && destIata.length === 3;
const startMissing = bothIata && !startDate;
const endMissing = bothIata && tripType === 'ROUND_TRIP' && !endDate;

useEffect(() => {
  onDateMissingChange?.({ start: startMissing, end: endMissing });
}, [startMissing, endMissing, onDateMissingChange]);
```

```tsx

className={`${INPUT_CLASS}${dateMissing.start ? ' !border-red-400 focus:!border-red-400' : ''}`}
```

## 결과 / 배운점

- 작성·수정·상세 세 화면의 항공편 카드와 비용 섹션이 같은 컴포넌트 하나를 사용한다. 검색 폼은 결과 카드와 같은 골격이라 검색 전후로 화면이 튀지 않는다.
- **정의는 한 곳, 사용은 여러 곳.** 같은 코드가 두 곳에 있으면 수정할 때 두 곳을 모두 기억해야 하고, 사람은 한쪽을 잊는다. 시간 포맷 함수가 두 벌이라 시간대 버그를 한쪽만 고친 것이 실제 사례. import는 어디서든 해도 되지만, 정의(원본)를 복제하는 것이 문제다.
- **시간대 함정은 한 번 고쳐도 변종이 남는다.** `toISOString().slice()`는 UTC를 그대로 자르고, `toLocaleTimeString()`은 시간대 미지정 시 실행 환경을 따른다(서버는 UTC). 시간 표시 코드는 "어느 시간대 기준인가"를 항상 명시하는 것으로 검수 항목화했다.
- **Tailwind v4의 important 표기는 클래스 끝에 붙는다.** v3의 `!border-red-400`이 v4에서는 `border-red-400!`. 프레임워크 버전이 올라가면 익숙한 문법도 검색으로 확인이 필요하다.
- UI 다듬기는 화면 단위로 잘게 나눠 한 줄 피드백으로 도는 것이 효율적이었다. 정렬 밀림, 오해될 문구, 빈 결과 안내처럼 작은 단위로 가져오면 plan 없이 즉시 수정으로 처리되고, 끝은 커밋으로 정의한다.
- RapidAPI 무료 쿼터(월 20건)는 개발 테스트가 소모한다는 것을 확인하고 PRO($9.99/월, 10,600건)로 전환했다. 외부 API 기능은 호출량 관리도 기능의 일부다.
