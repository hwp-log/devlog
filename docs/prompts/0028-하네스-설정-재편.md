### b) 4단계 사이클 도입 (Naive 증강 코딩)

**왜**
기존 작업 흐름은 "Plan Mode → TDD → 검토 → 커밋"으로 작업이 무거웠고, 작은 기능 하나 추가하는 데도 같은 절차를 거쳐 속도가 느렸다. 따라서 기존 프로세스를 수정할 필요가 있었다.

**목적**
기존 프로세스의 수정 및 효율화.
아래는 수정한 프로세스임.

- 1차: 바이브 (작동 코드 작성 / Plan Mode X / 테스트 X)
- 2차: TDD-Green 작동 확인 (= 바이브 결과 검증)
- 3차: TDD 리팩토링 (필요시 작성 / Plan Mode 필수 / Red-Green-Refactor)
- 4차: PR + 멘토 리뷰
- 작업 본질별로 어디까지 진행할지 판단 가능 (= 단순 유틸은 1차에서 마감 / 비즈니스 로직은 4차까지)
- 위에 해당 작업 설명: 멘토 조언("Component 단위 atomic 커밋 + 빠른 바이브 구현")과 Kent Beck 증강 코딩("작동하는 코드의 리팩토링 필요시, RED, GREEN 테스트로 리팩토링 타겟팅을 한 뒤 진행") 작업 목적에 맞게 채용.

**위에 프로세스 채용 이유**
- 빠른 구현과 단계적 리팩토링을 통한 생산성 증대 및 품질 관리
- 단계별 진입/탈출 지점 명확화 → 오버 엔지니어링 함정 방지
- 검토 우선순위를 통해 작업 효율을 높이고자 함 - 등급제 도입 (자세한 내용은 아래 "c) 검토 우선순위 5등급 도입" 참조)

### c) 검토 우선순위 5등급 도입

**왜**
증강 코딩 본질로 AI가 생성한 코드를 검토할 때, 모든 코드를 같은 기준으로 검토하면 시간이 과도하게 소모됐다. 단순 import 추가나 타입 정의까지 줄 단위로 검토하면 진짜 중요한 비즈니스 로직 검토에 쓸 집중력이 분산됐다. 검토 강도에 등급을 매길 기준이 필요했다.

**목적**
코드 영역별로 검토 강도를 5등급으로 분리하여 집중력 배분 최적화.

- ★★★★★: 비즈니스 로직 / 보안 / 인증 / 결제 / 외부 API (= 줄 단위 + 의도 확인 필수)
- ★★★★: 데이터 무결성 / DB 변경 / 마이그레이션 (= 영향 범위 검토 필수)
- ★★★: 성능 / 아키텍처 / 상태 관리 구조 (= 구조 검토 필수)
- ★★: 단순 유틸 / 헬퍼 함수 (= 작동 확인만)
- ★: 보일러플레이트 / UI 디테일 / import / 타입 정의 (= 스킵 가능)

검토 본질:
- ★★★ 이상 = 필수 검토
- ★★ 이하 = 작동 확인 통과 시 OK

**이유**
- AI 생성 코드의 양이 늘어날수록 전수 검토는 비현실적 → 우선순위 기반 검토가 필수
- 등급 기준이 명확하면 Claude Code에 "이 코드는 ★★★★★ 영역이니 줄 단위로 검토해줘" 같은 지시 가능 → 하네스 본질 강화
- b) 4단계 사이클과 결합하여 작업 단위별 검토 깊이 결정 가능

### d) 회고 양식 경량화 (5섹션)

**왜**
기존 회고 양식(목적 / 고민 / 방법 / 용어 박스 / 배운점) 5단계는 작성 시 항목 간 구분이 모호했다. 특히 "고민"과 "방법"이 자주 섞이고, "용어 박스"는 회고 본질보다 학습 정리 본질에 가까워 흐름이 끊겼다. 작성 시간도 회고당 평균 1시간 이상 소요되어 부담이 컸다.

**목적**
회고 본질을 의사 결정 기록에 집중시키고 작성 부담을 줄임.

기존 → 변경:
- 목적 / 고민 / 방법 / 용어 박스 / 배운점 (= 5단계)
- → 한 줄 요약 / 왜·목적·이유 / 작성한 프롬프트 / 코드 작성 & 수정 / 결과·배운점 (= 5섹션 경량)

핵심 차이:
- "왜·목적·이유" 3분리 = 의사 결정 본질 명확화 (동기 / 도달할 상태 / 채택 근거)
- "작성한 프롬프트" = 증강 코딩 흐름 추적 가능
- "용어 박스" 제거 = 학습 정리는 기술 블로그에서 언급하기로..

**이유**
- 의사 결정 기록 = 미래의 나 + 면접관 모두에게 가치 있음
- 학습 정리 = 회고는 작업의 흐름을 작성하는 것이지 학습한 내용을 작성하는 것이 아니기 때문.

### e) DECISIONS.md 폐기

**왜**
기존 DECISIONS.md 파일은 각 기능별 결정 이유를 작성하고 있었다. 그러나 이미 `docs/prompts`에 회고를 통해 각 기능별 결정 이유를 충분히 알 수 있었고, 이를 DECISIONS.md에 정리해서 작업하는 것은 비효율적이라고 판단이 되었다. 따라서 이를 폐기하고 관련된 기능을 작업할 때 회고에 관련된 내용을 검색하는 방식으로 전환하기로 하였다.

**목적**
각 기능에 관련된 작업 및 개선을 할 때, 관련된 과거 회고를 검색하도록 구조를 바꾸기.

- 각 회고 마지막 "## 결정 (Decisions)" 섹션에 결정 기록
- DECISIONS.md 폐기 (= 단일 파일 X)
- 결정 검색 = `docs/prompts/`에서 회고 검색으로 Claude Code에 지시

폐기된 DECISIONS의 내용 처리 방법:
- `0000-초기-결정-정리.md` 신규 작성 (= 4/13 ~ 4/24 시점 14개 결정)
- 이외 초기 결정이 아닌 내용은 각 회고에 부분 반영으로 처리

**핵심 내용 발췌 — 도입부 (하네스 + 증강 코딩 정의)**:

```markdown
다음 두 가지 개념을 적용해 구성했다:

- **하네스(Harness)**: AI 에이전트의 자율 행동에 제약을 걸어
  예측 가능한 범위에서 작업하게 만드는 규칙 구조
- **증강 코딩(Augmented Coding, Naive)**: AI가 코드를 생성하되
  단계별로 사용자가 통제하는 협업 방식
  (바이브 → 검수 → 리팩토링 → 검수의 4단계 사이클)
```

**핵심 내용 발췌 — Build Cycle (4단계 사이클 표)**:

```markdown
| 묶음 | 단계 | 코드 상태 | 테스트 상태 | TDD? | 필수? |
|---|---|---|---|---|---|
| **전반부**: 바이브 + 검수 (필수) | 1차 | 작성 (바이브) | 없음 | X | 필수 |
|  | 2차 | 그대로 | TDD-Green 작동만 확인 | X | 필수 |
| **후반부**: 리팩토링 + 검수 (선택) | 3차 | 리팩토링 | 활용 + 추가 | O | 선택 |
|  | 4차 | PR | 검증 | - | 선택 |
```

**핵심 내용 발췌 — Review Priority (검토 우선순위 5등급)**:

```markdown
| 등급 | 범위 | 검토 깊이 |
|---|---|---|
| ★★★★★ | 비즈니스 로직 / 보안 / 인증 / 결제 / 외부 API | 줄 단위 검토 + 의도 확인 |
| ★★★★ | 데이터 무결성 / DB 변경 / 마이그레이션 | 영향 범위 검토 |
| ★★★ | 성능 / 아키텍처 / 상태 관리 구조 | 구조 검토 |
| ★★ | 단순 유틸 / 헬퍼 함수 | 테스트 통과 시 OK |
| ★ (스킵) | 보일러플레이트 / UI 디테일 / import / 타입 정의 | 스킵 가능 |
```

**의의**:

- ★★ 등급은 1차 바이브 + 2차 작동 확인까지만 진행하는 규칙 검증
- 이론(4단계 사이클 + 검토 우선순위 5등급) ↔ 실전 매칭 첫 케이스

**전체 코드**:

```typescript
// lib/util/formatRelativeTime.ts
export function formatRelativeTime(dateString: string): string {
  const now = Date.now();
  const past = new Date(dateString).getTime();
  const diffMs = now - past;

  const minutes = Math.floor(diffMs / (1000 * 60));
  const hours = Math.floor(diffMs / (1000 * 60 * 60));
  const days = Math.floor(diffMs / (1000 * 60 * 60 * 24));

  if (minutes < 1) return '방금 전';
  if (hours < 1) return `${minutes}분 전`;
  if (hours < 24) return `${hours}시간 전`;
  if (days < 7) return `${days}일 전`;

  const d = new Date(dateString);
  return `${d.getMonth() + 1}/${d.getDate()}`;
}
```

**작동 확인 케이스**:
- `minutes < 1` → "방금 전"
- `hours < 1` → "N분 전"
- `hours < 24` → "N시간 전" ✅
- `days < 7` → "N일 전" ✅
- 7일 이상 → "M/D" 형식 fallback
