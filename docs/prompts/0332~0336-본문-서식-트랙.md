## 1. 한 줄 요약

"본문만 구식 에디터로 쓴 느낌"이라는 판단에서 출발해, 서식 렌더 규칙 → 툴바 정리 → 새 글 프리필 → 발행 시 정리 → 양식 5종 팝오버까지 다섯 커밋으로 글쓰기 경험을 다시 짰다.

## 2. 왜 / 목적 / 이유

**왜(동기·문제)**
상세 화면을 보니 홈페이지 전반은 세련됐는데 본문만 낡아 보였다. 사용자가 `[분위기]` `[촬영지 정보]` 같은 **대괄호로 소제목을 흉내내고** 있었고, 그게 일반 본문 굵기로 렌더되고 있었다.

원인을 파보니 서식을 안 쓴 게 아니라 **써도 화면이 안 변하는 상태**였다. Tailwind 4.3 preflight가 `h1~h6` 크기·굵기를 `inherit`으로, `ol/ul` list-style을 `none`으로 리셋하고 있었고, `.tiptap-content`에 그걸 되돌리는 규칙이 없었다. DB상 h2·h3 사용이 0건이던 이유가 이걸로 설명된다.

**목적(목표 상태)**
쓰는 사람이 서식을 몰라도 구조 있는 글이 나오는 것. 그리고 그 글이 읽는 화면에서도 같은 모습으로 보이는 것.

**이유(채택 근거)**
구조화 필드(스키마 변경)는 범위에서 뺐다. 판단 근거는 이거다 — **예시 글 몇 개를 써두면 뒤에 오는 사람이 그걸 따라 쓴다.** 서식만 제공하고 잘 쓰든 대충 쓰든은 사용자 몫이고, 그건 통제할 영역이 아니다.

단계 순서는 의존성이 정했다. 1단계 렌더 규칙이 없으면 2단계 툴바 버튼을 만들어도 눌렀을 때 화면이 안 변한다.

## 5. 결과 / 교훈

다섯 커밋 전부 실화면 확인 후 푸시. 유닛 테스트는 0335에서 6종, 0336에서 추가.

**"안 변하는 게 정상"을 의심하기까지가 오래 걸렸다.** h2를 넣어도 화면이 그대로라 사용자가 대괄호를 쓴 건데, 그건 사용자 잘못이 아니라 CSS가 없어서였다. 사용자가 이상하게 쓰고 있으면 **먼저 도구를 의심하는 게 맞다.**

**테스트가 통과했는데 실화면만 터진 사례를 두 번 만났다.** 0336의 Placeholder 데코레이션 소실이 대표적이다 — 스톡 확장이 뷰포트 범위 안 노드에만 데코를 붙이고 그 범위를 `doc.content.size` 변화 때만 재계산하는데, 같은 양식을 재적용하면 크기가 같아 재계산이 스킵되고 좌표가 한 점으로 붕괴했다. jsdom은 `getBoundingClientRect`가 0이라 전체 스캔으로 폴백해서 테스트에서는 절대 재현되지 않았다. **테스트 환경이 버그를 가릴 수 있다**는 걸 코드 주석으로 남겨뒀다.

**되돌릴 수 없는 작업에는 안전한 도구를 쓴다.** 0335에서 문자열 토크나이저 대신 jsdom을 택한 이유다. 실패하면 폼 에러가 아니라 본문 손실이고, 중첩 `blockquote > p` 경계에서 깨져도 감지할 방법이 없다. 런타임 의존성 승격 비용보다 정확성이 우선인 자리였다.

**방향이 두 번 뒤집혔다.** 조각 서식(촬영지 정보만/근처 볼거리만)은 실제 서비스 관행에 근거가 없어 폐기했고 — 네이버·티스토리 모두 템플릿을 통째로 불러온다 — 완결된 양식 5종으로 갔다. 도입부에 제목을 안 붙이기로 했던 것도 실화면에서 리듬이 어긋나 보여 뒤집었다. **둘 다 근거가 바뀌어서 뒤집은 것이라 번복이 아니다.** 다만 목업을 먼저 봤으면 더 빨랐을 결정이었다.

**남은 것** — 5단계(기존 글을 새 서식으로 다시 저장), 콜아웃 블록 신설, 양식 상수를 프리필 실텍스트 방식으로 개편. 백로그: `p.is-editor-empty:first-child` 죽은 규칙 정리, ToolbarButton 44px 터치 타겟, figcaption(v1.1 1순위).
