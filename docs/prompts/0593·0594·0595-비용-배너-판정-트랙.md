## 2. 왜 / 목적 / 이유

### 국면 ① 0593 — 목적은 정했는데 기준은 안 정했다

발단은 **축의 불일치**였다. 0592가 원본 링크를 비공개 한정으로 좁혔는데 배너는
`sourcePlanId`만 보고 떴다. 그래서 공개된 담은 플랜에서 **링크는 사라지고 배너는 남았다.**

여기서 확정된 것은 **배너의 목적**이다 — 출처 표시가 아니라 **담은 사람에게 확인을
요청하는 안내**다. 그리고 그 목적에서 근거를 하나 더 끌어냈다: 공개 시점에는
"원본 작성 시점의 금액입니다"라는 서술 자체가 **사실이 아니게 된다.** 확인하고 고친 뒤
공개했다면 그건 그 사람이 책임지는 금액이고, 안 고쳤더라도 그대로 두기로 한 판단이다.

목적은 옳았다. **그런데 그 목적에 맞는 기준을 따로 설계하지 않고, 눈에 띄던 축(공개 여부)을
그대로 썼다.** 0592가 방금 그 축으로 링크를 좁혔으니 배너도 같은 축이면 정합해 보였다.

### 국면 ② 0594 — 공개 여부는 금액이 낡았는지와 무관하다

**기준이 틀렸다.** 목적이 "확인하라"면 배너가 사라져야 하는 시점은 공개한 때가 아니라
**금액을 실제로 고쳤을 때**다. 공개 여부는 그 사실과 아무 관계가 없다 — 안 고치고 공개할
수도 있고, 고치고 비공개로 둘 수도 있다.

그래서 판정을 위한 사실을 새로 만들어야 했다. `MyPlan` 17개 필드 중 재사용 가능한 것은
없었고(후보 `isDraft`는 Boolean이라 금액을 담을 수 없다), 담은 시점의 비용 총액 스냅샷
`sourceCostTotal Int?`를 신설했다.

### 국면 ③ 0595 — 총액은 최종 상태만 본다

총액 대조는 **한 항목 +1만, 다른 항목 −1만**이면 합이 같아서, **실제로 고쳤는데 배너가
안 사라진다.** 0594 시점에 이미 알고 수용한 한계였고 다음 사이클에서 바로 닫혔다.

원인은 "중간에 무엇을 했는지가 최종 상태에서 지워지는 것"이다. git이 스냅샷이 아니라
커밋이라는 **이벤트**를 기록하는 것과 같은 이유로, "고쳤다"는 사실 자체를 남기는 방식
(`MyPlan.costEdited`)으로 바꿨다.

### 기각한 안들 — 왜 그것들이 아니었는가

결론의 근거는 채택한 안보다 기각한 안 쪽에 있다. **넷 다 같은 계열의 실패**다.

| 안 | 기각 사유 |
|---|---|
| **저장 한 번이면 끄기** | 확인만 하고 **안 고쳐도** 사라진다 — 배너가 아무 일도 안 한 게 된다 |
| **원본 플랜의 현재 총액과 비교** | `sourcePlanId`가 FK 없는 plain String(0103)이라 원본 삭제 시 판정 불가. 더 나쁜 건 **원본 주인이 자기 금액을 고치면 내가 아무것도 안 했는데 배너가 사라진다** |
| **항목별 `(day, order)` 튜플 해시** | **0588 드래그로 순서만 바꿔도** 배너가 사라진다 |
| **`updatedAt` 시각 비교** | `MyPlan`에 `updatedAt`이 없다. 있어도 "저장 한 번이면 끄기"와 같은 결함 |

여기에 **폼의 라이브 비교**가 하나 더 있다. 0594 계획 단계에서 CC가 제안했고
("금액을 고치는 즉시 배너가 사라지는 게 목적에 더 맞다") 사용자가 기각했다. 반례가 둘:

- ① 고쳤다가 되돌리면 배너가 **깜빡인다**
- ② 고치고 저장 없이 나갔다 다시 들어오면 사라졌던 배너가 **떠 있다** — 화면이 방금 한 말을 뒤집는다

둘 다 "저장 한 번이면 끄기"와 같은 계열이다. **판정 대상은 저장된 사실**이므로 판정 시점도
저장이어야 한다. 그래서 판정을 서버 컴포넌트 두 곳에서만 하고 화면에는 **불리언만**
내려보낸다 — 폼이 실수로 라이브 값과 비교할 수 없게 **구조로 막았다.**

### 0595 — "로그로 구별되어야 한다"

```
[검수 모드] 마이그레이션 전에 먼저 보고할 것:

- 기존 담긴 플랜 1건의 costEdited 백필값을 무엇으로 해야 하는지 판단 근거와 함께 제안
```

구분되지 않는다 — 실제로 그랬다(§4 검산 ②).

## 4. 코드 작성 & 수정

### 0593 — 두 화면의 조건 일치와 주석 정정

```tsx
{sourcePlanId && !isPublic && ( … )}
```

읽기 상세는 `isPublic`이 이미 prop으로 있었고(공개 토글용), 편집 폼은 없어서 추가했다.
`EditorState`가 아니라 **Props**로 둔 근거는 분명하다 — **공개 전환은 이 폼이 아니라
상세의 `PlanPublicToggle`이 한다.** 폼은 `isPublic`을 저장하지 않으므로 서버가 준 값을
그대로 쓰면 충분하다.

0580 주석의 구 문장은 이랬다.

> 조건은 sourcePlanId 유무 하나 — isOwner를 안 거는 이유는 담은 플랜을 나중에 공개로 돌리면
> **남에게도 같은 사실이 성립**하기 때문

"같은 사실이 성립한다"가 틀렸다. 공개 시점에는 그 금액이 원본 시점 값이 아니라
**공개한 사람이 책임지는 값**이다. 정정문에 그 논리를 그대로 적었다.

### 0594 — 스냅샷 신설·담기 기록·백필

마이그레이션은 **`ALTER TABLE`만** 담았다. 백필을 같은 파일에 넣으면 조건이 "그 시점의
데이터 상태"에 의존해 **새 환경에서 재생 시 담은 시점이 아니라 재생 시점 합계가 들어간다**
(사용자 지적). 구조 변경과 1회성 데이터 보정을 분리했다.

```sql
ALTER TABLE "my_plans" ADD COLUMN "source_cost_total" INTEGER;
```

1회성 백필은 커밋하지 않고 스크래치패드에서 실행했다. 담기 기록은 한 줄이다 —
`original.costs`가 이미 메모리에 있고 복사 루프가 행을 거르지 않아
**이 합 = 사본 `PlanCost` 합**이 성립한다.

```ts
// plan-finder/[id]/actions.ts:124
sourceCostTotal: original.costs.reduce((sum, c) => sum + c.amount, 0),
```

백필 재대조: 담긴 1건만 464,000, 담기 아닌 2건은 `null` 유지, NULL 잔여 0건.

### 0594 — 총액을 고른 근거 (그리고 그 근거가 0595에서 뒤집힌 자리)

상쇄 수정을 못 잡는 건 **알고 골랐다.** 근거는 **실패 방향이 안전**하다는 것이었다 —
못 잡으면 배너가 **남는다**(확인하라는 안내가 한 번 더). 반대 실패(안 고쳤는데 사라짐)보다
무해하다. 항목별 비교는 저장이 `deleteMany` + 전량 재생성이라 행 id 대응이 없고,
`(day, order)` 튜플 해시로 하면 0588 드래그와 충돌한다.

**이 논증은 그 자체로는 옳았다.** 틀린 건 "그러니 총액으로 충분하다"였다 —
안전한 실패 방향은 대역을 계속 쓸 이유가 아니라, **대역이 틀릴 때 덜 아프다는 것**뿐이다.

### 0595 — 조사에서 전제가 틀렸다

배경에 "`deleteMany` 전에 이미 조회하는 기존 비용 행"이라고 적혀 있었는데 **조회하고 있지
않았다.** `include`/`select`가 없어 스칼라 필드만 왔고, 실제 소비처는 `existing.startDate`
하나(0581 날짜 하한)였다. 비교하려면 조회를 **새로 추가**해야 했고, 두 방식 중 A를 골랐다.

- **A(채택)**: 기존 `findFirst`에 `costs` 관계를 얹는다 — 쿼리 추가 0회
- B: 트랜잭션 안 `deleteMany` 직전에 조회 — 원자성은 명확하나 트랜잭션이 길어진다

```ts
// my-plan/new/actions.ts:319 — select는 비교 키 4개만(order·planSpotId는 비교 대상이 아니다)
const existing = await prisma.myPlan.findFirst({
  where: { id: planId, ownerId: user.id },
  include: { costs: { select: { day: true, category: true, label: true, amount: true } } },
});
```

### 0595 — 이번 작업의 함정

**판정을 페이로드끼리 비교하면 아무것도 안 고쳐도 `true`가 된다.**
저장 경로가 페이로드를 그대로 쓰지 않기 때문이다.

- `amount <= 0`인 행은 **저장되지 않는다**
- **연결 비용의 label은 장소 이름으로 강제**된다(이름이 정본 — 0562 D②).
  그런데 편집 폼은 그 label을 **빈 문자열**로 들고 있다
  (`edit/page.tsx`: `label: c.planSpotId ? '' : c.label`)

즉 **폼이 들고 있는 값과 DB에 있는 값이 원래부터 다르다.** 이걸 모르고 비교하면
저장 버튼만 눌러도 "고쳤다"가 된다 — 금지 항목 "저장 이벤트만으로 `true` 세우기"에 정확히
걸린다. **이 함정 자체가 이 트랙의 네 번째 대역이다** — 페이로드는 "실제로 저장될 행"의
대역이고, 옆에 있고 관측하기 쉽다는 점까지 같다.

### 0595 — 해법: 쓰기와 비교를 같은 계산으로

규칙을 두 곳에 적으면 조용히 갈린다. 그래서 저장될 행 산출을 `costRowsToWrite()`로 빼고,
**`buildPlanRows`가 그 결과를 그대로 써서 `PlanCost`를 만들고 판정도 같은 결과를 비교**하게
했다.

```ts
// lib/plan/cost-snapshot.ts:67 — 선별·라벨 강제·order 규칙이 전부 여기 산다
export function costRowsToWrite(input: { … }): CostRowToWrite[] {
  for (const cost of input.dayCosts) {
    if (cost.amount <= 0) continue;                       // ① 0원 스킵
    const linkedName = cost.localId ? input.nameByLocalId.get(cost.localId) : undefined;
    rows.push({ …, label: linkedName ?? cost.label, … }); // ② 연결 비용 label 강제
  }
  …
}
```

```ts
// my-plan/new/actions.ts:227 — buildPlanRows가 그 결과로 쓰고, 그 결과를 반환한다
const rows = costRowsToWrite({ dayCosts, daylessCosts: dayless, nameByLocalId: … });
for (const row of rows) { await tx.planCost.create({ data: { … } }); }
return rows;                       // ← 호출부가 이 값으로 판정
```

```ts
// my-plan/new/actions.ts:358 — 비교 대상은 페이로드가 아니라 "실제로 쓴 행"
const writtenRows = await buildPlanRows(tx, planId, resolvedItems, payload.dayCosts, payload.daylessCosts);
if (!existing.costEdited && hasCostRowsChanged(existing.costs, writtenRows)) {
  await tx.myPlan.update({ where: { id: planId }, data: { costEdited: true } });
}
```

- 비교 키는 `(day, category, label, amount)` **다중집합**(`CostRowKey`) —
  `order`(0588 드래그)와 `planSpotId`(장소 재연결)는 금액 수정이 아니라 제외
- **한 번 `true`면 내리지 않는다** — `!existing.costEdited &&` 가드가 그 역할이자
  불필요한 UPDATE 회피

### 0595 — 백필 없음

담긴 플랜 1건을 원본과 `(day, category, label, amount)`로 전수 대조하니 **완전 일치**였다.
그래서 `false`가 사실과 맞고, `@default(false)`면 **백필 UPDATE 자체가 불필요**하다 —
0594에서 지적받은 "구조 변경과 데이터 보정 분리"가 저절로 지켜진다.

실패 방향도 안전하다: `false`면 배너가 뜨고, 실제로 고쳤다면 다음 저장에서 `true`로
올라간다. 반대(`true` 백필)는 확인이 필요한 플랜에서 배너를 **영영 잃는다.**
그리고 `costEdited`는 이벤트의 기록이라 **이벤트가 남지 않은 과거를 소급해 만들지 않는다.**

### 현행 조건 — 두 화면

| 화면 | 조건 | 위치 |
|---|---|---|
| 읽기 상세 | `isOwner && sourcePlanId && isCostUnchanged` | `PlanFinderDetail.tsx:444` |
| 편집 폼 | `sourcePlanId && isCostUnchanged` | `MyPlanNewForm.tsx:1212` |

양쪽 다 `isCostUnchanged = !plan.costEdited`이고 **서버 컴포넌트에서만** 계산한다
(`plan-finder/[id]/page.tsx:105` · `my-plan/[id]/edit/page.tsx:145`).
폼에 `isOwner`가 없는 건 **폼은 소유자만 진입**하기 때문이다 — 조건 문자열은 갈리지만
의미는 같다는 것을 양쪽 주석에 남겼다.

`isOwner`를 읽기 상세에 유지한 근거는 0593의 목적 정의에서 나온다: "확인 바랍니다"는
담은 사람에게 하는 요청이라, 공개된 담은 플랜을 남이 볼 때는 **할 일이 없는 사람에게 하는
말**이 된다(0592 원본 링크와 같은 결).

## 5. 결과 / 배운점

### 결과

- 세 사이클 모두 `npx tsc --noEmit` 통과, `npx next build` 컴파일 성공.
  `npm test` 실패 목록이 기존과 정확히 동일(auth 5스위트 + SpotPopup = 6스위트/8테스트) —
  회귀 없음. `migrate status` up to date (0594 후 31 / 0595 후 32 migrations).
- **실화면 확인 완료** — ① **상쇄 수정**(한 항목 +1만, 다른 항목 −1만으로 총액 464,000 유지)에서
  배너가 **사라진다**: 0594가 못 잡던 케이스를 0595가 잡는다.
  ② **무변경 저장**(아무것도 안 고치고 저장)에서 배너가 **남는다**: 페이로드를 비교했다면
  사라졌을 지점이고, `costRowsToWrite()` 단일 소스가 그걸 막는다.
- 최종 상태: 판정은 `MyPlan.costEdited` 하나. `sourceCostTotal`은 컬럼·조회·
  `isCostUnchangedFromSource` 모두 **남겼다**(담은 시점 금액 표시에 쓸 여지 — 사용자 확정).

### 배운점

- **진짜 묻고 싶은 것 대신 옆에 있는 관측하기 쉬운 것을 대역으로 썼다.**
  공개 여부는 "담은 플랜인가"의 대역, 저장 이벤트는 "고쳤나"의 대역, 원본과의 차이는
  "**내가** 고쳤나"의 대역이었다. 페이로드는 "실제로 저장될 행"의 대역이었다.
  **대역은 당장은 잘 동작하고, 어긋나는 건 나중이며, 어긋날 때 조용하다** —
  이 셋이 대역의 위험을 만든다. 배너가 잘못 뜨거나 안 떠도 아무도 에러를 보지 않는다.
  대역을 쓸 때 필요한 건 "지금 맞는가"가 아니라 **"둘이 갈리는 상황이 무엇인가"**다.
- **목적이 정해져도 기준은 따로 설계해야 한다.**
  0593에서 "배너는 확인 요청 안내"라는 목적을 확정하고도, 그 목적에 맞는 기준(금액 수정
  여부)이 아니라 방금 옆 작업(0592)이 쓰던 축을 그대로 가져다 썼다.
  **목적 합의와 기준 설계는 다른 단계**인데 한 단계로 처리했다.
- **최종 상태 비교는 이력을 지운다.**
  총액은 "지금 얼마인가"에만 답하고 "무엇을 했는가"에는 답하지 못한다. 상쇄 수정은 그 한계가
  드러난 한 사례일 뿐이고, **상태로 사건을 추론하려는 설계는 어디서든 같은 방식으로 샌다.**
  git이 스냅샷이 아니라 커밋을 기록하는 이유와 같다.
- **실수할 수 없는 구조가 주석보다 강하다 — 두 번 같은 결론이 나왔다.**
  ① 폼에 불리언만 내려보내면 "라이브 값과 비교하지 말 것"을 주석으로 적을 필요가 없다.
  ② 저장 규칙(0원 스킵·label 강제)을 판정 쪽에 다시 적었다면 지금은 맞아도 다음에 저장
  규칙이 바뀔 때 조용히 갈린다 — 쓰는 값을 그대로 돌려받아 비교하면 **갈릴 수가 없다.**
  덧붙여 **검증도 같다**: 잘못된 소스로 비교해도 5항목 중 3개는 통과한다. 통과 여부가 아니라
  **무엇을 비교했는지**를 나란히 찍어야 구조가 옳다는 증거가 된다.

## 결정 (Decisions)

- **판정은 상태 비교가 아니라 이벤트 기록** — `MyPlan.costEdited`. 저장 시점에 행이 달라졌으면
  `true`, **한 번 `true`면 내리지 않는다**(고쳤다 되돌려도 "고친 적 있다"는 사실은 유지).
- **비교 대상은 `buildPlanRows`가 실제로 쓴 행** — 페이로드가 아니다.
  쓰기와 비교가 `costRowsToWrite()` **한 계산을 공유**한다.
- **비교 키는 `(day, category, label, amount)` 다중집합** — `order`(0588 드래그)·
  `planSpotId`(장소 재연결) 제외.
- **판정은 서버에서만, 화면엔 불리언만** — 폼이 라이브 값과 비교할 수 없게 구조로 막는다.
  라이브 비교는 **재제안하지 않는다**(깜빡임 + 화면이 방금 한 말을 뒤집음).
- **`!isPublic` 기준(0593)은 폐기** — 공개 여부는 금액이 낡았는지와 무관하다.
  단 0593이 확정한 **배너의 목적**("출처 표시가 아니라 확인 요청 안내")은 살아 있고,
  `isOwner`를 읽기 상세에 거는 근거가 그것이다.
- **총액 대조(0594)는 폐기, `sourceCostTotal` 컬럼·술어는 유지** — 담은 시점 금액 표시에 쓸
  여지(사용자 확정).
- **`PlanFlight`는 합산 제외** — 담기가 항공을 복사하지 않아(0580) 스냅샷 쪽이 늘 0이고,
  나중에 항공권을 붙이면 "안 고쳤는데" 총액이 달라진다.
- **이전 상태는 `existing`에 `costs`를 얹어 읽는다**(A안) — 쿼리 추가 0회, select는 비교 키 4개.
- **마이그레이션에 1회성 백필을 넣지 않는다** — 재생 시 다른 값이 들어간다.
  0595는 `@default(false)`로 백필 자체가 불필요했다.
- **이벤트를 소급 생성하지 않는다** — 이벤트가 남지 않은 과거를 `true`로 만들지 않는다.
  실패 방향도 안전하다(`false`면 배너가 뜨고, 실제로 고쳤다면 다음 저장에서 올라간다).

## 겹치는 축 (다른 회고 참조)

- **배너의 외형·문구** — 색·면·문안의 정본은 **배너 외형·문구 묶음(0589·0590·0596~0598)**.
  이 편은 **언제 띄울지**만 다룬다. 층 분리의 정본은 `lib/plan/copied-plan-notice.ts`
  주석(0596) — 표시 조건은 `lib/plan/cost-snapshot.ts`가, 문구는 그 파일이 갖는다.
- **담기 복사 범위** — 배너가 존재하는 이유(담기가 비용을 복사한다)와 최초 조건
  (`sourcePlanId` 유무 하나)은 **담기 복사 범위 묶음(0579·0580·0582)**.
  그 편의 조건은 이 트랙에서 두 번 뒤집혔고, **현행 조건의 정본은 이 문서**다.
- **0588 드래그** — 비교 키에서 `order`를 빼는 근거. 순서 변경은 금액 수정이 아니다.
- **0562 D②** — 연결 비용 label = 장소 이름 강제. 0595 함정의 절반이 여기서 온다.
