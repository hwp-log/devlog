---

## 1. 한 줄 요약

가입 실패 시 "회원가입에 실패했습니다"뿐이던 generic 문구를 — 계정 존재 여부를 노출하지 않으면서 다음 행동(로그인·재시도)을 제시하는 "이 이메일로는 지금 가입할 수 없습니다. 이미 가입하셨다면 로그인하거나, 잠시 후 다시 시도해주세요."로 교체 + "로그인"에 /login 링크.

---

## 2. 왜 / 목적 / 이유

- **왜**: 실패의 흔한 실체는 중복 이메일인데 문구가 원인도 다음 행동도 안 알려줌. 그렇다고 "이미 가입된 이메일"이라 명시하면 계정 존재 여부가 새고, /login의 뭉뚱그림 기준("이메일 또는 비밀번호가 올바르지 않습니다")과 어긋난다.
- **목적**: 원인을 확정해주지 않으면서 사용자가 다음 행동을 알 수 있게. rate limit·서버 장애 케이스까지 포괄하도록 "잠시 후 재시도"를 병기 (사용자 확정).
- **전제 확인**: Supabase auth 설정 직접 조회(`GET /auth/v1/settings`, 읽기 전용) → **`mailer_autoconfirm: true`** (이메일 인증 꺼짐). 이 모드에선 중복 가입이 **에러**(422 User already registered)로 온다 — 인증이 켜져 있으면 위장 성공(identities 빈 배열)이라 에러가 아예 안 뜨는데, 그 경로는 이 프로젝트에서 발생하지 않음.

## 5. 결과 / 배운점

### 결과
- tsc·eslint 통과. `npm test`: 실패 2스위트/1테스트(lib/auth actions·SpotPopup) — 기존 목록과 동일, 신규 실패 0. signup/actions.test는 mock 통과 방식이라 무영향.
- **화석화 보고**: `lib/auth/__tests__/actions.test.ts:84`가 구 문구 '회원가입에 실패했습니다'를 단언 — 스위트 레벨 기존 실패(TextEncoder)로 실행 자체가 안 되지만, 스위트가 살아나면 이 단언은 실패한다. 테스트 수정 금지 규칙에 따라 보고만 (auth 테스트 정리 사이클에서 함께).

### 배운점
- "중복이면 뭐라고 뜨는가"는 코드만으론 확정 불가 — Supabase는 이메일 인증 설정에 따라 같은 중복이 에러(422)와 위장 성공으로 갈린다. `GET /auth/v1/settings`(anon key, 읽기 전용)로 `mailer_autoconfirm`을 확인하면 대시보드 없이 판정 가능.
- 서버 액션 수정 금지 제약에서 에러별 표시 분기가 필요하면 — 반환 형태를 구조화하는 대신 문자열 상수 동기 + 상호 참조 주석(레포 관례)으로 해결. 형태 변경 없이 표시층만 확장.

## 결정 (Decisions)

- 가입 generic 실패 문구 = "이 이메일로는 지금 가입할 수 없습니다. 이미 가입하셨다면 로그인하거나, 잠시 후 다시 시도해주세요." — 원인 미확정(계정 존재 비노출, /login 뭉뚱그림과 동일 기준) + 다음 행동 2개(로그인 링크·재시도).
- 형식 오류(supabase 호출 전 검증 3종)는 원인 명시 유지 — 계정 존재와 무관.
- 에러 문구 안 링크 방식 = 문자열 일치 분해 렌더 (SIGNUP_BLOCKED_ERROR 상수 + 상호 참조 주석). 반환 형태 구조화는 서버 액션 수정이라 배제.
- 이 프로젝트는 `mailer_autoconfirm: true` — 중복 가입은 항상 에러 경로. 이메일 인증을 켜면 위장 성공 경로가 생기므로 이 문구 설계 전제가 깨진다 (그때 재검토).
