## 1. 한 줄 요약

마커 클릭 시 뜨는 SpotPopup의 버튼 배치를 의도에 맞게 정리했다. 보기 상태에선 [수정][삭제]를 하단에 나란히 묶고, 수정 화면에선 마커 삭제를 제거해 [저장][취소]만 남겼다. 삭제는 "이 마커(클릭 대상)를 없앤다"는 의도라, 마커를 고른 보기 상태에서만 보이게 해 대상을 명확히 했다. 이로써 0029부터 쌓은 스토리 맵 기능이 일단락된다.

---

## 2. 왜 / 목적 / 이유

### 핵심 — 삭제는 "대상이 명확한 보기 상태"에만

- **왜(동기/문제)**: 기존엔 보기 상태에서 "수정"이 오른쪽 위, "마커 삭제"가 왼쪽 아래로 따로 떨어져 한 쌍으로 안 읽혔다. 게다가 수정 화면 안에도 "마커 삭제"가 또 있어, 수정하러 들어왔는데 거기서 삭제까지 되는 의도 혼선이 있었다.
- **목적(도달할 상태)**: 마커를 클릭한 보기 상태에서 "이 마커를 수정? 삭제?"를 한눈에 고르게. 수정 화면은 저장/취소 두 개로 의도가 섞이지 않게.
- **이유(채택 근거)**: 삭제는 "이 마커를 없앤다"는 의도다. 마커를 고른 *보기 상태*에서 보여야 "내가 클릭한 이 마커를 지운다"가 명확해진다. 수정 화면 안에 삭제가 있으면 — 방을 고치러 들어왔는데 그 방에 "집 허물기" 버튼이 있는 격이라, 의도가 섞인다. 그래서 삭제를 보기 상태 하단으로 옮기고(수정과 나란히), 수정 화면에선 뺐다.

> 면접용 한 문장: "삭제는 대상이 명확한 보기 상태(마커를 고른 시점)에만 두고, 수정 화면에선 저장/취소만 남겨 '수정 중 삭제'라는 의도 혼선을 없앴다 — 버튼 위치는 곧 사용자 의도의 표현이다."

[검수 모드]
- ★★★ 작성/수정 방에서 수정·저장·취소·삭제 다 정상 동작하나 (핸들러 안 끊겼나)
- ★★ 보기 하단에 수정·삭제, 수정엔 저장·취소만(삭제 없음)
plan 요청.

## 4. 코드 작성 & 수정

### components/SpotPopup.tsx — 보기 상태 하단에 [수정][삭제] 나란히

```tsx
// 변경 전 — 수정은 이름 영역 오른쪽 위, 삭제는 카드 맨 아래 따로
// (이름 영역) {!readOnly && <button onClick={enterEdit}>수정</button>}
// (카드 하단) {!readOnly && <button onClick={onDelete}>마커 삭제</button>}

// 변경 후 — 보기 상태(!readOnly && !isEditing)에서만 하단 나란히
{!readOnly && !isEditing && (
  <div className="px-4 pb-4 flex gap-2">
    <button type="button" onClick={enterEdit}
      className="flex-1 py-1.5 rounded-lg text-sm bg-slate-100 text-slate-600 hover:bg-slate-200 transition-colors">
      수정
    </button>
    <button type="button" onClick={onDelete}
      className="flex-1 py-1.5 rounded-lg text-sm text-red-500 border border-red-200 hover:bg-red-50 transition-colors flex items-center justify-center gap-1">
      <Trash2 size={12} /> 삭제
    </button>
  </div>
)}
```

핵심은 `!isEditing` 조건 — 수정 상태에선 이 블록 자체가 안 뜨니, 삭제가 *구조적으로* 수정 화면에서 사라진다. (조건으로 의도를 강제.)

### 상태별 결과

| 상태 | 버튼 |
|---|---|
| 보기 (`!readOnly && !isEditing`) | 하단 [수정] [삭제] 나란히 |
| 수정 (`isEditing`) | 하단 [저장] [취소]만 (삭제 없음) |
| 보는 방 (`readOnly`) | 버튼 없음 (0059 그대로) |

삭제 핸들러(onDelete)·수정 진입(enterEdit)은 그대로, 호출 위치만 보기 상태 하단으로 옮겼다.

## 5. 결과 / 배운점

### 결과
- 보기 상태: 하단에 [수정][삭제] 나란히 — "이 마커에 할 수 있는 두 가지"로 묶여 읽힘.
- 수정 상태: [저장][취소]만, 삭제 사라짐 — 의도 명확.
- 보는 방(readOnly)은 그대로 버튼 없음. 작성/수정 방 동작 정상.

### 배운점
1. **버튼 위치는 곧 사용자 의도의 표현이다.** 삭제를 어디 두냐가 "무엇을 지우는지"의 명확함을 결정했다. 대상(마커)을 고른 보기 상태에 둬야 "이걸 지운다"가 분명해지고, 수정 화면에 두면 의도가 섞인다.
2. **의도 분리는 조건으로 강제한다.** `!isEditing`으로 수정 상태에서 삭제 블록 자체가 안 뜨게 해, "수정 중 삭제"를 구조적으로 막았다. (0059에서 readOnly면 @dnd-kit 자체를 안 켠 것과 같은 결 — 숨기는 게 아니라 동작/표시 자체를 조건으로 차단.)
3. **위치만 옮길 땐 핸들러가 안 끊겼는지가 핵심.** 버튼을 옮겨도 onClick(enterEdit·onDelete)을 그대로 들고 내려와, 보이는데 안 눌리는 헛버튼을 피했다.

### 맵 기능 매듭 — 넣은 것과 안 넣은 것
0029부터 이어온 스토리 맵 기능이 0060으로 일단락. 마지막 국면(0057~0060)을 돌아보면:
- **넣은 것**: 여행순서 바꾸기(reorder), 보는 방 읽기 전용 동선(리스트↔카드 fade, panTo, 펄스), 마커 색 의미화(시작 초록/끝 빨강/중간 파랑), 버튼 의도 정리.
- **안 넣은 것(근거 있는 판단)**: 작성/수정 방 fade 통일 — 구조 분석상 unmount/mount라 JSX 구조 변경(★★★)이 필요하고, 업계 기준(iOS 가이드·NN/g)상 빠른 도구 조작엔 fade가 오히려 방해. "읽기=fade, 작성=빠릿"은 비일관이 아니라 맥락에 맞춘 일관(Figma Dev Mode 등 기업도 모드별 차등이 정상). *통일이 목적이 아니라 맥락에 맞는 게 목적* — 0058 "의미 없는 색만 제거"와 같은 원칙.
