## 2. 왜 / 목적 / 이유

### 발단 — 폭이 3벌이었다
전수 조사에서 화면 폭이 세 갈래로 갈려 있었다: 캡 1232(기본 분기) / wide 뷰포트−48
(스토리·플랜파인더 목록) / 개별값(스토리 본문 860, 어드민 768). 갈래마다 근거 유무를
갈랐다 — 860은 토큰(`--story-content-w`)까지 있는 값, 768은 커밋·회고 어디에도 판정
기록이 없는 값(0149), 1232는 기본값이 눌러앉은 것.

### 860의 재분류 — "근거 없음"이 아니라 "기록 안 된 실판정"
조사 시점에 860은 근거 없음으로 분류됐다. 실제로는 0321에서 검증 문헌 대역(680~780)
안의 760으로 통일했다가, 0322에서 실화면 "너무 좁다" 판정으로 올린 값이었다 — 판정은
있었고 기록이 없었던 것. **실판정이 문헌 대역보다 우선**한다는 원칙으로 860을 정본화했다
(`--reading-w`, 기존 `--story-content-w`는 파생 별칭).

### 규칙 — "그 화면에서 사용자가 뭘 하는가" 하나로
- **고르는 화면**(목록·지도): 좁으면 후보를 많이 못 본다 → 풀블리드
- **입출력 화면**(읽기·작성·설정): 집중 포커싱이라 좁을수록 피로가 적다 → 860

폭이 화면 종류(목록/상세/폼)가 아니라 **사용자 활동**으로 결정되면서, 화면마다
개별 판정하던 것이 규칙 하나로 수렴했다.

### 취소한 안 — 헤더 라우트별 폭 정렬
헤더가 라우트 무관 풀폭이라 캡 화면에서 본문과 정렬선이 어긋나는 것을 발견하고
헤더·푸터를 본문 분기에 맞추는 안까지 설계했으나 **취소했다**. 값이 어긋난 건 사실이나
사용자가 겪는 문제가 아니었고, 고치면 라우트 이동마다 헤더 폭이 변하는 없던 불편이
생겼다. 사실의 어긋남과 경험의 결함은 다르다 — 전자만으로는 고칠 이유가 안 된다.

## 4. 코드 작성 & 수정

### 0534 — 상세: 토큰 정본화 + 통째 제한

```css
--reading-w: 860px;                    /* 정본 — 0322 실판정 */
--story-content-w: var(--reading-w);   /* 파생 별칭 — 스토리 5개 사용처 무변 */
```

```diff
- <div className={isOwner ? undefined : 'max-sm:pb-[88px]'}>
+ <div className={`max-w-[var(--reading-w)] mx-auto${isOwner ? '' : ' max-sm:pb-[88px]'}`}>
```

히어로 포함 **통째** 제한 — 0525의 문제("소개문만 좁아 쏠림")는 폭 제한이 아니라
"한 화면 안 폭 갈림"이 원인이었으므로, 통째면 재발하지 않는다(0525 번복의 논리).
성립 검산: 일정 행 652 / 비용 2열 한 칸 211(열폭 420) / 항공 4열 482 — 전부 860 안.
1440px에서 ≈54~62자/줄(전폭 74자 대비 30% 개선, 권장 30~40자 위는 실판정 우선으로 수용).

### 0535 — 목록: WIDE 편입 + 그리드 wide 재유도

```diff
- const WIDE_ROUTES = ['/story', '/plan-finder'];
+ const WIDE_ROUTES = ['/story', '/plan-finder', '/my-plan', '/my-story'];
```

그리드 bp는 0532 산출식에 컨테이너 전제만 캡→wide로 교체해 재유도 — /my-plan은
캡에서 불성립이던 4·6열이 복원되고, 결과 숫자가 /plan-finder와 같아진 건 복사가 아니라
컨테이너·하한·gap이 전부 같아진 결과(0530 복사 사고와 구분). 검산: 전 뷰포트 하한 위반 0건,
플랜 2목록·스토리 2목록이 각각 완전 동일 거동.

### 0536 — 입출력: 세 화면 860 편입

- MyPage: 좌측 412(=860−400−48)에서 지표 4열 한 칸 103px vs 최악 값 88.7px — 2열 조판 무변 성립
- 어드민: 768의 판정 기록 없음(0149) → 규칙 편입, +92px에 고정 요소 없음
- 플랜 작성·수정: 공유 폼 양쪽 페이지에 같은 래퍼(상호 참조 주석 — 한쪽만 바꾸면 어긋남).
  0527 조판 전 산식 성립(2열 421 / 3열 342 / 항공 480 / 고정비용 522 / 카테고리 402)

### 부수 — 이미지 sizes 화석 3곳

폭을 바꿀 때마다 sizes가 옛 폭을 물고 있는 화석이 나왔다:

| 화석 | 실태 | 재동기 |
|---|---|---|
| 0534 히어로 `HERO_SIZES` 640px | 0512 컬럼 시절 값 — 0525 전폭(1232) 동안 저해상도 서빙 | 860 |
| 0535 `PLAN_CARD_SIZES` 767px/400px | 그리드 bp와 무대응, 2열 밴드 488px를 400으로 과소 서빙 | 그리드 밴드 1:1 |
| 0535 `StoryCard` sizes (md/lg/2xl 화석) | 0448 모바일 1열 전환 후 **1열 밴드를 50vw 절반 해상도로 서빙** | 그리드 밴드 1:1 |

## 5. 결과 / 배운점

### 결과
- 전 화면이 규칙 2원칙으로 수렴: 고르는 화면 4/4 풀블리드, 읽기·입력 6화면 860.
  잔여: /my-plan/[id](미개편 화면 — 위계 정돈 사이클에 편입), /til, auth(미판정).
- `npx tsc --noEmit` 커밋마다 무오류. 검산 전건 하한 위반 0. 조판·기능 diff 0줄.

### 배운점
- **실판정과 기록은 별개로 죽는다.** 860은 판정(0322)이 있었는데 기록이 없어 "근거 없음"
  으로 분류될 뻔했다. 판정이 기록을 남기지 않으면 다음 조사에서 값이 부정당한다.
- **번복은 원인의 재분류다.** 0525의 관찰(쏠림)은 유효했고, 틀린 건 원인 지목(폭 제한
  자체)이었다. 원인을 다시 가르면 결론이 뒤집혀도 과거 관찰은 살아남는다.
- **사실의 어긋남 ≠ 경험의 결함.** 헤더 폭 정렬은 계산상 명백한 불일치였지만 고치면
  없던 불편이 생겼다. "틀렸다"만으로는 고칠 이유가 안 되고, 사용자가 겪는가를 먼저 물어야 한다.
- **sizes는 폭의 종속 변수인데 아무도 안 따라간다.** 세 번의 폭 변경에서 세 번 다
  화석이 나왔다(640px·400px·50vw). 폭을 정하는 커밋이 sizes를 같이 보는 것을
  절차로 삼아야 한다(0534~0535에서 결정으로 명문화).

## 결정 (Decisions)

- **폭 규칙 2원칙**: 그 화면에서 사용자가 뭘 하는가로 폭을 정한다 — 고르는 화면(목록·지도)
  풀블리드 / 그 외(읽기·작성·설정) 860. 화면 종류별 개별 판정 폐지. (0534~0536)
- 읽기·입력 폭의 정본은 `--reading-w`(860, 0322 실판정 — 문헌 대역 680~780보다 실판정
  우선). `--story-content-w`는 파생 별칭, 개명은 스토리를 손대는 사이클에.
- 상세의 히어로·커버는 본문 컬럼 안 — 폭 제한은 화면 통째로만(부분 제한은 쏠림 재발).
- 컬럼·그리드 폭을 바꾸는 커밋은 이미지 `sizes`를 함께 재동기한다.
- 그리드 bp는 컨테이너 전제가 바뀌면 재유도한다 — 숫자 복사 금지(0530 전례).
- 헤더·푸터는 라우트별 폭 추종을 **하지 않는다** — 정렬선 불일치는 사용자가 겪는 문제가
  아니었고, 고치면 라우트 이동마다 헤더 폭이 변하는 새 불편이 생긴다. (취소된 안)
