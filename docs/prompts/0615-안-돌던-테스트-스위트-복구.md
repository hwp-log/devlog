## 2. 왜 / 목적 / 이유

- **왜**: CI를 붙이려 했는데 감시 대상이 빨간 상태였다. 실패한 채로 CI를 붙이면 늘 빨강이라, 진짜 문제(회귀)와 기존 실패가 구분되지 않는다. CI가 의미를 가지려면 기준선이 먼저 그린이어야 한다.
- **실측이 알고 있던 것과 달랐다**: 인지하고 있던 상태는 "auth 5개 실패"였다. 실제로 돌려 보니 auth는 개별 케이스 실패가 아니라 **파일 하나가 통째로 로드 실패**(jsdom에 TextEncoder가 없어 `lib/prisma.ts → cuid2 → @noble/hashes` import 체인이 던짐)라 9케이스가 아예 실행되지 않는 상태였고, 별도로 SpotPopup 1건이 실패하고 있었다.
- **실패의 성격이 두 가지로 갈렸다**:
  - 폴리필(①)은 **환경 문제** — 테스트도 앱도 틀리지 않았고, jsdom에 Node 전역이 없는 것이 원인.
  - SpotPopup `rating`(②)·auth 문구(③)는 **기대값 화석화** — 앱은 이후 사이클(0199 별점, 0612 문구)에서 바뀌었는데 테스트가 옛 명세를 단언하고 있던 것. 성격이 다르므로 수정의 정당화도 다르다: ①은 실행 환경 보정, ②③은 현행 명세 확인 후 갱신.

## 4. 코드 작성 & 수정

### 1. jest.polyfills.ts 신규 + setupFiles 등록 (환경 보정)

```typescript
// jest.polyfills.ts (신규)
// jsdom이 제공하지 않는 Node 전역 폴리필. setupFiles 단계(테스트 파일 import 전)에 주입 —
// lib/prisma.ts → cuid2 → @noble/hashes가 import 시점에 TextEncoder를 요구하므로
// setupFilesAfterEnv(프레임워크 로드 후)로는 늦다.
import { TextEncoder, TextDecoder } from 'node:util';

globalThis.TextEncoder = TextEncoder;
globalThis.TextDecoder = TextDecoder as unknown as typeof globalThis.TextDecoder;
```

```typescript
// jest.config.ts
const config = {
    testEnvironment: 'jsdom',
    setupFiles: ['<rootDir>/jest.polyfills.ts'],   // 추가
    setupFilesAfterEnv: ['<rootDir>/jest.setup.ts'],
```

## 5. 결과 / 배운점

### 결과
- `npm test` 전 스위트 그린 — 20스위트 / 207케이스 전부 통과. 이후의 테스트 실패는 전부 회귀로 간주할 수 있는 기준선 확보 (CI 부착의 전제 조건 — CI 자체는 미착수).
- auth 9케이스가 처음으로 실제 실행됨.

### 배운점
- **0612 회고가 이 실패를 예고해뒀고 그대로 맞았다** — 0612 결과 섹션에 "스위트가 살아나면 `actions.test.ts:84`의 구 문구 단언은 실패한다"고 보고해 뒀는데, 폴리필을 넣자 정확히 그 지점이 실패했다. 화석화 보고를 남겨둔 덕에 원인 분석 없이 바로 갱신할 수 있었다.
- **테스트가 있는 것과 도는 것은 다르다** — auth 9케이스는 import 단계에서 죽어 한 번도 실행된 적이 없는데, 정기적으로 돌리지 않으니 그 사실조차 모르고 "5개 실패"라는 부정확한 인지로 지내 왔다.
- **환경을 고치니 숨어 있던 화석이 드러났다** — ①(폴리필)을 안 했으면 ③(문구 화석)은 발견조차 안 됐다. 실패는 겹쳐서 쌓이고, 바깥 층을 벗겨야 안쪽 층이 보인다.

## 결정 (Decisions)

- **기대값 갱신은 실제값 베끼기가 아니라 명세 확인** — 실패한 기대값을 현재 출력값으로 덮어쓰지 않고, 앱 코드를 읽어 "그게 맞는 동작인지"(0199 rating, 0612 문구) 확인한 뒤 갱신한다. 실제값 베끼기는 버그도 명세로 승격시킨다.
- **import 단계 폴리필은 setupFiles** — `setupFilesAfterEnv`는 테스트 프레임워크 로드 후라, 테스트 파일 import 시점에 죽는 문제엔 늦다. 전역 폴리필은 `setupFiles`에 둔다.
- **auth 테스트가 문구 사슬의 유일한 자동 장치** — `actions.ts` 문구 ↔ `SignupForm.tsx` `SIGNUP_BLOCKED_ERROR`의 문자열 일치(불일치 시 /login 링크가 조용히 안 붙음)를 지키는 자동화된 장치는 이제 이 테스트뿐이다. 문구 변경 시 테스트가 깨지며 사슬을 상기시킨다.
