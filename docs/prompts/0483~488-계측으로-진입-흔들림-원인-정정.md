## 1. 한 줄 요약

스팟파인더 진입 시 화면이 흔들리는 증상의 원인을 지도 렌더 → `appear-up` → 헤더 리마운트로 두 번 잘못 짚었고, `layout-shift` 계측으로 원인을 확정한 뒤 헤더·애니메이션·스켈레톤 세 층을 차례로 걷어냈다.

---

## 2. 왜 / 목적 / 이유

### 왜 (동기·문제)

스팟파인더에 진입하면 화면이 흔들렸다. 모바일·데스크톱 공통이었고, 증상 묘사는 "콘텐츠가 위로 살짝 올라갔다가 지도가 뜨면서 누르듯이 내려간다"였다.

먼저 네이버 지도 쪽 알려진 이슈인지 검색했다. 공식 문서·커뮤니티에 해당 증상이 없었고, 문서에서 확인된 것은 타일 fadeIn이 기본 활성이라는 것뿐인데 그것은 레이아웃을 건드리지 않는다. 코드 내부 문제로 판단하고 조사에 들어갔다.

### 목적 (목표 상태·사용자 가치)

탭을 눌러 들어온 사용자가 첫 화면에서 요소가 튀는 것을 보지 않는 상태. 지도 화면은 진입 직후 바로 조작을 시작하는 곳이라, 흔들림은 조작 대상이 움직이는 것으로 이어진다.

### 이유 (채택 근거·판단 기준)

**가설 두 개가 코드 읽기만으로 세워졌고 둘 다 틀렸다.**

1. **지도 컨테이너 높이 미예약** — 조사 결과 `h-spot-finder-map`이 첫 서버 페인트부터 확정되고, 스켈레톤·폴백·실제 지도가 전부 같은 높이 상수를 쓴다. 높이 시프트는 존재하지 않았다. `flex-1`도 여기선 row라 폭 축이라 이전 붕괴 사례(0377)와 구조가 달랐다.
2. **`appear-up`의 translateY 10px** — 조사가 스스로 불일치를 짚었다. `appear-up`은 진입 직후 0.8초에 끝나는데 지도 SDK 로드는 그보다 느리고, 묘사된 방향(위→아래)이 `appear-up`(아래→위)과 반대였다.

그래서 계측으로 갔다. 핵심은 **`transform`은 `layout-shift`로 집계되지 않는다**는 성질이다. 이 하나로 진짜 리플로우와 transform 계열이 자동 분리된다 — 시프트가 잡히면 리플로우, 안 잡히면 transform.

계측 결과 진입 후 구간에 남은 시프트는 **`main`이 정확히 57px 이동한 한 건**이었다. 57px은 헤더 높이이고 지도 canvas 등장 시점과 무관했다.

**진짜 원인은 `HeaderGate`가 조건부 렌더로 반환 요소 타입을 바꾸는 것**이었다. `<header>` ↔ `<div>`로 타입이 바뀌니 헤더 서브트리가 리마운트되고, `position: sticky`는 `fixed`와 달리 정상 흐름을 점유하므로 헤더가 빠지는 순간 flex 형제인 `main`이 57px 당겨졌다. 소프트 내비에서만 나는 것도 설명된다 — 하드로드는 SSR 시점에 이미 숨겨진 채 그려져 시프트가 0이다.

**처방은 레포 안의 선례를 확장하는 것이었다.** `ThemeScope`는 같은 `usePathname`을 쓰면서도 안정 래퍼에 속성만 토글해 리마운트가 없었다. 구조를 토글하는 것은 `HeaderGate`뿐이었다. 그래서 마커를 `ThemeScope`에 추가하고 순수 CSS로 가시성만 가르는 방향(B안)을 택했다. A안(요소 타입 고정 + `hidden`/`display:contents` 클래스 토글)은 Tailwind v4 순서 충돌 전례(0462)가 있어 비채택했다.

**그런데 계측이 0건이 된 뒤에도 육안 흔들림은 남았다.** 그 시점의 판정이 중요했다 — 계측에 잡히는 것과 눈에 보이는 것이 **서로 다른 현상**이었다. 그래서 커밋 메시지에 "육안 흔들림은 별개 원인으로 잔존"을 명기하고 다음 원인으로 넘어갔다.

### 계측 요청 — layout-shift 관측 추가

```
스니펫에 layout-shift 관측을 추가할 것.
```

### 4-2. 0485 — 삭제된 `HeaderGate` (리마운트의 근원)

```tsx
// app/(protected)/_components/HeaderGate.tsx (e548ab5에서 삭제됨 — 삭제 직전 전문)
'use client';
import { usePathname } from 'next/navigation';

// 0226: SpotFinder는 모바일에서 앱 헤더 숨김(데스크탑 lg는 유지). 다른 탭은 항상 표시.
// RSC 서버→클라 경계를 넘어온 children을 cloneElement/props로 조작하면 fragile →
// composition(wrapper)으로 전환. 일반 block wrapper는 sticky를 깨므로 display:contents로 sticky 보존.
const HIDE_HEADER_ON_MOBILE = ['/spot-finder'];

export function HeaderGate({ children }: { children: React.ReactNode }) {
  const pathname = usePathname();
  const hideOnMobile = HIDE_HEADER_ON_MOBILE.some((r) => pathname.startsWith(r));
  if (!hideOnMobile) return children;
  // 모바일 hidden=헤더 숨김 / lg:contents=데스크탑 표시 + wrapper 무박스로 sticky 유지.
  return <div className="hidden lg:contents">{children}</div>;
}
```

**반환 요소 타입이 `children` ↔ `<div>`로 갈리는 것**이 리마운트를 만들었다.

## 5. 결과 / 배운점

### 결과

- `main` 57px 시프트 **계측상 0건**으로 확인(같은 스니펫으로 재측정)
- 육안 흔들림("뿌드득")도 `appear-up` 제거로 소멸
- 스켈레톤 → 실제 시트 교체 시 튐 제거, 안쪽 블록 구성까지 정합
- `HeaderGate` 삭제(유일 소비처 제거로 죽은 코드), 공유 치수 변수 4종 신설
- 이 결정이 이후로 이어졌다. 나중에 신설된 `spot-finder/loading.tsx` 주석에 "appear-up(0.24s 지연)은 제외 — 로딩 상태가 스스로 지연 페이드하면 표시가 늦어짐"이 적혀 있다

### 커밋 이력의 어긋남 (기록)

- **"57px" 산식은 판단보류.** 주석은 `h-14=56 + border 1px = 57`이라 적었는데, `glass-header`의 실제 선언은 `border-bottom: 0.5px`다. 계측값 57px과는 맞지만 CSS 리터럴은 0.5px이라 산식의 "1px"과 어긋난다. 브라우저 서브픽셀 반올림 결과인지는 확정할 수 없다.
- **0485 커밋 메시지가 미해결을 은폐하지 않았다.** "계측상 main 시프트 0건 확인. 단 육안 흔들림은 별개 원인으로 잔존"을 적었고, 19분·24분·25분 뒤 커밋이 차례로 다른 원인을 잡았다. 이 자기고지가 "세 번 정정"의 커밋상 근거다.
- **`NavLinks`의 `lastCenter`가 전제를 잃었다.** 리마운트된 새 인스턴스를 이전 위치에서 미끄러지게 하던 장치인데, 리마운트가 사라져 지금은 최초 마운트에서만 읽힌다. 무해하지만 잔존 로직이라 주석에 명기하고 정리는 후속으로 남겼다.

### 배운점

**계측 도구를 고르는 것이 절반이었다.** `transform`은 `layout-shift`로 집계되지 않는다 — 이 성질 하나가 리플로우와 transform 계열을 자동으로 갈랐다. 시프트가 잡히면 리플로우, 안 잡히면 transform. 도구를 그렇게 고르고 나니 한 번 실행으로 원인이 좁혀졌다.

**계측에 잡히는 것과 눈에 보이는 것은 다를 수 있다.** 0485에서 57px 시프트를 없애고 계측이 0건이 됐는데도 흔들림은 그대로였다. 여기서 "고쳤다"고 적었으면 다음에 다시 찾을 때 헤맸을 것이다. 커밋 메시지에 "별개 원인으로 잔존"을 적은 것이 이후 세 커밋의 출발점이 됐다.

**증상을 둘로 쪼개니 원인이 갈렸다.** 소프트 내비에서는 "위로 올라감 + 내려감"이 둘 다 나고, 강제 리프레시에서는 "내려감"만 났다. 이 대조가 두 원인이 별개라는 직접 증거였다 — 코드를 더 읽어서가 아니라 조작 경로를 나눠서 얻은 정보다.

**계측 데이터도 읽는 법이 있다.** `buffered: true`는 스니펫 실행 전 기록까지 딸려오므로 `t`가 음수인 항목은 이전 화면 것이다. 90건 중 89건이 그것이었고, 실제 구간은 마지막 한 줄뿐이었다. 필터를 안 걸었으면 노이즈에 묻힐 뻔했다.

**같은 계측으로 사라졌음을 증명했다.** 원인을 찾은 도구로 해결을 확인하니 "안 흔들리는 것 같다"보다 훨씬 강한 근거가 남았다. 가설로 고치고 눈으로 확인하는 것과는 수준이 다르다.

**라우트별 분기는 구조가 아니라 속성으로 건다.** `ThemeScope`와 `HeaderGate`는 같은 `usePathname`을 쓰는데 한쪽만 리마운트가 있었고, 차이는 정확히 이것이었다. 안정 래퍼에 마커를 붙이고 CSS로 가르면 하드로드와 소프트 내비의 첫 페인트가 같아진다.

**스켈레톤은 "비슷하게"가 아니라 같은 상수를 참조해야 한다.** 0487에서 시트 바깥 높이를 정확히 맞췄는데도 0488에서 안쪽이 튄 것은, 컨테이너를 맞춰도 첫 블록(그래버 40px)이 어긋나면 아래가 전부 밀리기 때문이다. 그리고 행 수처럼 화면 높이에 따라 달라지는 값은 맞추려 하지 말고 **넘치게 두고 클립으로 흡수**하는 편이 재드리프트를 막는다.

**같은 문제에 답이 반대일 수 있다.** 데스크톱 좌열은 `flex-1`로 채우고 모바일 시트는 고정 높이 + 클립으로 갔다. iOS Safari가 중첩 flex에서 grow를 계산 못 한다는 실측(0252)이 있었기 때문이다. "일관성"을 이유로 한쪽 방식을 강요했으면 모바일이 붕괴했을 것이다.
