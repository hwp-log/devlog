# A — 읽기 항공을 예상 비용 형제 그룹으로

## 한 줄 요약

## 왜 / 목적 / 이유

## 코드 작성 & 수정

### 핵심 발견 — 합치던 쪽은 lib이 아니라 소비처였다

`summarize-plan-cost.ts`는 이미 '항공'을 **별개 그룹으로** 내보내고 있었다:

```ts
const itemGroups = [
  ...(flight && flight.totalAmount > 0
    ? [{ day: null, label: '항공', items: [{ label: '항공', category: 'FLIGHT', amount: flight.totalAmount }] }]
    : []),
  ...(daylessItems.length > 0 ? [{ day: null, label: '여행 전체', items: … }] : []),
  …
];
```

합친 건 소비처였다 (`PublicCostSection.tsx`):

```ts
// before — day===null 그룹 둘(항공·여행 전체)을 뭉갬
const fixedItems = itemGroups.filter((g) => g.day === null).flatMap((g) => g.items);
```

→ **lib 무접촉**으로 풀렸다. story 3곳 소비처 영향 없음.

```ts
// after — FLIGHT 제외. CostCategory enum에 FLIGHT가 없어 실 PlanCost는
//   이 값을 절대 못 갖는다(label 문자열 '항공' 매칭보다 견고)
const fixedItems = itemGroups
  .filter((g) => g.day === null)
  .flatMap((g) => g.items)
  .filter((it) => it.category !== 'FLIGHT');
```

### 노선표는 슬롯으로

`PublicCostSection`은 `story/[id]/`에, `PublicFlightTable`은 `plan-finder/[id]/`에 있다.
직접 import하면 역방향 의존이 생기므로 `CoverPicker`의 `header` 슬롯(0528)과 동형으로 처리:

```ts
flight?: {
  tripType: 'ONE_WAY' | 'ROUND_TRIP';
  totalAmount: number;
  table: React.ReactNode;
} | null;
```

```tsx
// 호출부(PlanFinderDetail)
flight={publicFlight && {
  tripType: publicFlight.tripType,
  totalAmount: publicFlight.totalAmount,
  table: <PublicFlightTable data={publicFlight} />,

```

### 그룹 summary는 "N건"을 쓰지 않는다

```tsx
summary={`${flight.tripType === 'ROUND_TRIP' ? '왕복' : '편도'} · ${formatAmount(flight.totalAmount, currency)}`}
```

다른 두 그룹의 `groupSummary`("N건 · 금액")를 쓰면 왕복이 "1건"이 된다 — 실제로는 2편이라 거짓.
왕복/편도 어휘는 `FlightLeg`·`FlightSearchSection`과 한 벌.

### plan 이후 발견 — "첫 그룹 = 고정"이 전제였다

항공을 고정에서 빼자 **무장소 비용이 없는 플랜에서 항공권이 첫 그룹**이 된다.
기존 코드는 고정이 `mt-4`(카테고리 목록과 26px), 나머지가 `mt-1.5`로 **하드코딩**돼 있어
첫 그룹이 카테고리 목록에 붙었다.

```ts
const GROUP_MT = (first: boolean) => (first ? 'mt-4' : 'mt-1.5');
```

```tsx
<div className={GROUP_MT(true)}>                                   {/* 고정 */}
<div className={GROUP_MT(fixedItems.length === 0)}>                 {/* 항공권 */}
<div className={GROUP_MT(fixedItems.length === 0 && !flight)}>      {/* 일자별 */}
```

일자별이 첫 그룹인 경우(비용이 전부 일자별)의 같은 버그도 함께 해소됐다 — 기존에도 있던 것.

### 스켈레톤 짝 (CLAUDE.md §11)

- 항공 섹션 골격 삭제 — 그룹은 기본 접힘이라 로딩 중 노선표가 드러나지 않는다
- 접기 헤더 `[0, 1]` → `[0, 1, 2]`

### 보고 (§8 — 임의 수정 안 함)

그룹 회색 점이 `bg-[#b3b9bd]` 하드코딩(`PublicCostSection.tsx`), 일정 행 번호도 같은 값
(`PlanFinderDetail.tsx`). 기존 그룹들의 공통 화석이라 이번이 도입은 아니지만,
그룹이 하나 늘어 **같은 하드코딩이 한 곳 더 늘었다**. 토큰화는 별건.

### 수용한 극단

비용 항목 전무 **AND** 항공 `totalAmount === 0`이면 예상 비용 섹션 자체가 미렌더돼
노선표가 사라진다(현재는 보임). `PlanCost`는 `amount > 0`만 저장되고 항공가는 외부 API
실가격이라 발생 불가로 판단해 수용. 게이트를 넓히면 "총 ₩0 + 빈 막대"라는 더 이상한
화면이 생긴다.

### 배운점

초안 —

- **"두 곳에 나온다"의 원인이 데이터 층이 아닐 수 있다.** lib은 처음부터 항공을 별개
  그룹으로 내보내고 있었고, 뭉갠 건 소비처 한 줄(`filter(g => g.day === null).flatMap`)이었다.
  조사에서 이걸 먼저 확인해 lib·테스트·story 3곳을 건드리지 않는 범위로 좁혔다.
  (0556의 "화면이 다르다의 원인은 조판 층이 아닐 수 있다 — select 한 줄이었다"와 같은 유형)
- **원소를 빼면 남은 것의 전제도 함께 검사할 것.** 항공을 고정 그룹에서 빼자
  "첫 그룹 = 고정"이라는 조판 전제가 깨졌다. plan 단계에서 못 본 것을 구현 중 발견 —
  하드코딩된 `mt-4`가 "첫 번째"가 아니라 "고정"에 붙어 있던 게 원인.
- **부수 해소를 노리지 않아도 구조를 고치면 따라온다.** 편도 오표기는 별건 백로그였는데,
  거짓을 만들던 제목 자체가 사라지면서 재발 경로가 없어졌다. 표기를 고치는 대신
  표기가 필요 없는 구조로 간 것.

# B — 읽기 지표 밴드 4열

## 한 줄 요약

지표 밴드를 3열(기간·장소·총 비용)에서 4열(기간·장소·인원·총 비용)로 넓히고 총액 옆
"· N인"을 걷어냈다. 모바일에서도 4열을 유지하되 열 분배만 비균등으로 바꿨는데,
그 과정에서 **구 3열 조판이 천만원대 총액을 실제로 자르고 있었다**는 걸 실측으로 확인했다.

## 왜 / 목적 / 이유

초안 — 인원이 밴드에 합류한 건 C(폼 밴드)가 같은 4칸을 쓰기 때문. 동시에 총액 옆
"· N인"과 밴드가 같은 값을 두 자리에 두는 상태였어서, 지표로 올리며 아래를 걷어냈다.

모바일 4열 유지는 사용자 지시가 근거를 함께 줬다 — "2×2로 접으면 읽기와 형태가 갈려
'저장하면 이 모습' 예측이 깨진다."

## 작성한 프롬프트

```
A→B→C→D→E 순서 그대로 진행. (…)
검수 모드에 추가 — 각 사이클마다 다음을 확인할 것:
- 라이트·다크 양쪽 (토큰을 쓰는지, 하드코딩 색이 없는지)
- 360px 모바일 (열이 어떻게 접히는지, 가로 스크롤이 안 생기는지)
- 지표 밴드는 모바일에서도 4열 유지 — 2×2로 접으면 읽기와 형태가 갈려
  "저장하면 이 모습" 예측이 깨진다
```

360px 폭 문제를 보고했을 때의 결정 + 검산 지시:

```
1번으로. 근거: 지표 밴드는 한눈에 들어오라고 만든 자리라 크기를 깎으면 역할이 약해진다.
총 비용이 그중 제일 중요한 값이라 3번은 신호가 거꾸로 간다.
데스크톱도 원래 max-content 비균등이라 모바일 비균등이 기존 방식에 더 가깝다.

다만 백만원대(₩1,250,000) 8자리로 검산할 것 —
지금 표본은 ₩503,844 6자리라 통과해도 근거가 약하다. 넘치면 그때 다시 판단하자.
```

## 코드 작성 & 수정

### 열 분배 — 모바일만 비균등

```tsx
<div className="… grid grid-cols-[auto_auto_auto_1fr] sm:grid-cols-4 gap-x-2 …">
```

360px 산수: 콘텐츠 312(px-6) − gap 24 = 288. 균등이면 칸당 72px인데 백만원대가 그보다 크다.
앞 3칸을 콘텐츠 폭으로 두면 총 비용이 남는 폭을 전부 가져간다.

0516이 "균등 1fr"로 정한 건 **3열일 때** 판정이고 4열은 새 조건. 데스크톱(sm+)은 균등
그대로 두어 기존 판정이 유효한 구간은 안 건드렸다.

### 조건부 렌더 폐기

```tsx
// before — 총액 0이면 칸이 통째로 빠져 밴드 형태가 플랜마다 달라졌다
{summary.total > 0 && (<div>…</div>)}
// after
{summary.total > 0 ? formatAmount(summary.total, currency) : '—'}
```

장소 0곳·인원 1인은 "—" 대상이 아니다 — 없는 게 아니라 0이고 기본값이다.

### 기간 라벨을 lib으로 승격

```ts
// lib/plan/format-day-label.ts
export function formatDurationLabel(dayCount: number): string {
  return dayCount > 1 ? `${dayCount - 1}박 ${dayCount}일` : '당일';
}
```

공유하는 건 **문자열 산출뿐**이고 밴드 조판은 각 화면이 따로 짠다 (0556 결정: 폼 정합은
조판·용어만, 컴포넌트 공유 금지).

날짜 미설정은 이 함수가 모른다 — `page.tsx`가 `dayCount`를 1로 폴백해 실제 당일치기와
구분이 안 되므로, 호출부가 `startDate`·`endDate` 유무로 먼저 판정해 "—"를 쓴다.

# C — 작성 폼 지표 밴드

## 한 줄 요약

폼 제목 아래에 읽기와 같은 형태의 지표 밴드를 두어, 입력하는 동안 "저장하면 이 모습"이
상단에서 실시간으로 보이게 했다.

## 왜 / 목적 / 이유

초안 — 트랙의 출발점이던 문제("작성자가 저장 결과를 예측할 수 없어 쓸 의욕이 떨어진다")에
가장 직접적으로 대응하는 사이클. A·B에서 읽기를 목표 형태로 굳혔으므로 이제 폼이 그 형태를
상단에서 미리 보여준다.

## 작성한 프롬프트

```
C 진행. 확인 항목 추가:

- 새 계획(빈 상태)에서 밴드가 "— / 0곳 / 1인 / —"으로 뜨는지
  (기간·총액은 "—", 장소는 0곳, 인원은 기본 1인)
- 날짜를 고르는 순간 기간이 채워지는지, 장소를 추가할 때 곳수가 오르는지
- 밴드 아래 설명 문구는 넣지 않는다 (확정)
- 장소 수는 handleSave의 name.trim() !== '' 필터와 같은 조건으로
  — 저장 후 읽기 값과 어긋나면 안 됨
```

## 코드 작성 & 수정

### 저장 조건을 술어로 추출 — 두 곳에 적지 않는다

```ts
// 0562(C): 저장 대상 항목 판정 — 이름이 빈 행은 저장되지 않는다.
//   지표 밴드의 "장소 N곳"과 handleSave가 **같은 조건**을 써야 저장 직후 읽기 화면의
//   장소 수(= PlanSpot 행 수)와 어긋나지 않는다. 조건을 두 곳에 적으면 조용히 갈린다.
function isSavableItem(item: PlanItem): boolean {
  return item.name.trim() !== '';
}
```

`handleSave`의 인라인 필터를 이 술어로 교체하고 밴드가 같은 걸 쓴다.

### 기간 — dayCount만으로는 부족

```ts
const durationLabel =
  editor.startDate && editor.endDate && editor.days.length > 0
    ? formatDurationLabel(editor.days.length)
    : '—';
```

`days`는 `calcDays` 산출이라 역순 날짜(diff < 0)면 **빈 배열**이 된다. 길이를 함께 보지
않으면 `formatDurationLabel(0)`이 "당일"을 돌려줘 거짓이 된다. (읽기 쪽은 `page.tsx`가
dayCount를 1로 폴백해 사정이 달라, 같은 "—" 판정이라도 근거가 다르다.)

### 조판은 준용, 컴포넌트는 공유 안 함

읽기 밴드의 리터럴을 그대로 옮기고 **양쪽에 상호 참조 주석**을 달았다 —
0556 결정("폼 정합은 조판·용어만, 컴포넌트 공유 금지")에 따라 공유하는 건 값 산출
함수(`formatDurationLabel`)뿐이다.

## 결과 / 배운점

### 실측 — 실제 폼을 조작하며 밴드를 읽음

CDP로 React 제어 input에 네이티브 setter + `input` 이벤트를 넣어 실제 조작을 재현했다.

| 단계 | 밴드 |
|---|---|
| ① 빈 상태(새 계획) | `— / 0곳 / 1인 / —` |
| ② 날짜 2026-09-01~09-03 | `2박 3일 / 0곳 / 1인 / —` |
| ③ 인원 3 | `2박 3일 / 0곳 / 3인 / —` |
| ④ **항목 추가(이름 빈칸)** | `2박 3일 / 0곳 / 3인 / —` — 안 오름 |
| ⑤ 이름 "남산타워" 입력 | `2박 3일 / 1곳 / 3인 / —` |
| ⑥ 금액 50000 | `2박 3일 / 1곳 / 3인 / ₩50,000` |

④가 핵심 — 이름 빈 행은 저장되지 않으므로 세지도 않는다(`isSavableItem` 공유의 실증).

- 레이아웃: 360px 밴드 클리핑 0 / 768px 균등 4열 **칸당 174px — 읽기와 동일 수치**
- 다크: 값 `rgb(240,238,232)` 라벨 `rgb(122,120,112)` — **B에서 잰 읽기 밴드와 정확히 일치**
- `tsc`·eslint 통과, `npm test` 회귀 없음(기존 6스위트)

### 보고 (§8 — 임의 수정 안 함)

**폼 @360px에 가로 스크롤이 있다**(`scrollWidth 553` vs `clientWidth 360`). 원인은 밴드가
아니라 일정 행 `SortablePlanItem`의 6열 그리드(드래그·아이콘·이름·카테고리·금액·삭제) —
넘치는 요소가 행 입력(right=517)과 삭제 버튼(right=553)이다.

C 이전 커밋(`91a3e28`)에서 같은 조작을 했을 때 **`scrollWidth 553`으로 완전히 동일**하므로
기존 문제이고, **E 사이클에서 그 행을 재조판(카테고리·금액 제거)하면 해소될 자리**라
지금 고치지 않았다. 지금 손대면 E에서 다시 뒤집힌다.

### 배운점

초안 —

- **"같은 조건"은 주석이 아니라 코드로 묶어야 한다.** 밴드와 저장이 각각
  `name.trim() !== ''`를 적었어도 당장은 맞지만, 한쪽만 바뀌면 저장 후 숫자가 갈리고
  그건 화면에서 즉시 안 보인다. 술어 하나로 묶으니 갈릴 방법이 없어졌다.
- **같은 "—"라도 판정 근거는 화면마다 다를 수 있다.** 읽기는 dayCount 폴백 1 때문에
  날짜 유무를 보고, 폼은 거기에 더해 역순 날짜(빈 배열)까지 본다. 표시를 맞추려고
  판정까지 복사하면 폼에서 "당일"이라는 거짓이 나온다.
- **기존 결함을 발견해도 지금 고칠 자리가 아닐 수 있다.** 폼의 가로 스크롤은 실재하지만
  원인 블록이 다음 사이클의 재조판 대상이라, 여기서 고치면 두 번 일하고 커밋 이력만
  흐려진다. 발견 시점과 수정 시점을 분리하는 편이 낫다.

# D — 비용 상태 분리 + 2패스 저장 + 복원 3분류

## 한 줄 요약

일정 항목에서 카테고리·금액을 떼어 dayCosts 별도 컬렉션으로(DB PlanCost 동형), 비용 입력을
전부 "예상 비용" 아래로 통합했다. 조사 단계 DB 실측이 **시드 90행이 편집→재저장에서 전량
소실되는 기존 버그**를 찾아냈고, D의 복원 3분류가 이를 해소했다(실플랜 라운드트립으로 실증).

## 왜 / 목적 / 이유

초안 — 폼의 일정 행이 이름+카테고리+금액 한 몸(장부형)이라 읽기 행과 딴판이던 것의
**상태 층 원인**. DB는 이미 분리돼 있었고(PlanCost 독립·planSpotId nullable) 붙어 있던 건
폼 상태와 payload뿐이었다. E(행 재조판)는 이 분리가 선행돼야 성립.

## 작성한 프롬프트

```
D 들어가기 전에 상태를 정리하자. (…)
그다음 D plan 작성. 순서는 조사에서 확정한 대로:
① refactor: place.id 의미 통일(생성=Kakao / 편집=Spot) — 선행 별도 커밋
② feat: 비용 상태 분리 + 2패스 저장 + costBySpotId 배열화

plan에 반드시 포함할 것:
- 저장 → 재열람 → 재저장 라운드트립 검증 절차
- 장소당 비용 다건일 때 복원이 맞는지
- planSpotId가 null인 "기타 지출"이 일자별 그룹에 들어가는지
- 기존 34개 플랜에 파괴적 변화가 없는지
```

검증 방식 확정: "2번으로. 자격증명은 공유하지 않는다. 전후 DB 덤프 스크립트를 준비해줘. (…)
내가 할 일을 순서대로 적어줘."

## 코드 작성 & 수정

### 조사(plan 단계) DB 실측이 잡은 것

| 발견 | 의미 |
|---|---|
| `day≠null && planSpotId=null` **90행 실존**(시드) | "기타 지출" 형태가 이미 실존, 읽기는 이미 렌더 |
| **구 복원이 이 90행을 드롭** — daylessCosts 필터에도 costBySpotId에도 안 걸림 | 시드 플랜 편집→저장 = 비용 전량 소실(기존 버그) |
| 폼 합산이 daylessCosts 제외 | 읽기(summarize)는 포함 — 폼 총액 과소(기존 미정합) |

### place.id 제거 (`ef8713a`)

생성 경로 Kakao POI id / 편집 복원 Spot.id — 같은 필드에 다른 의미. payload 미포함이라
무해했지만 E가 키로 쓰는 순간 터진다. 스팟 해소는 서버가 (name, lat, lng)로 하므로
클라 id는 어느 의미로도 쓸 곳이 없음 → **필드 제거가 통일**.

### 상태·저장·복원 (`6f65f39`)

```ts
type DayCost = { localId: string | null; day; category; amount; label };
// localId = 연결 item.id(편집 = PlanSpot.id), null = 기타 지출
```

- 저장 2패스: 1패스 planSpot 생성 + `Map<localId, {id, name}>`, 2패스 dayCosts → planCost.
  **연결 비용 라벨은 서버가 장소 이름으로 강제**(단일 소스) — 장소당 다건 개방

- UI: 예상 비용 아래 회색 점 그룹 셋(고정/항공권/일자별 — 읽기와 같은 구조·이름),
  일자별은 날짜 탭 + [장소 드롭다운(그날 한정 + 기타 지출)/카테고리·금액].
  0561 "합산은 모든 입력 뒤" 예외 결정은 이 통합으로 대체(주석 정정)

## 결과 / 배운점

### 라운드트립 (전후 DB 덤프 + 정규화 멀티셋 diff, 저장 클릭은 사용자)

| 시나리오 | 대상 | 판정 |

### 배운점

초안 —

- **plan 단계의 DB 실측이 스펙에 없던 버그를 찾는다.** "기타 지출" 형태가 신규인 줄 알았는데

  먼저 정의하지 않은 비교는 거짓 경보를 낸다.
- **기본값은 저장 결과를 바꾼다.** S3 어긋남의 유력 원인은 드롭다운 기본값(그날 첫 장소) —
  기타 지출이 맨 끝 옵션이라 전환 없이 저장되기 쉽다. 실사용 검수가 아니면 CDP 재현만으로는
  (기계는 항상 옵션을 정확히 고르므로) 안 잡혔을 유형.

# E — 일정 행 재조판 + 썸네일 대표 지정 + CoverPicker 폐기

## 한 줄 요약

폼 일정 행을 읽기 행과 같은 골격([번호][72px 썸네일][이름·칩·주소])으로 만들고,
대표 이미지 지정을 별도 섹션(CoverPicker)에서 행 썸네일 클릭으로 옮겼다.

## 왜 / 목적 / 이유

초안 — 트랙 목표 ②의 마감. 대표 이미지를 행에서 고르게 하면 원인(장소)과 결과(커버)가
한 자리에 놓인다 — 구 CoverPicker는 후보를 URL 중복 제거한 별도 목록으로 보여줘
"어느 장소의 사진인지"가 끊겨 있었다.

## 작성한 프롬프트

```
E 사이클 진행 — 일정 행 재조판 + 썸네일 대표 지정 + CoverPicker 폐기
[목표] [드래그][번호][72px 썸네일][이름 입력 + 작품 칩 + 주소][삭제]
[확정된 결정] 대표 배지는 항목 단위 / 0497 안내 문구 폐기

```

## 코드 작성 & 수정

- **`resolvePlanItems`**: resolveReuse(200m+이름) → 인덱스 정렬 배열로
  `{spotId, coverUrl, movie, address} | null`. coverUrl = `spot.coverUrl ?? 최신 스토리
  사진`(0509) — 읽기 행과 같은 규칙. 구 액션은 중복 제거·커버 있는 Spot만이라 1:1 불성립 → 대체
- **행**: 썸네일·칩은 해소된 재사용 Spot만(없으면 자리 생략 — 읽기와 동일), 주소는
  `meta.address ?? place.address`(신규 Spot도 저장 시 Kakao 주소를 가지므로 저장 후
  읽기와 같은 표시 규칙), 번호는 그날 연속
- **대표 배지 = `coverItemId`(항목 단위)**: 클릭 토글, 편집 복원은 첫 해소 도착 시
  기존 coverUrl **첫 매치 1회** 초기화(배지는 항상 한 행), 대표 항목의 삭제·장소 변경 시
  배지·커버 동반 해제. 저장 payload·0497 edit 시맨틱 무변
- 해소 캐시는 CoverPicker의 디바운스(400ms)·seq 가드 관용구 이식. 신규 린트 규칙
  (`react-hooks/set-state-in-effect`)에 걸려 빈 목록 리셋·배지 초기화를 비동기 콜백 안으로
- 계획은 2커밋(표시/지정)이었으나 같은 JSX 블록이라 1커밋(`ef3accb`) — CoverPicker 대체라는
  한 기능

## 결정 (Decisions)

### A

- 항공은 독립 섹션이 아니라 **비용의 형제 그룹** — 순서는 고정 비용 / 항공권 / 일자별
- 0492의 "왕복 총액은 한 곳에만" 원칙은 유지, **위치만** 섹션 제목 → 그룹 헤더로 이관
  (회고 0492는 시점 기록이라 미수정, 정본은 코드 주석)
- 항공권 그룹 제목은 tripType 무관 `항공권` — 왕복/편도는 summary가 표기
- 접기 그룹의 첫 그룹 위여백은 **앞 그룹 존재 여부로 산출**(`GROUP_MT`) — 특정 그룹에
  고정하지 않는다
- 컴포넌트 간 방향이 역행할 땐 **슬롯으로 뒤집는다**(0528 `CoverPicker.header` 선례 적용)

### B

- 지표 밴드는 **4열 고정** — 모바일에서도 2×2로 접지 않는다(폼과 형태가 갈리면 예측이 깨짐)
- 열 분배는 **모바일만 비균등**(앞 3칸 auto + 총 비용 1fr), sm+는 0516 균등 유지 —
  0516의 균등은 3열일 때 판정이라 4열엔 자동 승계되지 않는다
- 밴드 칸은 **값이 없어도 빼지 않는다** — "—"로 채운다. 칸이 빠지면 밴드 형태가
  플랜마다 달라진다. 단 0곳·1인은 실값이라 "—" 대상이 아니다
- 인원의 정본은 **지표 밴드** — 총액 옆 "· N인"은 폐기
- 폼과 공유하는 것은 **문자열 산출 함수뿐**, 밴드 조판은 각 화면이 따로(0556 재확인)
- 조판 검증은 **CDP 뷰포트 실측**으로 — 헤드리스 스크린샷의 잘림은 아티팩트일 수 있다

### C

- 폼 밴드는 **파생 읽기 전용** — 입력 필드가 아니다. 설명 문구도 두지 않는다(라벨이 뜻을 담음)
- 밴드의 "장소 N곳"과 저장은 **같은 술어**(`isSavableItem`)를 쓴다 — 조건 복제 금지
- "—" 판정 근거는 화면마다 다를 수 있다 — 표시만 맞추고 판정은 각자의 폴백 사정에 맞게
  (읽기는 날짜 유무, 폼은 날짜 유무 + 역순 날짜)
- 폼↔읽기 밴드는 **리터럴 준용 + 상호 참조 주석**, 컴포넌트 공유는 안 한다(0556 재확인)
- 기존 결함이라도 **다음 사이클의 재조판 대상이면 그때 고친다** — 폼 360px 가로 스크롤은
  E에서(일정 행 6열이 원인)

### D

- 폼 비용 상태 = DB 동형(dayCosts ↔ PlanCost) — localId 하나로 연결, 라벨은 서버가
  장소 이름으로 강제(단일 소스)
- place.id는 **제거가 통일** — 의미가 둘인 필드는 맞추는 게 아니라 없앤다
- 복원은 day 유무로 3분류 — planSpotId 없는 day 비용(기타 지출·시드)은 드롭이 아니라 포섭
- 라운드트립 판정은 **정규화 멀티셋**으로 — 재생성되는 id·createdAt·order 원값은 비교 제외,
  불변량은 {값들} + 일자 내 상대 순서
- 항목 삭제 = 연결 비용 삭제, 날짜 축소 = 해당 일 비용 소멸 — 구 결합 구조의 동작 보존
- 복원이 실어 오는 값은 **그 화면에서 의미 있는 것만** — 연결 비용 라벨(사본)은 비운다

### E

- 대표 이미지 지정 = 행 썸네일 클릭(원인과 결과 한 자리), 배지는 **항목 단위**(coverItemId)
- 폼 썸네일·칩·주소의 표시 규칙은 **저장 후 읽기와 동일**(coverUrl = spot ?? 스토리 폴백,
  주소 = Spot ?? Kakao) — "저장하면 이렇게 나온다"의 성립 조건
- 구 액션의 상위집합 액션은 **대체**한다(병존 금지 — 같은 해소를 두 번 돌게 됨)
- 편집 복원 배지는 첫 해소 도착 시 URL 첫 매치 1회 — 이후는 사용자 클릭만
