## 1. 한 줄 요약

회원 탈퇴를 "익명화 보존" 방식으로 구현했다. 개인정보(이메일·프사)는 삭제하고 닉네임은 "잊혀진 여행자_XXXX"로 익명화하며, Supabase auth 계정만 삭제해 로그인을 막고, 작성한 콘텐츠(스토리·계획·좋아요)는 전부 보존한다. 단순 삭제가 아니라 "무엇이 개인정보이고 무엇이 콘텐츠인가"를 법·실무 근거로 구분한 것이 핵심이다.

---

## 2. 왜 / 목적 / 이유

### 방향 결정 — 완전 삭제 vs 익명화 보존

- **왜**: 탈퇴 시 데이터를 어떻게 처리할지가 먼저다. "무조건 다 파기"가 직관적이지만, 서비스 관점에서 콘텐츠(공개 피드·좋아요·촬영지 정보)를 잃으면 커뮤니티 가치가 무너진다.
- **법적 근거 (web_search 확인)**: 개인정보보호법상 파기 의무는 **개인을 식별할 수 있는 정보**(이메일·닉네임·프사)에 적용된다. 게시물 본문 자체가 곧 개인정보인 것은 아니다. 즉 개인정보(식별자)는 파기하되, 게시물은 작성자와의 연결을 익명화하면 남길 수 있다. 실무(카카오·잡코리아 등)도 이 방식이다.
- **결론**: **익명화 보존** 채택. 개인정보는 파기/익명화, 콘텐츠는 익명 신원에 연결해 보존.

### 예산(band)은 개인정보가 아니지만 계속 가린다

- 논의 중 "예산이 개인정보가 아니라면 공개 피드에서 굳이 band로 가릴 필요가 있나"라는 질문이 나왔다.
- **구분**: 법적 파기 의무(개인정보)와 프라이버시·UX 설계(band)는 **별개 층위**다. 금액은 개인정보가 아니므로 탈퇴 시 파기하지 않고 콘텐츠로 보존한다. 그러나 공개 피드에서 band로 가리는 것은 법이 아니라 설계 선택이며, ①심리적 프라이버시 ②허세·경쟁 방지("여행에 500만원 썼다" 과시 억제) ③가격대 비교 UX라는 이유로 여전히 유효하다.
- 즉 "탈퇴 시 보존"과 "공개 피드에서 band"는 각각 다른 이유로 둘 다 옳다. 모순이 아니다.

### 구현 방향 — User 익명화 + auth만 삭제

- **왜**: 콘텐츠(스토리·계획)는 `userId`/`ownerId`로 User를 참조한다. User 레코드를 삭제하면 콘텐츠가 Cascade로 딸려 삭제되거나 FK가 깨진다.
- **이유**: 그래서 **User 레코드는 삭제하지 않고 내용만 익명화(UPDATE)**한다. 익명화는 UPDATE라 Cascade(DELETE 시만 발동)와 무관하게 FK가 유지된다. Supabase `auth.users`와 Prisma `public.users`는 별도 테이블이고 FK가 없어, auth 계정만 삭제하면 로그인은 막히되 User 레코드는 남는다. 확증으로 이 구조를 먼저 확인한 뒤 진행했다.

## 3. 작성한 프롬프트

(요지. 실제 원문은 커밋 작업 기록에서 옮긴다.)

- **탈퇴 액션**: 본인 확인(auth.getUser) → Prisma 트랜잭션 익명화(email placeholder / nickname / avatarUrl null / sourceNickname) → 아바타 Storage 삭제 → auth.admin.deleteUser → signOut·redirect. `[하지 말 것]` User DELETE 금지(UPDATE만), auth 삭제를 익명화보다 먼저 금지, 콘텐츠(스토리 이미지·본문·계획) 삭제 금지.
- **문구 정확화**: 위험구역 안내를 실제 동작에 맞춰 항목별로(삭제/변경/보존/로그인 불가).

## 4. 코드 작성 · 수정

> 커밋 전 CC "읽고 보고만"으로 실제 파일과 대조 예정.

### deleteAccountAction 순서 (mypage/actions.ts)

```ts
// 1) 본인 확인
const { data: { user } } = await supabase.auth.getUser();
// 2) 트랜잭션으로 익명화 (원자적)
await prisma.$transaction([
  prisma.user.update({ where: { id: user.id }, data: {
    email: `deleted_${user.id}@deleted.local`,   // placeholder (email NOT NULL·UNIQUE → 고유값 교체)
    nickname: `잊혀진 여행자_${suffix}`,           // 익명화
    avatarUrl: null,
  }}),
  // sourceNickname 익명화: 이 사용자의 스토리/계획을 소스로 복사한 복제본들
  prisma.myPlan.updateMany({ where: { sourcePlanId: { in: myPlanIds } }, data: { sourceNickname: ... } }),
  // ...
]);
// 3) 아바타 Storage 파일 삭제 (트랜잭션 밖 — 외부 리소스)
// 4) auth 계정 삭제 (admin 클라이언트, service_role) — 마지막
await createAdminClient().auth.admin.deleteUser(user.id);
// 5) signOut + redirect('/')  ← try/catch 밖 (redirect는 throw 방식)
```

## 5. 결과 · 배운점

### 결과 (실제 검증)
- 탈퇴 후 재로그인 실패(auth 삭제 확인).
- 콘텐츠가 "잊혀진 여행자_CD2A"로 작성자 표시되며 보존 — 공개 피드·스토리 상세·**SpotFinder 촬영지 출처**까지 모두 익명화 반영.
- 개인정보(이메일·닉네임·프사)는 삭제/익명화, 스토리 이미지·본문·계획은 유지.

### 배운점 ① — "무엇이 개인정보인가"의 구분이 설계를 가른다

"탈퇴 = 다 삭제"가 아니다. 파기 대상은 **식별자**(이메일·닉네임·프사)이고, 콘텐츠(예산 포함)는 작성자 연결만 끊으면 보존할 수 있다. 이 구분을 정확히 해야 "개인정보보호법상 파기 의무를 지키면서 커뮤니티 콘텐츠는 보존"이라는 설계가 나온다. band를 예로, "개인정보가 아니다"(파기 불필요)와 "그래도 가린다"(프라이버시·UX)는 별개 층위임을 구분해야 논리가 무너지지 않는다.

### 배운점 ② — 익명화 보존의 기술적 관문

- **User 삭제 대신 익명화(UPDATE)**: 콘텐츠 FK를 유지하려면 User를 지우면 안 된다. UPDATE는 Cascade와 무관해 FK가 안 깨진다.
- **auth ↔ public.users FK 없음**: auth만 삭제하고 User는 남기는 구조가 가능함을 확증으로 확인.
- **sourceNickname 구멍**: 남이 내 공개 계획을 복사하면 원작자 닉네임이 `sourceNickname` 스냅샷으로 남는다. 탈퇴 시 이것도 익명화하지 않으면 닉네임(개인정보)이 복제본에 남는다. id 리스트 서브쿼리로 정확히 매칭해 함께 익명화했다. (놓치기 쉬운 개인정보 누출 지점.)
- **service_role 보안**: auth 삭제에 필요한 service_role 키는 RLS를 무시하는 관리자 키다. `import 'server-only'` + env(NEXT_PUBLIC_ 금지)로 클라이언트 노출을 원천 차단.
- **순서**: auth 삭제를 마지막에 둔다(먼저 하면 세션이 날아가 이후 작업이 꼬임). `redirect()`는 throw 방식이라 try/catch 밖에 둔다(catch가 삼키면 리다이렉트 실패).

### 배운점 ③ — 고지 문구는 "해석의 여지"를 없애야 한다

초안 문구가 "개인정보는 익명 처리됩니다"였는데, 실제로는 이메일·프사는 **삭제**, 닉네임만 **변경**이다. "익명 처리"라는 뭉뚱그린 표현은 "내 이메일이 익명으로 어딘가 남아있나?"라는 엉뚱한 해석을 낳는다. 법 문언의 핵심은 해석의 여지를 없애는 것(판례법이 그 여지를 메우는 과정)이므로, 항목별로 정확히 나눴다:
1. 이메일과 프로필 사진은 삭제됩니다.
2. 닉네임은 "잊혀진 여행자"로 변경됩니다.
3. 작성한 스토리·계획·좋아요는 익명 계정으로 남습니다.
4. 로그인은 다시 할 수 없습니다.

이 문구는 나중에 만들 가입 동의·처리방침 문서의 기준이 된다(콘텐츠 익명 보존을 정당화하려면 가입 시 동의가 필요).

### 한 줄 교훈
탈퇴는 "삭제 버튼"이 아니라 "무엇이 개인정보이고 무엇이 콘텐츠인가"를 법·실무로 구분하는 설계 문제다. 그리고 사용자에게 알리는 문구는 실제 동작과 1:1로 맞아 해석의 여지가 없어야 한다.

### 남은 과제
- 가입 동의·개인정보 처리방침 문서 작성 (탈퇴 시 콘텐츠 익명 보존을 정당화, 위 4줄 문구가 기준).
