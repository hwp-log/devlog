## 1. 한 줄 요약

프로그램 이동 중 유일하게 0ms 점프였던 퇴화(1지점) 경로를 morph로 바꾸고, 노브가
없는 fitBounds를 SDK 프로젝션 기반 자체 줌 계산으로 대체해 전 경로를 하나의
transition 상수(1000ms)로 통일. 이어서 칩·리스트의 비결정 순서를 규칙(스팟 수 →
최근 등록순)으로 확정하고, 첫 항목 자동 선택·초기 중심을 선택 스팟 좌표로 옮겨
"열면 최신 촬영지가 지도 정중앙에 카드로 떠 있고 상세 패널이 열려 있는" 첫 화면을
완성. 마커 카드 배율과 3열 구분선은 실물 대조로 수렴.

## 2. 왜 / 목적 / 이유

### 전 경로 morph 통일 (0169)
- **왜**: 클러스터 클릭 시 순간이동처럼 보이는 구간이 있었다. 50ms 샘플링 실측 결과
  칩 fitBounds ~516ms, 일반 분해 ~511ms, 리스트 panTo ~560ms로 대부분 이미 SDK
  이징이었고, **퇴화(1지점) 경로만 setZoom+setCenter로 0ms 즉시 점프**였다.
  이것이 관찰된 어색함의 실체였다.
- **목적**: 프로그램이 지도를 옮기는 모든 경로의 전환 질감을 하나로 맞추고, 그 속도를
  한 곳에서 조절할 수 있게 한다.
- **이유**: 퇴화 경로를 morph로 바꾸자 이번엔 다른 어긋남이 드러났다. morph는
  duration 노브를 받는데 **fitBounds는 SDK API 설계상 duration/easing을 안 받는다**.
  87행만 800ms로 올리면 1지점 이동(800ms)과 일반 분해(500ms 고정)의 질감이 갈린다.
  경로가 갈린 이유는 "목적지 줌을 아는가"였다 — 1지점은 좌표+상한 줌을 직접 지정할
  수 있고, 여러 지점은 뷰포트 픽셀·마진에 따라 달라지는 줌 계산을 SDK에 위임했다.
  그래서 그 계산을 우리가 직접 수행해 전 경로를 morph로 통일했다.

### 줌 계산을 프로젝션에 위임
- **왜**: fitBounds가 하던 계산(뷰포트 폭 ÷ bounds 폭의 log₂)을 재현해야 했다.
- **이유**: Web Mercator 표준 상수(타일 256px)를 하드코딩하지 않고
  `map.getProjection()`의 좌표↔월드픽셀 변환에 위임했다. 근거는 실측 —
  naver GL의 도/픽셀 비가 표준 256 기반 예측과 어긋났다(z11에서 0.000301°/px 실측
  vs 표준 0.000687). 상수 가정은 회귀 위험이고, 프로젝션 위임은 SDK 내부와 정의상
  일치한다.

### 칩·리스트 정렬 (0170·0171)
- **왜**: 칩 첫 자리가 수리남이었다. 원인을 실측하니 `fetchSpotFinderSpots`에
  orderBy가 아예 없어 **DB 반환 순서에 좌우되는 비결정 상태**였고, 칩은 그 배열에서
  작품이 처음 등장한 순서(객체 삽입 순서)를 따르고 있었다. 지금 순서가 우연이었다.
- **목적**: 탐색 진입점인 칩과 리스트가 "왜 이 순서인가"를 설명할 수 있는 규칙을
  갖게 한다.
- **이유**: 칩은 ① 스팟 수 내림차순 → ② 작품별 최근 스팟 등록 시각 내림차순.
  1차 기준은 콘텐츠 밀도(많이 기록된 작품이 탐색 진입점), 2차는 신선도(같으면 최근에
  움직임 있는 작품). 리스트는 최신 등록순 — 특정 작품을 앞세우는 하드코딩 대신
  규칙으로 처리했다. 실제로 미생 촬영지(서울스퀘어)를 하나 더 등록하자 미생이
  1차 기준만으로 1위가 됐다. **하드코딩 없이 규칙이 목적을 달성**한 셈이다.
- 집계는 서버 groupBy 쿼리 대신 이미 전량 내려온 `spots`의 클라 파생으로 했다.
  같은 사실을 서버 집계로 또 내려보내면 이중 소스이고 왕복이 추가된다. 반면 리스트
  순서는 소스(쿼리 orderBy)에서 정했다 — 리스트·마커·상세가 같은 배열 순서를
  공유하므로 소스에서 정하면 파생이 전부 따라온다. **같은 "정렬"이지만 층이 다르다.**

### 초기 자동 선택 (0172)
- **왜**: 첫 화면의 상세 패널이 비어 있어 "리스트를 클릭하면 상세가 나온다"는
  상호작용 문법이 안 보였다.
- **목적**: 첫 화면이 스스로 사용법을 안내하게 한다.
- **이유**: 여기서 정책 충돌이 하나 있었다. 선택에는 panTo가 묶여 있는데, 초기
  자동 선택에도 이동이 따라붙으면 0169에서 정한 "서울 확대 시작"이 데이터에 따라
  무력화된다(최신 스팟이 제주면 첫 화면이 서울로 시작하자마자 제주로 미끄러진다).
  그래서 **"조용한 선택"** — 리스트 하이라이트와 패널만 열고 지도는 안 움직인다.
  구현은 플래그가 아니라 **코드 경로 분리**: 초기 선택은 `useState` 초기값이라
  panTo가 있는 `handleSpotSelect`를 애초에 경유하지 않는다. 이동 없음이 조건 검사가
  아니라 구조로 보장되고, 나중에 누가 고쳐도 이동이 실수로 붙을 경로가 없다.

### 초기 중심 = 선택 스팟 좌표 (0175)
- **왜**: 자동 선택된 마커가 화면 크기에 따라 지도 열 중앙을 벗어났다. 클릭 선택은
  panTo로 중앙에 오는데 초기 선택만 고정 상수(INITIAL_CENTER) 기준이었기 때문.
- **이유**: 렌더 후 panTo로 맞추면 첫 화면이 한 번 움찔한다 — 0172에서 기각한
  방식이 되돌아온다. 대신 **지도 생성 옵션의 center 소스를 상수에서 `spots[0]`으로**
  교체했다. 처음부터 거기서 시작하므로 이동 자체가 없고, "이동 없음" 원칙과 정중앙
  요구를 동시에 만족한다. INITIAL_CENTER는 빈 데이터 폴백으로 존치.

### 마커 카드·구분선 (0173·0174)
- **왜**: 초기 자동 선택으로 지도 위 선택 카드가 첫인상의 중심이 됐는데 작았다.
  구분선은 시안 대비 약해 보였다.
- **이유**: 카드는 2.0배(116px)로 시작해 실물 대조로 1.5 → 1.3 → 1.2 → **1.25배
  (72.5px)** 로 수렴. 2.0배는 스택 점유 면적이 3.4배(지도 열 폭의 19%)라 인접 마커
  라벨·도로명을 덮었다. 구분선은 실측해 보니 **현행값이 시안과 동일(0.08)** 이었다 —
  "시안 대비 약함"은 값 차이가 아니라 시안의 열 배경·카드 구조 때문에 경계가 이중으로
  읽히는 환경 차이였다. 그래서 시안 팔레트의 한 단계 위(0.12, 시안 내 3개소에서
  실측)로 올렸다. 색을 발명하지 않고 기존 체계 안에서 해결.

### 0169 — 줌 산출 헬퍼 + morph 통일

`components/SpotFinderMapNaver.tsx` — fitBounds 호출 소멸, 전 경로가 공유 상수 사용.

```typescript
// 전환 질감 공유 상수 — 세 경로(퇴화·일반 분해·칩)가 이 한 곳을 본다
const STAGE2_TRANSITION = { duration: 1000, easing: 'easeOutCubic' };
```

줌 산출은 Mercator 상수를 쓰지 않고 SDK 프로젝션에 위임:

```
proj = map.getProjection()
pSW, pNE = proj.fromCoordToOffset(sw|ne)        // 현재 줌 기준 월드픽셀
dx = |pNE.x − pSW.x|,  dy = |pNE.y − pSW.y|
size = map.getSize();  W′ = size.width − left − right;  H′ = size.height − top − bottom

Δz = log2( min( W′/dx, H′/dy ) )                 // 두 축 모두 담기는 최대 확대
targetZoom = clamp(현재줌 + Δz, map.getMinZoom(), STAGE2_MAX_ZOOM)  // 상한 정책 무변
s = 2^(targetZoom − 현재줌)                       // 캡 반영 후 실제 배율

mid = (pSW + pNE) / 2
center = proj.fromOffsetToCoord({                 // 비대칭 마진 보정
  x: mid.x − ((left − right)/2)/s,
  y: mid.y − ((top − bottom)/2)/s,
})
map.morph(center, targetZoom, STAGE2_TRANSITION)
```

퇴화(1지점) 분기는 setZoom+setCenter를 morph로 교체:

```typescript
// 퇴화 스팬: GL fitBounds가 무시함(실측) + 분해 무의미 → 상한으로 morph.
// setZoom+setCenter는 0ms 점프(순간이동, 실측)라 기각. morph는 중심·줌 원자 전환이라
// setCenter 선행 시의 maxBounds 클램프 함정도 구조적으로 소멸
map.morph(points[0], STAGE2_MAX_ZOOM, STAGE2_TRANSITION);
```

### 0170 — 칩 집계·정렬 (클라 파생)

`lib/spot/queries.ts`에 `createdAt: true` 1필드 추가(RSC가 Date 직렬화 지원),
집계는 이미 내려온 `spots`의 useMemo 파생.

```typescript
// components/SpotFinderMapNaver.tsx
// 작품별 그룹핑 + 칩 정렬 — 이미 전량 내려온 spots의 파생 집계
// (별도 집계 쿼리는 이중 소스라 기각)
const movieGroups = useMemo(() => {
  const acc = spots.reduce<Record<string, { title: string; count: number; latestAt: number }>>(
    (rec, s) => {
      const t = new Date(s.createdAt).getTime();
      if (rec[s.movie.id]) {
        rec[s.movie.id].count++;
        rec[s.movie.id].latestAt = Math.max(rec[s.movie.id].latestAt, t);
      } else {
        rec[s.movie.id] = { title: s.movie.title, count: 1, latestAt: t };
      }
      return rec;
    },
    {}
  );
  return Object.entries(acc)
    .map(([id, v]) => ({ id, ...v }))
    // 정렬 규칙: ① 스팟 수 내림차순 → ② 최근 스팟 등록 시각 내림차순
    // ("전체" 칩은 별도 버튼 — 항상 맨 앞)
    .sort((a, b) => b.count - a.count || b.latestAt - a.latestAt);
}, [spots]);
```

## 5. 결과 / 배운점

### 결과 (사실)
- **줌 산출 정확도**: 헬퍼 산출 줌 vs 기존 fitBounds 도달 줌 — 전체 칩(캡 미발동)
  6.29 → 6.293 (**Δ +0.003**, 기준 ±0.05의 1/16), 서울 4 분해(캡 발동) 11 → 11
  (Δ 0). 마커 이탈 0.
- **전환 시간**: 퇴화 morph 513ms / 퇴화 줌+팬(제주 클러스터) 511ms·10프레임 /
  일반 분해(서울 4) 514ms·11프레임 — 3경로 동일 계열 확인 후, 체감 조정으로
  최종 1000ms 확정. 이제 세 경로가 상수 한 곳으로 함께 움직인다.
- **easing 확증**: `@types/navermaps` TransitionOptions에 `easing?: string; //
  default easeOutCubic` — 쓰려던 값이 곧 SDK 기본값. 런타임 대조로 무효 문자열
  (`'bogus'`)은 throw 없이 기본 이징으로 폴백함도 확인(오타 안전망).
- **칩 정렬 실측**: 미생 count 2 → 1위(1차 기준 단독 결정), 이하 서울의 봄 →
  오징어 게임 → 빈센조 → 수리남(2차 기준). DOM 칩 순서가 예상 표와 완전 일치.
- **초기 자동 선택**: 새로고침 시 지도 중심 (37.5658, 126.9475)·z11 완전 고정
  (이동 전무, 좌표 실측) + 패널 열림 + 리스트 하이라이트 + 지도 선택 카드.
  다른 항목 클릭 시 panTo 정상(기존 동작 무변).
- **마커 카드**: 2.0×(116px) → 1.5×(87) → 1.3×(75) → 1.2×(70) → **1.25×(72.5)**
  수렴. 2.0배 기각 사유는 스택 면적 3.4배(지도 열 폭의 19%)로 인접 라벨·도로명 가림.
  앵커 드리프트 0(선택 토글 3회 동일 좌표).
- **구분선**: 현행값이 시안과 동일(0.08)임을 실측으로 확인 → 체감 보강 목적으로
  시안 팔레트 상위 단계 0.12 채택. 다른 보더(검색창·칩·카드) 0.08 무변 확인.
- 잔무 발견: 필터로 선택 스팟이 제외될 때 패널은 유지되고 하이라이트만 소멸
  (기존 동작, 별도 UX 안건) / 모바일 플로팅 카드가 초기부터 열려 지도 상부를 덮음
  (단일 상태 공유의 자연 귀결, 별도 사이클).

### 배운점
- **"어색하다"의 실체는 대개 한 지점이다.** 전환 질감이 문제라고 느꼈지만 실측하니
  네 경로 중 셋은 이미 500ms 이징이었고 퇴화 경로 하나만 0ms 점프였다. 전면 개조가
  아니라 1줄 교체가 시작점이었고, 진짜 작업(fitBounds 대체)은 그 1줄을 조정하려다
  발견한 **두 번째 어긋남**에서 나왔다. 실측 없이 감으로 시작했으면 엉뚱한 곳을
  고쳤을 것이다.
- **비결정을 결정으로 바꾸는 것 자체가 작업이다.** 칩·리스트 순서는 "잘못된 순서"가
  아니라 **순서가 정의되지 않은 상태**였다. DB 반환 순서에 좌우되니 우연히 지금
  모양이었을 뿐이다. 정렬 규칙 도입의 진짜 성과는 미생이 앞에 온 게 아니라, 앞으로
  데이터가 늘어도 순서를 설명할 수 있게 된 것이다.
- **같은 "정렬"도 층이 다르면 해법이 다르다.** 칩은 클라 파생 집계(전 스팟이 이미
  클라에 있으니 서버 집계는 이중 소스), 리스트는 소스 쿼리 orderBy(파생들이 순서를
  공유하므로 소스에서 정하면 전부 따라옴). 어디에 사실을 두느냐가 매번 판단 지점이다.
- **금지보다 부재가 강하다.** 초기 선택에 지도 이동을 붙이지 않는 방법으로 플래그
  분기(`isFirstRender`) 대신 코드 경로 분리(state 초기값)를 썼다. 전자는 "실행하되
  조건으로 막는" 구조라 나중에 조건을 건드리면 새어 나가고, 후자는 **panTo 코드가
  그 경로에 존재하지 않는다**. 규칙을 코드 구조로 만들면 미래의 실수까지 막는다.
- **수치는 실물이 정한다.** "딱 두 배"는 체감 기준이지 실측 기준이 아니었다. 2.0에서
  시작해 다섯 번 왕복해 1.25로 내려왔고, 기각 이력을 주석에 남겼다. 반대로 구분선은
  "시안보다 약하다"는 체감이 값 차이가 아니라 환경 차이였음을 실측이 밝혔다 —
  체감은 문제 제기로는 정확하고 원인 진단으로는 부정확할 수 있다.
- **작업 대상을 오해할 수 있다.** 상세 패널 히어로를 2배로 키웠다가 롤백했다.
  실제 대상은 지도 위 마커 카드였다. 시안을 구조로 읽는 문제는 여전하고, 확인 질문
  하나가 한 사이클을 아꼈을 것이다.

## 결정 (Decisions)

- **프로그램 이동 전 경로 = morph + 공유 transition 상수**: `STAGE2_TRANSITION`
  (1000ms·easeOutCubic) 한 곳. fitBounds는 duration 노브가 없어 비채택.
- **줌 계산은 SDK 프로젝션 위임**: Mercator 상수 하드코딩 금지(naver GL의 도/픽셀
  비가 표준 예측과 어긋남 — z11 0.000301 vs 0.000687 실측).
- **칩 정렬 = ① 스팟 수 desc → ② 작품별 최근 등록 desc**, "전체" 칩은 정렬 제외·
  맨 앞 고정. 집계는 spots 클라 파생(서버 집계 쿼리는 이중 소스라 기각), 스키마 무변.
- **리스트 정렬 = 쿼리 orderBy createdAt desc**(소스 단일 결정, 클라 재정렬 금지).
- **초기 자동 선택 = spots[0], 지도 이동 없음**: 구현은 플래그가 아니라 state
  초기값(코드 경로 분리) — 이동 없음이 구조로 보장.
- **초기 지도 중심 = spots[0] 좌표**, INITIAL_CENTER는 빈 데이터 폴백으로 존치.
  렌더 후 panTo 방식은 비채택(첫 화면 움찔거림).
- **선택 마커 카드 = 1.25배(72.5px)**, 미선택·점·발광 무변. 2.0/1.5/1.3/1.2 실물
  대조 후 수렴, 기각 이력 주석 병기.
- **3열 구분선 = rgba(255,255,255,0.12)** (시안 팔레트 상위 단계, 구분선 두 곳
  한정). theme.ts border 토큰 상향은 전역 파급이라 기각.
