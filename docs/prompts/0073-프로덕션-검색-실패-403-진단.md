# 0073 회고: 프로덕션 항공편 검색 403 진단

- 작성일: 2026-06-05
- 소요: 약 40분
- 관련 커밋: `chore: 0073 항공편 검색 임시 진단 로그 추가`

## 한 줄 요약

로컬에서는 되는 항공편 검색이 프로덕션(Vercel)에서만 실패했다. 서버 진단 로그 한 줄로 원인이 "Sky Scrapper 403 — Vercel 환경변수의 API 키 값 불일치"임을 특정하고, 키 값 교체와 재배포로 해결했다.

## 왜 / 목적 / 이유

### 1. 증상 분류 — "결과 없음"과 "실패"는 다른 길

- 왜: 화면 메시지가 "검색 결과가 없습니다"가 아니라 "검색에 **실패**했습니다"였고, 브라우저 콘솔에는 에러가 없었다. 두 메시지는 우리가 의도적으로 갈라둔 분기다 — 전자는 정상 응답에 결과가 빈 것, 후자는 호출 자체가 에러로 떨어진 것.
- 목적: 어느 계층에서 죽었는지부터 좁히는 것. 콘솔이 깨끗한데 실패 메시지가 떴다는 것은 클라이언트는 무죄고 서버 액션 안에서 외부 API 호출이 실패했다는 뜻이다.
- 이유: 에러 메시지를 처음부터 원인 계층별로 갈라두면, 장애가 났을 때 메시지 자체가 첫 번째 진단 도구가 된다.

### 2. 요청 로그로 실패 단계 특정

- 왜: 처음에는 추측이 앞섰다 — 쿼터 소진인가, 연타로 인한 레이트 리밋인가. 추측은 후보를 늘리기만 하고 어느 것도 확정하지 못했다.
- 목적: 추측 대신 관측. 검색 한 번이 실제로 어디까지 갔는지 기록으로 확인하는 것.
- 이유: Vercel 요청 로그의 External APIs 목록을 보니 searchAirport 호출만 있고 searchFlights 호출이 아예 없었다 — 항공편 검색까지 가지도 못하고 공항 ID 조회 단계에서 죽고 있다는 뜻이다. 이 한 줄의 관측으로 쿼터·연타 가설이 전부 기각됐다.

### 3. 진단 로그 한 줄 — 에러의 이름을 직접 듣기

- 왜: 요청 로그는 "어느 단계"까지는 알려줬지만 "왜"까지는 알려주지 않았다. 서버 안에서 catch로 삼켜진 에러의 실제 메시지가 필요했다.
- 목적: 에러가 자기 이름을 직접 말하게 하는 것.
- 이유: 검색 액션의 catch에 `console.error('[flights] search failed:', e)` 한 줄을 추가해 배포하고, 프로덕션에서 검색 한 번을 누르자 Vercel 로그에 `Sky Scrapper 403`이 찍혔다. 403은 "이 키는 구독자가 아니다"라는 응답 — 같은 코드가 로컬에서는 되므로, Vercel에 설정한 환경변수의 키 값이 PRO 구독이 걸린 실제 키와 다르다는 결론이 즉시 나왔다(복사 누락·따옴표 포함 같은 복붙 사고). Vercel에서 키 값을 교체하고 재배포해 해결했다. 이 로그는 임시가 아니라 정식으로 남겼다 — 다음 프로덕션 장애 때도 같은 방식으로 일하게 하기 위해서다.

### 4. 배포 직후의 잔상 — Server Action not found

- 왜: 재배포 직후 열려 있던 탭에서 `Server Action was not found` 에러가 났다.
- 목적: 배포 이슈와 코드 이슈를 구분하는 것.
- 이유: Next.js는 빌드마다 서버 액션 ID를 새로 부여한다. 배포 전부터 열려 있던 페이지는 이전 빌드의 클라이언트 코드라 옛 ID로 새 서버를 호출하고, 서버는 그 ID를 모른다. 강력 새로고침으로 해소되는 정상적인 현상이며, 실서비스들이 배포 후 "새 버전이 있습니다" 안내를 띄우는 이유가 이것이다.

## 작성한 프롬프트

진단 로그는 plan 없이 한 줄 지시로 처리했다:

```
app/(protected)/my-plan/new/actions.ts의 searchFlightsAction catch 블록 맨 위에
임시 진단 로그 한 줄 추가해줘: console.error('[flights] search failed:', e);
— 다른 변경 없음.
```

## 코드 작성 & 수정

```typescript
// app/(protected)/my-plan/new/actions.ts
export async function searchFlightsAction(params: SearchFlightsParams) {
  try {
    // ... 공항 ID 조회 → 항공편 검색
  } catch (e) {
    console.error('[flights] search failed:', e); // 서버 로그 — 프로덕션 진단의 눈
    return { error: '항공편 검색에 실패했습니다' };
  }
}
```

이 한 줄이 Vercel 로그에 남긴 출력:

```
[flights] search failed: Error: Sky Scrapper 403
```

코드 수정은 이것이 전부였다. 실제 해결은 코드 밖 — Vercel 환경변수의 키 값 교체와 재배포였다.

## 결과 / 배운점

- 프로덕션 검색이 정상화됐다. 코드 변경은 진단 로그 한 줄뿐이고, 원인과 해결은 모두 실행 환경 설정에 있었다.
- **같은 코드라도 실행 환경이 다르면 사실상 다른 프로그램이다.** `.env.local`은 로컬 전용 파일이라 Vercel은 별도 설정값을 쓰고, 그 값이 다르면 같은 코드가 다르게 동작한다. 이번 주에 같은 교훈이 두 번 반복됐다 — 시간대(서버는 UTC라 timeZone 명시 필요), 그리고 환경변수. 로컬에서 되는데 배포 환경에서 안 되면 코드보다 환경 차이(환경변수·시간대·런타임)부터 의심한다.
- **추측은 가설을 만들 뿐이지만, 로그는 사실로 가설을 소거한다.** 쿼터·연타 가설로 30분을 썼고, 진단 로그 한 줄을 심는 데 2분, 읽는 데 1분이 걸렸다. 막히면 가설을 하나 더 만들기 전에 관측 수단부터 만든다.
- 에러 메시지를 원인 계층별로 갈라두면("결과 없음" vs "실패") 장애 시 메시지 자체가 첫 진단 도구가 된다. 진단의 순서도 계층을 따른다: 화면 메시지 → 브라우저 콘솔 → 서버 요청 로그 → 서버 에러 로그.
- 배포 직후 열려 있던 탭의 Server Action 에러는 구버전 클라이언트와 신버전 서버의 불일치로, 코드 결함이 아니다. 강력 새로고침으로 확인부터 한다.
