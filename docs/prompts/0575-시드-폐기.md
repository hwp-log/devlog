## 2. 왜 / 목적 / 이유

### 시드를 "갱신"이 아니라 "폐기"로 전환

**왜** — `public/seed/*.png` 12장이 출처가 불명확한 사진이라 공개 배포에서 걷어내야 했다.

**목적** — 저작권 리스크가 있는 파일을 레포에서 제거하고, 그 과정에서 드러난 위험한
시드 스크립트까지 함께 폐기해 "돌리면 데이터가 깨지는" 상태를 없앤다.

**이유** — 시드를 고쳐 DB와 맞추는 방법도 있었으나, ① 첫 줄 `deleteMany`가 현재
스토리 5건을 지우고 플랜 2건 연결을 끊는 구조라 맞춰도 위험이 남고 ② StorySpot·Spot을
만들지 않아 어차피 현재 상태를 재현하지 못하며 ③ 포트폴리오는 도메인 접속으로 보는
것이라 시드가 필요 없다. 고치는 것보다 없애는 쪽이 위험도 줄고 코드도 준다.

### `public/seed/*.png` 동반 삭제
- **왜**: 출처가 불명확한 파일이고, 참조처가 `seed.ts` 단독이었다.
- **이유**: seed.ts가 사라지면 참조 0건인 7.1MB 바이너리만 남는다.

### 주석 갱신을 (b)방치가 아니라 (a)갱신으로
- **이유**: 삭제된 파일을 가리키는 주석은 화석이 된다.
  특히 기존 주석의 "prisma db seed 비활성화"라는 서술이 사실과 달랐다 —
  아래 3절 참조.

## 4. 코드 작성 & 수정

### 1. `prisma/seed.ts` 삭제 (167줄)

내용 요약 — 12개 스토리 블록 + 아래 파괴적 선행 로직:

```typescript

await prisma.story.deleteMany({ where: { userId: user.id } });
```

이 한 줄이 폐기 판단의 핵심이었다. `Story.planId`는 `onDelete: SetNull`이라
스토리가 지워지면 플랜 쪽 연결이 예외 없이 조용히 해제된다.

```prisma
// prisma/schema.prisma:73
plan       MyPlan?  @relation(fields: [planId], references: [id], onDelete: SetNull)
```

## 5. 결과 / 배운점

### 결과
- 참조 전수 확인 결과 **코드 import 0건**. 언급은 `package.json` 1줄,
  `prisma.config.ts` 주석, `public/seed` 이미지, `docs/prompts` 과거 회고 5편뿐.
  회고는 시점 기록이라 손대지 않았다.
- 삭제 후 잔여 참조 검색(`prisma/seed.ts` / `db:seed` / `/seed/`,
  node_modules·docs 제외) → **새 주석의 자기 언급 1건 외 0건.**
- `npm run lint` — 오류 8건은 전부 이번에 손대지 않은 파일
  (NavLinks / SpotFinderHeader / backfill-* 스크립트). 회귀 없음.
- `npm test` — 6 스위트 / 8 테스트 실패. **기존 실패 목록과 정확히 동일**
  (auth 5스위트 + SpotPopup). 회귀 없음.
- DB 무변경. `prisma/migrations` 무접촉. `seed-dummy-plans.ts` 존치.

### 배운점
- **주석은 코드보다 조용히 썩는다.** 기존 주석은 "prisma db seed 비활성화"라고
  적혀 있었지만, `prisma.config.ts`에 `seed` 항목을 둔 적 자체가 없어
  **비활성화가 아니라 처음부터 미설정**이었다. 지시의 3번 항목
  ("prisma.seed 설정 제거")도 그래서 제거할 대상이 없었다.
  "막아뒀다"는 서술과 "애초에 없다"는 사실은 다음 사람에게 전혀 다른 정보다.
- **되살아나는 데이터가 가장 위험하다.** 시드는 보통 "있으면 편한 것"으로 취급되지만,
  DB 실물이 시드를 앞질러 간 뒤로는 실행 자체가 파괴 행위가 된다.
  갱신으로 따라잡는 비용 vs 폐기 — 실행할 일이 없다면 후자가 정답이었다.
- **지시가 사실과 다를 때 그대로 실행하지 않는 것.** 이번 지시에는 오류가 둘 있었다 —
  이미지가 TourAPI URL이라고 했으나 실제는 Supabase Storage였고,
  `prisma.seed` 설정을 제거하라고 했으나 그 설정 자체가 없었다.
  둘 다 1단계 조사에서 잡혔다. 지시를 의심해서가 아니라
  **실물로 확인하는 절차가 있었기 때문**이다.
- **1단계 조사가 방향을 바꿨다.** 애초 지시는 "갱신"이었으나, 조사 보고에서
  첫 줄의 `deleteMany`와 StorySpot 미생성이 드러나면서 폐기로 전환됐다.
  검수 모드(보고 후 승인)가 실제로 작동한 사례.

### 정정 사항
1단계 조사에서 배경으로 주어진 사실 두 가지가 실제와 달랐다.

1. **"사진을 관광공사 TourAPI URL로 교체했다"** — DB 5건의 이미지 10장은 전부
   **Supabase Storage**(`story-photos` 버킷)의 사용자 업로드 URL이고,
   TourAPI 도메인은 0건이었다. 관광공사 사진을 내려받아 다시 업로드한 것이다.
   (TourAPI 도메인 `tong.visitkorea.or.kr`은 별개로 Spot 커버에 쓰인다 —
   `next.config.ts`의 `remotePatterns` 참조.)
2. **"package.json의 prisma.seed 설정 제거"** — 최상위 `"prisma"` 블록이
   애초에 없었다. 69행의 `"prisma"`는 devDependency 버전이라 무관하다.
   제거할 설정이 존재하지 않아 대신 그 사실을 주석에 명시했다.
