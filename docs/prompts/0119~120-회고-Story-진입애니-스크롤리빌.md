# 0119~120 회고: Story 진입 애니메이션 + 스크롤 진입(Intersection Observer)

- 작성일: 2026-06-28
- 소요: 약 3시간 (0119~0120 누적)
- 관련 커밋: 42a291e(0119), 81c1cd0(0120)

## 1. 한 줄 요약

PlanFinder에서 만든 진입 애니(appear-up)를 Story에도 넣되, Story는 카드가 많아 스크롤이 긴 갤러리라 PlanFinder의 단순 delay stagger 대신 스크롤 진입(Intersection Observer)으로 "보이는 카드가 그때 떠오르게" 만들었다. 검색 전환은 통일하지 않고 기존 list-fade(crossfade)에 맡겨 역할을 분리했고, 첫 화면 카드만 stagger를 주고 스크롤로 들어오는 카드는 즉시 fade되게 했다.

## 2. 왜 / 목적 / 이유

### 같은 fade라도 "사용자 눈에 어떻게 보이느냐"에 맞춘다 (0119~0120)

- 왜: PlanFinder에서 쓴 appear-up을 Story에 그대로 옮기면 될 것 같았는데, 옮겨보니 결이 달랐다. PlanFinder는 카드가 적어 한 화면에 다 들어오는데, Story는 카드가 많아 스크롤이 길다. PlanFinder처럼 로드 시 delay stagger로 다 띄우면, 화면 밖 카드는 보이지도 않는데 이미 떠버려 스크롤해 내려가도 등장감이 없다.
- 목적: Story를 보는 사용자가 "갤러리를 훑는" 흐름으로, 스크롤해서 보이는 카드가 그때 떠오르는 진입 경험.
- 이유:
  1. 시스템상으론 PlanFinder도 Story도 둘 다 "카드"다. 하지만 **사용자 눈에 보이는 방식이 다르다.** PlanFinder는 정보가 좌우로 늘어선 가로 카드가 세로로 쌓여 "위아래로 읽는 짧은 리스트"로 보이고, Story는 썸네일 이미지가 박힌 카드가 격자로 길게 깔려 "스크롤하며 훑는 갤러리"로 보인다.
  2. 그래서 진입 방식도 "보이는 방식"에 맞춰야 했다. 한 화면에 다 들어오는 PlanFinder는 로드 시 delay stagger로 충분하지만, 스크롤이 긴 Story는 **뷰포트에 들어오는 카드만 그때 떠오르는** 방식(Intersection Observer)이 맞다. 첫 화면 카드는 stagger로 순차 등장시키고(`0.36 + Math.min(index,8)*0.12`), 스크롤로 새로 들어오는 카드는 delay 0으로 즉시 떴다.
  3. 이건 PlanFinder 회고와 같은 축이다 — "색 막대를 사용자 눈으로 다시 봤다", "타이핑이 콘텐츠 페이지엔 안 맞는다"와 마찬가지로, 기준은 시스템(코드상 같은 카드, 같은 appear-up keyframe)이 아니라 **사용자가 어떻게 인지하느냐**다. 시스템이 어떻든 사용자 눈에 짧은 리스트면 한 번에, 긴 갤러리면 스크롤 따라 떠오르게 한다.

### 진입은 appear-up, 검색 전환은 list-fade — 통일하지 않고 분리 (0119)

- 왜: PlanFinder에선 검색·필터를 누르면 카드가 다시 appear-up으로 등장하게 통일했는데(0118), Story에 같은 방식을 적용하려니 기존에 이미 검색 전환용 list-fade(View Transitions crossfade)가 있었다. appear-up까지 붙이면 검색할 때마다 두 애니가 동시에 돌아 충돌한다.
- 목적: 첫 진입과 검색 전환이 각자 맞는 애니로 깔끔하게 동작하고, 둘이 서로 간섭하지 않는 상태.
- 이유: 두 페이지는 **상황이 다르다.** PlanFinder 검색은 클라이언트 필터라 "검색 시 카드 다시 fade"가 자연스러웠지만, Story 검색은 서버 요청(URL query, debounce 300ms)이라 페이지가 새로 렌더되고 이미 list-fade가 그 전환을 부드럽게 담당하고 있었다. 여기에 appear-up까지 얹으면 crossfade되면서 또 떠올라 이중 애니가 된다. 그래서 역할을 나눴다 — **첫 진입은 appear-up, 검색 전환은 기존 list-fade.** `isFirstRenderRef`로 "첫 렌더만 appear-up, 검색 재렌더엔 미부착"으로 구분했다. 무지성으로 "PlanFinder랑 똑같이"가 아니라 Story 맥락에 맞춰 다르게 처리한 것이다.

### 스크롤 진입 = Intersection Observer (0120)

- 왜: 0119에선 첫 화면 카드를 인덱스 선형 delay stagger로 띄웠는데, 화면 밖 카드도 delay만 다를 뿐 "이미 떠버린" 상태였다. 스크롤해서 내려가면 새 카드가 그냥 거기 있을 뿐 등장감이 없다.
- 목적: 스크롤해서 뷰포트에 들어오는 카드가 그때 떠오르며 나타나고, 한 번 뜬 카드는 다시 스크롤해도 재등장하지 않는 경험.
- 이유: 0119의 delay stagger는 "로드 시 다 뜨는" 방식이라 카드가 적을 때만 맞다. 스크롤이 긴 Story는 **"이 카드가 화면에 보이기 시작하면 그때 실행"**이 맞고, 그건 Intersection Observer(뷰포트 감지)가 필요하다. 프로젝트에 IO 훅이 없어 `lib/use-in-view-once.ts`를 새로 만들었다(once 패턴 — `io.unobserve`로 한 번 보이면 관찰 해제, 재등장 방지). StoryCard는 Server Component라 IO(클라이언트 전용 브라우저 API)를 직접 못 붙여, props만 받는 순수 렌더는 그대로 두고 `CardReveal` 클라이언트 wrapper로 한 단계 감쌌다. 0119에서 StoryCardList 안에 있던 stagger 계산은 이때 CardReveal 안으로 옮겼다 — IO 진입 시점에 delay를 정해야 하니까. 그리고 "첫 화면 stagger 구간"과 "스크롤 진입 즉시"를 가르려고 `isFirstRenderRef`를 `initialPhaseRef`(setTimeout 200ms 후 false)로 바꿨다. 200ms 안에 IO로 잡힌 카드(=첫 화면)는 stagger, 그 뒤 스크롤로 들어오는 카드는 delay 0이다.

### 스크롤 진입 훅 + CardReveal wrapper (0120)

```ts
// lib/use-in-view-once.ts (신규 — 프로젝트에 IO 훅이 없어 신규 작성)
'use client';
interface Options { threshold?: number; rootMargin?: string; }
export function useInViewOnce<T extends Element>(options: Options = {}) {
  const ref = useRef<T | null>(null);
  const [inView, setInView] = useState(false);
  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const io = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) {
        setInView(true);
        io.unobserve(el); // once — 한 번 보이면 관찰 해제
      }
    }, { threshold: options.threshold ?? 0.15, rootMargin: options.rootMargin });
    io.observe(el);
    return () => io.disconnect();
  }, [options.threshold, options.rootMargin]);
  return { ref, inView };
}
```

```tsx
// app/story/_components/CardReveal.tsx (신규)
// StoryCard(Server)를 클라 wrapper로 감싸 IO 적용.
// 0119의 StoryCardList 안 stagger 계산이 여기로 이동 — IO 진입 시점에 delay 결정.
export function CardReveal({ children, index, initialPhaseRef }: Props) {
  const { ref, inView } = useInViewOnce<HTMLDivElement>({ threshold: 0.15 });
  const [delay, setDelay] = useState(0);
  const decidedRef = useRef(false); // 한 번만 delay 결정
  useEffect(() => {
    if (!inView || decidedRef.current) return;
    decidedRef.current = true;
    // 첫 화면 카드(initialPhase)는 stagger, 스크롤 진입 카드는 즉시
    setDelay(initialPhaseRef.current ? 0.36 + Math.min(index, 8) * 0.12 : 0);
  }, [inView, index, initialPhaseRef]);
  return (
    <div ref={ref}
      className={inView ? 'appear-up' : undefined}
      style={inView ? { animationDelay: `${delay}s` } : { opacity: 0 }}>
      {children}
    </div>
  );
}

// StoryCardList: 0119의 delay 계산 제거 → CardReveal로 감싸기만.
// isFirstRenderRef → initialPhaseRef로 교체(200ms 후 false): "첫 화면 stagger 구간"을
// 시간으로 끊어, 그 안에 IO로 잡힌 카드만 stagger / 이후 스크롤 진입은 즉시.
const initialPhaseRef = useRef(true);
useEffect(() => {
  const t = setTimeout(() => { initialPhaseRef.current = false; }, 200);
  return () => clearTimeout(t);
}, []);
{stories.map((story, i) => (
  <CardReveal key={story.id} index={i} initialPhaseRef={initialPhaseRef}>
    <StoryCard {...story} />
  </CardReveal>
))}
```

## 5. 결과 / 배운점

### 결과
- Story 진입이 eyebrow→헤드라인(랜덤 4종)→검색바→카드 순으로 떠오르고(첫 화면 카드는 인덱스 선형 stagger), 검색 전환은 기존 list-fade가 담당해 둘이 충돌 없이 동작한다. 스크롤해서 내려가면 뷰포트에 들어오는 카드가 그때 떠오르고, 한 번 뜬 카드는 재등장하지 않는다. (커밋 2개 배포 완료, tsc 통과.)

### 배운점
- **도구의 목적을 잃지 않는 게 기준이다.** 시스템 패턴이든 논리든, 결국 "사용자가 이 도구로 뭘 하려는가"가 먼저다. 진입 방식(짧은 리스트면 한 번에, 긴 갤러리면 스크롤 따라), 검색 전환을 list-fade에 맡긴 분리, IO를 쓸지 delay를 쓸지 — 전부 그 목적에서 거꾸로 정해졌다. 아래 판단들은 이 한 줄의 변주다.
- **같은 컴포넌트라도 사용자 눈엔 다르게 보인다.** 코드상 PlanFinder도 Story도 카드(같은 appear-up keyframe)지만, 사용자는 PlanFinder를 "한 화면에 든 짧은 리스트", Story를 "스크롤하며 훑는 긴 갤러리"로 인지한다. 그래서 PlanFinder는 로드 시 한 번에, Story는 스크롤 따라 떠오르게 했다. 기준은 시스템 구조가 아니라 그 "보이는 방식"이다.
- **무지성 재사용이 아니라 맥락에 맞춘 분리.** PlanFinder는 클라 필터라 검색 시 appear-up이 자연스러웠지만, Story는 서버 렌더 + 기존 list-fade라 검색 전환을 list-fade에 맡기는 게 맞았다. "PlanFinder랑 똑같이"가 아니라 페이지 상황이 달라서 다르게 처리했다. 진입 모션(appear-up)과 전환 모션(list-fade)의 역할을 나눈 것이다.
- **delay stagger와 Intersection Observer는 쓰임이 다르다.** 로드 시 delay stagger는 "한 번에 다 뜨는" 방식이라 한 화면에 드는 짧은 목록에 맞고(0119), 스크롤이 긴 목록은 "뷰포트 진입 시 실행"하는 IO가 맞다(0120). 같은 "진입 애니"라도 목록 길이에 따라 기법을 골라야 한다. 그래서 0119의 stagger 계산을 0120에서 IO wrapper(CardReveal) 안으로 옮겨, 진입 시점에 delay를 정하게 했다.
- **Server Component엔 IO를 직접 못 붙인다.** IO는 브라우저 API라 클라이언트 전용인데 StoryCard는 Server Component였다. 순수 렌더(props만 받는) 카드는 그대로 두고 클라이언트 wrapper(CardReveal)로 한 단계 감싸 해결했다 — 서버/클라이언트 경계를 깨지 않으면서 클라 기능을 더하는 패턴. 훅(useInViewOnce)을 따로 빼 재사용 가능하게 만든 것도 같은 맥락이다.
