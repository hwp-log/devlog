# 0068 회고: 항공편 검색을 계획 작성/수정에 통합

- 기간: 2026-06-03 ~ 2026-06-04
- 관련 커밋: `be453d1`(plan_flights 테이블) / `635a78f`(lib/flights 검색 모듈) / `fa38a1a`(편집기 통합)

## 1. 한 줄 요약

항공편 검색(Skyscanner 데이터, RapidAPI)을 마이플랜에 연결하면서, 상세 페이지의 별도 저장 구조를 폐기하고 항공편 저장을 계획 작성/수정 트랜잭션에 통합했다.

## 2. 왜 / 목적 / 이유

### 항공편을 편집기로 통합한 재설계

- **왜**: 첫 구현(상세 페이지의 별도 저장 액션)은 `savePlanFlightAction(planId, offer)` 형태라 **planId가 이미 존재해야만 동작**했다. 새 계획을 작성하는 시점엔 planId가 아직 없으므로 "작성하면서 항공편 넣기"가 원천적으로 불가능했고, "저장 → 상세 진입 → 항공편 따로 추가"라는 2단계가 강제됐다. 여행 정보가 분산되는 문제는 이 구조적 제약의 증상이었다.
- **목적**: 작성 시 함께 입력하고, 수정 시 불러와 수정하고, 상세에서는 읽기 전용으로 보는 상태 — 항공편이 계획의 내용으로 다뤄지는 흐름.
- **이유**: create 트랜잭션 안에서 계획을 먼저 생성하면 그 자리에서 planId가 나오고, 같은 트랜잭션에서 plan_flights 행을 만들 수 있다. 계획과 항공편이 함께 저장되거나 함께 실패하는 원자성도 확보된다. update는 같은 트랜잭션에서 upsert(있으면 갱신) / deleteMany(비우면 삭제)로 처리했다.

### plan_flights 별도 테이블 + 비정규화

- **왜**: 항공편은 계획당 1건이고, 직항 전용이라 가는편/오는편 각 1편으로 형태가 고정돼 있다.
- **목적**: 검색 결과를 그대로 저장하고 그대로 복원하는 단순한 구조.
- **이유**: planId unique 별도 테이블에 out_\*/ret_\* 컬럼을 펼쳐 넣었다. 레그를 별도 테이블로 나누면 조인과 정렬만 늘고 얻는 게 없다. 가격은 totalAmount 단일 컬럼 — Skyscanner 응답이 여정(itinerary) 단위 가격만 주고, 왕복 항공권 자체가 하나의 운임 상품이라 레그별 가격은 존재하지 않는 데이터다. 통화는 앱 전체 KRW 단일이라 currency 컬럼을 두지 않았다.

### 검색 API: Air Scraper (RapidAPI)

- **왜**: Duffel은 한국 미지원, Amadeus는 셀프서비스 신규 가입이 닫혔다. 무료로 검증 가능한 항공 검색이 필요했다.
- **목적**: IATA 코드와 날짜로 직항 항공편 목록과 KRW 가격을 받는 것.
- **이유**: RapidAPI의 Air Scraper(Skyscanner 데이터)를 무료 Basic(월 20건 Hard Limit, 초과 과금 없음)으로 구독했다. searchFlights V2에 currency=KRW를 넘기면 원화 정수 가격이 오는 것을 라이브 호출로 확인했다. 키는 `.env.local`의 RAPID_API_KEY로 두고, 검색은 server action 경유라 클라이언트에 노출되지 않는다. 검색 결과는 직항(stopCount=0)만 걸러 가격 오름차순 상위 5개를 반환한다.

### 날짜 입력 없는 검색

- **왜**: 항공편 날짜를 따로 받으면 계획 날짜와 어긋난 입력이 생긴다.
- **목적**: 가는편=계획 시작일, 오는편=계획 종료일로 자동 연동되는 상태.
- **이유**: 날짜가 없으면 검색 버튼 비활성(선행 조건). 검색은 버튼 클릭 시에만 호출해 월 20건 쿼터를 보호한다.

## 4. 코드 작성 & 수정

create 트랜잭션 — planId가 생기는 자리에서 항공편을 함께 생성:

```ts
// app/(protected)/my-plan/new/actions.ts
const result = await prisma.$transaction(async (tx) => {
  const plan = await tx.myPlan.create({ data: { /* 계획 필드 */ } });
  await buildPlanRows(tx, plan.id, payload.items);
  if (payload.flight) {
    await tx.planFlight.create({
      data: { planId: plan.id, ...flightFields(payload.flight) },
    });
  }
  return plan;
});
```

update 트랜잭션 — 있으면 upsert, 비우면 삭제:

```ts
// app/(protected)/my-plan/new/actions.ts
if (payload.flight) {
  await tx.planFlight.upsert({
    where:  { planId },
    create: { planId, ...flightFields(payload.flight) },
    update: flightFields(payload.flight),
  });
} else {
  await tx.planFlight.deleteMany({ where: { planId } });
}
```

수정 진입 시 역매핑 — plan_flights 행을 EditorState.flight로 복원(전 필드, Date↔ISO 무손실):

```ts
// app/(protected)/my-plan/[id]/edit/page.tsx
const flightSlot: FlightOffer | null = plan.flight ? {
  tripType: plan.flight.tripType as 'ONE_WAY' | 'ROUND_TRIP',
  totalAmount: plan.flight.totalAmount,
  outbound: {
    origin: plan.flight.outOrigin,
    destination: plan.flight.outDestination,
    departsAt: plan.flight.outDepartsAt.toISOString(),
    arrivesAt: plan.flight.outArrivesAt.toISOString(),
    airline: plan.flight.outAirline,
    flightNo: plan.flight.outFlightNo,
  },
  return: plan.flight.retOrigin ? { /* ret_* 동일 매핑 */ } : undefined,
} : null;
```

```ts
// app/(protected)/my-plan/[id]/PlanDetail.tsx
// Before — Timestamptz를 UTC로 잘라 9시간 어긋남 (NRT 11:40 출발이 02:40으로 표시)
```

## 5. 결과 / 배운점

**결과**

- e2e 통과: 새 계획 작성 → 검색·선택 → 저장 → 상세 읽기 카드 → 수정 진입 복원 → 재저장 → 뒤로가기 유지.
- ICN↔NRT 왕복 라이브 검색에서 직항 상위 5개(₩396,410~)와 KRW 정수 가격 확인.
- 계획과 항공편이 한 트랜잭션으로 저장돼, 절반만 저장되는 상태가 구조적으로 생기지 않는다.

**배운점**

1. 저장 액션의 전제 조건이 기능의 흐름을 결정한다. "항공편을 어디서 저장하나"는 UI 선택이 아니라 구조 문제였다 — planId 선행이 필요한 별도 액션은 새 계획을 지원할 수 없다.
2. "저장이 안 된다"는 증상은 양 끝 로그 + 판독표로 갈랐다. 클라이언트 로그(payload 조립 직후)와 서버 로그(액션 진입 직후)의 null/객체 조합으로 원인 후보를 절반씩 제거 — 결과는 둘 다 정상 객체였고, 실제 원인은 코드 수정 직후 핫리로드가 server action까지 따라오지 못한 상태에서의 저장이었다. 추측으로 코드를 고치기 전에 데이터(DB 행 유무)부터 확인한 것이 시간을 아꼈다.
3. `toISOString()`은 UTC다. 표시용 포맷에 쓰면 KST에서 9시간 어긋난다. 같은 함정이 다음 작업(0069)의 todayStr()에서도 반복될 뻔해 검수에서 차단했다 — "Date를 문자열로 만들 땐 기준 시간대를 먼저 묻는다"를 검수 항목에 추가.
4. Claude Code는 "Conversation compacted" 직후 plan 모드가 풀려 검수 없이 구현으로 들어갈 수 있다. compaction이 보이면 모드부터 확인하고, plan 파일에 이전 plan이 남아 있으면 새 plan인지 대조한다.
5. Skyscanner 계열 응답의 시각은 공항 현지 시각(시간대 정보 없음)이다. 한국–일본은 동일 UTC+9라 무탈하지만, 시차가 다른 노선에서는 소요시간 계산이 어긋날 수 있다 — 다른 시간대 노선을 지원할 때 다룰 항목으로 기록한다.
