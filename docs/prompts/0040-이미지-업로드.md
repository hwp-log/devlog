# 0040: Tiptap 이미지 업로드 연동

## 한 줄 요약

`lib/supabase/storage.ts` 신설 + TiptapEditor에 파일 input + 이미지 버튼 핸들러 연결해서 에디터 안에서 사진 첨부 가능하게 완성.

## 왜·목적·이유

0038에서 Tiptap 에디터, 0039에서 Storage 버킷 + RLS 4개가 준비된 상태. 이제 두 개를 연결해서 사용자가 에디터 툴바의 이미지 버튼을 누르면 → 파일 선택 → Supabase Storage 업로드 → 반환된 공개 URL이 에디터에 `<img>`로 삽입되는 흐름을 완성하는 작업.

핵심 결정:

1. **업로드 함수를 `lib/supabase/storage.ts`로 분리**: TiptapEditor 안에 인라인으로 적기보다 별도 모듈로 빼서 재사용 가능하게.
2. **파일 경로는 0039 규약 그대로 `{userId}/{uuid}.{ext}`**: RLS의 `(storage.foldername(name))[1]` 검증과 맞물려야 함.
3. **userId를 props로 받음**: StoryWriteForm → TiptapEditor 흐름. Client Component에서 `auth.uid()` 직접 호출 불가하니 Server Component에서 미리 조회해서 내려주는 패턴.
4. **이미지 버튼 = 숨겨진 file input 트리거**: `<input type="file" hidden>` + `ref.current.click()`. 깔끔하고 표준적.

## 코드 작성 & 수정

### lib/supabase/storage.ts (신설)

```typescript
import { createClient } from '@/lib/supabase/client'

export async function uploadStoryImage(file: File, userId: string) {
  const supabase = createClient()
  const ext = file.name.split('.').pop()
  const path = `${userId}/${crypto.randomUUID()}.${ext}`

  const { data, error } = await supabase.storage
    .from('story-photos')
    .upload(path, file)

  if (error) {
    console.error('업로드 실패:', error)
    return null
  }

  const { data: { publicUrl } } = supabase.storage
    .from('story-photos')
    .getPublicUrl(data.path)

  return publicUrl
}
```

### handleLink 클로저 null 가드 추가


## 결과·배운점

**동작 확인**

`단밤 포차` 더미 글 작성 중 사진 업로드 → Supabase Storage에 `{userId}/{uuid}.jpg`로 저장 → 공개 URL이 에디터에 `<img>`로 삽입 → 저장 후 상세 페이지에서 렌더링 성공. 종단간 흐름 완성.

**잘 된 점**

- 0038~0039의 결정(파일 경로 규약, Public 버킷, RLS 4개)이 0040에서 한 줄의 추가 코드 없이 그대로 동작. 사전 설계가 효과 확인.
- 업로드 함수를 별도 모듈로 분리 → 나중에 Spot 사진 업로드(`spot-photos`)할 때 동일 패턴으로 갈음 가능.
- 숨겨진 file input + ref 트리거 패턴 → 디자인 자유도 ↑(Tiptap 툴바 스타일에 맞춰 버튼 커스터마이즈 가능).

**놓친 함정 — TypeScript 클로저 narrowing**

`editor`는 `useEditor()` 반환값이라 `Editor | null` 타입. 컴포넌트 본문에서 `if (!editor) return null`로 좁혔는데, **이벤트 핸들러 함수 안에서는 그 좁힘이 풀림**. 

이유는 클로저가 생성될 때의 타입을 캡처하기 때문 — 컴포넌트가 리렌더되면서 editor가 다시 null이 될 수도 있다고 TS가 판단. handleLink, handleImageUpload 같은 핸들러는 함수 진입 직후 다시 `if (!editor) return` 가드를 둬야 함.

이건 React + TypeScript에서 반복적으로 만나는 함정. "한 번 좁혔으니 안에서는 안전" 가정이 클로저에서 깨지는 패턴.

**파일 경로 규약의 위력**

0039에서 `{userId}/{uuid}.{ext}` 규약을 정해뒀더니 0040 코드는 단순히 그 규약을 따르기만 하면 됐음:

```typescript
const path = `${userId}/${crypto.randomUUID()}.${ext}`
```

이 한 줄이 RLS 정책 4개와 자동으로 맞물려 동작. "규약을 먼저 정하고 코드는 그걸 따른다"는 게 어떤 의미인지 체감.

**Server Component → Client Component props drilling**

`auth.uid()`는 서버에서만 호출 가능 → page.tsx에서 미리 조회해서 props로 내림 → StoryWriteForm → TiptapEditor. Next.js 16 App Router의 표준 패턴.

만약 클라이언트에서 `supabase.auth.getUser()`를 호출했다면:
1. 네트워크 왕복 1회 추가
2. 로딩 상태 처리 필요
3. SSR 시점에 userId 없어서 깜빡임 발생

→ Server Component에서 미리 받아서 내리는 게 정답. props drilling을 두려워하지 말 것.
