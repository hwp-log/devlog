# 0106 회고: 촬영지 작품 연결 데이터 토대

- 작성일: 2026.6.16
- 소요: 약 3시간 (설계 + 1~5단계 구현 + 시드 스크립트 실데이터 삭제 위험 차단)
- 관련 커밋: 5e161b7 (feat), 820c2f9 (fix)

---

## 1. 한 줄 요약

사용자가 여행 기록의 촬영지(Spot)에 "어느 작품인지"를 자유 입력 + 자동완성으로 연결하는 데이터 토대를 작성했다. Movie 테이블·Spot.movieId·시드·자동완성 조회 함수까지 SpotFinder의 기반을 깔고, 작업 중 발견한 시드 스크립트의 실데이터 삭제 위험을 함께 차단했다.

---

## 2. 왜 / 목적 / 이유

### 가. 자유 입력 + 자동완성 — 운영자 전수 입력을 버린 이유

- **왜**: K-드라마는 분기별 신작에 주 단위 방영까지 연 수십 편 규모라(web_search로 확인), 운영자가 작품을 전수 입력하는 방식은 신작 속도를 못 따라가고 누락이 많다.
- **목적**: 사용자가 촬영지를 다녀와 글을 쓰는 그 순간, 작품이 목록에 없어도 막히지 않고 동선을 완성할 수 있게 한다.
- **이유**: 성지순례는 작품이 화제 된 직후 즉시 일어나고(web_search로 확인), 사용자의 1순위 니즈는 촬영지를 묶어 동선을 짜는 것이다. 방문 후 글을 쓰는 순간 작품이 목록에 없으면 동선을 못 짜는 치명적 문제가 생긴다. 따라서 입력 자체를 막을 수 없다고 판단했다. 운영자 전수 입력은 사용자의 방문 타이밍을 항상 뒤따라가 구조적으로 성립하지 않는다.
- **데이터 오염 대응**: 자유 입력의 표기 중복(예: "오징어게임" vs "오징어 게임")은 입력 단계 자동완성(기존 작품 우선 제시)으로 1차 방어하고, 남는 중복은 운영자가 사후에 하나로 병합한다. 한 번 병합하면 이후 같은 표기는 자동으로 연결돼 미래 중복까지 막힌다. Stack Overflow 태그 동의어(synonym) 시스템과 같은 접근이다.

### 나. Spot 레벨 nullable 연결 — 작품 꼬리표를 점에 단 이유

- **왜**: 한 여행기에 여러 작품이 섞일 수 있고, 동선에는 촬영지가 아닌 장소(공항·숙소·식당)가 함께 있다.
- **목적**: 점(촬영지)마다 작품을 달아 여러 작품 공존을 허용하고, 비촬영지는 작품 없이 둔다.
- **이유**:
  - Story(글) 레벨에 작품을 달면 "글엔 작품 둘인데 이 점은 어느 쪽?" 모순이 생긴다. SpotFinder가 점 단위로 작품을 묶으므로 꼬리표도 점에 다는 게 맞다.
  - 모든 장소가 촬영지는 아니므로 nullable이 맞다. 0099에서 닉네임을 NOT NULL로 강제한 것과 반대 판단이다 — "언제 강제하고 언제 선택으로 두냐"의 구분.
  - 작품 삭제 시 onDelete SET NULL — 작품을 지워도 촬영지 기록은 남고 연결만 해제. 0098의 데이터 무결성 감각.

### 다. status 필드(APPROVED/PENDING) — 지금 안 쓰는데 미리 둔 이유

- **왜**: 시드(운영자)와 사용자 자유 입력을 구분할 자리가 필요하다.
- **목적**: 나중에 운영자 검토·병합 화면이 "PENDING만 보여줘"로 바로 동작하게 한다.
- **이유**: 필드는 나중에 추가하면 마이그레이션 비용(Prisma 7 수동 마이그레이션)이 든다. status는 곧 쓸 게 확실하므로 지금 같이 작성하는 게 싸다. 0099의 "입구에서 보장" 연장이되 방향은 "싸고 곧 가치 생김 → 지금".

### 라. 시드는 작품 제목만 — 촬영지 시드를 뺀 이유

- **왜**: 시드 촬영지(Spot)를 넣으려면 Spot이 Story에 매달리는 구조(storyId 필수, Cascade) 때문에 시드 전용 Story·숨김 처리 등 특수 케이스가 줄줄이 필요하다.
- **목적**: 자동완성 마중물(기존 작품 제시)만 확보하고, 촬영지는 사용자(관리자 계정 포함) 글로 채운다.
- **이유**: 콜드스타트는 사용자가 있을 때 문제인데 초기엔 사용자가 없어 발생하지 않는다. 자동완성 마중물은 작품 제목(Movie)만으로 충족된다. 촬영지 시드는 비용 큰 데 비해 당장 가치가 없어 미뤘다(YAGNI). 시드 작품 제목은 이미 관리자 계정으로 작성한 Story들에서 추출, 정식 표기로 통일.

### 마. 시드 스크립트의 실데이터 삭제 위험 차단 (작업 중 발견)

- **왜**: 이번 작업에서 두 가지가 겹쳤다.
  (1) prisma.config.ts의 seed 설정 — CC가 4단계에서 넣은 뒤 "나중에 정리"로
      의식적으로 미뤄둔 것(기술 부채).
  (2) seed.ts의 Story deleteMany — 이전부터 있던 잠복 위험. 4단계 시드 작업 중
      "읽고 보고만"으로 발견. test@dotrip.com(관리자 계정)의 Story를 전부 삭제 후
      재생성하는 비멱등 로직이라, prisma db seed를 치면 실제 글·촬영지가 사라진다.
- **목적**: Movie 시드를 안전하게 단독 실행하고, 위험한 자동 실행 경로를 막는다.
- **이유**: Movie 시드를 seed.ts에서 별도 파일(seed-movies.ts)로 분리하고,
  prisma.config.ts의 seed 설정을 제거했다. 이제 db seed를 쳐도 "seed script 없음"으로
  종료돼 Story가 삭제되지 않는다. 미뤄둔 설정(기술 부채)은 갚고, 발견한 잠복 위험은
  차단한 것 — 두 결이 한 작업에 겹쳤다. 0097부터 이어온 "원천 차단" 감각.

## 4. 코드 작성 & 수정

### 1단계 — schema.prisma (Movie 모델 + Spot 연결)

```prisma
// prisma/schema.prisma
enum MovieStatus {
  APPROVED
  PENDING
}

model Movie {
  id        String      @id @default(cuid())
  title     String
  status    MovieStatus @default(APPROVED)
  createdAt DateTime    @default(now()) @map("created_at")
  updatedAt DateTime    @updatedAt @map("updated_at")
  spots     Spot[]
  @@map("movies")
}

// Spot 모델에 추가
model Spot {
  // ... 기존 필드
  movieId   String?  @map("movie_id")
  movie     Movie?   @relation(fields: [movieId], references: [id], onDelete: SetNull)
  // ...
  @@index([movieId])
}
```

### 2단계 — 수동 마이그레이션 SQL (구조)

```sql
-- prisma/migrations/20260616120000_add_movie_table/migration.sql
CREATE TYPE "MovieStatus" AS ENUM ('APPROVED', 'PENDING');

CREATE TABLE "movies" (
    "id" TEXT NOT NULL,
    "title" TEXT NOT NULL,
    "status" "MovieStatus" NOT NULL DEFAULT 'APPROVED',
    "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updated_at" TIMESTAMP(3) NOT NULL,
    CONSTRAINT "movies_pkey" PRIMARY KEY ("id")
);

ALTER TABLE "spots" ADD COLUMN IF NOT EXISTS "movie_id" TEXT;
CREATE INDEX "spots_movie_id_idx" ON "spots"("movie_id");
ALTER TABLE "spots" ADD CONSTRAINT "spots_movie_id_fkey"
  FOREIGN KEY ("movie_id") REFERENCES "movies"("id")
```

```ts
async function main() {
```

### 5단계 — 자동완성 조회 함수 (읽기 전용)

```ts
// lib/movie/queries.ts
import 'server-only';
import { prisma } from '@/lib/prisma';

function normalizeForSearch(s: string) {
  return s.toLowerCase().replace(/\s+/g, '');
}
function escapeLike(s: string) {
  return s.replace(/[%_\\]/g, '\\$&');
}

export async function searchMovies(rawQuery: string, limit = 8) {
  const normalized = escapeLike(normalizeForSearch(rawQuery));
  if (!normalized) return [];          // 빈 입력 가드 (전체 LIKE 폭주 방지)
  const pattern = `%${normalized}%`;

  const rows = await prisma.$queryRaw<...>`
    SELECT m.id, m.title, COUNT(s.id) AS spot_count
    FROM movies m
    LEFT JOIN spots s ON s.movie_id = m.id
    WHERE m.status = 'APPROVED'
      AND REPLACE(LOWER(m.title), ' ', '') LIKE ${pattern}   -- DB측 정규화
    GROUP BY m.id
    ORDER BY spot_count DESC, m.title ASC                     -- 인기순, 동률은 제목순
    LIMIT ${limit}
  `;
  return rows.map((r) => ({ id: r.id, title: r.title, spotCount: Number(r.spot_count) }));
}
```

> 양쪽 정규화 규칙을 일치시킴: JS `toLowerCase + replace(/\s+/g,'')` ↔ SQL `LOWER + REPLACE(..., ' ', '')`. 표준 Postgres 함수만 사용해 pg_trgm 확장 불필요.

## 5. 결과 / 배운점

### 결과

- SpotFinder 데이터 토대 완성: Movie 테이블 + Spot.movieId(nullable) + RLS + 시드 12개 + 자동완성 함수.
- 자동완성 정규화 실제 DB 검증: "오징어게임"(공백 없이) 입력 → "오징어 게임"(공백 있게) 매칭 확인.
- 시드 멱등 검증: 재실행 시 12개 모두 "이미 존재" skip.
- 시드 스크립트의 실데이터 삭제 위험 차단 (db seed 트리거 제거).
- 커밋 2개 분리: feat(작품 연결 기능) / fix(시드 삭제 문제 차단).

### 배운점

- **도메인 특성이 구조를 정한다.** "운영자가 힘드니까"가 아니라 "성지순례는 화제 직후 즉시 일어나고 동선이 핵심이라, 방문 순간 작품이 없으면 못 짠다"가 자유 입력을 불가피하게 만들었다. 기술 선택의 진짜 근거는 도메인에 있었다.
- **막지 못하면 사후에 정리한다.** 자유 입력의 오염을 입력 차단으로 풀려다 실패하고, 자동완성(예방) + 운영자 병합(사후)으로 갈랐다. Stack Overflow가 같은 길을 갔음을 확인했다 — 바퀴를 새로 만든 게 아니었다.
- **추측이 사고를 부른다.** 시드 촬영지를 넣으려다 Spot 구조(storyId 필수)와
  충돌, 시드 Story 숨김 같은 특수 케이스가 불어났다. 한발 물러서 "촬영지 시드는
  지금 필요 없다"로 줄이니 특수 케이스가 통째로 사라졌다.
- **작업 중 인접한 위험을 발견한다.** Movie 시드를 작성하다, 같은 파일의
  Story 시드가 실데이터를 deleteMany로 삭제한다는 걸 "읽고 보고만"으로 알아챘다.
  내가 만든 기술 부채(미뤄둔 seed 설정)를 갚는 작업이, 이전부터 잠복해 있던
  더 큰 위험(실데이터 삭제)을 드러냈다. 0089 회고의 "가린 것 옆의 더 큰 구멍"과
  같은 패턴 — 한 곳을 정리하려 들면 인접한 구멍도 보인다.
- **위험도에 따라 검수 깊이를 달리한다.** 설계도(schema)·읽기 함수는 가볍게, 실제 DB 변경(마이그레이션 실행)·실데이터 삭제 가능 지점은 줄 단위로. server-only 가드가 tsx 단독 실행을 막은 것도 "에러"가 아니라 차단이 정상 동작한 증거였다.
